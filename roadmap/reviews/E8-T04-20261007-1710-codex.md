# Review E8-T04 — needs changes

## Findings

1. **major** `src/main/java/com/agilityhub/core/payments/application/CardPayments.java:124` — An exhausted request with no returned intent is treated as a definitive payment failure. Stripe can capture the payment while its response is lost; after three such failures, this code marks the invoice `FAILED`, allowing `/retry` to charge again with a new idempotency key. Stripe explicitly treats network failures and HTTP 500 outcomes as indeterminate. This breaks R-12-18/21/29’s payment reconciliation and idempotency requirements. Distinguish failures known to occur before submission from uncertain outcomes; preserve the original operation/key for uncertain charges. Add a regression where capture succeeds but the response and webhook are delayed. [Stripe error-handling guidance](https://docs.stripe.com/error-low-level).

2. **major** `src/main/java/com/agilityhub/core/payments/application/PaymentRefunds.java:67` — Exhausted refund commands permanently reserve money. For example, an invalid provider configuration makes `refund()` throw before creating a refund; recovery eventually sets `processedAt`, but `refundFailed()` only checks provider/refund statuses, which remain absent. After configuration is repaired, a new refund gets `REFUND_EXCEEDS_PAID`; replaying the original command cannot execute because `ready()` excludes it. R-12-20 and the recoverability requirements remain incomplete. Provide a safe retry path for the original operation, or release its reservation after a definitive non-submission failure, and test recovery after configuration repair.

3. **major** `src/main/java/com/agilityhub/core/payments/application/PaymentRefunds.java:236` — Refund allocation uses each row’s total `amountPaid`, including earlier manual payments, instead of its stored Stripe capture. Consider two €10 rows: A received €9 manually and €1 through Stripe; B received €10 through Stripe. A dashboard refund of the entire €11 Stripe payment can allocate €10 to A and €1 to B, falsely refunding A’s manual payment and leaving B apparently refundable. This contradicts R-12-20 and the capture limit already enforced by `upfront()`. Bound each allocation by `stripeCapturedAmount` minus its effective refunds; test mixed manual/Stripe rows, including reversal.

4. **major** `src/main/java/com/agilityhub/core/payments/application/PaymentRefunds.java:102` — Any existing refund operation suppresses all cancellation compensation, even a partial administrative refund. A €12 booking partially refunded by €2 remains `PAID`; cancelling it on time with policy `REFUND` then returns immediately, leaving the remaining €10 unrefunded. R-12-20 requires the cancellation policy to apply. Deduplicate the cancellation’s compensation while accounting for amounts already refunded or reserved, rather than treating any refund operation as full compensation. Add partial-refund-then-cancellation coverage.

5. **major** `src/main/java/com/agilityhub/core/payments/application/CardPayments.java:169` — Run completion is calculated from invoice states, not unresolved Stripe collections. If attempt 1 fails, attempt 2 is submitted, and a late success arrives for attempt 1, the invoice becomes `PAID` and the run becomes `COMPLETED` while attempt 2 remains `SUBMITTED`. This violates R-12-13’s explicit requirement that every Stripe collection be resolved and hides outstanding reconciliation in D6. Calculate completion from collection states and test this interleaving. Also refresh provider totals after late events on already completed runs; `BillingRunRepository.progress()` currently rejects those updates.

6. **minor** `src/main/java/com/agilityhub/core/payments/application/PaymentRefunds.java:218` — Successful refunds initiated directly in Stripe update the ledger without a `PAYMENT_REFUNDED` audit entry. Positive audits exist only in `execute()`, which dashboard refunds never call; reversals do create audits, so such a refund can leave only its negative reversal in the audit history. R-12-20, S14 R-14-09 and AGENTS rule 8 require transactional audit coverage. Audit successful reconciliation exactly once per refund, including dashboard-originated refunds, and avoid duplicating the command-path audit.
