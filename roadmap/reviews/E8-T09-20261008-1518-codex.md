# Review E8-T09 — needs changes

## Findings

1. **major** `src/main/java/com/agilityhub/core/payments/persistence/PaymentOperationRepository.java:76` — Recovery can replay an uncertain payment after Stripe’s idempotency guarantee expires. If Stripe captures a charge, the response is lost, and recovery resumes after a prolonged outage, `claim()` permits another POST with the original key regardless of its age. Stripe may have pruned that key and create another charge. This leaves point 1 and R-12-21/29 incomplete. Persist the first submission time and require reconciliation before replaying outside the guaranteed window. Add a recovery test after 24 hours with provider keys that expire. [Stripe’s idempotency contract](https://docs.stripe.com/api/idempotent_requests).

2. **major** `src/main/java/com/agilityhub/core/payments/application/PaymentRefunds.java:169` — Successful webhook reconciliation does not complete a refund command whose response was lost. It writes `refundStatus`, but leaves `resultId` null. Consequently, `reserve()` and `remaining()` count the amount both as refunded and as pending. For a €12 payment with a €2 refund whose responses exhaust retries, a successful webhook leaves only €8 available instead of €10; cancellation compensation also under-refunds. This violates points 2/4 and R-12-20/21. Atomically associate the webhook’s refund ID with the command and remove it from pending reservations. Test lost responses through exhaustion, followed by successful reconciliation and refunding the remainder.

3. **major** `src/main/java/com/agilityhub/core/payments/application/stripe/StripeCalls.java:30` — Exhausted rate limiting still permanently reserves refund money. A fresh command receiving only rate-limiter HTTP 429 responses becomes `submissionUncertain=true`; after exhaustion it is excluded from recovery, retains its reservation, and awaits a webhook for a refund that was never created. Point 2’s “never reserves money for good” requirement remains incomplete. Preserve definitive rate-limit rejection information and safely release or retain a retryable command when no earlier uncertain submission exists. Add an adapter regression covering repeated 429 responses followed by recovery. [Stripe documents rate limiting before its idempotency layer](https://docs.stripe.com/error-low-level).
