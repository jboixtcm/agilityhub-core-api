## Findings
1. **minor** `src/main/java/com/agilityhub/core/platform/persistence/JndiDomainDns.java:56-63` — When the JVM resolver throws `UnknownHostException`, the adapter asks JNDI for `A` but throws away the answer and always returns `[]`.
   - **Problem:** if JNDI does return A records (the JVM lookup failed briefly, but the DNS has the name), the code still logs "found nothing" and returns "no address". `recheckOf` then counts it as a real miss (`FAILED`), not `SKIPPED`. This is the same failure-taken-as-miss problem as round-2 point 1, in a narrower path. Review #1 asked that only "answered, no matching record" counts towards `BROKEN`.
   - **Fix:** when the JNDI retry gets a non-empty `A` attribute, return those values, or throw `LookupFailed` because the two resolvers disagree. Add a case to `T_17_03_R_17_03_anAddressLookupTellsNoAddressFromNoAnswer` where `records` returns a `BasicAttribute("A", "203.0.113.10")` and `resolver` throws.
2. **minor** `docs/DEPLOY.md` § «Trusted domains before the DNS cutover» — The first option says «Verify them … steps 2 and 3», but this doesn't work for these domains.
   - **Problem:** `club:apply` with `trustedDomains` creates the domains already `VERIFIED`. `PlatformDomains.check()` refuses a `VERIFIED` domain with `INVALID_STATE` (`PlatformDomains.java:123`), so step 3's [Verifica] fails. Only the `dig` check by hand is actionable, and it changes nothing in the Core.
   - **Second gap:** the runbook does not say what to do when a trusted domain is already `BROKEN`. With `platform.domainRecheckDays = 0`, `recheckPlan` returns nothing, so P9 never restores it. The way back is [Verifica], which accepts `BROKEN`, or setting the parameter back to 7.
   - **Fix:** reword the first option as «check that the records are in place (`dig …`) before the first re-check is due». Add a line: a domain already `BROKEN` comes back through [Verifica] (step 3) once the records point here.
3. **nit** `src/main/java/com/agilityhub/core/platform/persistence/ClubRepository.java:151-155` — The `save()` override reads the stored club with `findById` and then calls `mongo.save`.
   - **Problem:** the merge is only atomic when the caller is in a transaction. Console writes are (`ConsoleTransactions.write`). For any full save outside a transaction (e.g. a CLI path, if one exists), a P9 plain check that commits between the read and the write would be overwritten. That one domain would then be due a day early, with no status impact.
   - **Fix:** either document that `save` relies on the caller's transaction, or accept this as is.
4. **nit** The commit `ad3ded5` also contains `docs/DECISIONS_PENDENTS.md` (E126/E127) and `roadmap/tasks/E9-T07.md`. Those look like organizer edits picked up by the publish script, not the executor's work, so AGENTS rule 10 is not breached by the executor. Worth confirming on your side.
