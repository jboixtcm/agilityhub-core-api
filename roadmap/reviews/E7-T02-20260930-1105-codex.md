# Review E7-T02 — needs changes

## Findings

1. **major** `src/main/java/com/agilityhub/core/clubs/messaging/application/engine/NotificationDispatcher.java:251` — Accepted sends can still be sent twice. After five settlement failures, the accepted result exists only in `unsettled`; the database delivery remains `QUEUED`, and its two-minute lease is never renewed. After expiry, another dispatcher can claim and resend it—even without a process restart. This leaves organizer round-2 item 2 and R-11-09 incomplete. The regression test recovers before lease expiry. Persist accepted outcomes independently of the failing settlement and recover without another provider call; test both lease expiry with a second dispatcher and dispatcher replacement.

2. **major** `src/main/java/com/agilityhub/core/clubs/messaging/application/engine/NotificationDispatcher.java:157` — Queued email bypasses bounce suppression at send time. Suppression is checked when building deliveries and adding cap fallbacks, but `sendEmail()` sends the stored target without checking either current bounce mark. If two notifications are queued and the first hard-bounces, the second still sends; pending retries behave likewise. R-11-08 requires subsequent email to that address to stop. Recheck contact/account suppression before every email attempt and terminate suppressed deliveries without calling the provider. Add a queue → bounce → dispatch/retry test.

3. **major** `src/main/java/com/agilityhub/core/clubs/messaging/application/engine/NotificationDispatcher.java:205` — Push expiry can be permanently lost. On `GONE`, `quietly()` swallows failures of the transaction containing subscription expiry and `PushUnsubscribed`, then the delivery is finalized as `FAILED`. For example, one failed outbox write rolls back expiry, but no pending work remains to retry it: the subscription stays `ACTIVE`. This violates R-11-07 and step 7. Include subscription bookkeeping in the retried settlement, retaining the provider outcome; inject an expiry/outbox failure and assert eventual `EXPIRED` plus exactly one event without resending.

4. **major** `src/main/java/com/agilityhub/core/platform/application/ClubSmsUsage.java:32` — The monthly counter can move backwards during rollover. A sender that calculated September before midnight but reaches `reserve()` after another sender initialized October matches `MONTH.ne(key)` and overwrites October’s count with September/1. The next October send resets it again, losing usage and permitting sends beyond the cap. `firstCapNotice()` has the same backwards-marker problem. R-11-06 requires an atomic club-local monthly cap and one notice per month. Make rollover monotonic or store counters/notice markers per month, and test delayed old-month operations after new-month initialization.

5. **minor** `src/main/java/com/agilityhub/core/clubs/messaging/domain/NotificationLinks.java:81` — N-42’s `OPEN_JOBS` falls through to `/tauler`, so its email action does not open automatic processes. S15 §2 specifies `/parametres#processos`; R-11-11 and organizer round-2 item 7 require the corresponding deep link. Add an explicit mapping and correct `NotificationLinksTest`, which currently asserts `/tauler`.
