# Review E5-T28 — needs changes

## Findings

1. **major** `src/main/java/com/agilityhub/core/payments/application/CheckoutService.java:88` — Rejecting a pending dog can strand another dog’s unpaid rows. Checkout includes debts from already validated submissions (`SignupService.submissions`), but rejection expires the entire session while cancelling only the pending dogs’ rows. The other rows remain `CHECKOUT_PENDING`; the provider’s expiry callback exits immediately because the session is already `EXPIRED`, and subsequent checkouts fail with `INVALID_STATE`. This violates S04 R-04-23/26 and T-04-22. Cancel the rejected rows and release the surviving rows back to payable state within the rejection transaction. Extend the existing mixed ACTIVE/PENDING-dog checkout test with rejection and a successful replacement checkout.

2. **major** `src/main/java/com/agilityhub/core/payments/application/CheckoutService.java:44` — Rejection can occur after `prepare` commits but before the provider creates its session. Rejection marks the local session `EXPIRED`, attempts provider expiry before that session exists, and merely logs the failure. Creation then continues and returns a live checkout URL for the rejected signup. The late-payment marker records the eventual charge but does not prevent it. This leaves step 4/A3-01 incomplete. Reconcile local state after provider creation, expire a session whose signup was rejected, and test this ordering with a gated provider.

3. **major** `src/main/java/com/agilityhub/core/payments/api/CheckoutController.java:36` — Failure in `checkout.answered(...)` leaves the already committed checkout and payment rows pending without a replayable response. `IdempotencyFilter` abandons the unfinished key, but retrying it reaches `prepare` and fails because the rows are already `CHECKOUT_PENDING`. The provider URL is not persisted elsewhere for recovery. This breaks checkout retry semantics in `CONVENCIONS_API.md` §7 and S04 R-04-26. Persist a recoverable association between the key, session and provider result, or compensate failures after provider creation. Add a test that fails response persistence and retries the same key.

4. **major** `src/main/java/com/agilityhub/core/clubs/scheduling/application/WeekValidationUseCase.java:52` — Re-validation activates DRAFT classes and emits `WeekValidated` while explicitly suppressing `WEEK_VALIDATED` audit. S14 R-14-09/10 requires that action and explicitly exempts it from suppression when there is no field diff; AGENTS rule 8 also applies. `CalendarIT:466` currently asserts the prohibited omission. Preserve `validatedAt`, but record the validation event in the same transaction, ensuring the audit writer retains it despite unchanged week fields. Update the test to require the audit entry.

5. **minor** `src/test/java/com/agilityhub/core/clubs/census/api/SignupCensusCorrectionsIT.java:112` — All six new tests lack `T-xx-nn` identifiers; the new mandate unit test in `CensusRulesTest:31` does too. Rule and decision identifiers alone do not satisfy AGENTS rule 5. Map and rename them using the applicable spec test IDs, retaining the descriptive suffixes.
