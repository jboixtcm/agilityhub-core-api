# Review E11-T08 — minor issues

## Findings
1. **major** `src/main/java/com/agilityhub/core/shared/api/RateLimitFilter.java:56`: the `STRIPE_WEBHOOK` key takes `clubId` straight from the URL. That `clubId` is free text the caller chooses, so the per-IP limit is gone: one address that rotates made-up ids (`/webhooks/stripe/x1`, `x2`, …) gets a fresh bucket on every request. All routes share one Caffeine cache in `RateLimits.java:55`, capped at 100 000 entries, so that flood also pushes out other routes' buckets, for example `TOKEN` and `SIGNUP_*`, and resets their counts. INC-67 asked for `clubId:ip` "com a les rutes `SIGNUP_*`". Those routes key on a club *resolved* from the Host, and an unknown host falls back to `unknown` (`RateLimitFilter.java:59-60`), so the precedent is a resolved club, not raw path text. The executor flagged the bypass under Questions but not the cache eviction. Suggested fix: use the path segment only when it is a known club (the existing `TenantHostResolver`/`ClubConfigService` lookups, which are cached), otherwise key it `unknown:ip`; or also charge a plain per-IP `WEBHOOK` bucket. Add a test where rotating made-up club ids from one IP hits 429.
2. **minor** `src/main/java/com/agilityhub/core/migration/application/PlayoffPlanner.java:458-459`: `businessDate` still reads a BSON date in **UTC**, while `PriceDateConverter.day` reads it in `ZoneId.systemDefault()`. The report itself says this makes the Playoff price match a day early when the writer JVM is east of UTC. The startup conversion hides this for most documents. But a price that keeps its date because conversion would duplicate another's start (`PriceRepository.java:60-62`) is still read differently by the two paths. Suggested fix: call `PriceDateConverter.day(...)` there (or a shared helper), so one rule reads a legacy date.
3. **minor** `src/main/java/com/agilityhub/core/clubs/catalogs/persistence/PriceRepository.java:60-62`: in the duplicate-key case, two prices with the same start survive the conversion: a legacy date twin and a string twin. The only trace is a WARN with the id. `forPlan` sorts on `validFrom` across mixed BSON types (strings sort before dates), and `current()` takes `findFirst`. So billing silently uses the string twin, and the admin list shows both as CURRENT. INC-68 was rated "Alta" for exactly this kind of wrong-price outcome. Suggested fix: add a DEPLOY.md note, or a count in the runner's log line, so an operator removes the twin by hand. At minimum, tell the organizer that this state can exist on staging.
4. **minor** `src/test/java/com/agilityhub/core/clubs/catalogs/persistence/PriceDatesIT.java:112`: the legacy fixture writes midnight with `ZoneId.systemDefault()`, and the converter reads with the same zone. So the test cannot catch a zone mismatch between the JVM that wrote and the one that converts, which is the assumption the report calls out under Assumptions. Suggested fix: add a converter unit test with a fixed non-UTC zone. Alternatively, record in DEPLOY.md that the API and `bin/core` containers must run in the same `TZ`.
5. **minor** Evidence `roadmap/evidence/E11-T08/01…09`: session 1's logs hold neither the command nor its exit code, and the report admits this ("Session 1's commands are not recorded"). That breaks the AGENTS.md evidence rule (exact command + exit code). Logs `02` and `06` are also named `*-green` while they are failures. The final reruns (`11`, `13`, `15`, `16`) cover the green side, but the red side of INC-68, INC-67.2/3 and INC-66.1 depends on these unlabelled logs.
