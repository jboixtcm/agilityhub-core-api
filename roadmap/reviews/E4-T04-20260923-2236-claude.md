## Findings

1. **major** `src/main/java/com/agilityhub/core/clubs/activities/application/ActivityTransactions.java:13-20` — Every activity write for a club goes through one of 256 in-JVM `ReentrantLock` "lanes", chosen by hashing the tenant id. The lock is held for the whole transaction, including the retry backoff sleeps.
   - **Why it matters:** Step 4 / R-07-08 require concurrent registrations to be serialized by Mongo (`$inc registrationSeq` on the Activity, `WriteConflict` → at most 3 retries with 50–150 ms backoff). Because the lane lock already serializes same-club requests inside one JVM, T-07-24 (both variants) and T-07-25 never exercise Mongo contention. They would pass even if the Mongo-level guard were broken.
   - **Multi-instance risk:** The executor's earlier-attempt note `it8` ("bounded local contention") suggests the lanes were added because 20 contenders exhausted the 3 retries. With several API instances, that could return `STALE_VERSION` (409) to members on popular activities instead of 201 or `WAITLISTED`.
   - **Side effect:** Unrelated clubs that hash to the same lane block each other.
   - **Suggested fix:** Either prove the Mongo path alone. For example, disable the lanes in one T-07-24 variant, or run it against two application contexts, and check that the retry budget (possibly with more attempts or longer backoff) keeps 20 contenders at 1 `ACTIVE` + 19 `WAITLISTED`. Or record an ADR / pending decision that a single instance is assumed.

2. **minor** `src/main/java/com/agilityhub/core/clubs/activities/application/ActivityRegistrationService.java:74` + `:108` — A FIFO promotion publishes `ActivityRegistrationChanged` with the registration's original `origin`. So if the club created a waitlisted registration through impersonation, the later system promotion is sent as `BACKOFFICE`. The N-32b handler (`ActivityNotifications.java:50`) then sends EMAIL + SMS under `CLUB_CHANGES`.
   - **Why it's wrong:** S07 §5 line 163 says promotion is done by the system. The `BACKOFFICE` variant in §8 is meant for changes the club makes.
   - **Suggested fix:** Emit `origin: APP` (or mark the event as system-originated) when `promoted: true`, and add an assertion for it.

3. **minor** `src/test/java/com/agilityhub/core/clubs/activities/application/ActivityIT.java:154-164` — T-07-15 does not check what S07 line 280 lists: no `promotedAt` check, no N-32b with `promoted`, and no "cancellation outside the deadline (impersonation) → no promotion" case.
   - Under `EVENT_START` both deadlines are the same, so that branch needs a `REGISTRATION_CLOSE` parameter fixture.
   - Suggested fix: add those assertions.

4. **minor** `ActivityIT.java:190-201` — T-07-19 checks `cancelReason = MEMBER_LEFT` but not "sense notificació" (no N-32b row after `dispatch()`). The inactivity half checks only the count, not the N-32b that S07 line 284 requires for `INACTIVITY`.
   - Suggested fix: assert the notification counts.

5. **minor** `ActivityIT.java:144-153` — T-07-14 never checks the N-32b / `ActivityRegistrationChanged` that S07 line 279 requires for both the `ACTIVE` and the `WAITLISTED` registration.

6. **minor** `ActivityIT.java:95-105` and `:106-123` — T-07-10 does not check the 5 `RingBlockCreated` events or `GET /weeks/{id}/calendar` → `activityTitle`. T-07-11 does not check "INSTRUCTOR → 403" (S07 lines 275-276).
   - Suggested fix: add these to T-07-10/T-07-11 so the T-07 names cover the rows they cite.

7. **minor** `src/main/java/com/agilityhub/core/clubs/activities/application/PublicActivityService.java:27-28` — The `ACTIVITIES` module is checked before the API key. A caller with no key or a wrong key can therefore tell whether a club slug exists and whether its activities module is on (404 `MODULE_DISABLED` vs 403 `INVALID_API_KEY`).
   - Suggested fix: check the key first, as `PublicPlansController` does (unless the plans endpoint has the same order, in which case record it as intended).

8. **nit** `PublicActivityService.java:37` — The public list loads every activity of the club (`activities.findAll()`) and filters in memory. The cache limits the cost, but a query on state and date would scale better.
