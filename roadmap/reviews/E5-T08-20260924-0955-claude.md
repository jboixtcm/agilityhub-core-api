# Review E5-T08 — minor issues

## Findings
1. **minor** `src/main/java/com/agilityhub/core/clubs/bookings/application/WaitlistNotifications.java:87-90` (`offerDelivered`): the N-46 gate depends on whether the N-15 APP row is already in `notifications` when the check runs. The two consumers handle different outbox events, so they can run at the same time.
   - **Scenario:**
     1. The N-15 consumer reads the entry as `NOTIFIED`.
     2. The booking transaction commits and demotes the entry.
     3. `notifications.N-46.booked` runs, finds no N-15 row and skips.
     4. The N-15 consumer then writes «S'ha alliberat una plaça!».
   - **Result:** the member gets the offer and never gets «La plaça ja s'ha ocupat». Before this change, the member always got N-46.
   - The gate also reads the messaging collection on `variables.entityId` + `createdAt`. That query looks unindexed, and it runs for each demoted entry.
   - **Why it matters:** R-08-13 (E5-T03 #3 asked for this gate, but this ordering has no test).
   - **Fix:** have the N-15 consumer record delivery on the entry (a field compared against `notifiedAt`), then have N-46 read that field. Or accept the race and record it in the report.
2. **minor** `WaitlistNotifications.java:127` (`notifications.N-46.held` on `SeatHoldReleased`): the catalog row for `SeatHoldReleased` says «no notifica», but this event now triggers N-46.
   - The executor proposes a catalog note but did not apply it, which is correct. The organizer still has to accept this new trigger explicitly under AGENTS rule 2.
   - `SeatHoldReleased` is also emitted when a hold expires or is released, not only on confirmation. On those events the consumer can run `demoteIfFull`. I believe this is harmless because the demotion is idempotent and only runs when the class is full, but no test covers it.
3. **minor** `src/main/java/com/agilityhub/core/clubs/census/persistence/CensusRepository.java:40-43`: `save()` now silently drops `@ForeignOwned` fields.
   - Any census code that does `member.lastDogForClass = …; save(member)` will lose the write without an error. Examples: the future S14 erasure, or a later change to transfer. Today `DogService` is the only writer, and it was switched to `setField`.
   - **Fix:** fail fast when a `@ForeignOwned` field differs from the stored value in `save`, or at least document the rule in `docs/playbooks`.
   - **Side effect to confirm:** `increment` no longer bumps `Dog.version` or `Member.version` for `trainingSeq` either. The executor says E5-T07 does not depend on that (the conflict comes from the `$inc` itself). E5-T07 is still awaiting verification, so the organizer should cross-check.
4. **minor** `src/test/java/com/agilityhub/core/clubs/activities/application/ActivityIT.java` (T-07-15), E4-T04 #2: the test does not reproduce the scenario that was reported.
   - The review's case was a `BACKOFFICE`-origin (impersonated) waitlisted registration whose promotion went out with EMAIL + SMS. The test promotes an `APP` registration, so the "channels only APP" assertion would also have passed before the fix. Only the `origin=SYSTEM` payload assertion tells the two apart.
   - **Fix:** add the case of an impersonated `WAITLISTED` registration that gets promoted, and check that N-32b is APP only.
5. **nit** `src/main/java/com/agilityhub/core/clubs/activities/application/ActivityRegistrationService.java:14`, `:113`:
   - `SYSTEM_ORIGIN = "SYSTEM"` is a string literal, while `DomainEvent.Origin.SYSTEM` already exists. Use the enum.
   - Only the payload `origin` becomes SYSTEM. The envelope origin (`ActivityEvents.java:16`) still carries the actor who triggered it (APP/BACKOFFICE). Readers of `domain_events` therefore see two different origins for the same promotion. Either align them or document it.
6. **nit** `src/main/java/com/agilityhub/core/clubs/activities/api/PublicActivitiesController.java:38,47`: `CLUB_NOT_FOUND` is still in `@ContractErrors` for both keyed routes, but those routes can no longer return it. The OpenAPI therefore still advertises it.
   - Other keyed public routes still reveal whether a club exists before checking the key (404 vs 403): `PublicPlansController`, `PublicClubPagesController`. The public API now behaves differently from one route to another.
   - Also, spec T-07-17 says «sense clau → 401», but the error catalog makes `INVALID_API_KEY` 403. The catalog wins here; please note this in the report.
7. **nit** `src/main/java/com/agilityhub/core/clubs/bookings/application/BookingEvents.java:21-28` (step 9):
   - The review only asked for a note in `seeds/README.md`. The executor also changed `occurredAt` for all booking and `ClassBelowMinimum` events to `BookingContext.now()`.
   - As a result, seed events can now have an `occurredAt` up to a week in the future, which no longer matches the outbox `createdAt`.
   - I found no consumer that sorts or filters on `occurredAt` for these events (`JobFailureNotifications` and `ActivityNotifications` read it only for other event types), so this is acceptable. It is still a behaviour change that the report should mention.
8. **nit** `src/main/java/com/agilityhub/core/clubs/bookings/application/BookingConsumers.java:207-215` (step 16):
   - The test in `WaitlistIT` publishes a hand-made `ClubModulesChanged` instead of switching the module through the S02 endpoint. I checked that the producer's payload (`ClubSettingsService.java:101-102`, `diff.modules.before/after` as sorted name lists) matches what `switchedOn` parses, so the logic works; there is just no end-to-end test.
   - Switching WAITLIST off still leaves `counters.waiting` stale until the class's next recount. This is outside the finding and was already so before.
