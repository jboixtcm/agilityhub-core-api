# Review E4-T06: minor issues

## Findings
1. **minor** `src/main/java/com/agilityhub/core/clubs/activities/api/ActivityContracts.java:81`: the OpenAPI description of `ActivityRegistrationListItem.position` says "WAITLISTED only; null otherwise", and the snapshot publishes that text. The code does something else. `ActivityRegistrationService.cancelled(...)` (line 62) copies `r.position()` into the cancelled registration. So when a waitlisted registration is cancelled, the item comes back `CANCELLED` and still carries its number. In `T_07_21_aRegistrationListItemAlwaysSendsCancelReasonNullUntilItIsCancelled`, the `gone` registration is exactly this case: waitlisted at position 2, then cancelled. The test never asserts `cancelled.position`, so the mismatch goes unnoticed. The executor's report and the OpenAPI changelog also describe the three fields as "`null` until they apply". Suggested fix, either one:
   - make the description accurate ("the waitlist position; kept after a waitlisted registration is cancelled; null once promoted or if never waitlisted") and assert it in the test;
   - or clear `position` on cancellation.

2. **minor** `ActivityContracts.java:116` (`MemberActivityDetail.endsAt`) and `:28` (`Activity.endsAt`): for a start-only activity, the app's detail view `GET /me/activities/{id}` and the staff view still send `endsAt = <next day 00:00 local>` as a UTC instant. The test confirms it: `2026-09-19T22:00:00Z`. Neither schema has a description saying so.
   - The task's objective is "an activity without an end time reaches the app with a made-up end".
   - Step 3 lists only `ActivityListItem`, `RegisteredActivity` and the 03/25 rows, and the executor stated this openly as Assumption 5. So this is not a scope violation.
   - The risk is that the web uses `endsAt` to show the hours on the detail screen, which has no mockup.
   - Suggested fix: add a schema description on both `endsAt` fields ("derived instant; for an activity without `endTime` it is the next local 00:00. Display `startTime`/`endTime`."). Alternatively, the organizer decides whether `endsAt` should also be `null` in the member detail.

3. **nit** `ActivityContracts.java:51` together with `ActivitiesController.java:55`: the list rows are converted to the `ActivityListItem` record and serialised with `ALWAYS`. So `fields=` only chooses which properties carry values; every property is still sent. `allRings` is a primitive `boolean`, so a request like `fields=title` gets `allRings: false`. That is a false value, not "not selected". The other properties in the same situation come back `null`, even where the schema marks them non-null (`typeDisplay`, `title`). This pattern existed before this task (the global Jackson inclusion is already `ALWAYS`), but the new primitive column makes the output wrong rather than empty. The `fields=` check in `T_07_21_T_07_29_…` asserts only the selected keys. Low impact on D7, which never sends `fields`. Worth a follow-up for how `fields=` works across all lists.

4. **nit** `src/test/java/com/agilityhub/core/shared/api/ApiExceptionHandlerTest.java:34,58`: this change (`"abc"` → `"xyz"`) is outside the task's scope. The reason is sound: a random UUID `traceId` can contain `abc`, but never `x`, `y` or `z`, and the assertion means the same thing. It is disclosed as Assumption 6. The organizer should simply know that E4-T06 touches a shared test.
