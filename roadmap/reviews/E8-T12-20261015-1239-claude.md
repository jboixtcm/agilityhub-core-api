# Review E8-T12 — needs changes

## Findings

1. **major** `src/main/java/com/agilityhub/core/payments/application/PaymentRefunds.java:267-270` with `:470-471` and `PaymentIntentLedger.java:57-62`: **a dashboard refund that settles directly is now steered away from the row the admin is repaying, and that row's N-55 stays stale.**
   - **Cause.** Round 5 made every current intervention a `Reservation(paymentId, paymentId, owed)`. `settled()` gives an unlinked dashboard refund `operation == null`, so `settlementShares(amount, null, null)` subtracts all reservations, interventions included, from each row's capacity before it allocates. The money therefore goes to rows that hold no intervention.
   - **Concrete case** (traced by hand through the current code):
     - One €24 capture covers A and B (€12 each). A is cancelled with `REFUND`, its compensation refund fails, and A's intervention is €12 (`withoutReservation(A).freeFor(A) = min(12, 24)`).
     - Following N-55, the admin refunds €12 from the Stripe dashboard. Stripe delivers `succeeded` directly, with no `pending` event first, which is common for card refunds.
     - In `settlementShares`, A's €12 intervention fills A's capacity, so A has €0 unreserved and B has €12. The settlement lands on **B**, and `upfront.refund(B, …, full=true)` marks B `REFUNDED` although B's booking is still active.
     - `absorb()` then recomputes A: `share(A).free() = 12`, `balance().free() = 24 − 12 = 12`, so `due = 12`. `interventionOwed` is unchanged, so A still shows **€12 owed** and no new notice goes out.
     - If the admin pays again, the member gets €24 back for one cancelled €12 booking. `refunded ≤ captured` still holds, so no `REFUND_OVER_CREDIT` is reported either.
   - **Regression.** Before round 5 the same settlement landed on A (row order, tier 0) and A's due became 0. This breaks E103 #2, "N-55 never asks for money already repaid", and E107's "a refund settles → recompute each `interventionOwed`".
   - **Why the tests miss it.**
     - The fixed tests only pass by luck of allocation. In `interventionsShareTheRemainingCapture`, the €3 succeeded refund lands on a cancelled row that still has unreserved capacity (A with €5 when A owes €7, or C with €5 when C owes €7). In `repaymentRefreshesClaimsBeforeAbsorbingCredit` there is the same kind of slack.
     - The new oracle `sharedInterventionInvariant` (`CapturedPaymentInvariantsIT.java:1124-1133`) only puts an **upper** bound on current interventions. A stale intervention that stays within the capture passes it.
     - The pending path happens to work: the pending reservation is allocated before the intervention's, the intervention drops to 0, and the later settlement finds A unreserved.
   - **Fix.**
     - When `operation == null` (an unlinked dashboard settlement), allocate as if the intervention reservations were absent, with rows in intervention preferred. For example, run `settlementShares` on a `withoutReservation(...)` view that drops every intervention reservation.
     - Add a regression: two rows, A's intervention €12, then a direct `succeeded` dashboard refund of €12 (expect `interventionOwed(A) == 0` and B `PAID` with no refunds) and of €5 (expect €7).
     - Strengthen the oracle with a lower bound so a stale claim fails. For example: after any settlement, no row without an obligation receives a share while an intervention row still has capacity. Or: each current intervention equals its recomputed due.

2. **minor** `PaymentRefunds.java:181-188, 214-218`: **one event can send two N-55 notices for the same payment.** `reconsiderCompensation` refreshes intervention rows inside `absorb()` before the credit reductions, then runs `compensateRemaining` again on every row afterwards. If the reductions free money, the same payment gets two `UpfrontRefundIntervention` events with different totals in one transaction (for example €7, then €12). E101 only promises a new notice when the positive total changes, so this is allowed, but it is noise for the admin. Suggested fix: refresh once, after absorption (or with the second pass only), or say in the report that this is accepted.

The tests (`failSecondFirst`) assert "first failure gets the larger share", which is deterministic but is the executor's reading of the instruction. The report says so under Assumptions. The organizer should confirm that reading.
