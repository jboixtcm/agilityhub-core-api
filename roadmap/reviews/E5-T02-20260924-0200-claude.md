# Review E5-T02 — needs changes

## Findings
1. **major** `src/main/java/com/agilityhub/core/payments/application/UpfrontPayments.java:96` and `clubs/bookings/application/BookingConsumers.java:39-41` — **The PAY_TO_BOOK flow never finishes outside the tests.**
   - The consumers only act on `UpfrontPaymentSucceeded{bookingId}` / `UpfrontPaymentFailed{bookingId}`.
   - The only producer, `UpfrontPayments.checkout(...)`, emits `UpfrontPaymentSucceeded{paymentId, memberId, amountPaid, provider}` with no `bookingId`. Nothing emits `UpfrontPaymentFailed`.
   - T-08-24 passes only because it publishes hand-built events that carry `bookingId`.
   - Result: after checkout succeeds through `FakeCheckoutGateway`/Stripe, the booking stays `PAYMENT_PENDING`. Once the P7 timeout lands in E5-T05, a paid booking will be cancelled as `PAYMENT_TIMEOUT` (N-40).
   - `BookingRepository.byCheckoutSession` (`persistence/BookingRepository.java:65`) was clearly meant for this, but nothing calls it.
   - The report does not disclose any of this: assumption 6 mentions only the signup event.
   - Fix (R-08-18, task step 7 "default adapter over the existing payments code"): add `bookingId` to the success event for `concept = SINGLE_CLASS` lines (it is already in the checkout metadata), or resolve the booking through `checkoutSessionId`. Add an IT that completes the fake checkout end to end. Also check that the `SINGLE_CLASS` `UpfrontPayment` line does not show up in, or get cancelled by, the signup flows (`selected`/`reject` work per member).
2. **major** `.gitignore:10` — **The evidence logs are not committed.**
   - `*.log` is ignored, and there is no `!roadmap/evidence/E5-T02/*.log` exception (E4-T05 and earlier tasks have one).
   - `git ls-files roadmap/evidence/E5-T02` shows only the two `.py` scripts. `01-verify.log` … `08-e4-smoke.log` exist only in the local working tree.
   - The report says "the final run's log is the one committed". The AGENTS.md evidence rule requires the long outputs to be committed.
   - Fix: add the exception and re-publish. E5-T01 has the same gap.
3. **minor** `clubs/bookings/application/BookingTransactions.java:34-41` + `BookingConcurrencyIT` — **The concurrency tests never reach the `seat_locks` path.**
   - The in-JVM fair "lanes" serialise every write to a class before Mongo is touched.
   - So T-08-29/31/32 never exercise the `seat_locks` write conflict or the retry. They would still pass with `locks.lock(...)` removed.
   - The DoD's "never an overbooking" is therefore proven for one instance only, while the javadoc claims Mongo stays authoritative across replicas.
   - Suggest one test that bypasses the lanes (for example two raw `TransactionTemplate` hold transactions on the same class) and asserts the WriteConflict → retry → `CLASS_FULL` outcome.
4. **minor** `clubs/bookings/application/BookingConfirmationService.java:78-81` — **The checkout call to the payment provider runs inside the retried Mongo transaction.**
   - A WriteConflict retry creates a second `UpfrontPayment` (rolled back) and a second provider Checkout Session (not rolled back, left behind at the provider).
   - It also keeps the class's seat lock held for the whole duration of the HTTP call.
   - Fix: pass `bookingId` as the provider idempotency key, or open the checkout after commit.
5. **minor** `clubs/bookings/application/BookingCancellationService.java:103` + `BookingAudit` — **An impersonated late cancellation is not audited as late.**
   - It writes only `BOOKING_CANCELLED_BY_CLUB`.
   - Step 6 asks for `BOOKING_CANCELLED_LATE` on **any** `late = true` cancellation (S14 R-14-09).
   - This is disclosed as assumption 9, but it means an audit filter on `BOOKING_CANCELLED_LATE` misses these cancellations.
   - The organizer should decide; the simplest fix is to write both entries.
6. **minor** `clubs/bookings/application/BookingCounters.java:27-33` — **A same-class swap can raise a false `ClassBelowMinimum`.**
   - This applies with `limitUnit = MEMBER`: another dog of the same owner in the same class.
   - `cancelLocked` → `recount(inTime = true)` can publish `ClassBelowMinimum` and SET the guard. The new booking's `recount` then CLEARs it in the same transaction, but the event is already in the outbox.
   - Result: N-54 (E5-T05) is sent although the count never dropped (R-15-12b).
   - Fix: evaluate the alert once per transaction, at the end.
7. **minor** `src/test/java/com/agilityhub/core/clubs/bookings/api/BookingsIT.java:150-168` — **T-08-17 covers only part of its spec line.**
   - The spec asks for `swapBookingId` "fet, tardà o d'una altra setmana → SWAP_NOT_ALLOWED sense cap canvi".
   - Only "another week" and "no swap chosen" are asserted. The last block asserts `BOOKING_LIMIT_REACHED` on a **hold**, which is a different path.
   - Add a confirm with a LATE_WINDOW or DONE `swapBookingId` while another booking is still swappable.
8. **minor** `clubs/census/persistence/CensusRepository.java:56` — **Every booking bumps `Member.version`.**
   - `setField` for `lastDogForClass` runs on every confirmation.
   - An admin saving that member's form after the member books gets `STALE_VERSION`.
   - Two bookings by the same booker also conflict on the member document.
   - Suggest not bumping `version` for this denormalised field (R-08-23), or document the trade-off.
9. **nit** `clubs/bookings/application/BookingNotifications.java:98-99` — **N-36 renders with an uncatalogued variable.**

11. **nit** `clubs/bookings/application/BookingQueryService.java:69-71,75` — `GET /bookings` loads each booking with its own `findById`, and each member with its own `census.member` (N+1 queries per page). Use the projected rows, or batch the reads with `$in`.
