# Review E3-T17: minor issues

Round 2 covers the organizer's five points:
- **Point 1:** D2 document edits are merged by type, and the automatic empty card row is added only at submission.
- **Point 2:** the reused dog's record is frozen on 13 routes.
- **Point 3:** validation applies only the types sent with files.
- **Point 4:** the dog now gets its own `SIGNUP_SUBMITTED` audit entry.
- **Point 5:** the nits are fixed.

Each fix of points 1–4 has a test that fails on the unfixed code (logs `15` and `20`). The code matches the amended S04 R-04-06 and R-04-23. No new parameter, event, notification or error code is used.

## Findings
1. **minor** `SignupService.java:488-495` (`saveDocuments`) and `SignupService.java:750-751` (`dogValues`): for the reused dog, D2 can replace a whole document type but cannot add or remove a single file. R-04-19 asks for «afegir/treure fitxers».
   - **What happens.**
     - `POST /dogs/{id}/documents` and `DELETE …/files/{fileId}` are now frozen for this dog, as point 2 asks.
     - That leaves `PATCH /dogs/{id}` as the only path. A type sent with files replaces the whole submitted row for that type (`merged.put(type,row)`).
     - To keep the submitted files of a type while adding one, D2 has to send their `fileKey`s again. `SignupDogView.documents[].files[]` only exposes `name` and `downloadUrl`.
   - **Example.** The applicant sent a card with 2 files. D2 wants to add a third, or drop one of the two. It cannot do either without the applicant's keys, so it can only swap the whole type or withdraw it.
   - **Status.** The executor raised this as round-2 question 3 and marked it non-blocking. The web task that adopts `PATCH /dogs/{id}` for documents (organizer decision on question 4) cannot be built without it.
   - **Fix.** Additive: add `fileKey` (or the file `id`) to each `SignupDogView.documents[].files[]` row, and add an IT that adds one file to a submitted type and keeps the others. `claimSignup` already accepts a key bound to the same `dogId:type`. Otherwise the organizer should accept the gap explicitly for the web task.
2. **minor** `FollowupController.java:36` (`PUT /dogs/{id}/observations`): this route is not frozen.
   - Today it is a 501 contract stub. Its description (R-10-12) says it will write `Dog.remarks`, which is the dog record.
   - The freeze has no entry for it: no `CensusAccess.unfrozen` call, and no `INVALID_STATE` in its `@ContractErrors`. The report does not mention it either.
   - Once E6-T03 implements it, the route would write the reused dog's record while the readmission is pending, and a rejection would not undo it. That breaks R-04-06 («la fitxa del gos no es toca») and R-04-23.
   - **Fix.** Add a line to E6-T03 (or a `MESSAGES.md` note) saying it must call `CensusAccess.unfrozen(dog)` and document `409 INVALID_STATE (READMISSION_PENDING)`. Or add the guard to the stub now.
3. **nit** `SignupService.java:511` (`claimDocuments`) with `signup.requireDogDocumentAtSignup=true` (the Cànic default is `false`): a D2 `PATCH` that withdraws the reused dog's submitted card (`VACCINATION_CARD` with `files:[]`) answers `422 DOG_DOCUMENT_REQUIRED`.
   - This happens although R-04-06 says a type sent without files keeps the dog's own document, and the dog already has one.
   - The same applies at submission: a readmission whose dog has a RECEIVED card must still send a new one.
   - No test runs with the parameter set to `true`.
   - **Fix.** Either skip the check when the reused dog has its own card document, or have the organizer confirm that the parameter wins over R-04-06.
4. **nit** `SignupService.java:773` (`dogReadmissionView`): when the reused dog has no card document at all, `changedFields` lists `documents` even though the applicant sent nothing.
   - This comes from the automatic PENDING card row.
   - It is accurate in the sense that validation will create the card. But D2 will show «documents changed» for a submission without documents.
   - `T_04_12_aReusedDogWithoutACardDocumentGetsTheEmptyCardAtValidation` does not assert `changedFields`.
   - **Fix.** Pin the intended value in that test, or exclude the automatic row from the comparison.
5. **nit** `roadmap/evidence/E3-T17/22-test-summary.log:3-17`: the «Classes of this round» list has 14 classes, but round 2 changes only one test class, `SignupSecurityFixesIT` (`git diff --stat 59c9d43 e663872 -- src/`).
   - The rule asks for one line per class the task adds or changes. Here the extra lines are the targeted run's classes.
   - It is harmless, but the heading overstates the change.
