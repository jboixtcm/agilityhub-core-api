# Review E3-T16: needs changes

The change is small. Steps 1, 2 and 4, the snapshot and the evidence all look right. My only substantive objection is the new `taxId` check (Assumption 1). It goes further than S02 in two places, and one of its tests contradicts the spec id it is named after. Both fixes are one line each.

## Findings

1. **major** `src/main/java/com/agilityhub/core/platform/domain/GenericCountryProfile.java:13-16` and `src/test/java/com/agilityhub/core/platform/domain/CountryProfileTest.java:48-50`: the `GENERIC` profile now validates the tax id (4 to 40 ASCII letters and digits).
   - **What the spec says.** S02 §2 on the `CountryProfile` interface: «`GENERIC` (document lliure amb tipus, sense lookup, E.164 obligatori, **cap validació de NIF**)». R-02-06 gives the example «Club a Portugal: `GENERIC` (**NIF sense validar**…)». T-02-04 says «`GENERIC`: cap validació de format».
   - **What the test does.** The new test `T_02_04_spanishTaxIdsAreACifNifOrNieWithTheirCheckCharacter` asserts that `GENERIC` refuses `"AB1"` and `"ÀÉÍ-ÒÚ"`. That is the opposite of the T-02-04 it is named after, so the E3-T11 traceability pass would carry a test that contradicts its own spec.
   - **Consequence.** A GENERIC club with a 3-character id, or an id with non-ASCII letters, gets `400 VALIDATION_ERROR` on `PUT /club` and on `club:apply`.
   - The report states this rule as an assumption but does not mention that it conflicts with S02.
   - **Fix:** make `GenericCountryProfile.validateTaxId` accept any non-blank value (or any value at all), and change the `GENERIC` half of the test to assert exactly that.

2. **minor** `ClubSettingsService.java:118-122` and `ClubDefinitionWriter.java:109-112`: the check runs on the **stored** `taxId` on every write, not only when the `taxId` changes.
   - **Why.** `validate(tree)` runs on the whole merged club, and `club:apply` checks `next.taxId()` even when the definition did not touch it.
   - **What breaks, `club:apply`.** R-02-06 says «Canviar de perfil (S17) no revalida dades existents». Today, a GENERIC club with `taxId: "PT501234567"` that is switched to `countryProfile: ES` by `club:apply` fails with `VALIDATION_ERROR {field: club.taxId}`.
   - **What breaks, `PUT /club`.** Any ES club whose `taxId` was stored before this task in a form the check now refuses cannot save any settings change, even just a theme colour. It gets a bare `400 VALIDATION_ERROR` with no field hint. Examples of such values: the old SettingsIT fixture `EXAMPLE-ORG`, or a VAT-style `ESG63189617`.
   - **Fix:**
     - in `PUT /club`, check only when the request has `taxId` and it differs from `before.taxId()`;
     - in `club:apply`, check only when `next.taxId()` differs from `old == null ? null : old.taxId()`;
     - add one IT for each of the two cases above.

3. **nit** `SettingsContracts.java:452` (`ClubUpdate.displayCity`) and `:440` (`ClubSettings.displayCity`): the property's description says «null clears it», and the test sends `displayCity: null`. But the snapshot types it as `"type": "string"` only (`openapi.json:3531-3534`), and `GET /club` returns `displayCity: null`.
   - A client generated from the snapshot (E3-W12) cannot send `null` to clear the field.
   - Other optional club fields follow the same house pattern, but this one explicitly promises null.
   - **Fix:** declare `types = {"string", "null"}`.

4. **nit** `seeds/club-canic.yaml:7-12` against S02 R-02-10: R-02-10 still says the Cànic seed has «identitat fictícia excepte nom/domini».
   - The real CIF and registered office follow the product owner's instruction and the 25-09 change log, so the seed itself is right.
   - But the rule text is now stale, and the report's doc proposals (a)–(c) do not mention it.
   - **Fix:** add a doc proposal for the organizer to amend R-02-10.

5. **nit** `ClubSettingsService.java:121`: a refused `taxId` on `PUT /club` gives `VALIDATION_ERROR` without `details.field`, while `club:apply` gives `{field: club.taxId}`. The rest of `PUT /club` validation is equally bare, so this is optional. Still, the web can only highlight the field if it knows which one failed.
