# Review E5-T03 — minor issues

## Findings
1. **minor** `src/main/java/com/agilityhub/core/clubs/bookings/application/WaitlistNotifications.java:104` — The `notifications.N-46.booked` consumer runs on **every** `BookingCreated` in a WAITLIST + ALL_AT_ONCE club, which today means every booking at the Cànic. Each time it opens a write transaction and takes the class's `seat_locks` lock before it knows whether any entry is NOTIFIED or demoted. That adds lock contention on busy classes at week opening, and in the normal case it does nothing: the confirmation transaction already demoted the entries (`BookingConfirmationService`, `waitlist.demoteIfFull`). · Task "Fixed conventions" (serialisation per class) · Fix: first run a cheap read-only check for NOTIFIED entries, or for ACTIVE entries with `notifiedAt`, and return early when there are none. Take the lock only when a demotion is still needed.
2. **minor** `WaitlistNotifications.java:107` — The N-46 idempotency id is `N-46:{entryId}:{notifiedAt}:app`, not the (`eventId`, recipient, channel) scheme that task step 8 requires ("same shape as N-08a"). The deviation makes sense, because the same demotion arrives through two events, and it is written down (Assumption 4, MESSAGES item 3). The organizer still has to accept it explicitly, since it breaks the stated convention. · Task step 8.
3. **minor** `WaitlistNotifications.java:91` + `:105-107` — Suppose the outbox delivers `WaitlistNotified` only after the seat has been claimed. The losers are skipped for N-15 because they are no longer NOTIFIED, but they still get N-46 («La plaça ja s'ha ocupat») for an offer they never heard about. No test covers this order. · R-08-13 · Fix: send N-46 only when the matching N-15 row exists (id `…:{entryId}:app` of that offer), or accept the behaviour and record it.
4. **minor** `N-46 path / BookingConfirmationService.java` (PAY_TO_BOOK) — A direct booking that takes the last seat as PAYMENT_PENDING does demote inside the transaction. But it emits neither `BookingCreated` (that comes only when the payment succeeds) nor `WaitlistConsolidated`. So N-46 goes out late, when the payment succeeds, or never, if the payment fails and a new release re-notifies the same entries. This does not apply to the Cànic (no SINGLE_CLASS), but it is a product-level gap. · R-08-13, R-08-18 · Fix: note it in the report, or also trigger N-46 from the demotion itself.
5. **minor** `BookingViews.java` `waitlistEntry(...)` — `position` is always returned. Task step 7 and the `GET /waitlist-entries/{id}` description say "position (FIFO only)". In ALL_AT_ONCE clubs the queue number means nothing, and screen 07 could show it. · S08 §6 / step 7 · Fix: return `null` when `waitlist.mode = ALL_AT_ONCE`, or confirm that the web hides it.
6. **minor** `src/test/java/.../WaitlistIT.java:337` — The cross-tenant check accepts `isIn(403, 404)`. Task step 9 requires "cross-tenant 404 everywhere". The report says E5ContractIT covers cross-tenant 404 per route; if so, tighten this assertion to 404, or drop it so it does not look like it accepts 403.
7. **minor** `WaitlistService.java:112` vs `SeatHoldService.java:520` — For a demoted entry (ACTIVE with `notifiedAt`), the hold answers `SEAT_TAKEN` only when the class is full, and `WAITLIST_NOT_NOTIFIED` otherwise. The claim always answers `SEAT_TAKEN`, without checking capacity. If a seat is freed below the notice threshold (no new offer), the claim gives the wrong code. The hold would normally stop the flow first, so impact is low. Fix: use the same rule in both places.
8. **nit** `WaitlistNotifications.java:137` / `NotificationRepository.java` allow-list — N-15 carries the variables `mode` and `entityId`, but the catalog row only lists `dog_name, class_date, class_time, confirm_by`. It is recorded as a catalog proposal (MESSAGES item 2), which is acceptable. The organizer should still decide on it, since AGENTS rule 2 says catalogs are closed.
9. **nit** `BookingCounters.java:473` — Uses the fully qualified `com.agilityhub.core.platform.application.Module` inline; import it instead. Also, `counters.waiting` is forced to 0 while WAITLIST is off, and nothing recounts it when the module is switched back on. The value stays stale until the next join, leave or cancellation on that class.
10. **nit** `WaitlistService.join` — The check order puts the eligibility chain first, then `CLASS_NOT_FULL`, then `ALREADY_BOOKED` (Assumption 1). As a result, a dog already booked in a class that is not full gets `CLASS_NOT_FULL`, not `ALREADY_BOOKED`. This is acceptable, but the web copy should know about it.
