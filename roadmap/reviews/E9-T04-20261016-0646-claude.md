# Review E9-T04 — minor issues

## Findings

1. **major** `src/main/java/com/agilityhub/core/courses/application/BuildSessionService.java:200` (`retrying`) together with `shared/api/IdempotencyFilter.java:230-249`. **Problem:** a keyed `finish` that races a tap answers `500`.
   - **Why it happens:** `finishBuildSession` declares `Idempotency-Key`, and clients and the IT (`BuildSessionsIT:87`) always send it on POSTs. So `finish` runs inside the idempotency filter's request transaction. In that case `retrying` runs the work once and does not retry it.
   - **Race:** phone A taps the last obstacle while phone B presses *finish*. The tap's transaction commits on the session document between B's `get(id)` and B's `sessions.close(...)`. B's `findAndModify` then gets a raw Mongo `WriteConflict`.
   - **Result:** nothing converts that conflict. `ApiExceptionHandler` has no conflict mapping, so B gets `500 INTERNAL_ERROR`. This is the same failure the session fixed for unkeyed taps ("never a 409 or a 500") and for E117.
   - **Same exposure, lower likelihood:** a keyed `POST /build-sessions` hitting a join-code `DuplicateKey`. Also a `POST /build-sessions/join` sent with a key, where two phones push to `participants` at once.
   - **No test for it:** `T_16_10_simultaneousTapsOnOneSessionAllApply` only covers unkeyed PATCHes.
   - **Fix (either one):**
     - Add `POST /api/v1/build-sessions(/[^/]+/finish)?` and `/join` to a retrying route group in `IdempotencyFilter`, as FOLLOWUP/BILLING do.
     - Or, in the joined-transaction branch, wrap `work.get()` with `WriteConflicts.guard`. That gives `409 STALE_VERSION`, never a 500.
   - **Test to add:** a keyed finish racing taps.
2. **minor** `BuildSessionService.java:126` (`finished`). **Problem:** `finish` is gated by `courses.allowInstructorPublish`.
   - R-16-11 does not gate `finish`. With the switch off, an INSTRUCTOR who built the course cannot close their own session, and it stays open until P9 marks it `ABANDONED` (≥ 12 h).
   - The assumption is documented, but it is a product decision, not something the spec says.
   - **Suggestion:** raise it as a question to `@organizer`. A possible alternative: complete the session and skip only the setup registration.
3. **minor** `RingSetupService.java:113-116` (`built`, refresh path). **Problem:** when the active setup already shows the placement, `rebuilt` sets `expectedUntil = null`.
   - This silently erases an `expectedUntil` that a person set at registration or renewal.
   - No audit entry is written for the refresh either.
   - **Fix:** keep `current.expectedUntil()` and recompute `expiresAt` from it, as `renew` does with its input. Alternatively, record why it is dropped.
4. **minor** `BuildSessionService.java:176-177`. **Problem:** the export's marker check counts **all** markers, but R-16-04 (`RingGeometryRules:68`) counts **active** ones.
   - Six markers with one inactive pass the check, yet the Unity app gets only five usable markers.
   - Seven markers are refused with `rule: TOO_FEW_MARKERS`, which is misleading.
   - **Fix:** decide on active versus stored markers as part of open question 1. If more than six can occur, use a correct rule name, or document that `TOO_FEW_MARKERS` covers "not exactly six".
5. **minor** `courses/api/BuildSessionStreams.java:86-90, 179-182`. **Problem:** one daemon thread does every `emitter.send` for every stream: heartbeats, polls and after-commit refreshes.
   - These are blocking servlet writes. A stalled mobile client (full TCP send buffer) blocks that thread until the socket write times out.
   - Meanwhile heartbeats and the < 2 s delivery stop for **all** sessions on that instance. Small events make this unlikely, but a single slow client can cause it.
   - **Suggestion:** run each subscriber's send on a small pool or a per-subscriber queue, or at least put a write timeout on the connector.
6. **minor** `BuildSessionStreams.java` / `SecurityConfiguration.java:96-104`. **Problem:** a stream is authorised once, when it opens, and then lives up to 30 min.
   - An expired or revoked token keeps receiving events, and so does a membership that loses INSTRUCTOR or the `COURSES` module.
   - The async-dispatch skip in `RequiresModuleInterceptor:400` is correct for ending the stream, but nothing re-checks during it.
   - **Suggestion:** cap `TIMEOUT` at the access token's remaining lifetime (`exp`), or note it as an accepted risk in the report.
7. **minor** `BuildSessionStreams.java` + `BuildSessionRules.outlived`. **Problem:** a session open for longer than `courses.buildSessionMaxHours` already refuses writes, but its open streams get no `finished` until the next daily P9 run (up to about 24 h later).
   - **Suggestion:** in `Subscriber.update`/`poll`, send `finished` (or end the stream) once the session is outlived.
8. **nit** `BuildSessionsController.java:70` (`finishBuildSession`). **Problem:** `@ContractErrors` leaves out `RING_WITHOUT_GEOMETRY`, which `RingSetupService.built` (line 107) can throw. It is hard to reach (`RING_GEOMETRY_IN_USE` protects the geometry), but the list should match what the code throws.
9. **nit** Organizer note E117 asked for `dismantle`, `renew` **and `end()`** to be guarded. Only the HTTP paths are guarded: `end()` stays raw for P5f and the ring-deactivation consumer. The reasoning is sound, but the report should state it as a deviation from the note, not only as an assumption, so the organizer can accept it explicitly.
10. **nit** P9's item `ABANDON_BUILD_SESSION`, `WOULD_ABANDON_BUILD_SESSION` and the counter `buildSessionsAbandoned` are not in S15 R-15-19, and R-15-19 says P9 touches only technical collections. The executor did file this as proposal 2 in the report. Make sure it also reaches `roadmap/MESSAGES.md` for `@organizer`/`@jordi`; the MESSAGES diff exists but I did not compare its wording.
