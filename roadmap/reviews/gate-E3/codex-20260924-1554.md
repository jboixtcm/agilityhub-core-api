# Gate E3 audit — fail

## Findings

The snapshots contain functional defects beyond the acknowledged W04 work. The findings below are based on source inspection; external-service failures were not reproduced.

1. **major** `agilityhub-core-web/apps/clubs/src/SignupPage.tsx:1311` — Consent can be recorded against a legal version the applicant did not accept. The draft stores only `privacyAccepted`, configuration reloads preserve it (`:1732`), and submission attaches the latest configuration version. **Spec:** R-04-17. **Scenario:** accept v1 → reload after the club publishes v2 → submit without accepting again → API records acceptance of v2. **Fix:** retain the accepted version and invalidate acceptance whenever the legal version changes.

2. **major** `agilityhub-core-web/apps/clubs/src/SignupPage.tsx:1359` — Final submission does not use the normalized identity document used by the identity check. `identityDocument()` infers NIE or takes the separate passport field (`:376`), but submission spreads the original person draft, initially typed DNI. **Spec:** R-04-01; screens 16–19. **Scenario:** a valid NIE or passport passes screen 16 → final submission sends DNI with the wrong value/type → validation fails. **Fix:** use one canonical document value for both requests.

3. **major** `agilityhub-core-web/apps/clubs/src/SignupPage.tsx:1366` — The supported empty-plan signup sends `planId: ""` instead of omitting it. The API accepts no plan only when its identifier is null and the catalog is empty (`agilityhub-core-api/src/main/java/com/agilityhub/core/clubs/signup/application/SignupPolicy.java:43`). **Spec:** R-04-09. **Scenario:** club with no signup plans → complete the form → `PLAN_NOT_AVAILABLE`. **Fix:** omit empty `planId` and `planIdRequested` values.

4. **major** `agilityhub-core-api/src/main/java/com/agilityhub/core/clubs/census/application/SignupService.java:227`; `agilityhub-core-web/apps/clubs/src/SignupPage.tsx:1517` — Screen 19 cannot faithfully quote the selected plan and omits the required total. Configuration derives one set of monthly options from the first monthly plan; the front displays those options for every public plan and has no PACK charge or total row. After the add-dog cutoff, configuration also omits the payable TODAY option entirely (`SignupService.java:229`). **Spec:** R-04-14/15, screen 19, T-04-32. **Scenario:** select a €135 pack → monthly options appear instead of the €135 pack charge; add a dog after the cutoff → its additional fee is absent from the preview. **Fix:** return/render a quote for the selected plan and mode, including all lines and total.

5. **major** `agilityhub-core-web/apps/clubs/src/SignupPage.tsx:1331` — Retry state is lost between signup creation and checkout. Each attempt generates new idempotency keys, clears the draft before checkout, and retains neither the created resource nor its capability for recovery (`:1334`, `:1369–1382`). **Spec:** R-04-26/27; screen 19 cancellation/retry behavior. **Scenario:** signup commits but checkout fails → resubmit → a new signup request receives “already pending” or duplicate-chip failure; checkout cancellation reloads a cleared draft. **Fix:** persist stable operation keys and the completed signup stage until checkout is resolved.

6. **major** `agilityhub-core-api/src/main/java/com/agilityhub/core/clubs/census/api/SignupController.java:146` — Signup upload responses discard headers required by the storage implementation. `AttachmentService.java:48` supplies `If-None-Match: *`; `S3AttachmentStorage.java:15` signs that condition; the response DTO drops it and the browser sends only Content-Type (`agilityhub-core-web/apps/clubs/src/SignupPage.tsx:879`). **Spec:** R-04-08; signed-upload contract. **Scenario:** use the S3 storage adapter → browser PUT lacks the signed conditional header → upload cannot satisfy the signed request. **Fix:** expose and send the required upload headers; cover the S3 signing contract.

7. **major** `agilityhub-core-api/src/main/java/com/agilityhub/core/payments/application/CheckoutService.java:43` — Provider checkout creation occurs before the database transaction commits, without a durable provider operation identifier. A fresh UUID is generated at `:39`, followed by the provider call and database writes. **Spec:** R-04-26/27; partial failures and retries. **Scenario:** provider creates a session → subsequent database write/commit fails → retry creates another provider session while the first has no committed local record. **Fix:** persist the checkout operation first and invoke the provider with a stable idempotency identifier through a recoverable post-commit process.

8. **major** `agilityhub-core-api/src/main/java/com/agilityhub/core/payments/application/UpfrontPayments.java:71` — Changing a plan rewrites the original amount of a partially paid payment. **Spec:** S04 §3 `UpfrontPayment`, §5: amounts are immutable and corrections create new records. **Scenario:** a €100 line has €50 paid → change plan → the existing line becomes €50 due/€50 paid, erasing its original amount. **Fix:** preserve the original line and represent cancellation, credit and replacement charges explicitly.

9. **major** `agilityhub-core-web/apps/clubs-admin/src/dashboard/SignupReviewPage.tsx:471` — D2’s plan selector contains only the current proposal, and its dry-run handler never applies recalculated payment lines. It also retains the old `priceId` (`:323`, `:337`). **Spec:** R-04-13/14/16; D2; T-04-33. **Scenario:** administrator needs to change a requested monthly plan to a pack → no alternative is selectable; a changed identifier would still carry the previous price and leave the displayed amount stale. **Fix:** load selectable plans/prices, update them together, and apply the complete dry-run response.

10. **major** `agilityhub-core-web/apps/clubs-admin/src/dashboard/SignupReviewPage.tsx:157` — Dog edits send the member’s version instead of the dog’s version.
