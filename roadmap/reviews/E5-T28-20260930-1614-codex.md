# Review E5-T28 — needs changes

## Findings

1. **major** `src/main/java/com/agilityhub/core/payments/application/CheckoutService.java:86` — Lost-answer recovery rebuilds the provider request from mutable member data. After the first provider call succeeds but response persistence fails, an admin can change the contact email or payment method. Retrying the same key then sends different `customerEmail` or `setupFutureUsage` under the same session ID. The documented Stripe integration will reject this because retries must preserve parameters; the catch block then expires the local session without expiring the existing provider session. This leaves round-2 item 3 incomplete (`CONVENCIONS_API.md` §7). Persist the original provider request or a recoverable provider result. Extend the recovery test with an intervening member edit and a provider double that rejects changed parameters. [Stripe idempotency contract](https://docs.stripe.com/api/idempotent_requests).

2. **major** `src/main/java/com/agilityhub/core/payments/application/CheckoutService.java:176` — The late-completion guard accepts a session when **any** associated row remains `CHECKOUT_PENDING` (`UpfrontPayments.checkoutPending`). For a pre-fix mixed checkout where rejection cancelled one dog’s rows but left another dog’s rows pending, completion marks the session `COMPLETE`, pays the surviving rows and records no `lateCompletionAt`. Money charged for the rejected rows therefore misses E34 reconciliation. Step 4 explicitly covers sessions whose rows were closed. Require every recorded `upfrontPaymentId` to remain pending for that session; otherwise expire it, release surviving rows and record the late completion. Add a mixed cancelled/pending regression test.

3. **major** `src/main/java/com/agilityhub/core/payments/application/UpfrontPayments.java:193` — Restoring `PARTIAL` preserves the amount but loses its payment history. A manually paid partial row enters checkout through `pending → state`, which replaces its provider with `STRIPE` and its `paidAt` with the checkout time. `released` subsequently sets the provider to `null` and retains that overwritten timestamp. Thus rejecting another dog in a mixed checkout corrupts the surviving payment’s original method/date; a later correction inherits those values. This contradicts S04 R-04-16 and §3/§5 payment-history requirements. Preserve the received-payment metadata across checkout transitions, and test a partial payment with the clock advanced before checkout and rejection.
