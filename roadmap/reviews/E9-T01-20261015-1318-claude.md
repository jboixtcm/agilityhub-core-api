## Findings
1. **nit** `src/main/java/com/agilityhub/core/configuration/E9ContractConfiguration.java:75-80`: the discriminator is added by a customizer that hard-codes the path, and it does no null checks: `api.getPaths().get("/api/v1/ring-setups/{id}").getGet().getResponses().get("200").getContent().get("application/json")`.
   - **Why:** report assumption 2 says springdoc drops the annotation's discriminator, so the workaround itself is justified. But if the route, the status or the media type is ever renamed, startup and the snapshot fail with a bare NPE instead of a clear message.
   - **Suggested fix:** use `Objects.requireNonNull(..., "S16 ring-setup detail response")`, or look up the operation by `operationId = getRingSetup`. Either gives a readable failure.
2. **nit** `src/main/java/com/agilityhub/core/courses/api/CoursesController.java:60` (published as the `getCourse` description in `docs/openapi/openapi.json`): the new text says "Course visibility still applies". A client will read that as "a MEMBER never sees a `CLUB` course", because R-16-03 grants `CLUB` only to staff, and the guard does answer `404 COURSE_NOT_VISIBLE` today.
   - **Why:** R-16-16 lets a MEMBER read a course that a visible setup references, and those are typically `CLUB` courses. The task's Fixed conventions defer that part to E9-T03, but the published contract does not say it is deferred. E9-W02 builds mocks from this description.
   - **Suggested fix:** add one sentence, for example "MEMBER access to a `CLUB` course referenced by a visible setup (R-16-16) lands in E9-T03." Or have the organizer carry that note into E9-T03's contract delta.
3. **nit** `src/test/java/com/agilityhub/core/configuration/E9ResponseContractTest.java:66-71` (`responseValidator`): it validates with networknt `V202012`, which ignores the OpenAPI `discriminator` keyword. Only the `const` values make the branches exclusive, and the test proves that part correctly: each fixture fails against the other branch, and a missing, `null` or unknown `view` is rejected.
   - The discriminator mapping is only checked structurally, by asserting the strings `propertyName` and `mapping`. That is enough for this contract.
   - Worth one line in the report, so nobody assumes the discriminator itself was validated.

I checked the following and found no defects:
- The new `memberVisibility()` call in `course()` runs before the lookup, so a MEMBER with the parameter off cannot tell whether a course exists.

- `view` is `READ_ONLY`, computed in the response DTO, never persisted, and appears consistently in `RingSetupCreated.setup` and in the setup history page.
- The snapshot diff is exactly the two schemas, one description and one discriminator. The OpenAPI version is 3.1.0, so `const` is valid.
- No catalog item, parameter, error code or club literal was added.
