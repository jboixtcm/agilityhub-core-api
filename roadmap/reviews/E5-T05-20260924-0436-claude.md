# Review E5-T05: minor issues

## Findings
1. **major** `src/main/java/com/agilityhub/core/clubs/dashboard/domain/RiskCardBuilder.java:21-24` (not touched by this change). Step 8 says to "wire E3-T04's dashboard risk card to [`GET /risk-review`] and remove any remaining double". Only the `notified` names were wired, through `SchedulingDashboard`. The dashboard still computes its own statuses, with different rules:
   - its enum is `CANCELLED/AT_RISK/WILL_CANCEL/PENDING_DECISION`, while the form-A statuses are `AUTO_CANCELLED/…/WILL_REVIEW`;
   - it trusts `counters.booked`, while `RiskReviewQuery` recounts;
   - a class with registrants that nobody has been warned about yet shows `AT_RISK` on D1 but `WILL_CANCEL` in `GET /risk-review`.

   After this change `riskNotice = adminNotifiedAt != null || !riskNotified.isEmpty()`. So S15 §6's example c4 (0 registrants, admins warned) is `AT_RISK` on D1, while the spec and `/risk-review` say `WILL_CANCEL`. The report's claim "The same names now feed S14's D1 card" is accurate, but the double is still there. Fix: build the D1 risk card from `RiskReviewQuery.review()`, mapping its statuses onto S14's enum if S14 keeps its own names, and add a D1-vs-`/risk-review` parity assertion.
2. **minor** `src/test/java/com/agilityhub/core/clubs/bookings/api/RiskReviewJobIT.java:288-290`. The comment says "Nothing once the class has started … the guard is startsAt", but the test asserts nothing about a started class. It only checks the second alert (`hasSize(8)`). R-15-12b's explicit rule "Amb `date == today` i `startsAt ≤ now` no s'envia res" has no test. Fix: add an in-time drop on a class whose `startsAt ≤ now` (or move the clock past it) and assert there is no `ClassBelowMinimum`.
3. **minor** `src/main/java/com/agilityhub/core/clubs/bookings/application/WaitlistConsumers.java:48-61`. The new `alerts.WaitlistExpired` R-15-12b path has no test (grep finds no test that references it).
   - It calls `recount(classId, true, …)` for every `WaitlistExpired`, without checking the spec's "que deixi la classe igual".
   - It runs in a separate consumer transaction, while R-15-12b says "dins la mateixa transacció". `WaitlistFifoJob.apply` already calls `counters.recount(e.classSessionId(), false, …)` inside the item transaction (`WaitlistFifoJob.java:51`). Passing `true` there would honour the spec with no extra consumer.

   Fix: do the check in the job's transaction, or add an IT for the consumer.
4. **minor** `RiskReviewJob.java:53-61`. With `classes.riskAutoCancelSameDay = false`, today's classes take the warn branch with no `startsAt ≤ now` check. A CATCH_UP or manual run in the evening therefore sends N-16 "Possible anul·lació" for a class that has already started or finished. `RiskReviewQuery.java:46-62` has the same gap: it lists today's started ACTIVE classes as `WILL_CANCEL`/`WILL_REVIEW` even though no review will act on them. Suggest applying the `skippedStarted` guard to both branches and excluding started classes from form A, or recording the choice as an assumption.
5. **minor** `RiskNotifications.java:69` together with `messages_*.properties` `notif.N-16.body`. The admin copy of N-16 reuses the member template with `dog_name = ""`, so admins receive "la classe de  del dijous…". The report flags this only as a future E7 question (proposal 5), but the text is broken now. Suggest an ICU `select` on an audience variable, or omitting the dog phrase when `dog_name` is empty. Either needs no new catalog item.
6. **minor** `WeekOpeningJob.java:69-81`. R-15-11 step (1) invalidates "la cache de configuració i de graelles". Grids are only invalidated indirectly, through S09's `TrainingCounterReset` consumer, which runs only with `FREE_TRAINING` and is asynchronous. It is not done in P1's own transaction. With `FREE_TRAINING` off, no grid cache is dropped. Either confirm there is no other grid cache or invalidate it directly.
7. **minor** `CleanupRepository.java` (whole class). It is new persistence code that reads and deletes in `dog_documents`, `attachment_uploads`, `domain_events`, `job_runs` and `stripe_events` through raw `MongoTemplate` with a manual `clubId` criterion, bypassing `TenantRepository` (AGENTS rule 4). The scoping looks right and T-15-27 checks the other club's upload. But cleanup is scoped per club, so `domain_events` and `job_runs` without a `clubId` (platform or identity events) are never purged. Note this in the report or add a platform pass.
8. **minor** `CleanupRepository.expiredRuns` "keeps the last 5 runs" counting any row, including SKIPPED rows and dry runs (assumption 8). For continuous jobs the five newest rows are minutes old, so this is harmless. For daily jobs, five dry runs by an admin could push out every real run older than 90 days. R-15-19 says "execucions". Consider excluding `dryRun = true` from the kept five.
9. **nit** T-15-15 has no test method named after it. It runs inside `T_15_13_…` (the report says so). AGENTS rule 5 asks for spec-id names, so a separate `T_15_15_…` method, or at least the id in the method name, would make coverage auditable.
10. **nit** `clubs/common/domain/ForeignEvent.java`. It is a consumer-side envelope that implements `DomainEvent`, so it could be published by mistake, and it forced an extra `EventCatalogContractTest` sample. Other consumers deserialize the owning context's event type (`SchedulingEvent`). If ArchUnit allows `clubs.common` → `clubs.scheduling.domain`, consuming `SchedulingEvent` directly would be simpler.
11. **nit** Evidence numbering goes 01, 02, 04–08 with no `03-*.log`, and the report does not explain the gap. `04-test-summary.log` says "the same totals and list as the previous green run", but that run has no log. With `-q`, the `07-verify.log` tail contains no Maven summary, so the green result rests on the stated exit code plus the XML-derived totals.
