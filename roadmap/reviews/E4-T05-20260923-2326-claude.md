# Review E4-T05 — minor issues

## Findings
1. **minor** `seeds/demo-canic.yaml:23` + `DemoSeedService.java:519` — every demo member now gets a phone number `+34 600000001…`. These are real-format Spanish mobile numbers that someone may actually own. The seed then sends N-08a SMS intents to them: 2 at seed time (the Saturday class cancelled by the Torneig), plus the 6 cancellation recipients in each smoke run. They stay `QUEUED` only because no SMS provider is configured locally. If a provider is ever set on a local stack, the seed or the smoke would text real people. That goes against the fictional-data rule (AGENTS rule 6, task «Fixed conventions»). · Fix: use a number range that can never be dialled or assigned, or have the local profile refuse SMS dispatch, and state which one in `seeds/README.md`.
2. **minor** `src/main/java/com/agilityhub/core/shared/application/DemoSeedActor.java:13` — a public static helper in the production jar that sets an authenticated `SecurityContext` for any account and role (`ROLE_ADMIN`/`MEMBER`) and opens a `CurrentUser`. Only one caller checks the profile (`DemoPlanningService.apply`); the helper has no guard of its own. Any future code path could use it to skip role checks. · Fix: add an ArchUnit rule that only `Demo*` seed classes may call it, or have it check the `local`/`test` profile itself.
3. **minor** `src/test/java/com/agilityhub/core/clubs/census/application/DemoPlanningSeedIT.java:359` — `T_06_28_seedSourcesContainNoRealStaffOrMockupFirstNames` hard-codes six names (`Estel, Josep, Neus, Jordi, Marc, Núria`). The D4c mockup alone also has `Montse` (lines 8/19) and the registrants `Laura`, `Anna`, `Pau` (lines 262–265); R-07-05's example also uses «Pau + Blat». The seed's `firstNames` (from E2-T11) contains **`Pau`**, which is exactly a D4c mockup first name. So the test is weaker than Step 5 and the report claim («no real name … or the mockups»). Also, `staff.canic.yaml` does not exist, so that half of the check never runs. · Fix: build the name list from the cited mockups (D3/D4/D4b/D4c/D7/10/23), and let the organizer decide whether `Pau` stays, since it is inherited from E2-T11.
4. **minor** Report «Assumptions» vs Step 1(e) — the task asks for D4 counters `4/5, 3/5, 5/5 +1, 2/5, 1/1`. The seed produces Monday 08:30 Muntanya C+D+E as **`3/4`** (capacity comes from the levels). This appears only in the «Final arrangement»/`seeds/README.md`, not among the stated deviations. · Fix: list it as a deviation (or pick a class whose computed capacity is 5).
5. **minor** `bin/e4-smoke:176` / Step 2 «the second run of the script is idempotent» — each run uses a new Compose project and requires an empty database. The script also permanently generates and validates W+3 and cancels the seeded D4c class. So a second run on the *same* stack was never exercised, and the run suffix plus final cancellations only protect disposable data. The report says this openly («Each smoke run uses a new disposable Compose project»), but it reinterprets the Verification wording. · Fix: the organizer should accept this explicitly. The DEPLOY doc should also say the smoke must not target the stack the E4-W front tests use; it can't today, because of the empty-DB guard.
6. **minor** `DemoPlanningService.java:407-411` — the planning run is recorded once per club. Later runs report 0 changes whatever `--week-start` or run date is given. On any stack that lives longer than a few days the data ages: W+1 «Esborrany» becomes the current or a past week, and the W+2 D4c class passes. After that, cancellation fails the past-date guards, and the only fix is a fresh database. `seeds/README.md` mentions a fresh DB only for a *changed* spec. · Fix: document the ageing and the "fresh project per front test run" rule in `seeds/README.md` (DEPLOY already hints at it), so E4-W05 does not reuse an old seed.
7. **minor** `DemoPlanningService.java:401` — one `@Transactional` covers `DemoActivitySeeder.upload` → `AttachmentService.putLocal`, and file-system writes are not rolled back. If a later step fails, the image and PDF stay orphaned in the attachment directory. The impact is local-only. · Fix: upload files after the transaction commits, or note it as an accepted limitation.
8. **nit** `ClassSessionService.java:567` `bookingCounters` — this public, mutating application method has no role guard, no audit and no capacity check (`booked > capacity` is accepted). The report presents it as «the S08 writer path», so E5 will inherit it. · Fix: add a Javadoc or ArchUnit note limiting callers to the bookings context, and add a capacity check (or leave one to E5 explicitly).
9. **nit** `bin/e4-smoke:123,362` — the summary prints `bin/core activities:finish-ended` / `scheduling:finish-ended`, but the script runs `java -jar /app/app.jar --core.command=…` inside the container, not `bin/core`. Functionally equivalent; the label is misleading against the Step 2 wording.
10. **nit** Seed data — the R-06-10 class has 4/5 booked plus 2 waiting, a waitlist on a class that still has free places. The task asks for exactly this, but the real S08 adapter would never produce it. Front tests (T-06-28) should not treat it as a general invariant; a line in `seeds/README.md` would help.
