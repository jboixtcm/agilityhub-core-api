## Findings
1. **minor** `src/main/java/com/agilityhub/core/clubs/followup/application/FollowupTransactions.java:37` and the `@ContractErrors` of `TasksController.java:75,116,130,148`, `AttachmentsController.java:66,80,110`, `FollowupController.java:101,113`
   - **What is wrong:** after this round, nine more routes run in `FollowupTransactions.run`. When its 10 attempts run out it throws `409 STALE_VERSION`, but none of these routes declares it or mentions it in its description:
     - `POST /tasks`, `DELETE /tasks/{id}`, the completion and the reopening;
     - `POST /attachments/upload-url`, `POST /attachments`, `DELETE /attachments/{id}`;
     - `POST /followup/{id}/read`, `POST /followup/read-all`.
   - Only `PATCH /tasks/{id}` and `PUT /dogs/{id}/observations` declare it. The completion and the reopening already had this gap since round 1; this round spreads it.
   - `POST /attachments/upload-url` is also the S03/S07 upload route (`DOG_DOCUMENT`, `DOG_PHOTO`, `ACTIVITY_*`). Those clients can now get a `STALE_VERSION` as well, and its retries are counted under `context=followup` (assumption 29).
   - **Why:** a client-visible error code is missing from the published contract (CONVENCIONS_API error contract, AGENTS rule 9). A `STALE_VERSION` on a request that sends no `version` (read-all, upload URL) is hard for a front end to map.
   - **Fix:** add `STALE_VERSION` to those `@ContractErrors`, or add one sentence to each description («a write conflict that outlasts the retries → 409 STALE_VERSION»). Then regenerate the snapshot and add a `docs/openapi/CHANGELOG.md` line.
   - Or the organizer can rule that the exhaustion path is transversal and not declared per route. That matches today's code: `POST /bookings` does not declare it either.
2. **nit** `TasksController.java:210,239,254`, `AttachmentsController.java:55,77`, `FollowupController.java:120`

   - **Why:** if the two drift apart, a replayed key answers a different status than the first response (CONVENCIONS_API §7). Only the completion's replay is asserted in the round-5 tests.
   - **Fix:** read the status from the handler's `@ResponseStatus`, or add one replay assertion per keyed route (the creation's double-click replay already exists).
