# Review E3-T09 — needs changes

## Findings

1. **major** `src/main/java/com/agilityhub/core/clubs/census/application/SignupService.java:86` — Checkout still receives the LEFT record’s primary email during a pending readmission. `CheckoutService.create()` passes this directly to the payment provider as the customer email, despite the applicant submitting a replacement address. This is a regression caused by deferring contact updates under E38; the executor acknowledges it remains unresolved. Use the submitted primary address for pending-readmission checkout, without changing the account’s login email, and extend T-04-12/T-04-22 to assert the provider request.

2. **major** `src/main/java/com/agilityhub/core/clubs/census/application/SignupNotifications.java:32` — Recipient limits charge every outbox delivery attempt, including retries of the same event. With the accepted cap set to 1, a transient exception after consuming the allowance but before sending N-39/N-01 causes the retry to skip delivery and return successfully; the dispatcher then marks the consumer processed although no email was sent. This breaks the retry behavior documented in `docs/playbooks/new-event-consumer.md`. Make admission idempotent by event/delivery ID, preserving an admitted notification’s retries, and test a failed first attempt followed by successful delivery.

3. **minor** `src/main/java/com/agilityhub/core/clubs/census/application/SignupNotifications.java:58` — N-01 overwrites the event’s preserved applicant locale with the current dog’s signup locale. If readmission A is rejected and readmission B reuses the same dog before the outbox drains, A’s email uses B’s locale; the same mutable lookup also supplies B’s dog name and upfront total. R-04-06(c) requires the original submission’s locale, and S04 §8 requires its confirmation data. Preserve the event’s locale and submission-specific notification values; test two successive readmissions before dispatch.

4. **minor** `src/main/java/com/agilityhub/core/clubs/census/application/SignupService.java:405` — Synchronous eviction can still lose a race with an in-flight configuration load. A GET reads the old configuration, the parameter write commits and evicts, then that GET stores the old value for another 60 seconds. Subsequent GETs after the successful write therefore remain stale, leaving step 5 partially fixed. Use generation-aware loading, such as the existing `CacheLoads`, and add a deterministic test that pauses a load across the commit/eviction.
