# Review E5-T04 — minor issues

## Findings

1. **major** `src/main/java/com/agilityhub/core/clubs/training/application/TrainingTransactions.java:33` + `src/test/java/com/agilityhub/core/clubs/training/api/TrainingConcurrencyIT.java:39-66`: the concurrency tests never reach the partial unique index.
   - `book()` takes the in-process lanes `dog:…`, `member:…` and `slot:<startsAt>` (`TrainingBookingService.lanes`). These are fair `ReentrantLock`s held around the whole retried transaction.
   - In T-09-32 all 20 requests share the lane `slot:2026-10-05T08:00Z`. In T-09-33 all 5 share `dog:s09-d-rock`. So in the one test JVM they run strictly one after another.
   - The `{201=1, 409 SLOT_TAKEN=19}` result is therefore produced by the Java lock. The index `training_active_seat` and the `trainingSeq` `$inc` write conflict play no part. The test would still pass if the index or the `$inc` were removed.
   - Why it matters: the DoD and R-09-06 name the index as "the final guarantee", and it is the only guard across replicas (the report says so itself, Assumption 15). `TrainingApplicationTest.T_09_32` only checks the retry classifier with fake exceptions.
   - Fix: add a real-Mongo test that bypasses the lanes. Options: a test-only `TrainingTransactions` without locks; two service instances; or at least insert two ACTIVE rows with the same `{clubId, ringId, startsAt, seatIndex}` and assert `DuplicateKeyException`, then drive the retry to `SLOT_TAKEN`. Do the same for T-09-33 with the `$inc` (write conflict → retry → `TRAINING_LIMIT_REACHED`).

2. **minor** `TrainingBookingService.java` step (3), together with the lanes: a double booking of one dog can happen across replicas.
   - With `bookings.limitUnit = MEMBER`, two members of one family group can book the same shared dog at the same time on two different rings.
   - Their `$inc`s hit different `Member` documents, and the unique index is per ring and seat, not per dog. Only the in-process `dog:` lane stops it.
   - Across replicas both commit, which breaks R-09-06 ("no overlapping TrainingBooking of the same dog").
   - Fix: also `$inc` `Dog.trainingSeq` (or touch the dog) whatever the unit is.

3. **minor** `TrainingBookingService.java` (steps 3 and 5) vs S06 `RingBlockService` / `ClassSessionService`: write skew between a training booking and a ring block or class.
   - The booking reads "no class, no block" and inserts. The S06 caller reads "no live booking" through `TrainingConflictPort` and inserts.
   - The two sides share no document, and training takes a different lock than S06's catalog reference lock (Assumption 15). Both can commit, leaving a block or class over an ACTIVE booking without `RING_HAS_BOOKINGS` (R-09-13).
   - Low probability, but it is exactly the conflict R-09-13 exists to prevent.
   - Fix: make both sides write one shared per-ring (or per ring and day) document, e.g. `$inc` a ring sequence, so Mongo raises a write conflict.

4. **minor** `src/main/java/com/agilityhub/core/clubs/census/application/TrainingMemberAccess.java` (`lastDogForTraining`): every booking bumps `Member.version`.
   - It uses `CensusRepository.setField`, which does `inc("version", 1)` and sets `updatedAt`.
   - Result: an admin with the member's census form open gets `STALE_VERSION` whenever the member books training. The new `increment()` avoids this for `trainingSeq`, but this write does not.
   - Fix: write `lastDogForTraining` without the version bump, as `increment` does.

5. **minor** `src/main/java/com/agilityhub/core/clubs/training/application/TrainingOccupancyService.java:38`: the MEMBER view still carries the block `id` (`member ? null : block.note()`, but `block.id()` is always set).
   - R-09-12 and step 6 say the member result is redacted to `{type, reason}`. The code comment justifies keeping it ("S06 already lists it"), but that is a deviation.
   - Fix: pass `null` for MEMBER, or record the exception as an assumption in the report.

6. **minor** `TrainingBookingService.cancel`: the impersonating admin's late cancellation is refused once `now ≥ endsAt` (`!now.isBefore(b.endsAt())`).
   - R-09-10 and R-09-16 set no such limit. This is an unreported rule.
   - Fix: remove it, or list it in the report's Assumptions.

7. **nit** `TrainingConsumers.days()`: day-level invalidation for `RingBlockCreated` probably always falls back to a whole-club invalidation.
   - It parses `payload.from/to` with `Instant.parse(x.toString())`. The outbox stores them as BSON dates (the curl log shows `"from":{"$date":…}`), so the parse throws and is caught, and the code drops the whole club's cache.
   - This is functionally safe but not what Assumption 14 claims. No test covers the per-day path for blocks.
   - Also, a `ClassSessionUpdated` that moves a class to another day only invalidates the new day; the old day stays stale for up to the 60 s TTL.

8. **nit** `TrainingNotifications.code()`: N-47 is sent when `by = ADMIN`, while the catalog row says `by ≠ MEMBER`.
   - So SYSTEM cancellations get N-07 or nothing instead of N-47. It is reported and sent to the organizer, and is consistent with R-09-14.
   - N-47 also carries `change` and `has_admin_text`, which are not in the catalog variables. These are proposed, which is fine, but the organizer should confirm before E8.

9. **nit** Weak assertions:
   - `TrainingIT.T_09_13…:316` accepts either `INVALID_SLOT_GRANULARITY` or `INVALID_TIME_RANGE`.
   - `TrainingConcurrencyIT.T_09_34` checks the rings `containsExactlyInAnyOrder` and never checks catalog order. That order is covered only sequentially, in `T_09_11`.
