# Review E9-T01 — needs changes

## Findings
1. **major** `src/main/java/com/agilityhub/core/courses/api/RingSetupsController.java:79` (+ `E9ContractIT.java:197-198`) — `GET /me/ring-setups` calls `guards.memberVisibility()`, so a MEMBER gets `404 NOT_FOUND` when `courses.showSetupToMembers = false`. The spec asks for something else:
   - T-16-09 says: «`showSetupToMembers=false` → `setup` absent per a MEMBER i present per a INSTRUCTOR». The list should still answer 200, each `MeRingSetup` with `setup = null`.
   - Step 1 puts the 404 only on `GET /ring-setups/{id}`.
   - The contract test asserts the 404, so E9-W02's mocks will copy the wrong behaviour.
   
   **Fix:** drop `memberVisibility()` from `myRingSetups` and keep only `guards.rings(ringIds)`. Change the test to expect `501` for MEMBER and document R-16-09's null-setup rule in the operation description.
2. **minor** `src/main/java/com/agilityhub/core/courses/api/CourseRequests.java:63-64` — `RingGeometryRequest.lengthM/widthM` have `@DecimalMin("10") @DecimalMax("60")`. An out-of-range ring therefore gets `400 VALIDATION_ERROR` before the stub. R-16-04 says `width/length ∈ [10, 60]` is one of the checks that answer `422 GEOMETRY_INVALID{details}`, and the published operation declares exactly that. As built, E9-T02 can never return the spec'd code for this case without changing the published form.
   
   **Fix:** publish the range in the schema only (`@Schema(minimum, maximum)`) and leave enforcement to E9-T02 as `GEOMETRY_INVALID`. Or ask the organizer which code wins and record the answer.
3. **minor** `src/main/java/com/agilityhub/core/courses/application/CourseContractGuards.java:41` and `src/test/java/com/agilityhub/core/configuration/E9Fixtures.java:28` — the club course fixture is `ownerType CLUB` + `visibility PUBLIC`. S16 §3 forbids that combination: «`PUBLIC` … només `AGILITYHUB` o `ACCOUNT` que ho publica».
   - The guard treats such a course as readable by any MEMBER of the club. That contradicts R-16-03 («`CLUB` → INSTRUCTOR/ADMIN … MEMBER només via `RingSetup`»).
   - The matrix test's `MEMBER → 501` on `GET /courses/{id}` only passes because of this invalid state.
   - `POST/PATCH /courses` accept `visibility: PUBLIC` from a club, while session 2 made `/platform/courses` reject anything but `PUBLIC`. The two rules are asymmetric.
   
   **Fix:** reject `visibility = PUBLIC` on club writes with `400 VALIDATION_ERROR` (or document it as E9-T02's rule), and make the guard grant PUBLIC reads only when `ownerType ≠ CLUB`. Seed the club fixture as `CLUB`/`CLUB` and take the MEMBER-501 path through `e9-public`.
4. **minor** — some test names cite spec ids that test something else (AGENTS rule 5: the name must match the id and the rule it asserts):
   - `T_16_16_*` is used in `E9ResponseContractTest` (twice), `E9PersistenceIT` and `ArchitectureTest` (two rules). In S16 §11, T-16-16 is the mobile E2E test («registre en < 5 tocs»); these tests check R-16-16 or catalog rules.
   - `E9PersistenceIT.T_16_06_calendarDatesStayDateOnlyAcrossDstBoundaries`: T-16-06 is ring geometry, not date storage.
   - `E9ContractIT.T_16_21_courseUploadUrlsCheckTheClubFileParametersBefore501`: the file type/size checks are T-16-14.
   - `T_16_07_T_16_11_fourUniqueGuards…`: T-16-11 is the ring-over-club inventory precedence.
   
   **Fix:** rename them after the ids they really assert (`T_16_14_…`; `R_16_16`-style or `E9_T01_…` for contract-only checks).
5. **nit** `src/main/java/com/agilityhub/core/courses/api/ChallengesController.java:48` — `POST /challenges/{id}/attempts` publishes `200`. Every other creating POST in this task publishes `201`, and S19 §6 gives no reason to differ. Suggest `201` before E9-W02 mocks it.
6. **nit** `docs/openapi/openapi.json` (`components/schemas/JsonNode: {}`) — the Jackson type name leaks into the public contract through `rawMetadata`, `progressJson` and `rules`. Suggest a named "any JSON" schema (or inline `{}`) on those properties instead of a `JsonNode` component.
7. **nit** `src/main/java/com/agilityhub/core/courses/application/CourseSchemas.java:40,44` — `validateExport` reports failures as `400 COURSE_MODEL_INVALID`. That code describes a bad client model; a failed server self-check of the export is a server error. Flag this for E9-T04 (export a 5xx / internal failure instead).
8. **nit** `src/main/java/com/agilityhub/core/courses/persistence/CourseJsonConverter.java:41` — `new Decimal128(node.decimalValue())` throws for numbers above 34 significant digits or out of exponent range. A schema-valid model with such a literal would become a 500 on the first E9-T02 write. Suggest a fallback to double, or a clear `COURSE_MODEL_INVALID`.
