# Review E6-T03 — needs changes

## Findings

1. **major** `src/main/java/com/agilityhub/core/clubs/census/application/DogService.java:205` — Concurrent observation saves can return **500 instead of 409 STALE_VERSION**. Two requests with different idempotency keys can both pass the version check before either saves. The losing Mongo transaction then raises a write conflict; this route joins `IdempotencyFilter`’s transaction, which neither retries nor translates that conflict, and the generic exception handler returns `INTERNAL_ERROR`. This violates task step 4 / S10 R-10-12’s optimistic-locking contract. Use a retryable transaction boundary that includes idempotency, audit and outbox, rechecking the observations version on retry. Add a concurrent-save test expecting one 200 and one 409.

2. **minor** `src/main/java/com/agilityhub/core/clubs/followup/application/FollowupProjection.java:47` — Duplicate detection compares timestamps with different precision. Event JSON retains submillisecond precision, while Mongo stores `activityAt` in milliseconds: replaying `.519123Z` against stored `.519Z` takes the “new change” branch and calls `unreadForEveryone`. An instructor who clicked the row after its first consumption therefore loses that read mark when the same event is replayed. The consumer discards the supplied `eventId`; existing replay tests use whole-second timestamps and miss this. This violates S10 §7’s event-idempotency requirement and R-10-13. Deduplicate using the event ID and make ordering precision consistent; test a submillisecond event with a read between deliveries.

## Not checked

Maven tests, Docker/manual flows and OpenAPI generation were not rerun because they modify files or state. The concurrency and replay findings are based on source inspection; existing logs and test XML were inspected.
