2. **major** `identity/application/TokenService.java:153-169` (INC-36, S01 R-01-06): during the grace, the token returned is made by rotating the family's **live** token. This has two consequences:
   - **(a) Theft detection can be dodged forever.** Each token rotated this way gets its own fresh grace, because `rotate()` sets its `lastUsedAt`. Take A→B (legitimate), then the attacker presents A within 30 s: B→C goes to the attacker. The victim presents B within 30 s: C→D. The attacker presents C: D→E, and so on. As long as each use comes within 30 s, the family is never revoked. "Un segon cop dins del marge" is enforced only per token, not per family.
   - **(b) The INC-07 symptom can come back.**
     - With two concurrent holders, the first holder's B is rotated without it knowing. A body client (`learn`, native) using B after 30 s gets `REFRESH_REUSED` and the family is revoked.
     - Two tabs share the cookie, but their responses can arrive in either order. If tab 1's `Set-Cookie: B` lands after tab 2's `C`, the jar holds a rotated B. The next refresh, about 15 min later (the access token lifetime), revokes the session.
   - `IdentityCoreIT.T_01_04_INC_36_*` checks only the DB state, not which token each caller ends up holding.
   - **Fix:** either
     - give no grace to a token that was rotated *by* a grace use (store the reason, or set `graceUsedAt` on the rotated live token as well), or
     - in the grace, issue a sibling child without rotating the live token, and cap the family's live tokens.
   - Add a test for the A/B/C ping-pong and for the out-of-order holder case.
