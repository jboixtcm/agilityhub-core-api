# Review E5-T09 — minor issues

## Findings
1. **minor** `src/main/java/com/agilityhub/core/clubs/catalogs/application/CatalogService.java:151-161`: the new S05 check against live bookings is not serialized with training bookings, so a booking can slip through while the ring is being switched off.
   - **Scenario:** `PATCH /rings/{id}` runs `futureActive(ringId)`, finds nothing and commits `allowsFreeTraining=false`. At the same moment `TrainingBookingService.bookInTransaction` (line 68) reads the ring as still reservable and inserts a booking. The two transactions write different documents, so Mongo raises no write conflict. The result is an `ACTIVE` booking on a ring that is no longer reservable, which S09 R-09-13 says must be impossible.
   - **Why it matters:** S06 already closes this race with `ring_day_locks` (`RingScheduleAccess.lockRingDay`, MODEL_DADES_PLATAFORMA row added 24-09). S05 does not use it.
   - **Fix:** in `RingReservability.futureActive`/`stopsBeingReservable`, touch the ring-day locks for every day in the booking window, and make sure the booking path touches them too. Alternatively, record the gap as an explicit R1 single-instance assumption (E26).
2. **minor** `CatalogService.java:151` / `docs/specs/S05-catalegs.md` R-05-07, T-05-12, R-05-08, T-05-28: code and spec now disagree in three places.
   - **Status code:** the code answers **422** `RING_HAS_BOOKINGS` when a ring is deactivated or loses `allowsFreeTraining` while it has live training bookings. The amended R-05-08/T-05-28 and the ruling say **409**, while CATALEG_ERRORS rule 0 says 422. The executor chose the catalog and asked (Question 1). That is defensible, but the organizer must settle it before verification.
   - **R-05-07 row (line 122):** still says that deactivating a ring with future training bookings gives `409 RING_IN_USE`.
   - **T-05-12 (line 271):** still expects 409.
   - Only the ruling's «or deactivating a ring» backs the new deactivation behaviour. The S05 text needs aligning whatever is decided.
3. **minor** `src/main/java/com/agilityhub/core/clubs/bookings/application/DemoBookingSeeder.java:50`: the re-anchor booking filter does not do what the report says.
   - **Report and seeds/README claim:** registrants are booked only into ACTIVE classes of the weeks the re-anchor *generated*.
   - **Actual filter:** «class ACTIVE with 0 booked and 0 waiting». So a `bookings` row that lands on an ACTIVE class of a **kept** week, one without registrants, gets demo bookings added to a week the README says is «kept as it is».
   - **Fix:** pass the `fresh` week offsets from `DemoPlanningSeeder`, for example through the `Input`, and filter on `row.week()`, in the same way `dated` does for loose classes, blocks and cancellations.
4. **minor** `src/main/java/com/agilityhub/core/clubs/scheduling/application/DemoPlanningSeeder.java:76`: a weekly re-anchor leaves the current week as a draft.
   - **Scenario:** after the first run, W0 is VALIDATED, W+1 is GENERATED and W+2 is VALIDATED. Re-anchoring **one** week later makes the old W+1 the new W0, and it is kept GENERATED (DRAFT classes). The current week then has no bookable classes in the member app.
   - **Impact:** this is exactly the «staging demo» use case of E4-T05 #6. The IT and the CLI evidence only re-anchor **two** weeks later, where the kept week happens to be VALIDATED.
   - **Fix:** validate a kept, still-GENERATED, non-past week whose `planning.weeks` row has `validate: true`. Otherwise, document in seeds/README that re-anchoring must happen at a two-week cadence, and add a one-week case to `T_06_28_reanchor…`.
5. **nit** `src/main/java/com/agilityhub/core/platform/application/jobs/SchedulerTick.java:52`: two gaps in the lease renewal.
   - The `tick` lease is renewed only *between clubs*, so a single club whose jobs run longer than 55 s still loses the lease in the middle of the tick.
   - The IT's «renewed lease keeps a second tick out» step calls `locks.renew(...)` directly, so the `RENEW_AFTER` branch inside `SchedulerTick.run` has no dedicated assertion.
   - **Fix:** either renew from `JobRunner`'s item loop too, or state the limit in the javadoc. Add an assertion that drives the branch through `tick.run` with two clubs.
6. **nit** `src/test/java/com/agilityhub/core/platform/application/jobs/JobFrameworkIT.java` `T_15_05_aClubWithNoRunHistoryStartsFromItsLatestOccurrenceOnly`: the test id does not match the rule it cites.

   - The same mismatch already exists in `T_15_05_missedWindowSkipsAndAlerts`.
   - **Fix:** rename both to `T_15_04_…` (AGENTS rule 5).
7. **nit** `src/test/java/com/agilityhub/core/arch/ArchitectureRules.java:106` `COUNTER_WRITERS`: the rule is looser than step 6 asks.
   - Step 6 asks to restrict `counters` to «the S08 writer path», but the rule allows any class in `clubs.bookings..` **and** `clubs.scheduling..`.
   - `callMethod` also misses method references (`classAccess::counters`).
