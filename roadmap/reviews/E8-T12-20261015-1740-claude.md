## Findings
1. **minor** `CapturedPaymentInvariantsIT.java:846` `T_12_17_e8t12_round6_point3_oneNoticePerPaymentPerEvent`: **no test guards point 3.**
   - Counterfactual `151` adds round 5's pre-absorption refresh back, and every `round*` IT still passes, including this test and the per-event `oneNoticePerPayment` check in every generator.
   - The executor's argument holds when I trace the code. `creditReductions()` only acts when `withoutClaims().balance().free() < 0`, and then every recomputed claim is already 0. A second refresh is therefore idempotent, and point 3 holds by construction.
   - E111 asked for a test with "an event whose credit reduction frees money". The test uses billing's credit void instead.
   - The organizer should explicitly accept "holds by construction" in place of a failing-first test. Alternatively, add a unit assertion that `creditReductions()` is the same with and without claims.
2. **minor** `CapturedPaymentInvariantsIT.java:1262-1299` (`sharedInterventionLowerBound`) and `PaymentIntentLedgerTest` `…round6_point2_generatedClaimsEqualTheirRecomputedDue`: **the "lower bound" oracle is not independent of the code under test.**
   - Both recompute the due with production `PaymentIntentLedger.withoutReservation(id).freeFor(id)`, which uses the same `reservationShares`/`allocate` preference logic that round 6 changed.
   - So they prove that the persisted claims are a fixed point of the production allocation, not that the allocation is right.
   - They keep the other rows' stored claims, so both split orders (A 12/C 7 and A 7/C 12) are fixed points, and the oracle cannot see a point-4 order error.
   - The explicit regressions cover these paths: round 6 point 1 ×7, and round 5 point 1 with `failSecondFirst`.
   - Suggested fix: order the oracle's claims itself (sort by `compensationInterventionAt`, then subtract claim by claim), or say in the report that it is a consistency check.
3. **nit** `PaymentRefunds.java:158-162` (`intervene` first-entry branch):
   - `upfront.intervention(...)` and `retries.warnIntervention(...)` run *before* the claim is recomputed. When an unlinked pending dashboard refund already covers the row (owed becomes 0), the log still says "Refund compensation needs an admin" for a payment that has no N-55 and owes €0.
   - The branch also runs for an obligation that comes only from the `operations.byKey("refund:"+id)` fallback (`:126`, the `lateBooking` path at `:320`). Such a row has no stored compensation, so it is never in `failedAt` (`:256`). `claims()` then always returns 0 for it, and it never notifies again.
   - I could not build a reachable money case for the fallback (it may even suppress a wrong notice), but the intent is unclear.
   - Suggested fix: warn only when the recomputed `owed > 0`, and add a short comment on the fallback-only obligation.
4. **nit** `PaymentRefunds.java:255-257`: **extra database reads.** `intentLedger()` now issues one `upfront.compensation(id)` `findOne` per row, although `forIntent` has just loaded those documents. `intentLedger()` runs several times per event (each `compensateRemaining`, `intervene`, `absorb`, `reportOverpayment`). This is fine at 2–3 rows; reading `compensationInterventionAt` and the reasons from the loaded rows would avoid the extra reads.
5. **nit** `CapturedPaymentInvariantsIT.java:803-804`: **one case missing from the matrix.** It covers €12/€5 × row A/B × succeeded/pending except `1200,a,pending`. Add it so the matrix is symmetric (it costs one case).
