# Review E5-T24: minor issues

## Findings
1. **minor** `src/main/java/com/agilityhub/core/clubs/followup/application/AttachmentService.java:43-47,106-113`: a MEMBER's add-dog upload fails while signup is closed. This is the executor's open question 2, and it is now a real conflict with the spec. Amended CONVENCIONS_API §5 says the client never sends a bearer to a signed URL. But `putSignupLocal` still relies on a bearer: only a bearer lets `requireSignupOpen()` skip its check. So when `signup.enabled=false` or the club is not ACTIVE, a MEMBER who follows §5 gets `422 SIGNUP_CLOSED` on `PUT /signup/uploads`, even though `POST /signup/upload-urls` gave them the URL. R-04-27 says a MEMBER adding a dog keeps these routes. The task said "keep it", so this is out of scope, but it is a follow-up, not a nit.
   - **Suggested fix:** when the caller is authenticated at `POST /signup/upload-urls`, store their `accountId` on the grant. In `putSignupLocal`, skip `requireSignupOpen()` for a grant that carries an account, since its signature already authorises it.
2. **minor** `src/main/java/com/agilityhub/core/clubs/common/api/ExportsController.java:60-65`: `GET /exports/{id}/download` still needs a bearer, although it is a local signed URL (`expires` + `signature`). The amended §5 says a signed URL authorises itself, including on the local profile. The executor correctly left it alone (the task named three routes) and asked about it (question 1). The organizer should decide: either amend §5 to exempt export links (S14 R-14-12, caller-owned job) or schedule a fix.
3. **nit** `src/main/java/com/agilityhub/core/clubs/followup/persistence/UploadGrantRepository.java:12-18`: the Javadoc says "the grant's own `clubId` becomes the tenant", but no code opens a `TenantContext`. `putLocal` and `openLocal` run with no tenant at all. Nothing downstream needs a tenant today, so it works. Either fix the comment, or open `TenantContext.open(grant.clubId())` in `signedGrant` so later code that calls `TenantContext.require()` does not fail.
4. **nit** `src/main/java/com/agilityhub/core/shared/api/SignedFileRequests.java:19-25`: the matcher decides `permitAll`, whether the bearer is ignored and whether the route has no tenant, and it matches on the raw `getRequestURI()`. `RateLimitFilter` (its comment near `:28`) deliberately matches on the decoded, `;`-stripped path that Spring routes. It is safe today because `StrictHttpFirewall` rejects `%2F`, `%2E` and `;`. For consistency and defence in depth, use the same `UrlPathHelper` path.
5. **nit** `AttachmentService.claimDogDocument` (`:84-96`) vs `claim` (`:123-135`): the same ADMIN `DOG_DOCUMENT` key behaves differently depending on the route.
   - The S03 route `POST /dogs/{id}/documents` refuses an unbound, expired grant with `409 INVALID_STATE`.
   - A D2 PATCH accepts that grant with no time limit (assumption 2).
   - Such keys are also never cleaned up, because P9 only cleans `SIGNUP_DOCUMENT` (assumption 3).
   - The claim is also limited to the caller's own upload. R-04-19 says «que l'ADMIN ha pujat al mateix club», which does not require the same account (assumption 1).

   The organizer should confirm these three assumptions and log the missing cleanup in `docs/INCIDENCIES_OBERTES.md`.
6. **nit** `src/test/java/com/agilityhub/core/clubs/census/api/SignupPlansFollowUpIT.java:118`: the rename to `R_05_19_T_05_07_…` was asked for, but the test does not cover all of T-05-07. T-05-07 asks for price lines for the three plan types and for «sense preu», in `ca`, `es` and `en`. The test only checks TERAPIA's `priceLabel` in `ca` and `es`. Either extend it or note which test covers the rest of T-05-07.
