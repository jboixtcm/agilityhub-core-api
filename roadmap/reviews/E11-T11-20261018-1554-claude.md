# Review E11-T11 — minor issues

## Findings
1. **minor** `src/main/java/com/agilityhub/core/platform/application/privacy/ErasureService.java:174` — No integration test runs the cleanup that a cancel triggers. In `ErasureIT.R_14_14_thePlatformCancelsAnAccountRequestBlockedHalfway`, club A's part has already emptied `filesPending`, so the cancel finds nothing to clean. The IT then pushes a file into the request *after* the cancel, so it tests the daily retry, not the cancel. The only test of `cancelAccountRequest → cleanAfterCommit` is the Mockito check in `ErasureServiceTest`. That leaves unproven that the `afterCommit` hook actually fires inside `ConsoleTransactions.write` on the platform route, which has no tenant. Step 1 names this case ("cancelled after some clubs were erased"). · Suggested fix: in the IT, make club A's cleanup fail once (or push the pending file *before* the cancel). Then assert the file is gone right after `DELETE /platform/erasure-requests/{id}`, before any daily run.
2. **minor** `src/main/java/com/agilityhub/core/platform/persistence/privacy/ErasureRequestRepository.java:65` + `ErasureExecutor.java:105` — `fileDeleted` still does `inc("version", 1)`, and a cleanup can now run while the request is still open (`SCHEDULED`/`BLOCKED`). Another club's part does a compare-and-set on `version`. If it read the request before a cleanup pulled a file, it fails with `409 STALE_VERSION`. The executor calls the window "milliseconds" (Assumption 2), but that only holds if the per-club daily runs never overlap. Every club defaults to the same `jobs.dailyTime`, and I did not verify that the scheduler runs clubs one after another. The overlap is the length of a whole club part (all the `ErasureStep`s), not milliseconds. The failure heals itself (the next daily run retries), but it shows up as a job item error. · Suggested fix: leave `version` alone when pulling a pending file. Deleting a file is not a status transition that T-14-24 has to serialise.
3. **minor** `src/main/java/com/agilityhub/core/platform/application/privacy/ErasureFilesCleanup.java:66` — Files deleted by the new per-club cleanup (the `afterCommit` hook) are never counted in the `erasures` job's `filesCleaned` counter. `filesCleaned` is only reported for `DELETE_FILES` items, so the run history shows `0` even when files left the store. · Suggested fix: have `ErasureExecutor` count the files of a `PARTIAL` part in the job effect, or mention the gap in the job's Javadoc.
4. **nit** `src/main/java/com/agilityhub/core/payments/application/BankAccountVault.java:180` — With no profile set, the application now refuses to start without `BILLING_BANK_KEY`, which is what step 9 asks. Side effect: `bin/core …` does not read `.env` and sets no profile. The AGENTS.md commands (`bin/core club:apply seeds/club-canic.yaml`, `bin/core identity:seed-test-accounts`) now fail on a developer host unless `SPRING_PROFILES_ACTIVE=local` is exported. DEPLOY.md mentions this; README/AGENTS do not. · Suggested fix: one line in README's profile paragraph, or default `bin/core` to `local` when no profile is set.
5. **nit** `src/main/java/com/agilityhub/core/platform/persistence/privacy/PrivacyTraceRepository.java:27` — Step 3 removes only `PUBLISHED` `InstructorChanged` records. Two cases still keep the old `shortName` in the outbox for good: a rename written shortly before the erasure (still `PENDING`, published later), and a dead-lettered or failed record. This matches the existing rule for the member's own records, and the executor says so (Assumption 4). · Suggested fix: none required. Optionally, note this case under §13 of S14.
6. **nit** `BankAccountVault.java:185` — The permissive `(key, clearAllowed)` constructor is package-private but still in main code, so "tests only" is a convention, not something the build enforces. An ArchUnit rule, or a comment-level `@VisibleForTesting`, would enforce it. Acceptable as it is.
7. **nit** `RefreshTokenRepository.java:137` — `graceSiblingAt` is written but not mapped in `RefreshToken` (Assumption 5). Any later full-document `save()` of a `RefreshToken` would silently drop it. It is harmless today because it is only a marker. The S01 §3 row now lists it as a stored field, so mapping it, or saying "marker, not read" in the row, would keep the spec and code aligned.
