## Findings

1. **minor** `src/main/java/com/agilityhub/core/clubs/messaging/persistence/NotificationRepository.java:146`: the `claimAccepted` update may lease the wrong delivery.
   - **What is wrong:** the query filters the `deliveries` array twice: a top-level `deliveries.acceptedAt $exists` (added so the partial index is used) and a `$elemMatch`. The update then writes through `deliveries.$`. MongoDB documents `$` as ambiguous when a query has more than one array predicate: the position can come from the `$exists` term, which is the first delivery with an `acceptedAt`, not from the `$elemMatch`.
   - **When it happens:** one notification with two accepted deliveries during a database outage, for example EMAIL and SMS. The first delivery's lease is still held, and the second one's lease has expired. The poll can re-lease the first one (a lease steal) and leave the expired one waiting.
   - **Impact:** nothing is sent twice, because an accepted delivery is only ever settled. The cost is repeated lease-stealing and settlement write conflicts. No test covers two accepted deliveries in one notification.
   - **Why it matters:** R-11-09 and the step 6 table, which says "neither" for claims.
   - **Fix:** keep one array predicate. Put `acceptedAt: {$gte: EPOCH}` inside the `$elemMatch` and use a plain or sparse index on `deliveries.acceptedAt`. Add a test with two accepted deliveries: one lease live, one expired.

2. **minor** `src/main/java/com/agilityhub/core/clubs/messaging/application/engine/NotificationDispatcher.java:335-375`: the residual risk for failure-path row 7 is understated.
   - **What is wrong:** `record()` tries `markAccepted` 5 times, 50–150 ms apart. If all 5 fail, the acceptance lives only in `unsettled`. `settleWaiting()` then retries only the settlement. It never retries `markAccepted` and never renews the lease.
   - **Failure scenario:** a short failure of the mark write, followed by a settlement that keeps failing for more than 2 minutes for some other reason (for example the outbox write, as in the step 1 test). The claim's original lease then expires and `claimDue` sends the message again. The report's residual text only covers "every write fails and the process stops, or the database stays unreachable".
   - **Why it matters:** step 1 ("a delivery that the provider accepted never reaches the provider again") and R-11-09.
   - **Fix:** in `settleWaiting`, write `markAccepted` first for an accepted outcome that has no durable mark yet (this also renews the lease). Or renew the lease while the outcome waits, which was the task's second suggested design. Then correct row 7.
