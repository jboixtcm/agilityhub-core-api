## Findings
1. **major (DoD)** `roadmap/tasks/E9-T05.md` Evidence §4: the Definition of Done says "CI is green on the final commit", and the executor did not show this. They could not see CI and asked the organizer to check it. Also, by the report's own account, the E9 gate is still waiting on **E9-T06**, which is `ready` and carries E9-T04's review findings. So E9 is not closed in the API until E9-T06 lands. · Fix: before verifying, check the CI run for commit 699e7700 (or the commit after the publish), and decide whether E9-T05 can be `verified` while E9-T06 is open.

2. **minor (behaviour change beyond E117 point 4)** `courses/application/RingSetupService.java:80`: `access.course(placement.courseId(), false)` checks more than "is the course deleted". It also runs the R-16-03 visibility check. If a colleague placed their own private course, an instructor who cannot read that course now gets `COURSE_NOT_VISIBLE` on `POST /ring-setups {placementId}`; before this change it was `201`. This matches `BuildSessionService.start` (line 81), and `COURSE_NOT_VISIBLE` is already in the route's `@ContractErrors`, so nothing breaks in the contract. But the report and the javadoc only describe the deleted → `404` case, and no test covers this path. · Fix: say so in the report, or check only liveness here (`live(placement.courseId()) == null → 404`).

3. **minor (privacy, R-16-16)** `courses/application/RingSetupService.java:283` `plannedCourseName`: this uses `live()` and has no visibility check. A member who reads `GET /class-sessions/{id}` then sees the **name** of a private course that a class plans, even though the course is not shown by an active setup. R-16-16 lets a member see a non-readable course only through an `ACTIVE` setup. The model stays protected; only the name leaks. · Fix: return empty for a course that is neither `CLUB`/`PUBLIC` nor shown by a setup, or have the organizer rule that the name is acceptable.

4. **minor (R-16-10, orphaned file)** `courses/application/BuildSheetService.java:31`: attaching a second sheet replaces `buildSheetFileKey`, but the previous file's grant stays bound to `Placement:{id}`. The old file is never released and never cleaned up. The IT only re-attaches the **same** key (`PlacementsIT:261`), so the "replaces the previous sheet" claim in the operation description has no test. · Fix: add a test that attaches a second key and asserts the first one is released or deleted (or that this is accepted). Alternatively, open an incidence for orphan build sheets next to the S15 P9 cleanup.

5. **minor (contract)** `courses/api/PlacementsController.java:86`: `STALE_VERSION` was added to `attachBuildSheet`'s `@ContractErrors`, even though the task's convention is "No new contract". It can only come from a Mongo write conflict through `WriteConflicts.guard`, since `attachSheet` matches any version. It is documented in `docs/openapi/CHANGELOG.md`. Similarly, `plannedPlacement` and `PlannedPlacement` are new schema, but the organizer ordered those (E117 point 3). · Fix: the organizer should acknowledge both deltas explicitly. No code change needed.

6. **minor (assumption on T-16-19)** S16 §11 T-16-19 says `GET` returns the sheet "amb URL signada" (with a signed URL). The implementation streams the PDF bytes (`200 application/pdf`), as E9-T01's contract published it (assumption 1). This is defensible, but it is a spec/contract mismatch the organizer should rule on. The web (E9-W02/W03) depends on that ruling.

7. **nit (AGENTS rule 5, test names)** `DemoCoursesSeederTest.java:76,81`: `aSeedWithoutACoursesSectionWritesNothing` and `aModelRowIsTypeXYAndRotation` have no T-id. `DemoCoursesSeedIT`'s name, `T_16_08_T_16_10_…`, cites T-16-10 (R-16-11), but there is no direct test of R-16-10 in it, so the name is accurate. Fine.

8. **nit (evidence)** `02-demo-seed-targeted.log` was overwritten by four attempts, and only the last one is kept. The executor admits this, but it breaks the "one log per failed attempt" rule. The executor also states that the E117 fixes were written before their tests: "failing first" is replaced by the counterfactual run (`11-counterfactuals.log`, M1–M8 all fail as claimed, `All mutants reverted: True`). That is acceptable evidence, but it is not the ordering the protocol asks for.

9. **nit (seed realism)** `seeds/demo-canic.yaml`: the placements are created with `warnings: []` and `READY_TO_BUILD`. Worth one line in `seeds/README.md` saying the demo placements carry no client warnings by construction.
