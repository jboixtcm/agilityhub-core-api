# Review E3-T08 — needs changes

## Findings

1. **major** `src/main/java/com/agilityhub/core/payments/application/UpfrontPayments.java:97` — A cheaper replacement plan can overcharge an applicant with a retained `PARTIAL` row. For example, a €100 row with €50 paid, changed to a €60 quote, leaves €50 outstanding instead of €10. `replacement()` retains the original debt and merely suppresses new charges. This violates step 7 / S04 §5 / E39. The executor discloses this unresolved case, so “all 13 steps done” is premature. Resolve the adjustment semantics with the organizer and prevent collection of the excess; cover the downgrade in both dry-run and validation tests.

2. **major** `src/main/java/com/agilityhub/core/payments/application/UpfrontPayments.java:113` — Replacing legacy signup rows without `submissionId` throws `NullPointerException`: mapping the matching submission to `null` before `findFirst()` is invalid. Consequently, a legacy application's dry-run can succeed while validation fails with 500 whenever replacement creates a charge. This contradicts the documented legacy compatibility and step 7. Find the `Submission` first, then extract its nullable ID; add a legacy-row regression test.

3. **major** `src/main/java/com/agilityhub/core/clubs/census/application/SignupService.java:337` — D2 exposes prices that validation refuses. The seeded `TERAPIA` plan has a `MAINTENANCE_FEE` price in `planOptions[].prices`, but `plan.price()` is null because `SignupPlanCatalog.offer()` selects `MONTHLY_FEE` for every MONTHLY plan. Sending the exposed maintenance `priceId` therefore returns `422 PLAN_NOT_AVAILABLE`; omitting it stores a null `member.priceId`. Step 5 explicitly requires admin plan/price selection. Resolve and persist the applicable selected price while preserving Teràpia’s entry-only upfront quote, and test this seeded case.

4. **major** `src/main/java/com/agilityhub/core/clubs/census/application/SignupService.java:50` — Checkout scoping drops unpaid rows immediately after validation because `submissions()` includes only `PENDING` dogs. Submit with Stripe enabled, validate with `upfrontAmountPaid = 0` (allowed by R-04-16), then open checkout: the scope is empty despite outstanding current-submission rows. Non-CARD methods get `409 INVALID_STATE`; CARD creates a setup-only session without collecting the debt. Step 7 requires submission isolation, not removal of current unpaid charges when dogs become ACTIVE. Retain the relevant submission scope across validation and test this sequence.

5. **minor** `src/main/java/com/agilityhub/core/clubs/census/application/SignupNotifications.java:48` — The new N-01 variants reach EMAIL only. APP calls receive neither a variant nor rendered copy, and `NotificationRepository.safe()` strips `upfront_total` and `payment_instructions`. The persisted applicant APP notification therefore cannot convey the required payment information, and the admin variant is not identified. Steps 3/6 and S04 §8 include these audiences/channels. Persist the appropriate copy or rendering metadata and allow-listed payment variables; assert APP content, not only the presence/absence of `OPEN_SIGNUP`.
