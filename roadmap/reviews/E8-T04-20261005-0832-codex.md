# Review E8-T04 — needs changes

## Findings

1. **major** `src/main/java/com/agilityhub/core/payments/application/StripeWebhooks.java:91` — A late checkout overwrites the payment reference belonging to an already successful checkout. Reproduction: session A expires, session B pays the same signup rows, then A completes. `completeWebhook` queues A’s refund, but this unconditional loop replaces B’s reference with A’s; `CheckoutService.java:249` also overwrites the captured amount with zero. A’s refund webhook can then mark B’s legitimately paid rows as refunded. This breaks steps 12–13 and R-12-20/21. Update row references and captured amounts only when that checkout actually settles those rows; retain late captures on their own session/operation. Add the A-expired/B-paid/A-late regression.

2. **major** `src/main/java/com/agilityhub/core/payments/application/PaymentRefunds.java:114` — A refund delivered before its checkout completion is permanently lost. Until completion writes the PaymentIntent reference, `upfront.forIntent(intent)` returns nothing; this method returns `false`, and the inbox records `IGNORED`, sets `processedAt`, and deletes the replay payload. The later completion marks the rows paid without the refund. R-12-20/21 requires correct settlement despite event ordering. Defer unmatched refunds until capture correlation is available. The new early-refund test covers an existing invoice collection, not this upfront-payment case.

3. **major** `src/main/java/com/agilityhub/core/payments/application/PaymentRefunds.java:112` — Refund targeting depends on a race with the provider response. `operations.forResult(refundId)` becomes available only after `provider.refund` returns and line 89 commits. If the webhook arrives first for a checkout containing multiple upfront rows, settlement instead distributes the refund across those rows in repository order, potentially refunding a different row from the requested target. Later processing cannot correct it because the refund ID is already recorded. R-12-20 requires the requested payment to be refunded. Correlate through durable operation metadata or defer settlement until the target is known; test a refund of the second row with webhook delivery before response persistence.

4. **major** `src/main/java/com/agilityhub/core/payments/application/StripeWebhooks.java:90` — Checkout completion is treated as successful payment without checking `payment_status`; the sanitizer also discards that field. Meanwhile, `StripePaymentProvider.java:64` leaves payment-mode methods unrestricted. Stripe’s dynamic methods can include delayed payments, for which Checkout completes before payment succeeds. This can mark upfront rows paid and activate a `PAY_TO_BOOK` booking even if payment subsequently fails; asynchronous completion/failure events are unhandled. See [Stripe’s payment-method defaults](https://docs.stripe.com/payments/payment-methods/dynamic-payment-methods) and [fulfillment requirements](https://docs.stripe.com/checkout/fulfillment.md?payment-ui=stripe-hosted). Restrict checkout to supported card methods and validate payment status, or implement asynchronous settlement. Add an unpaid-completion regression for R-12-21 and S08 R-08-18.

5. **major** `src/main/java/com/agilityhub/core/payments/persistence/StripeInbox.java:36` — Recovery can indefinitely starve later work. Both this query and `PaymentOperationRepository.java:41` repeatedly select an unsorted first 100 unresolved records; failed attempts remain eligible without retry scheduling or rotation. Once 100 records remain unresolved, later recoverable payments/webhooks can receive no retries, including records belonging to other clubs. This undermines step 8’s internal retry guarantee and step 13’s recoverability. Introduce fair selection and scheduled backoff with an explicit policy for persistent failures; test recovery behind more than 100 failing records.

6. **minor** `src/main/java/com/agilityhub/core/clubs/census/application/CensusQuery.java:66` — The member payment projection omits `CARD.invalid`, and `CensusResponses.PaymentMethodView` has no corresponding field. Consequently, the D10 member response cannot drive the required “Targeta no vàlida” badge, despite invalidation being persisted. This leaves step 9 / R-12-22 incomplete. Expose a safe card-validity field, update OpenAPI, and assert the member response before invalidation and after successful card setup.

7. **minor** `src/main/java/com/agilityhub/core/payments/application/StripeWebhooks.java:144` — Sanitization removes refund metadata, although the handler subsequently reads `metadata.reason`. Every persisted refund therefore receives the fallback `requested_by_customer`; `PaymentRefunds.java:108` and `:128` also always write a null `byAccountId`, despite the durable operation retaining the initiating actor and reason. This loses the refund provenance specified in S12 §3 and R-12-20. Populate requested refunds from the correlated operation’s reason and actor, and test those stored fields.
