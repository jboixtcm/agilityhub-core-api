# Review E11-T01 — minor issues

## Findings
1. **major** `src/test/java/com/agilityhub/core/platform/privacy/ErasureIT.java:177-330` — T-14-19 is only partly tested. Two of its required assertions are missing: (a) after erasure, `POST /signup` with Montse's old DNI must create a **new** member with a new number, not a readmission; (b) `GET /invoices/{id}` must stay readable and show the anonymised name «Abonat suprimit #87». The test checks the raw Mongo invoice document but never calls the endpoint. The task asks for "each new test named after its rule", and T-14-19 is in the Steps (step 3). Without (a), nothing proves that the `idDocument → ERASED-{id}` rewrite really stops S04 readmission from matching. **Fix:** add both checks to the T-14-19 IT.

2. **minor** Several test names cite spec ids that mean something else, which breaks AGENTS rule 5 ("tests named after the spec ids … that really assert the rule"):
   - `ErasureIT.T_14_14_R_14_15_theConsoleErasesAnAccount…` and `ErasureIT.T_14_14_R_14_18_consentsAndThePlatformViews…`: in S14 §11, T-14-14 is the `lastChange` test.
   - `ErasureIT.T_14_15_R_14_15_aRequestBlockedAtItsExecution…`, plus `ErasureExecutorTest.T_14_15_*` and `ErasurePolicyTest.T_14_15_placeholders…`: T-14-15 is the xlsx members-export test.
   - `ErasureServiceTest.T_14_14_*` and `ErasureExecutorTest.T_14_14_*`.
   - `ErasureServiceTest.T_14_16_aRetentionRequestExecutesNow…`: T-14-16 is the 5,001-row async export test.

   The report's rules table repeats these ids, so the organizer's traceability is wrong. **Fix:** rename them. Use T-14-18/T-14-19/T-14-20/T-14-24, or plain `R_14_xx_` names where no spec test exists (account-scope erasure, consents, platform view).

3. **minor** `ErasureExecutor.java:128-134` (`accountGoes`) — the code and the report disagree on when a member-scoped request keeps the account. The report (Assumptions, "Account kept") and the spec's R-14-15 exception say the account is kept when another club has an **ACTIVE** membership. The code keeps it whenever another club's membership is **not ERASED**, so a SUSPENDED membership (someone who left another club) also keeps the account. Keeping it is arguably the safer choice, since erasing it would leave the other club's LEFT member pointing at an erased account. But it is a deviation that is neither stated in the report nor tested. **Fix:** document it as an assumption or question in the report, and add a test with a SUSPENDED membership elsewhere.

4. **minor** `ErasureNotices.java:26,36-37` — for a console (ACCOUNT-scope) request, N-52's `club_name` is the hard-coded string `"AgilityHub"`, and `execute_date` is formatted in UTC with a fixed `dd/MM/yyyy`, not in the recipient's locale. This is a user-facing literal outside `messages_*.properties` (CONVENCIONS_I18N). **Fix:** take the platform name from i18n or configuration, and format the date with the account's locale.

5. **minor** `ErasureExecutor.java:73-77` — when an ACCOUNT request is BLOCKED in club B after club A has already pseudonymised its members (`erasedClubIds=[A]`), the request has no exit. `DELETE /members/{id}/erasure` refuses ACCOUNT scope (`ErasureService.cancel`), and there is no platform cancel route. So the request stays BLOCKED/live forever, and club A's data is half-erased under a request nobody can cancel. The spec's §5 does allow "plataforma" to cancel. **Fix:** raise this in the report or MESSAGES as a proposal (a platform cancel route), or state that it is out of scope.

6. **minor** `MemberDataExports.java` / `ErrorCode` — `DATA_EXPORT_TOO_SOON` returns `422`, while S14 R-14-13 and §6 say `409`. The executor raised this as question 1, which is fine. But the published OpenAPI now contradicts the spec until the organizer rules, so the web client should be told.

7. **minor** `MemberDataPackage.java:33-35` — the "third-party name" filter for the data package is a fixed key list (`displayName`, `actorName`, …). Any other key holding a staff name passes straight into `data.json`. R-14-13 says "mai el nom d'un tercer". Examples: `instructorName`; `class_sessions.attendanceSummary.savedByName` (question 3) is filtered only because `savedByName` happens to be in the list. No test checks the package for staff names beyond `actorName` in audit entries. **Fix:** add a T-14-17 assertion that no fixture staff name appears anywhere in `data.json`.

The DoD item "CI green on the final commit" has no evidence: no CI run link or id. The code reached `main` through the combined publish commit fb421860 (together with E11-T06 and E11-T07). **Fix:** update §2 with the CI run of fb421860, or of the commit after it.
