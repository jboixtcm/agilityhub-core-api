## Findings

1. **minor** `src/main/java/com/agilityhub/core/clubs/catalogs/application/CatalogService.java:160` (S05 side of R-09-13): a concurrent booking always wins against an admin ring change.
   - `update` has no retry loop, and `lockBookableSlots` now `$inc`s every grid slot of the ring for the whole booking window (the report estimates about 120 documents).
   - So any booking on any slot of that ring during the change's transaction turns the admin's PATCH into `409 STALE_VERSION`. In all 4 lanes-off rounds of the final verify the result was `201 / 409 STALE_VERSION` (log lines 2464–2467).
   - It is safe (never a live booking on a ring that stopped being reservable), but on a busy club the admin may have to retry again and again.
   - The lanes-off burst never covers the other order, where the ring change commits first and the retried booking sees `RING_NOT_RESERVABLE`, through the real `CatalogService.update`. The only test of that order, `TrainingLanesOffIT.java:247-258`, fakes S05 with `slotLocks.bookable` plus a raw `updateFirst` on `rings`. The order of operations inside `CatalogService` (lock, then `futureActive`, then ring update) is therefore proven from one side only.
   - Suggested fix: wrap the ring branch of `update` in the same 50–150 ms retry the other contexts use. At least, log it as a follow-up and record it with the retry-budget ruling (E26).

2. **minor** (for the organizer) `docs/MODEL_DADES_PLATAFORMA.md:66` still lists `ring_day_locks`, but the code now only uses `ring_slot_locks` (`RingSlotLock.java`).
   - The executor proposed the replacement correctly, in the report (Round 2 Q1) and in `roadmap/MESSAGES.md:710`. It did not edit the model on its own.
   - Until the organizer applies it, the model and the code disagree on a technical collection. `docs/DEPLOY.md` is already updated.

3. **nit** `src/main/java/com/agilityhub/core/clubs/scheduling/persistence/RingSlotLockRepository.java:15-21`: the collection is created with blocking database I/O inside the repository constructor.
   - Every other startup setup uses an `ApplicationRunner` bean (`EmailConfiguration.emailCollections:66`, `SharedConfiguration.sharedIndexes:27`, `PlatformConfiguration.platformIndexes:22`, …).
   - Suggested fix: move it into a `schedulingCollections` runner, to match the codebase and keep bean construction free of database calls.

4. **nit** `src/main/java/com/agilityhub/core/clubs/scheduling/application/SchedulingTransactions.java:34-37`: `conflict()` retries only on 112 and `TransientTransactionError`, not on `DuplicateKey` (11000). The training side retries both (`TrainingTransactions.retryable`), and the S05 `write()` maps `DuplicateKeyException` to `STALE_VERSION`.
   - The new shared document is written by an upsert on `_id`. If a block's first upsert of a fresh ring slot ever came back as 11000 instead of 112, the S06 side would return a 500 instead of retrying.
   - The executor measured 112 for the seat index inside transactions, so the risk is low. Treating 11000 as a conflict here too would make S06 match S05 and S09.

5. **nit** `src/test/java/com/agilityhub/core/clubs/scheduling/application/SchedulingTransactionsTest.java:19` is named `T_06_23_…`, but T-06-23 is «validació concurrent amb un `PATCH` de classe … mai una classe `DRAFT` en una setmana `VALIDATED`». This test checks retry backoff timing and interrupt handling, not that rule (AGENTS rule 5). Rename it, for example `E5_T07_schedulingRetriesWaitAJitteredBackoff…`. It also sleeps for 250–750 ms in a unit test. That is acceptable, but a jitter source injected into the class would make it instant.

6. **nit** `roadmap/tasks/E5-T07.md:78-89`: the round-1 JaCoCo table still lists `RingDayLockRepository`, which is now deleted. It is labelled as round 1 and the Round 2 table replaces it, so this is only a readability point. A one-line «superseded by Round 2» note would help.
