## Findings
1. **minor** `src/main/java/com/agilityhub/core/platform/application/definition/ClubDefinitionWriter.java:129-133` — The default-locale check only tests that the key is present (`instructions.has(next.defaultLocale())`). A whitespace-only text therefore gets through: the schema's `localizedText` only asks for `minLength: 1`.
   - **Failure scenario:** a definition with `MANUAL.instructions: {ca: " ", es: "…"}` passes the schema and the writer, and is stored as is.
     - `CensusClubSettings.manualInstructions("ca")` then returns `null`, because a blank value does not fall back to another locale. A `ca` reader of screen 19 and of N-01 sees no instructions at all.
     - `ClubDefinitionMapper.instructions()` drops blank values, so the export is `{es: …}`. Re-applying that export fails with `REQUIRED`, which breaks the R-17-01 round trip that this task claims.
   - **Rule:** S17 R-17-05, «`MANUAL`: instruccions amb `defaultLocale` obligatori»; R-17-01 (export round trip).
   - **Suggested fix:** check `instructions.path(next.defaultLocale()).asText("").isBlank()`, or add a `"pattern": "\\S"` to the schema's `localizedText`. Add one case to `ClubDefinitionCodecTest` or `ClubDefinitionsIT`.
2. **nit** `ClubDefinitionWriter.java:129` — The R-17-05 check only runs when the definition declares `instructions`. Two cases get through:
   - A definition that changes `club.defaultLocale` without declaring `instructions` keeps stored instructions that may lack the new default locale.
   - A locale outside `club.locales` (for example `en` on the ca/es Cànic) is accepted. Pages refuse it (`pages.validate(page, defaultLocale, locales)`).
   - **Suggested fix:** validate the merged `next.paymentProviders().MANUAL.instructions` instead of the declared node, or record both cases as known limits in assumption 1.
3. **nit** `src/test/java/com/agilityhub/core/platform/application/definition/ClubDefinitionsIT.java` (`T_04_14_T_02_12_canicSeedCarriesItsCashPaymentInstructions`) — The name cites T-04-14, but the test asserts none of it.
   - T-04-14 (S04 §12, R-04-10) is about `SEPA_DD` without an IBAN (`ACCOUNT_NOT_PROVIDED`), a disabled `CARD` answering `422`, and the mandate text under `ES` versus `GENERIC`.
   - What the test asserts is S04 §2 row 19, R-04-10's `paymentMethods[].instructions`, T-02-12 (idempotent seed) and T-17-01 (export round trip).
   - **Rule:** AGENTS hard rule 5 (tests named after the spec ids they really assert).
   - **Suggested fix:** a name like `R_04_10_T_02_12_T_17_01_canicSeedCarriesItsCashPaymentInstructions`.
4. **nit** `src/test/java/com/agilityhub/core/clubs/census/api/SignupSecurityFixesIT.java` (`R_04_19_R_04_06_aSubmissionRefusesAKeyRemovedFromTheReusedDogsOwnCard`) — The `POST /me/dogs/signup` assertion does not isolate the removed key.

   - **Suggested fix:** also assert `kept` → `400`, or say in the Javadoc that this half covers the grant binding, not the removed-key check. The changelog wording («answers the same … its dog is always a new one») is already accurate.
