# Review E11-T04 — minor issues

## Findings

1. **minor** `deploy/compose.prod.local.yaml:6` — Core still receives `SPRING_DATA_MONGODB_URI`, which bypasses the production connection configuration assembled from `MONGODB_HOST`, credentials, authentication database and replica-set settings. [Spring Boot’s implementation](https://github.com/spring-projects/spring-boot/blob/v3.5.0/spring-boot-project/spring-boot-autoconfigure/src/main/java/org/springframework/boot/autoconfigure/mongo/PropertiesMongoConnectionDetails.java) confirms that precedence. Consequently, Step 2 and round-2 correction 2 still lack runtime evidence for that production wiring. Keep the URI override only on the seed/local-host fixture, and repeat the Caddy checks with Core using the base configuration.

2. **minor** `deploy/backup/backup.py:74` — The inventory excludes views but retains their `system.views` collection. The pinned [mongodump implementation](https://github.com/mongodb/mongo-tools/blob/100.18.0/mongodump/prepare.go) excludes that system collection, so the namespace comparison at line 234 rejects an otherwise valid backup whenever an application database contains a view. This contradicts the documented handling of views under Steps 3–4. Align inventory filtering with the dump’s namespace rules and add a backup/restore regression containing a real view.

3. **minor** `docs/DEPLOY.md:61` — The pre-deploy sequence runs verification with the same `core.env` used for backup. That file’s prescribed principal has Put/List permissions, whereas verification calls `HeadObject`, which [requires GetObject](https://docs.aws.amazon.com/AmazonS3/latest/API/API_HeadObject.html). Supplying the age identity alone therefore leaves this command failing with access denied. For Step 5’s executable runbook, explicitly select the separate recovery environment file on the verification command. The MinIO rehearsal uses root credentials and does not expose this mismatch.
