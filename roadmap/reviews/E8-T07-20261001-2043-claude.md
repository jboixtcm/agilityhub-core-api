## Findings
1. **minor** `src/test/java/com/agilityhub/core/payments/api/BillingCycleIT.java:541`: `T_12_19_R_12_14_rolledBackComesFromTheRunAndTheAdminsReasonIsFreeText` is misnamed.
   - **Why:** T-12-19 in S12 §12 is the CSV export test (R-12-26). This test is about §5 `CANCELLED{ADMIN}`/`{ROLLBACK}` and R-12-19's free-text reason, and the report itself files it under «R-12-14, R-12-19».
   - **Effect:** AGENTS rule 5 (names follow spec ids) is broken, and whoever implements the CSV export will find a `T_12_19_` test that has nothing to do with it.
   - **Fix:** rename it `R_12_19_R_12_14_…` (or `T_12_13_R_12_14_…`).

2. **minor** `src/main/java/com/agilityhub/core/payments/domain/InvoicingRules.java:298-302` and `BillingRunService.java:293-303`: the waiting-receipt incident overloads `NO_BANK_ACCOUNT` and puts billed members into `skipped[]`. The executor flagged this (assumption 1, catalog proposal in MESSAGES), so it is compliant with rule 2, but the organizer should rule on its effects.
   - **The code no longer matches its definition.** R-12-07 defines `NO_BANK_ACCOUNT` as «`SEPA_DD` amb `iban=null`». Here it also covers members who are `LEFT`, pay cash, or have a new mandate.
   - **Billed members appear as skipped.** In `…aWaitingReceiptWhoseMemberCannotBeDebitedIsAnIncidentAndStaysOut`, `mas` gets a periodic SEPA invoice in the same run, and so does `serra-joan` (as cash). Both are still listed in `incidents`/`skipped[]` as «Sense compte bancari». The contract describes `skipped` as «the members with an incident», which R-12-07 says are omitted.
   - **The incident doesn't name its receipt.** D6 cannot tell which receipt is stuck.
   - **A changed mandate is permanent.** `mandateRef` is frozen on an immutable receipt (R-12-10), so that receipt can never be remitted again. The incident recurs every month until the admin cancels it or settles it by hand. The ruling should say whether that is intended, or whether to re-freeze under the current mandate (E8-T03 review #1's alternative).
   - **Suggested fix:**
     - add an optional `invoiceId`/`displayNumber` to the incident, an additive change like `InvoicePreview`'s;
     - decide on the three proposed codes.

3. **nit** `BillingSimulationService.java:109`: `kpis.count` now includes the waiting receipts (assumption 7).
   - D6's «Es generaran {n} rebuts» shows 9 while the run generates 8 (`run.invoiceIds`, test at `BillingCycleIT.java:457`).
   - `RemittanceSimulated.totals.count` changes meaning in the same way.
   - The task asks for this to match «Import de la remesa»; the organizer should confirm that the count should include them too.

4. **nit** `BillingRunService.java:194-206,240`: for a receipt the admin had already cancelled, the rollback emits a second `InvoiceCancelled{ROLLBACK}`, and counts it in `cancelledInvoices` (8, though the rollback itself cancelled 7).
   - This is defensible under R-12-14's «`InvoiceCancelled` per rebut», and D6 is the only consumer (CATALEG_ESDEVENIMENTS).
   - Confirm assumption 5.

5. **nit** `BillingRunService.java:289` with `BillingSimulationService.java:122`: staleness compares every unbilled charge of every `ACTIVE` member, not only the charges the drafts bill.
   - A new single-class charge for a member with an incident, or one not invoiced this month, makes the simulation stale although the run would not change.
   - This satisfies the step's wording but makes the simulation stale more often than needed. Comparing the charge ids found in `month().invoices()` lines would be exact.

6. **nit** `src/main/java/com/agilityhub/core/payments/persistence/BillingDocuments.java:117,126`: `withHint("invoice_club_series_number_all")` makes numbering depend on that index existing.
   - If the index is missing (a restore with `--noIndexRestore`, a manual drop), every run and every manual receipt fails with a Mongo planner error, i.e. a 500, instead of falling back to a slower plan.
   - `@PostConstruct` creates the index, so the risk is low. A note for the runbook is enough.

7. **nit** `src/test/java/com/agilityhub/core/payments/api/InvoiceNumberingIT.java:115-117`: the evidence `System.out.println` dumps runs and explains the queries on every CI `verify`. Gate it behind a system property.
