# Review E5-T25: minor issues

## Findings
1. **minor** `src/main/java/com/agilityhub/core/clubs/bookings/application/BookingViews.java:131` (`dog()`), with `BookingContracts.java:93` (`HoldDog`): a migrated dog can be sent with `sex: null` in fields the schema says can't be null.
   - **What happens:** `PlayoffPlanner` (around `:297`) maps an unrecognised Playoff `dogSex` to `null`. `HoldDog.sex` is still published as required, with values `MALE|FEMALE` only.
   - **Why this task makes it worse:** the problem used to affect only `SeatHoldResponse.dog`. It now also affects `Booking.dog` and `WaitlistEntry.dog`, which screen 07 and the waiting-list detail read every time. These are exactly the fields the web's E5-W04 will use to replace its overlays, and it needs `sex` for the Catalan article.
   - **Status:** the executor raised this correctly as question 1. It stays open.
   - **Fix:** the organizer should decide before E5-W04 adopts the snapshot. Either make `HoldDog.sex` nullable (the web then writes «amb Duna» with no article), or make the migration require a sex. Add a test that pins the choice.
2. **nit** `BookingViews.java:115-122` and `:131`: a missing dog used to give `dogName: null`; it now throws `IllegalStateException`, which means a 500.
   - **Impact:** on staff lists like `GET /class-sessions/{id}/waitlist-entries` (`BookingsController.java:310`), one bad entry now breaks the whole D4/D12 list.
   - **Why it's only a nit:** nothing deletes dogs today (assumption 3), so the risk is low. But it is a behaviour change, and the error doesn't go through `ApiException` (AGENTS rule 9).
   - **Fix:** keep the invariant, but log it and leave staff lists tolerant. Or add it to INC-xx as a known hardening item.
3. **nit** `BookingViews.java:83-84` (`BookedBy.self`): when an ADMIN uses their own back-office token to read a booking they made while impersonating, they get `self: true` together with `viaClub: true`.
   - This matches the description ("the reader's own account"), and 07 is a MEMBER-only screen.
   - But this combination isn't tested: `MemberFlowContractIT` reads as `admin` only to check `dog`. It isn't documented either.
   - **Fix:** say in the schema description that the field is meant for member screens, or pin the staff case in the IT.
4. **nit** `src/main/java/com/agilityhub/core/clubs/bookings/api/BookingsController.java:280-283` (`claimSeat`): the claim also takes `{seatHoldId, swapBookingId?}` with an `Idempotency-Key`, and R-08-15 says it runs "the same transaction as R-08-08". So the retry scenario with a different swap choice applies here too.
   - Its header has no "one client UUID per request body" description, and its operation description only says "a repeated key returns the same response".
   - Step 6 only asked for `POST /bookings`, so this is out of scope. For consistency, give the claim the same header description in a later pass (INC).
5. **nit** Test names in `src/test/java/com/agilityhub/core/configuration/S08MemberFlowContractTest.java` reuse spec ids that don't match what the test checks (AGENTS rule 5):
   - `R_08_10_T_08_42_…` only checks the schema. T-08-42 is the daylight-saving scenario; the real T-08-42 check is in `MemberFlowContractIT`.
   - `S08_07_T_08_27_…` is named after T-08-27, which is about impersonation (R-08-19).
   - The amended rules got no new T-ids, so borrowing the nearest ones is understandable.
   - **Fix:** the organizer should either add T-ids for the 26-09 amendments to S08 §12, or accept the names as they are.
