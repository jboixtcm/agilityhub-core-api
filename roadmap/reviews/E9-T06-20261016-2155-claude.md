## Findings
1. **minor** `src/main/java/com/agilityhub/core/courses/api/BuildSessionStreams.java:71,122,233-235` — the sender cap limits how many sends run at once on the whole instance, across every club. It does not count stalled clients.
   - **How it fails:** the pool is `ThreadPoolExecutor(0, 64, …, SynchronousQueue)`, so a task is accepted only if a thread is idle or a new one can start. `heartbeat()` queues one send per subscriber in a tight loop on the timer thread. With more than about 64 healthy subscribers on one instance, the 65th and later sends find every thread still busy writing. Those healthy streams are dropped (`drop("no sender")`) every 20 s, and their reconnections then compete for the same 64 threads. `poll()` and `refresh` fan out the same way.
   - **The report understates it:** the class Javadoc and «Known limit» describe the cap as biting only "while every sender is held" by stalled clients. In fact it can bite with no stalled client at all.
   - **Why it matters:** R-16-11 («< 2 s», live mode). Point 5's alternative was «refuse new subscribers above N stalled ones», and that is what the cap was meant to approximate.
   - **Suggested fix:** let a burst wait instead of being refused, e.g. `core = max = SENDERS` with a bounded `LinkedBlockingQueue`. Refuse or close a stream only when the number of senders blocked longer than `WRITE_TIMEOUT` reaches the cap.
   - **Test to add:** `SENDERS + 1` readers that keep reading, plus one `heartbeat()`: no stream is closed.
   - At today's scale (one club, a few phones per session) this will not happen, hence minor. At the least, the «Known limit» text and the Javadoc should state it correctly.
2. **minor** `src/test/java/com/agilityhub/core/courses/api/BuildSessionsIT.java:705-711` `T_16_10_aStalledStreamHoldsItsSenderNoLongerThanTheWriteTimeout` — the test name claims a behaviour, but the test only reads two connector properties (20000 / 60000).
   - Nothing proves that a client which stops reading frees its sender within about 20 s. The executor says so in the round-2 assumptions.
   - From memory of Tomcat's source, NIO's `setSocketOptions` sets both the read and the write timeout from `connectionTimeout`, so the claim is very likely right. Still, the name overstates what is tested.
   - **Suggested fix:** rename the test to what it asserts (e.g. `…theConnectorsWriteTimeoutIs20s`), or add a real-socket test that stops reading.
3. **minor** `src/main/resources/application.yml:76-80` — `server.tomcat.connection-timeout: 20s` is global. It is also the read-inactivity timeout for every request body on every route, for example multipart uploads of `COURSE_IMAGE` and build-sheet PDFs from slow mobile networks. It drops from 60 s to 20 s for the whole API, not just the build-session streams.
   - Neither the report nor `docs/openapi/CHANGELOG.md`/DEPLOY mentions this side effect.
   - **Suggested fix:** list it in the report as a known limit. If uploads matter more, apply the write timeout to the stream only, e.g. a per-connector setting or the async request's own timeout.
4. **nit** `src/main/java/com/agilityhub/core/courses/application/BuildSessionService.java:57,163,188,274`
   - The test hook `pauses` runs on every production `finish` and `join`, and is written with the fully qualified `java.util.function.Consumer`. It is harmless because it mirrors `draws`.
   - A plain import would match the file's style.
   - The hook name and its point strings (`"finish"`, `"join"`) are typed separately in the service and in the test, so a renamed point fails silently. In that case the test would no longer force the race and would quietly lose its value.
5. **nit** `src/test/java/com/agilityhub/core/courses/api/BuildSessionsIT.java:646` `T_16_10_twoKeyedFinishesAtOnceGiveOne200AndOne422` — the test covers only the "new setup" path (`activate`).
   - It does not cover the refresh path of `built` (`RingSetupService.java:118-124`), where the ring's active setup already shows the placement. On that path, `replaceActive` returning `false` throws `ApiException(STALE_VERSION)`, which `retrying` never retries.
   - Inside a snapshot transaction a concurrent update normally appears as a raw write conflict, not as "0 matched", so this is probably fine.
   - A second case, two finishes on a ring whose setup already shows the placement, would close the question.
