## Findings
1. **minor** `bin/e5-perf:173-179` / report «Gate E5, the k6 line»: the peak does **not** run while P1 fans out, even though the comment and the report say so («while P1 fans N-33 out (T-15-30)»).
   - `s.run_after(self.club, "WEEK_OPENING", opening)` (`bin/e5-smoke:192-198`) waits until the `WEEK_OPENING` job run is `SUCCEEDED`, and only then calls `run_k6("peak", …)`.
   - The evidence shows the timing: «660 N-33 rows within 0.4 s» of `WeekOpened`, so the fan-out was over before the k6 container even started.
   - Step 5 says the T-15-30 scenario must be «the same peak **while** `week-opening` runs». What is actually proven is «P1 then peak». Step 5 marks this scenario optional, so it does not block the gate, but the claim in the report is inaccurate.
   - **Fix:** start k6 without waiting (for example, launch it in the background at the 20 s mark with the arrivals timed for 20:00), then collect `run_after` afterwards. Otherwise, reword the report and the script comment to «P1 before the peak» and leave T-15-30 open.
2. **minor** `src/test/java/com/agilityhub/core/platform/application/CacheInvalidationRaceIT.java:95,121,134`: two of the four test names cite the wrong spec ids (AGENTS rule 5: names must match the rule the test asserts).
   - `T_02_01_moduleToggle…` tests a module toggle. That is **T-02-09** (R-02-07, `PUT /club/modules/PUSH`). T-02-01 is the `scopeRef ?? club ?? default` parameter resolution.
   - The two `T_02_11_domain…` tests check host → club resolution. That is **T-02-06** (R-02-01). T-02-11 is about 403 for INSTRUCTOR/MEMBER on `/parameters` and tenant isolation.
   - `T_02_08_…` is correct (S02: «`ClubConfig` refrescat»).
   - **Fix:** rename them to `T_02_09_…` and `T_02_06_…`, and update the report's line «S02 T-02-01/T-02-08/T-02-11 cache freshness».
3. **nit** `CacheInvalidationRaceIT.java:121-141`: the two host tests simulate the domain change themselves. They do a raw `mongo.updateFirst` and then call `hosts.invalidate()` by hand.
   - That proves `CacheLoads`, but not the production path that invalidates (`ClubDefinitions:54` / the domain endpoint). The config tests do go through the real `PUT` endpoints.
   - **Fix (optional):** drive one host test through `club:apply`, or through whichever service really changes the domains.
4. **nit** `src/test/java/com/agilityhub/core/arch/ArchitectureRules.java` (`BOOKING_TIME_OVERRIDE`): the rule allows any top-level class whose simple name starts with `Demo`, in any package.
   - Examples: `DemoIdentityService`, `DemoSeedRepository`, or a future `DemoSomethingController` in `..api..`.
   - The organizer asked for «only the `Demo*Seeder` and seed classes». Today only `DemoMembers`, `DemoScenarioSeeder` and `DemoTrainingSeeder` call `asOf`, so nothing is violated yet.
   - **Fix:** narrow the rule to `Demo*Seeder` / `DemoMembers` / `DemoSeed*` names, and forbid them in `..api..` packages.
5. **nit** `perf/e5-seat-holds.js` `member()` / Assumption 17: the gates `holds_created == SEATS` and «50/50 seats filled» depend on how targets are spread (`targets[index % targets.length]`) over the rows the list marks `BOOKABLE`.
   - Those states and `freeSeats` come from the 30 s base cache, which follows the S15 R-15-11 contract, so the list keeps showing full classes as `BOOKABLE`.
   - This passes because arrivals divide evenly: 30 per class.
   - Say this in `perf/README.md`, so that a later change of the pool size or the class count (a VUS count that is not a multiple of the class count) is not read as an overbooking or throughput regression when the seat gate fails.
