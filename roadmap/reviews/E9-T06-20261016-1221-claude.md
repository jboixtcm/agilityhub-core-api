# Review E9-T06 — minor issues

## Findings
1. **minor** `src/main/java/com/agilityhub/core/courses/application/RingSetupService.java:153-156` (reached from `BuildSessionService.finished`, line 159) — `finish` now registers the setup *before* it closes the session. When the setup is new, it goes through `activate`, and `activate` turns a raw write conflict into `ApiException(STALE_VERSION)`. `BuildSessionService.retrying` never retries an `ApiException`. So two phones that each send `finish` on the same session, with different keys, on a ring whose active setup shows another placement, get `200` and `409 STALE_VERSION`. Before this change the second got `422 BUILD_SESSION_FINISHED`, because the close came first and conflicted raw on the session document, so the retry saw the closed session. This goes against step 1 («a write conflict … retries the whole request; exhausted → 409») and against R-16-11 / the S16 endpoint table, which give `BUILD_SESSION_FINISHED` for a closed session. It is never a 500, and the report's Assumptions mention `activate`'s conversion, but not this regression. Suggested fix: a variant of `activate` for `built` that keeps the raw conflict, as E117 does for jobs and consumers. Add a test: two keyed finishes of one session at once → one `200` and one `422 BUILD_SESSION_FINISHED`.
2. **minor** `src/test/java/com/agilityhub/core/courses/api/BuildSessionsIT.java:~583` `T_16_10_phonesJoiningAtOnceWithKeysAllJoin` — step 1 asks for «two keyed joins at once». This test passed under mutant M1 twice (`08`, `09`), so it never showed the old 500. The executor says so honestly (question 2), but the step's join case is still not proven. Suggested fix: force the conflict deterministically, as the keyed-start test does with `BuildSessionDraws`. For example, a hook that commits a participant push on the session between the join's read and its write.
3. **minor** `deploy/test_access_log.py` — `.github/workflows/ci.yml` never runs it. Its only Python steps are `bin/security-secret-policy-test.py` and `bin/security-scan-test.py`. So nothing guards the Caddy filter after this commit. Suggested fix: add the test to CI (Docker is available there), or at least the static check `test_E9_T06_no_site_logs_without_the_filter`.
4. **minor (needs a ruling)** `deploy/Caddyfile:20-34` — step 9 asks that the production Caddyfile drop `access_token` from the access log. The executor added the filtered `(access_log)` snippet but did not import it, so access logging stays off as `docs/DEPLOY.md` §Logs requires. That reasoning holds: turning logging on would start logging the other signed capabilities and client IPs. But it is a departure from the step as written, and the organizer has to accept it (report question 1).
5. **minor** `src/main/java/com/agilityhub/core/courses/api/BuildSessionStreams.java:52,198-201,233-238` — a stalled client is "closed" only logically. The watchdog takes it out of its session, but its sender thread stays blocked until the servlet write returns. `senders` is an unbounded `newCachedThreadPool`, and `application*.yml` sets no `server.tomcat.connection-timeout`, so Tomcat's default write timeout applies. Many clients that stop reading therefore hold one thread each. Also, `expired()` calls `emitter.complete()` on the container's timeout thread, and that call blocks while a send holds the emitter's lock. The Assumptions document this. Suggested fix: cap the pool (or reject new subscribers above N stalled ones), set an explicit write timeout, and record both values as a known limit in the report.
6. **nit** `src/main/java/com/agilityhub/core/courses/api/BuildSessionsController.java` `joinBuildSession` — the filter now treats `POST /build-sessions/join` as a keyed, retried route (`BUILD_SESSIONS`). But the method declares no `@RequestHeader("Idempotency-Key")`, unlike create and `finish`, so the published contract probably does not advertise the key for join. I could not run the OpenAPI query to confirm. Suggested fix: declare the header so the contract matches the behaviour.
7. **nit** `docs/MODEL_DADES_PLATAFORMA.md:251-252` — `BuildSession` gets a new stored field, `setupId`, but the model entry does not list it. S16 R-16-11 does mention it, so E109 is met on the spec side. Suggested fix: the organizer updates the model at the source together with the other S16 lines (this is the api's copy only).
