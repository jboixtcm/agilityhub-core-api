## Findings
1. **minor** `clubs/bookings/application/BookingConfirmationService.java:114-118`: when the provider call fails, the booking can be cancelled twice.
   - **What happens:** `charges.abandon()` commits `UpfrontPaymentFailed{bookingId}` to the outbox. Then `cancelBySystem()` runs in a second transaction, with no check that the booking is still PAYMENT_PENDING.
   - **The race:** the outbox dispatcher runs every second (`OutboxDispatcher` `@Scheduled(fixedDelay = 1000)`), and other replicas may run it too. If `BookingConsumers` (line 41) cancels the booking first, `cancelLocked` throws `422 BOOKING_NOT_CANCELLABLE`. A write conflict between the two, followed by a retry, gives the same result.
   - **Consequences:**
     - That 422 replaces the original provider failure, which is then neither rethrown nor logged.
     - `IdempotencyFilter` treats a 422 as a business outcome and stores it, so the member's `POST /bookings` replays `BOOKING_NOT_CANCELLABLE` forever instead of releasing the key.
   - **Tests:** `SingleClassCheckoutIT` cannot see this, because it dispatches by hand.
   - **Fix, either of:**
     - apply the consumer's guard: cancel only if the booking is still PAYMENT_PENDING (re-read it inside the locked transaction);
     - or leave the cancellation to the `UpfrontPaymentFailed` consumer.

     In both cases, keep the original failure: wrap `abandon` and `cancel` in try/catch and use `failure.addSuppressed(...)`.
2. **minor** `clubs/bookings/application/SingleClassCharges.java:~36`: `prepare` only checks that a `PaymentProvider` bean exists. The signup flow also checks that the club has the provider enabled (`clubs.providerEnabled("STRIPE")` → `PAYMENT_PROVIDER_NOT_ENABLED`, `CheckoutService.create:27`). So a club with SINGLE_CLASS + PAY_TO_BOOK but without Stripe enabled would still open provider checkouts in staging/prod. Suggest the same check before `prepareBooking`, with the error code the signup flow already uses.
3. **minor** `BookingsController.java` `confirmed(...)`: a gap between the two transactions.
   - **The case:** the provider checkout opened, but storing the 201 then fails, for example with `STALE_VERSION` after the retries run out.
   - **The result:** the filter releases the key. The client never receives `checkoutUrl`, because it is not persisted on the booking. A retry with the same key answers `409 SEAT_HOLD_EXPIRED`. Meanwhile the seat stays PAYMENT_PENDING, and so blocked, until P7 cancels it about 30 min later.
   - **Why it matters:** the case is rare, but a member would lose a seat they are paying for without being told. This is not among the assumptions the report lists.
   - **Fix, either of:** persist `checkoutUrl` in `Booking.charge`, so `GET /bookings/{id}` can show it again; or treat a failed store like a failed provider call (abandon + cancel).
4. **nit** R2 assumption 1 (a P7 timeout leaves the line `CHECKOUT_PENDING` and the session `PENDING`).
   - **The problem:** in local/test nothing ever expires them. In prod, a Stripe payment started just before `expiresAt` can be captured for a booking that is already cancelled; the report defers the refund to E8.
   - **Suggestion:** P7 (`PaymentTimeoutsJob`) should call `SingleClassChargePort.abandon` / `CheckoutService.expire` for the booking's session. This belongs to E5-T05 / E5-T08, so it could be routed there instead of fixed here.
5. **nit** Provider-failure path (R2 assumption 2): the member gets N-40, whose wording is about a *payment timeout*, together with an HTTP 500. The behaviour is documented, but the N-40 text does not describe what happened. The report should say this, or it should go to MESSAGES.md as a catalog question (for example, a reason variable).
6. **nit** Catalog payload (`CATALEG_ESDEVENIMENTS.md:66`): `UpfrontPaymentSucceeded` / `Failed` now carry `bookingId` and `memberId`, and `Succeeded` also carries `amountPaid`; the catalog row lists only `paymentId, concept, provider`. This is correctly proposed in the report and in `MESSAGES.md`, and the organizer allowed carrying `bookingId`. It is listed here only so the organizer records the ruling.
