# Review E11-T04 — needs changes

## Findings

1. **major** `deploy/backup/backup.py:111-122` — The daily backup runs `fsync` + `lock: true` and keeps every write on production Mongo blocked for the whole count → full `mongodump` → recount sequence. `run()` allows that to last up to 900 s.
   - **Why it matters:**
     - A13 / Step 3 ask for `mongodump --oplog`, which already gives a consistent dump without blocking writes. Under the lock, `--oplog` does nothing useful.
     - The lock exists only so that `--verify` can compare against a manifest written at backup time. The task says "compare … with the source".
     - If the ops container is SIGKILLed or OOM-killed while holding the lock, production stays write-locked until someone unlocks it by hand. DEPLOY.md:131-135 admits this.
     - That failure is realistic here: during the locked phase the dump is written to the RAM-backed `/work` tmpfs (finding 3).
     - The lock is also the only reason the backup user needs `hostManager` (finding 4).
   - **Fix:** drop the lock.
     - Option A: take the manifest counts as a snapshot read at the dump's final optime (`readConcern: snapshot` + `atClusterTime`).
     - Option B: record counts without a lock and let `--verify` compare the restored counts with the counts at the archive's last oplog entry.
     - If the organizer chooses to keep the lock, it should be an explicit decision recorded in MESSAGES. The tool should also refuse to start when `/work` free space is smaller than the expected dump size.

2. **major** `deploy/compose.prod.local.yaml:5-6` — The core service in `compose.prod.yaml` was never started as it is written for production. The local proof overrides `SPRING_PROFILES_ACTIVE: local` and `SPRING_DATA_MONGODB_URI`. Not exercised as a result:
   - the `staging | prod` Mongo wiring through `MONGODB_HOST/USERNAME/PASSWORD/REPLICA_SET/AUTH_DATABASE` (`application.yml:197-206`);
   - `TrustedProxyConfiguration`'s startup guard;
   - HSTS;
   - the strict SendGrid/Twilio/VAPID/OIDC-secret checks;
   - the S3 export and attachment beans (`ExportConfiguration`, `AttachmentConfiguration`, which apply only to staging/prod);
   - the prod `RefreshCookies` and `TenantFilter` code paths.

   Step 2 asks for "the same services" on the Mac, so E12-T01 would be the first time the release configuration boots. The prod checks only require non-blank values, and MinIO is already in the stack, so a faithful boot is possible.
   - **Fix:** keep the `local` profile only for the one-shot `seed` container. Run `core` with `staging` (SMS allow-list empty) or `prod`, using fictional non-blank provider values and `EXPORT_S3_*`/`ATTACHMENT_S3_*` pointed at MinIO. Then repeat the four Caddy checks.
   - Related: the image used (`main` at `d46818b`) predates E8-T01, so the `BILLING_BANK_KEY` fix is proven only at the Compose-config level (`local-proof.py:94-97`), not that Core actually uses the key.

3. **minor** `deploy/compose.prod.yaml:143` + `backup.py:105-133, 151-169` — `/work` is a tmpfs with no size limit, so the kernel default applies (50 % of RAM).
   - **During backup** these files exist at the same time: `dump.archive.gz`, `backup.tar` and `backup.tar.age`, i.e. three copies of the compressed dump.
   - **During restore** these exist at the same time: `.age`, `.tar`, the extracted dump and the full uncompressed WiredTiger data directory of the temporary mongod.
   - The runbook runs `restore --verify` on the production droplet before every deploy and on D0/D+7 (DEPLOY.md:52-53, 253). As data grows this competes for RAM with the production mongod and JVM, and can trigger the host OOM killer.
   - **Fix:**
     - Use a disk-backed private volume, or set an explicit tmpfs `size=` plus a `mem_limit`.
     - Delete each intermediate file once the next one exists. Better still, stream `mongodump | age`.
     - Document the RAM/disk sizing rule.

4. **minor** `deploy/mongo-health.js:17` — The backup account gets the built-in `hostManager` role, which also grants `shutdown`, `killop`, `setParameter`, `logRotate`, etc. That credential lives in the cron env file on the host. **Fix:** create a custom role with only `{cluster: true}` → `fsync`, `unlock` (or no extra role at all once finding 1 is fixed).

5. **minor** `deploy/Caddyfile:22` (and `:61`, `:67`) — `header /index.html Cache-Control "no-cache"` never applies to `/` or to SPA deep links.
   - Caddy runs `header` before `try_files`, so the path matcher sees the original path, not the rewritten `/index.html`.
   - Effect: after a deploy or rollback that switches `*_DIST_DIR`, browsers can keep using a heuristically cached `index.html` that references hashed assets which no longer exist.
   - **Fix:** match on "not a hashed asset" (for example `@html not path /assets/*`), or put `try_files` and `header` inside one `route` block.
   - The smoke at `local-proof.py:156-158` checks only the body; it should also assert the response header on `/` and on a deep link.

6. **minor** `docs/DEPLOY.md:163` — The cron line appends all output to a file, so cron's MAILTO never fires. There is no `||` hook, and `flock -n` contention also returns 1. Step 3 asks for "exit codes a cron can alert on", but the documented line does not alert on anything. **Fix:** add a failure hook (for example `|| logger -p user.err …`, or a dead-man's-switch ping on success), and give "lock busy" its own exit code (`flock -E`).

7. **minor** `deploy/Caddyfile:43-50` / `local-proof.py:183-187` — The `domain`→`host` ask bridge has only been tested on the "deny" path. Today any non-2xx response denies, including Core's 401 for the missing route, so the rewrite to `/internal/domains/allowed?host=` (S17 R-17-03 §6) has never been observed working.
   - **Fix:** add a local-only stub upstream in the override that approves exactly one fixture host and records the query it received. Assert that the host gets a certificate and that the stub saw `host=<that host>`. This needs no unconditional approval in production.

8. **minor** `deploy/.env.prod.example:68`, `backup.py:93` — The backup principal on the host holds `DeleteObject`, and the host also stores the private age identity.
   - Someone who compromises the droplet can therefore read every retained backup and delete all of them. That includes data erased under GDPR that is still inside the 30-day window.
   - **Fix:** run retention through an S3 lifecycle rule (or Object Lock) so the cron principal is write/list only. Consider encrypting to a recipient public key, with the identity supplied only when verifying.
   - Separately, ADR-003 §Backups says the backup also packs volumes and `.env`. The implementation deliberately leaves both out (DEPLOY.md:192-195) and defers them to an unscripted "separate escrow". The report should flag this as an ADR deviation, as AGENTS requires.

9. **nit** `docs/DEPLOY.md:79` — The release runbook hard-codes an operator's personal path (`/Users/jordib/Dropbox/…/heavy.sh`). Refer to "the host lock wrapper" generically.

10. **nit** Small tidy-ups:
    - `compose.prod.yaml:11` and `backup/Dockerfile:1` use the floating `mongo:7.0` tag, and DEPLOY step 4 pulls `mongo` on every deploy. A patch upgrade can happen silently and rollback is not reproducible; pin the patch version or digest.
    - The backup image tag `agilityhub-backup:e11-t04` names a task id in production.
    - `backup.py:164` has `import shutil` inside the loop.
    - `test_E11_T04_named_archive_cannot_escape_prefix` uses an empty listing, so it never really tests a key outside the prefix next to valid ones.
