# Review E8-T09 — needs changes

## Findings

1. **major** `src/main/java/com/agilityhub/core/payments/application/PaymentRetryPolicy.java:41` — Concurrent executions can erase evidence of an uncertain submission. `ready()` does not claim the operation exclusively. Worker A can record `previouslyUncertain=false`, then worker B can submit the same operation while A handles a pre-submission configuration failure. A unconditionally resets the shared marker to false; if B’s response is lost, B does not restore it because its own `previouslyUncertain` was true. Exhaustion can then mark a captured charge failed, enabling another charge, or release an uncertain refund reservation. This breaks points 1–2 and R-12-21/29. Use an exclusive, fenced execution claim or attempt-specific uncertainty records, and test this interleaving with two workers.

2. **major** `src/main/java/com/agilityhub/core/payments/application/PaymentRefunds.java:150` — Point 2 remains incomplete for provider configuration errors returned by Stripe. A correctly shaped but invalid/revoked API key passes `client()` validation; Stripe’s HTTP 401 becomes an ordinary `ApiException` in `StripeCalls`, so `submissionUncertain` remains true. After exhaustion, the refund cannot execute again, its reservation remains, and a replacement refund receives `REFUND_EXCEEDS_PAID` even after credential repair. No refund was created to produce a reconciliation webhook. Preserve definitive rejection information and release or safely retry these operations; add an adapter test returning HTTP 401. This violates point 2 and R-12-20’s recoverability requirement. [Stripe error semantics](https://docs.stripe.com/error-low-level).

3. **major** `src/main/java/com/agilityhub/core/payments/application/CardPayments.java:174` — The new completion predicate can leave a run permanently `CHARGING` after an invoice is cancelled before charging. Generation creates a Stripe `CREATED` collection; `InvoiceActions.cancel()` changes only the invoice, and `prepare()` skips cancelled invoices. The collection therefore remains `CREATED` forever and now prevents completion, even after every submitted payment settles. This regresses the R-12-19 cancellation flow while implementing point 5. Resolve unused collection attempts when cancelling, or distinguish abandoned, never-submitted attempts in completion logic; test cancellation before `card-charges`.

4. **major** `src/main/java/com/agilityhub/core/payments/application/CardPayments.java:171` — Completion still excludes Stripe attempts belonging to invoices whose frozen payment method is SEPA or MANUAL. R-12-18 permits retrying a failed invoice after its member switches to CARD. In a mixed run, submit that retry while another card invoice is collecting; settling the original card invoice makes this method report completion while the converted invoice’s Stripe collection remains `SUBMITTED`. Point 5 and R-12-13 require checking every Stripe collection. Determine outstanding attempts across all run invoices, independently of their original payment method, and add this mixed-provider regression.

5. **minor** `src/main/java/com/agilityhub/core/payments/application/PaymentRefunds.java:233` — The new settlement audits lack the required webhook provenance. Stripe processing establishes only `TenantContext`; `PaymentAudits.refunded()` uses the default audit actor and origin, producing `actorRole=SYSTEM`, `origin=null`, and no `details.job` for an unauthenticated webhook. S14 §3 requires an explicit origin and distinguishes WEBHOOK from SYSTEM. Establish trusted webhook audit context for immediate and deferred reconciliation, and assert these fields alongside the existing audit-count assertions.
