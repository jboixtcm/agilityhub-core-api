# Review E8-T05 — needs changes

## Findings

1. **major** `src/main/java/com/agilityhub/core/clubs/census/application/InactivityPeriodService.java:109` — Moving an approved period can cancel bookings outside its new interval. For example, changing Nov–Dec to Feb–Mar calls `cancelInside` for Jan–Mar, cancelling January bookings too. The reverse move has the same problem. R-13-04/06 require cancellation only for newly included months. Compute the interval difference **new minus old**, bounded by the new start and end, and test moves in both directions.

2. **major** `src/main/java/com/agilityhub/core/clubs/census/application/InactivityPeriodService.java:134` — `terminate` can extend a period without checking overlap or cancelling newly covered bookings. An ACTIVE Oct–Nov period can be terminated “through January”, overlapping an existing January request and leaving December bookings active. R-13-02/06 must remain true after admin changes. Reject extensions through this endpoint or apply the same overlap and cancellation logic as `change`.

3. **major** `src/main/java/com/agilityhub/core/clubs/census/application/InactivityPeriodService.java:70` — Approval does not serialize with new bookings or registrations. Its census lock is not acquired by booking confirmation or activity registration. A concurrent registration can read eligibility before approval, remain invisible to the cancellation sweep, and commit afterward; the transactions need not write any common document. This violates R-13-06/07 despite each operation being transactional. Introduce a shared member eligibility lock/version acquired by both flows, and test this interleaving.

4. **major** `src/main/java/com/agilityhub/core/clubs/census/api/InactivityController.java:91` — The new keyed writes bypass the intended transaction retries. These routes fall through to `IdempotencyFilter`’s outer request transaction; `LifecycleTransactions.run` then immediately executes without retrying because a transaction already exists. Concurrent requests with different keys can conflict on `census_write_locks` and return an internal error instead of retrying and returning the documented business conflict. The new pack/payment routes have the analogous wiring. Register these routes for service-owned transactions and use `keyed` to commit the response with the effects. Add concurrent HTTP tests using distinct keys.

5. **major** `src/main/java/com/agilityhub/core/payments/application/PackBalanceService.java:75` — A usable pack is returned before checking the member’s plan, so booking confirmation consumes sessions for a MONTHLY member, including after a pack-to-membership change. S08 R-08-17 explicitly disables pack rules for MONTHLY plans. The executor’s fixture-based assumption does not resolve that contradiction. Gate pack applicability before selecting a balance, preserve refunds of earlier consumption, and test a monthly member with an **unexpired** remaining pack.

6. **minor** `src/main/java/com/agilityhub/core/clubs/common/application/LifecycleSavedViewSeeder.java:8` — The required “Baixes previstes” system view is installed only through `DemoSeedStep`. Its caller, `DemoPlanningService.apply`, rejects staging and production, and no other production installation path calls `seedPlannedLeaves`. Consequently real clubs never receive the view required by R-13-17/task step 12. Install it through normal club provisioning plus an idempotent backfill; test that path instead of calling the helper directly.

7. **minor** `src/main/java/com/agilityhub/core/clubs/census/application/InactivityPeriodService.java:154` — Finishing an ACTIVE period for leave saves the transition without emitting `InactivityEnded`; `InactivityScheduler.java:42` also suppresses that event for `finishReason=LEAVE`. S13 §5/§7 and AGENTS rule 8 require the domain event. The exception suppresses **N-18c**, not the outbox event; `CensusNotificationFacts` already filters that notification. Emit `InactivityEnded{LEAVE}` transactionally and test that no N-18c is delivered.

8. **minor** `src/test/java/com/agilityhub/core/clubs/bookings/api/LifecycleIT.java:142` — The claimed T-13 coverage is incomplete. The extension test checks history, an event count and fees, but creates no booking in the added months and never verifies N-18d delivery. There is also no successful termination behavior test or T-13-26 race between pack expiry and direct leave. These are explicit acceptance cases in the task. Add assertions for those outcomes and narrow the executor report’s coverage claim until they pass.
