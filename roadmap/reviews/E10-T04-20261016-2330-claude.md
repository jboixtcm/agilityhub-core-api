# Review E10-T04: needs changes

## Findings
1. **major** `src/main/java/com/agilityhub/core/identity/api/CurrentUserFilter.java:49` — **The support-token restriction checks the raw, still-encoded path.**
   - **What is wrong:** The R-17-10 check `SupportAccessService.restricted(method, path)` runs on `request.getRequestURI()`, which is not decoded. Spring MVC routes on the decoded path segments. So `GET /api/v1/members/%65xport?format=xlsx` would not match `RESTRICTED`, yet MVC would still send it to the members export handler. The same applies to `/api/v1/%65xports/{id}/download` and `/api/v1/remittances/{id}/%66ile`. Spring Security's `StrictHttpFirewall` blocks only `%2F %5C %25 %2E %3B %00`, so an encoded letter gets through.
   - **Why it matters:** A support token could then download personal-data exports and SEPA files with full IBANs. S17 R-17-10 forbids exactly that ("no pot … exportar dades personals (`403 SUPPORT_RESTRICTED`)").
   - **Codebase convention:** Other filters already match on "the path Spring routes (decoded, without `;` parameters)" through `UrlPathHelper.getPathWithinApplication` (`SecurityConfiguration.buildSessionStream`, `RateLimitFilter`, `HealthRequests`).
   - **Fix:** Use that decoded path. Better still, enforce the rule at the handler: a `@SupportRestricted` annotation or a method-security check on `CurrentUser.support()`. Add a `T_17_09_…` case with an encoded path.
   - I did not run this. The reasoning comes from how Spring 6 `PathPattern` matching works.
2. **minor** `deploy/Caddyfile:87` — **A verified `clubs-admin` domain is served the wrong app.**
   - **What is wrong:** Verifying a `clubs-admin` domain in the console now makes Caddy issue it a certificate. But Caddy still picks the SPA from the static `CLUB_ADMIN_HOSTS` list, so the new host gets the `clubs` SPA until someone edits the env var and recreates Caddy (`docs/DEPLOY.md:351,408`).
   - **Why it matters:** WP-17-D and S17 §2 promise a domain that works once it is verified. Neither the report nor the operation description mentions this manual step.
   - **Fix:** Either document the step in the verify operation and the report as a known limitation, or open a follow-up (for example an `app` hint from `/internal/domains/allowed`, or a dynamic host matcher).
3. **minor** `src/main/java/com/agilityhub/core/shared/api/IdempotencyFilter.java:101,172` — **INC-49 keys are scoped to an unchecked club id.**
   - **What is wrong:** `CONSOLE_CLUB` takes the club id from the raw path segment. The filter then claims an idempotency row in that "tenant" before `guards.club(id)` runs.
   - **Consequences:** A request to a club that does not exist leaves `idempotency_records` rows under a `clubId` that matches no club. An encoded id would scope the key differently from the club the handler opens. The impact is low, but it breaks AGENTS rule 4 in spirit: tenant rows should only exist for real tenants.
   - **Fix:** Decode the segment (same helper as finding 1) and skip or abandon the claim when the club does not exist. Alternatively, check the club exists before claiming.
4. **minor** `src/main/java/com/agilityhub/core/platform/application/PlatformDomains.java` — **The R-17-03 re-check is not implemented.**
   - The weekly re-check ("si falla 3 cops → `BROKEN` + avís a plataforma") is missing, and nothing ever sets `DomainStatus.BROKEN`. The parameter `platform.domainRecheckDays` and the event `ClubDomainBroken` are already in the catalogs.
   - The executor calls this out of scope (S15 P9 is optional in S17 §13), which is acceptable. The organizer should still track it explicitly, because `BROKEN` now appears in the contract and in the `DELETE` rule.
5. **nit** `src/main/java/com/agilityhub/core/configuration/AuditConfiguration.java:36` (unchanged) — **Audit role for support actions.**
   - Actions taken with a support token are audited with `actorRole = ADMIN`, because the role comes from the token's `roles` claim. They carry `origin = PLATFORM_SUPPORT` and `support = true`.
   - S14 §3's `actorRole` enum has `PLATFORM`. The spec does not say which role a support action should carry, so the organizer should decide and record it in S14 §3.
6. **nit** `src/test/java/com/agilityhub/core/payments/api/SupportAccessIT.java` — **Test placement.** `SupportAccessIT` (and the extended `ConsoleProviderLockIT`) sit in `payments.api` only to reuse `BillingItSupport`. They belong under `platform.api` or `identity.api` next to `PlatformDomainsIT` and `PublicApiKeyIT`.
7. **nit** `src/main/java/com/agilityhub/core/platform/persistence/JndiDomainDns.java:33` — **TXT parsing.** When a TXT record is split into several strings, JNDI returns them as `"a" "b"`. Stripping the quotes leaves `a b`, which never equals `agh-verify-…`.
   - This is harmless for the 43-character token used today. It is worth a comment, or concatenating the strings without the space.
