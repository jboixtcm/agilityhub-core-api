# Review E10-T02 — needs changes

## Findings

1. **major** `src/main/java/com/agilityhub/core/platform/application/PlatformClubChanges.java:73` — Explicit `"legal": null` passes request validation, bypasses the legal-content check and is persisted. `ClubConfigService.load()` subsequently dereferences `club.legal()`, breaking configuration-dependent requests; even the PATCH response loads configuration through usage calculation after the mutation commits. This violates the S17 configuration contract and AGENTS rule 9. Reject the value with a catalog error or implement a consistently supported empty representation. Add a regression covering both persistence and subsequent reads.

2. **major** `src/main/java/com/agilityhub/core/identity/application/ConsoleAdministrators.java:51` — The last-admin guard does not share the lock used by existing club team mutations. Console removal serializes through the Club document, whereas `RoleAssignmentService` uses `team_write_locks`. With two active administrators, concurrent console suspension of A and club-side demotion of B can both count two administrators and commit changes to different memberships, leaving none. This violates R-17-09. Use the same tenant-level serialization boundary across administrator writers and test the mixed-path race.

3. **major** `src/main/java/com/agilityhub/core/platform/application/PlatformProviders.java:81` — Provider removal checks usage without coordinating with payment-method assignment. Concurrently, `MemberService.payment()` can read the provider as enabled and assign it while removal observes zero users. The transactions write different documents, so both can commit, leaving a member using a removed provider. Disabling has the same gap. This violates R-17-05. Serialize provider assignment and removal/disable through a shared transaction lock and add concurrency coverage.

4. **major** `src/main/java/com/agilityhub/core/platform/api/PlatformClubsController.java:66` — Creation forwards `catalogs.fromTemplate` directly to `PlatformCatalogClone.source()`, which resolves only by database ID. S17 §3 documents `fromTemplate: club-template-default`, but the seeded template has that **slug** and a generated UUID ID. The documented definition therefore fails with `TEMPLATE_CLUB_NOT_FOUND`. Resolve template references by slug and use the resolved ID for tenant scope; preserve ID semantics for the separate `fromClubId` clone endpoint. Test with a template whose ID differs from its slug.

5. **minor** `src/main/java/com/agilityhub/core/platform/application/PlatformProviders.java:60` — `paymentProviders.SEPA_XML.invoiceSeriesPattern` is accepted by the published definition schema and illustrated in S17 §3, but the provider update discards it. Creation can succeed while invoicing retains its default pattern. Following the model’s precedence, translate the accepted field into the existing `billing.invoiceSeriesPattern` parameter, define conflict handling when both locations are supplied, and test creation/export round-tripping.

6. **minor** `src/main/java/com/agilityhub/core/platform/application/PlatformConsoleQueries.java:33` — Storage usage reads `Club.usage.storageBytes`, defaulting to zero, but there is no production writer for that counter. Clubs therefore continue reporting zero after uploads. The storage metric requested by S17 §2/§6 is only partially implemented. Calculate it from tenant-scoped storage records or maintain the counter on upload/deletion, with tenant-isolation coverage.
