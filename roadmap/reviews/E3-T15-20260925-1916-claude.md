# Review E3-T15 — minor issues

Both review majors are fixed:
- **Charge after the write:** the service checks the bucket, stores the decision, and takes the token only once the decision is stored. A failed write takes nothing.
- **Decision outlives the pending event:** a decision has no `expiresAt` while its event can still retry. Retention starts after the commit that marks the consumer processed.

Log `03` shows the three new ITs failing on the unfixed code. The final clean verify (`09`/`10`) and both smoke runs look real and consistent. The findings below are test gaps and leftovers; none of them blocks the gate.

## Findings
1. **minor** `src/main/java/com/agilityhub/core/clubs/census/application/SignupNotifications.java:64` — **the "never charge twice" guard has no test through the service.**
   - The `decided.stored()` check stops a second delivery of the same event, whose decision someone else stored first, from charging again.
   - No test runs that path through `decide`. The only check is on the repository flag (`SignupFollowUpFixesIT.java:234`). If `decided.stored()&&` were deleted, every test would still pass.
   - The same applies to the `deciding` lock: no test would fail without it.
   - The path is reachable. `deliver` runs outside the outbox transaction (`NOT_SUPPORTED`), so a delivery slower than the 5-minute lease can overlap a second claim.
   - Suggested fix: in `withFailingAdmissionWrites` style, add a repository subclass whose `insert` stores the document and then throws `DuplicateKeyException`. With cap 1, assert that the bucket is still untouched afterwards (a following event for the same address is admitted).
2. **minor** `SignupNotifications.java:25` (`CAPPED`) — **the N-39 side of both fixes is untested.**
   - Every E3-T15 test uses N-01. Nothing asserts that a `…:N-39` decision gets its `expiresAt` after processing.
   - `CAPPED` repeats the codes already written into the `deliver` switch (`:118`, `:141`). If the two drift apart, or the event-type key has a typo, every N-39 decision would silently never expire.
   - Suggested fix: add one assertion to an existing N-39 IT (`<eventId>:N-39` `expiresAt` = processed + `jobs.retention.domainEventsDays`). Optionally take the code from a single place.
3. **minor** `SignupNotifications.java:79-88` — **setting the expiry after commit is best effort, and nothing cleans up when it fails.** A decision is kept forever with no `expiresAt` when:
   - the after-commit update fails (only a WARN is logged);
   - the process dies between the commit and `afterCommit`;
   - the event ends `FAILED` (Assumption 4).

   Impact is low: decisions hold no personal data. But S15 P9 (R-15-19) neither reports nor deletes them, so they are invisible. Suggested fix: add to the executor's doc proposal that P9 reports decisions with no `expiresAt` whose event is `PUBLISHED` or already deleted, or have the organizer accept the leftover explicitly.
4. **nit** `SignupFollowUpFixesIT.java:460` — **Step 2 is read differently from its wording.**
   - After 25 h the hourly bucket has refilled, so the first competing event B is **admitted**. A's retry then also sends, so the address gets two N-01 in one hour with cap 1.
   - This matches E3-T12 round 2 (the cap counts decisions, not sends). The test covers "refused while the cap is full" with a third event C.
   - The task's wording ("the competing event is refused") could be read the other way; the organizer should confirm this reading (the executor's Assumption 2).
5. **nit** `src/main/java/com/agilityhub/core/shared/application/RateLimits.java:74` and `SignupNotifications.java:27` — **the lock is broader than its javadoc says.**
   - The javadoc says the caller serialises the check-and-charge per recipient. In fact `deciding` is one lock for the whole instance, across all clubs and recipients, and it is held during a Mongo insert.
   - This is harmless with today's single-threaded dispatcher. Either fix the wording or lock per recipient (a striped lock).
