## Findings
1. **minor** `docs/specs/S01-agilityhub-id-i-acces.md:70` (R-01-06): the spec does not record the security cost of the new grace.
   - **What happens:** someone who replays a stolen rotated token within 30 s gets a sibling, which is an independent branch of the family. The victim's token is left alone. Reuse detection only fires if the thief later forks again or replays a spent token. A careful thief keeps a session for up to `auth.sessionDays` and is never detected.
   - **Where it is written:** only in the report's «Design note», as is the «two body clients» known limit. R-01-06 describes the mechanism but not this consequence.
   - **Why it matters:** this weakens theft detection compared with strict rotation. Option (b) from the organizer allows it, but Jordi should approve it explicitly.
   - **Fix:** add a sentence to R-01-06 or an S01 §13 entry stating the trade-off. The organizer should get Jordi to ratify it.
2. **minor** `identity/application/TokenService.java:196-200` `families()`: the token shown for each family is effectively random.
   - **Why:** it keeps the first token per family. A child and its sibling share `createdAt` (`old.createdAt()`), and the tie is broken by `_id`, which is a random UUID (`AccountSessionRepository.active` sorts by `createdAt, _id`; `refreshTokens.sessions` sorts by `createdAt` only).
   - **Effect:** `GET /me/sessions` (`MeController.java:137-139`) can show the never-retired leftover of an earlier race. That shows a stale `lastUsedAt` and device label for the session.
   - **Fix:** keep the token with the latest `lastUsedAt` per family, and add a test asserting which token is listed.
3. **nit** `TokenService.java:158-165` / `RefreshTokenRepository.liveChild`: the chain guard («a token whose child has moved on gets no grace») is a plain read.
   - **Why it is not atomic:** the grace never writes the child. So if the child is rotated concurrently in another transaction, Mongo sees no write conflict, and the grace still issues a sibling after the child has moved on.
   - The race window is small.
   - **Fix:** a conditional write on the child (for example `replacedByHash: null` → set a `graceSiblingAt`) inside the grace transaction would make the guard atomic.
4. **nit** `payments/application/BankAccountVault.java:63-64`: the refusal is a bare `IllegalStateException`, thrown when an IBAN is stored.
   - **Effect:** in a staging deployment without the key, a member who submits a signup or a D10 change gets a generic 500 after typing their IBAN.
   - **Rule:** AGENTS rule 9 says to throw `ApiException(ErrorCode.X)`. `INTERNAL_ERROR` with a cause, as `BuildSessionService.java:216` does, would follow it.
   - **Fix:** use `ApiException(INTERNAL_ERROR)` and consider failing at startup outside `local`/`test` instead. Separately, the public `BankAccountVault(String key)` constructor defaults to `clearAllowed = true` and is used only by tests. Make it package-private or test-only so production code cannot pick the permissive default.
5. **nit** `courses/persistence/VenueRepository.java:28-41` `freeSlug`: the return value can be wrong.
   - **When:** two first rings of the *same* club race. The second call sees the slug taken, moves to `{slug}-2`, and its `ensure` upsert matches the venue that already exists (no duplicate key).
   - **Effect:** it returns `{slug}-2`, but the venue's slug is `{slug}`, which contradicts `@return the slug of the club's venue`. The caller ignores the value, so nothing breaks today.
   - **Fix:** return `club().map(Venue::slug)` after `ensure`, or change the method to return `void`.
6. **nit** `docs/DECISIONS_PENDENTS.md`: the commit adds row E133, an organizer ruling on E10-W03 that has nothing to do with this task. The publish script probably picked it up from the shared working tree. The organizer should confirm that this row was meant to be published.
