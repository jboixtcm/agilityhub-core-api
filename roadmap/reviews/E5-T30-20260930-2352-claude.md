# Review E5-T30: minor issues

Round 2 covers all five of the organizer's items, and each new behaviour test fails on the old code (logs `11` and `19`). The full `clean verify` passes with nothing excluded (logs `22` and `23`). Most findings below are gaps in tests or documentation. Finding 1 is an open design question for the organizer.

## Findings

1. **minor** `src/main/java/com/agilityhub/core/platform/application/jobs/JobCatalog.java:24` and `clubs/bookings/application/PaymentTimeoutsJob.java:40`: P7's new signup sweep only runs in clubs where `SINGLE_CLASS` is on.
   - **What goes wrong:** take a club with `BILLING` and `STRIPE` but without `SINGLE_CLASS`. A session that stopped before reaching the provider stays `PENDING` in the database, and its rows stay `CHECKOUT_PENDING`. That lasts until D2's validation, a rejection or a new checkout happens. Only the read view in `UpfrontPayments.selected` hides it. Readers that query Mongo directly still see `CHECKOUT_PENDING` (`DashboardRepository:59`, `CensusListProjection:82`). Today they count it as unpaid, just like `DUE`, so nothing shows yet.
   - **Why it matters:** item 2 and S04 R-04-26 name P7 as the process that releases these rows. The executor asked this as question R2-1, and no test covers a club without `SINGLE_CLASS`.
   - **Fix:** the organizer should answer R2-1 before verifying. If the answer is yes, run the signup part whenever `BILLING` is on (a separate job, or P7 without the module gate), and add a test on a club without `SINGLE_CLASS`.

2. **minor** `PaymentTimeoutsJob.java:40-50`: P7's run results gain a second item kind that S15 R-15-17 does not define.
   - **What's new:** `entityType CheckoutSession`, `EXPIRE_CHECKOUT` / `WOULD_EXPIRE_CHECKOUT {checkoutSessionId, minutesExpired}` and the counter `expiredCheckouts`. R-15-17 and T-15-25 only define `WOULD_CANCEL {bookingId, minutesPending}`.
   - **Where it's visible:** in the dry run of `POST /jobs/payment-timeouts/trigger` and in D11's [Simula] card.
   - **Status:** the executor proposed the change in `MESSAGES.md`. It is not a closed-catalog item, but it is contract surface that needs the S15 amendment and a T-15-25 extension.
   - **Design nit:** the bookings job now imports `payments.application.CheckoutService` directly. For booking checkouts, the same class goes through `SingleClassChargePort`. A port method would keep the boundary the same.

3. **minor** `src/main/java/com/agilityhub/core/payments/application/CheckoutService.java:237`: item 3 now also changes PAY_TO_BOOK checkouts, and nothing tests that (executor's assumption 5).
   - **What changed:** a booking paid before `bookings.paymentPendingMinutes` runs out but confirmed after it, before P7 cancels the booking, is now **confirmed**. It used to be an E34 late completion.
   - **Why no test catches it:** every booking test goes through `fake.complete(id)`, which passes `paidAt = null`, which is read as "now".
   - **Fix:** add a `SingleClassCheckoutIT` case with two payments confirmed after the deadline: one paid before it (booking confirmed, no mark) and one paid after it (E34 mark).

4. **minor** `src/main/java/com/agilityhub/core/shared/persistence/IdempotencyRepository.java:27` and `payments/application/PaymentProvider.java:13`: the 10-minute lease is only safe if no keyed request outlives it.
   - **The gap:** the lease is never renewed. For the checkout, the one open-ended step is the provider call, and no timeout is set or documented. The requirement ("keep the provider calls' timeouts well within `CLAIM_LEASE`") appears only in the report's "For E8" list.
   - **Fix:** write it into the `PaymentProvider` contract javadoc, next to the idempotency-by-`sessionId` contract from E5-T28, where E8 will read it.

5. **nit** `src/main/java/com/agilityhub/core/shared/api/IdempotencyFilter.java:229`: `records.held(record)` runs for every non-`ApiException` failure.
   - **What goes wrong:** if Mongo is unreachable, it throws. That hides the original failure and skips `records.abandon`.
   - **Fix:** wrap it (`try { held = records.held(record); } catch (RuntimeException e) { held = true; failure.addSuppressed(e); }`).

6. **nit** `src/main/java/com/agilityhub/core/payments/application/CheckoutService.java:62`: when `abandon`'s key lock fails (the claim was taken over), the provider's `failure` is dropped without a trace.
   - **Why it matters:** the `409 IN_PROGRESS` from `abandon` replaces it. Provider timeouts, the likely cause of a takeover, then go unrecorded.
   - **Fix:** log a WARN with `checkoutSessionId` and `clubId` only (no e-mail), or `addSuppressed`.

7. **nit** `src/main/java/com/agilityhub/core/payments/persistence/SignupCheckoutRepository.java:35`: the new club-wide `lapsedSignup(now)` behind P7's plan has no cross-tenant test (AGENTS rule 4).
   - **Fix:** a lapsed session in a second club should never appear in club A's P7 plan. This is one extra assertion in `T_04_22_T_15_25_P7Expires…`.

8. **nit** `src/test/java/com/agilityhub/core/shared/persistence/IdempotencyIT.java:217`: `E5_T30_aStoppedRequests…` is not named after a `T-xx-nn` id (AGENTS rule 5).
   - **Context:** it follows the class's existing naming, and the executor says so in the report. If CONVENCIONS_API §7 ever gets a test id, rename it.
