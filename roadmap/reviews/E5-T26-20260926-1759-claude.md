## Findings

1. **minor** `src/main/java/com/agilityhub/core/clubs/followup/api/AttachmentsController.java:131` — **SVG is now served `inline` on the API origin.**
   - **What happens:** `download()` makes every `image/*` inline, and the executor's assumption 4 says SVG is included on purpose. `image/svg+xml` gets through the default `files.allowedTypes = image/*` (CATALEG_PARAMETRES l.124), and an anonymous `POST /signup/upload-urls` accepts it (`AttachmentService.signupUpload`: `type.startsWith("image/")`). So a stranger can upload an SVG. When an ADMIN opens that signup file's link in D2, the SVG now renders as a document on the API origin. That origin also serves `/oauth2/authorize` (AgilityHub ID). Before this task the same file came back as `application/octet-stream` with `attachment`.
   - **How much it matters:** the CSP (`default-src 'self'`, no `unsafe-inline`) plus `nosniff` stops script, so the impact is limited to spoofed content. But inline buys nothing for the stated goal. Browsers ignore `Content-Disposition` for `<img>`, as the executor's own assumption 5 says. Only the MIME type fixed the `<img>` case. A31 makes the local stack the one that actually runs, so this is live.
   - **Fix:** send `attachment` for `image/svg+xml`, or add `Content-Security-Policy: sandbox` to download responses. Otherwise, record it in `docs/INCIDENCIES_OBERTES.md`.

2. **nit** `src/main/java/com/agilityhub/core/platform/api/ClubCorsConfigurationSource.java:26` — **the web can't read the stored name through `fetch()`.**
   - `Content-Disposition` is not in `exposedHeaders` (`Retry-After, ETag, Content-Language`).
   - Step 2 asks for "the stored name". If the web's app downloads a file by `fetch`/blob from its own origin, it cannot see that name.
   - This does not matter for `<img>` or `<a href>` navigation. Add the header, or tell the web in the report's Web section.

3. **nit** `SignupSecurityFixesIT.CONVENCIONS_API_5_localDownloadsAnswerTheStoredTypeAndNameAndShowImagesInline` — **the IT covers neither a dog photo nor an activity image.**
   - Step 2 names "a dog's photo or an activity's image". The IT uses a `DOG_DOCUMENT` PNG and never downloads a `DOG_PHOTO` or `ACTIVITY_IMAGE` through `/attachments/files/{id}`.
   - The code path is the same, so the risk is low.
   - The fallback branches the report relies on (assumption 4) are also untested:
     - an unparsable stored type falls back to `octet-stream`;
     - a wildcard `image/*` falls back to `attachment`. `image/*` is reachable, because `validate()` accepts the literal `image/*` as a type.

4. **nit** Step 3 and the Definition of Done ("each [step] has a test that fails before the fix").
   - Step 3's preflight needed no code change. Its IT fails on tree A only because of step 4 (`404 UNKNOWN_HOST` on the cross-origin PUT).
   - The executor says so openly, and the preflight assertions are a pin, not a before/after proof. The organizer should accept this explicitly.

5. **nit** Assumption 1 is a behaviour change the organizer should acknowledge.
   - `PUT /api/v1/signup/uploads` no longer follows S04 R-04-27's "Host → club (`404 UNKNOWN_HOST` si no resol)". It now takes the grant's club whatever the host.
   - An anonymous grant PUT with a member's bearer while signup is closed now answers `422`. Before, the bearer let it through.
   - Both fit CONVENCIONS_API §5 and steps 3–4, but they change the letter of R-04-27 for this one route. A one-line note in the spec or in MESSAGES would avoid the question coming back later.

6. **nit** Out of scope; for `INCIDENCIES_OBERTES.md`.
