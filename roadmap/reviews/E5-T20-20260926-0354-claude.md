# Review E5-T20 — minor issues

## Findings
1. **minor** `src/main/java/com/agilityhub/core/clubs/activities/application/ActivityApiService.java:58-61`: `waitlistRank` is set from `projection.waitlistRanks(id)` whatever the row's state is.
   - **What goes wrong:** the rank map is a second read, separate from the page aggregation. A promotion or cancellation between the two reads can produce an `ACTIVE` or `CANCELLED` row with a non-null rank, or a `WAITLISTED` row with `null`.
   - **Why it matters:** the schema description (`WAITLIST_RANK`) promises "null for any other state". `ActivityProjection.registration` (`:82`) does guard on `r.state()==WAITLISTED`, so the list and the member views disagree on this point.
   - **Fix:** apply the same guard when the row's `state` is present (`"WAITLISTED".equals(row.get("state")) ? ranks.get(id) : null`). Or read the ranks before the page and drop any rank whose row is not `WAITLISTED`.
2. **minor** `src/main/java/com/agilityhub/core/clubs/activities/api/ActivitiesController.java:166` and report step 1 / CHANGELOG: the text says an activity with rings and no date (or no hours) gets `400 INVALID_TIME_RANGE` "like the publication".
   - **Not true:** the publication refuses both cases earlier, with `422 ACTIVITY_INCOMPLETE` and `fieldErrors` (`ActivityRules.publish:38-45`).
   - **Behaviour is acceptable:** S07 §6 only lists 422 `OUTSIDE_OPENING_HOURS` and 400 `INVALID_TIME_RANGE` for `ring-conflicts`, and replacing the NPE/500 is a real fix.
   - **Fix:** reword the OpenAPI description to say the preview answers `INVALID_TIME_RANGE` when there is no window to block. Drop the "like the publication" claim from the report and the CHANGELOG.
3. **minor** CONVENCIONS_API §4 (amended 26-09) only partly holds outside D7. `x-fields` is now published on 14 lists, but:
   - `GET /bookings` ignores `fields` and returns whole `BookingListItem`s.
   - `GET /jobs/{name}/runs` publishes `x-fields: ["id"]` but returns whole items.
   - The item schemas of `/weeks`, `/class-sessions`, `/ring-blocks` and `/training-bookings` still require every property, although their runtime makes items sparse. Generated clients will reject valid sparse responses.
   - The three "Contract only" paged lists (`/platform/audit-entries`, `/platform/erasure-requests`, `/platform/security-events`) now carry a `fields` parameter whose description points to `x-fields`, but they publish none. `ListFieldsContractIT.universalList` excludes them.

   Step 3 only asked for sparse items on the two D7 lists, so this is not a DoD gap. The executor raised it as question 2. The organizer should open the follow-up, because the web will read `x-fields` as a promise of sparse items everywhere.
4. **nit** `src/main/java/com/agilityhub/core/clubs/activities/application/ActivityLists.java:27`: both lists still register an `id` filter that is not in their `x-filterable`, so `filter=id:eq:…` is accepted on `/activities` and on D7 registrations. Step 5 made `filter=activityId` a `400 INVALID_FILTER` for exactly this reason ("not x-filterable"). The inconsistency predates this task. Either publish `id` or refuse it, in a follow-up.
5. **nit** `src/main/java/com/agilityhub/core/clubs/activities/application/ActivityProjection.java:82`: `registration()` runs one `waiting()` query for each `WAITLISTED` registration it projects. On `GET /me/activities`, `mine[]` makes one query per waitlisted row. It is small today, but a member with several waitlisted activities pays N round trips. Computing the ranks once per activity in `ActivityQueryService` would avoid it.
6. **nit** `src/test/java/com/agilityhub/core/clubs/activities/application/ActivityIT.java:536-537`: the comment says "without `fields` every key is sent (assertConforms above)". Since the schema now requires only `registrationId`, `assertConforms` no longer proves that. `assertNoEnd` (`:437`, `has(field)`) is what proves it. Reword the comment so a later refactor does not drop `assertNoEnd`, thinking the schema covers it.
7. **nit** Step 2, data already stored: nothing handles club-level overrides of `learn.baseUrl` / `learn.recommendationsTtlMinutes` written while they were `CLUB`-editable. Such an override would stay in effect, and the club can no longer `DELETE` it (`403 PLATFORM_ONLY`).
   - The seeds contain no such override (grep of `seeds/`), so this only matters if an environment already has one.
   - Worth one line in the report (no migration needed / how to clean up).
