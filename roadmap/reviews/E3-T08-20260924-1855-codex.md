## Findings

1. **major** `src/main/java/com/agilityhub/core/clubs/census/application/SignupService.java:57` — Checkout still loses validated, unpaid submissions when several dogs are submitted. Submit dog A, then dog B; validate A with `upfrontAmountPaid = 0`. `Member.signup` identifies B, so A now fails both filters: it is no longer `PENDING`, and its submission differs from the member’s latest submission. Checkout excludes A’s outstanding rows. This leaves round-2 point 4 incomplete (R-04-16/25/26). Track payable submissions independently of the latest `Member.signup`, while excluding superseded readmission rows. Add a regression covering two add-dog submissions and validation of the older one.

2. **major** `src/main/java/com/agilityhub/core/clubs/census/application/SignupService.java:398` — The invoice-date constraint compares against a recalculated start date, rather than the frozen submission’s start date. For example, submit on August 5 with `ALTERNATIVE` and split day 16, then change `signup.firstMonthSplitDay` to 8. With the same plan, validation accepts August 8 although `signup.upfront.firstMonth.startDate` remains August 16 and the original payment rows remain in force. This violates step 10 and S04 §3. Use the frozen first-month start for an unchanged quote; test both `dryRun` and validation after a parameter change.

3. **minor** `src/main/java/com/agilityhub/core/clubs/census/application/SignupNotifications.java:36` — The new admin notification reads `plan_name` from the member’s latest signup, while selecting dogs from the particular event. Two add-dog submissions with different plans before outbox dispatch therefore make the first notification describe dog A with dog B’s plan. This fails step 6’s submission-specific N-01 content. Resolve the plan from the event’s existing `planId`, and the submission locale from its snapshot. Add a test that queues both submissions before dispatching notifications.
