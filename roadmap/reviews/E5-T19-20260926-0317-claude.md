## Findings

1. **minor** `SignupService.java:509-515` (`claimDocuments`) and `SignupService.java:547` (`writeDocuments`, `doc.files=files`): a D2 `PATCH` drops the rows of files removed through S03 (their `removedAt`). It also quietly brings back a removed signup file when D2 sends its key again.
   - **Why this is new.** Step 2 makes `DELETE …/files/{fileId}` reach signup files. After that, the stored card is `[A(removedAt, removedByAccountId), B]`.
   - **Scenario 1: a normal later edit.** D2 sends back its view's rows `[B, C]`. `writeDocuments` replaces `doc.files`, so the record of A's removal is lost from the document. A's `SIGNUP_DOCUMENT` grant is then unreferenced, and P9 deletes the file.
     - Without that later edit, the same removed file stays referenced for good, because P9 counts `files.fileKey` whatever its `removedAt`.
     - This contradicts report assumption 5 («the stored rows keep `removedAt`, and P9 still counts them as referenced»).
   - **Scenario 2: a stale drawer.** D2 deletes A, then saves a form that still lists A's key.
     - A is not in `currentFiles`, because `activeFiles` filters it out. So `claimSignup(A, dog:type)` succeeds: the grant is bound to the same entity.
     - A comes back as a new active row with the same id and a new `uploadedAt`, and the removal is gone.
     - The dog's `version` does not protect against this, because `DocumentService.remove` never changes it.
     - An S03 key in the same situation gets `400 FILE_NOT_FOUND` (its purpose does not match), so the two kinds of file behave differently.
   - The same loss of `removedAt` rows happens when a reused dog is validated (`applyReadmission` → `writeDocuments`). That part predates this task (E3-T17), but it is the same code path.
   - **Rules:** R-04-19 and the task's convention «No physical deletion of business data. Only P9 deletes orphan files.» The deletion itself is P9's, but here it depends on whether D2 happened to edit the type later.
   - **Fix.**
     - In `writeDocuments`, carry the existing `removedAt` rows over into the new `files`.
     - In `claimDocuments`, refuse (`400 FILE_NOT_FOUND`) a key whose row in the stored document has `removedAt`.
     - Extend `R_04_19_R_04_08_d2RemovesOneFileOfAPendingPublicSignupDog`: after the `DELETE`, (a) a `PATCH` that sends back the view keeps the `removedAt` row, and (b) a `PATCH` that sends the removed key does not bring the file back.

2. **nit** `docs/openapi/CHANGELOG.md` (E5-T19 entry, last bullet): the entry says the `400 VALIDATION_ERROR (documents.files.fileKey, DUPLICATE)` applies to «a D2 edit». In the code (`SignupService.java:512`), the check also runs at submission, so the public `POST /signup` and `POST /me/dogs/signup` now refuse a key sent twice. `MESSAGES.md` says this; the contract changelog does not. **Fix:** name the two submission routes in that bullet.

3. **nit** `SignupService.java:513`: for a kept file, the `name` D2 sends is checked (required, ≤ 80 characters) but then ignored, because the stored row is copied as it is. So D2 cannot rename a file, and neither the `DogPatch.documents` nor the `SignupDocumentFile.fileKey` description says so. **Fix:** add «a kept file keeps its stored name» to the description, so E4-W13 does not offer a rename.

4. **nit** `SignupService.java:503`: the per-request limit of 10 files (`TOO_MANY_FILES`, R-04-08) now also counts the kept files. D2 has to send back every kept file, so adding one file to a type that already has 10 (possible through S03 uploads, or on a long-lived reused dog's own card) answers 400. **Fix:** count only the new signup claims against R-04-08's limit, or have the organizer accept the limit as it is.

5. **nit** `DogService.java:79`: a `documents` edit always adds `diff.documents = {replaced: true}`. So a `PATCH` that sends back exactly what the view shows still changes the dog's version, emits `SignupEdited`, writes a `SIGNUP_EDITED` audit entry and refreshes the dashboard. The IT asserts only that «sending back the view's files changes nothing» in the stored document. This predates the task, but step 1 makes sending the view back the normal D2 path. **Fix, optional:** compare the old and new file keys per type before marking `documents` as changed.

6. **nit** Report assumption 4: signup files claimed before this change keep their storage key as `id`, so `DELETE …/files/{fileId}` still cannot reach them, and a kept old row keeps that id. The task allows re-seeding development data. The organizer should confirm that no shared or deployed environment holds pending public signups from before this change, or re-seed it.

7. **nit** Evidence: the committed `SignupService.java` differs from the tree that ran the clean verify by one Javadoc line (report, after 1b). The report claims `./mvnw -q -DskipTests test-compile` exits 0, but gives no log. This is harmless, but it is a claim without evidence.
