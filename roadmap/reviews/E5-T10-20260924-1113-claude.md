# Review E5-T10 — minor issues

## Findings
1. **minor** `src/main/java/com/agilityhub/core/clubs/bookings/application/PaymentTimeoutsJob.java:36`, `payments/application/CheckoutService.java:72` — `SingleClassChargePort.abandon` only expires the checkout session locally, through `CheckoutService.expire`. It does not call the provider. After P7, a late provider success hits `finish()`: the session is no longer `PENDING` (or it is past `expiresAt`), so `finish()` silently returns without an event. The new IT asserts exactly this: `…aTimedOutBookingExpiresItsCheckoutSoALateSuccessNeverSettlesIt…` checks that no `UpfrontPaymentSucceeded` is emitted.
   - **Conflict with the spec:** S15 R-15-17 and T-15-25 say that a later `UpfrontPaymentSucceeded` "troba la reserva `CANCELLED` → S12 reemborsa". With this change, S12 (E8) never sees that event. If Stripe charged the card (for example, a payment at minute 29 whose webhook arrives after P7), nothing triggers a refund and nothing is logged.
   - **Why it matters:** Step 7 asked for this behaviour, but the report does not flag the divergence from T-15-25, and the step's wording ("can no longer capture money") only holds on our side.
   - **Fix:** log WARN, or record the event for S12 reconciliation, when a completed payment arrives for an `EXPIRED` booking session. Also add an organizer note that E8 must handle "completed at the provider, expired locally" with a refund.
2. **minor** `src/main/java/com/agilityhub/core/platform/application/jobs/JobRunner.java:204-209` — Assumption 4 describes a second case: the lease is lost without a reaper, for example after the Mongo TTL removed the lock. The holder then closes its own row as `FAILED` with "Lease lost before the run finished" and `leaseExpired=true`, which publishes `JobFailed` and lets the next tick do a `CATCH_UP`. No test covers this branch: `grep "Lease lost"` finds only the production line. `T_15_31_aReapedHolder…` covers only the case where the row was reaped. Add an IT that deletes the `job_locks` document during `apply` and asserts the row is `FAILED`, `leaseExpired=true`, only item-1 was applied, and one `JobFailed` was published.
3. **minor** `src/main/java/com/agilityhub/core/clubs/bookings/application/BookingConfirmationService.java:147-150` — Step 4 requires that any later failure be added to the original with `addSuppressed`. No test makes `cancelPaymentPending` or `abandon` throw and then checks that the original exception is rethrown with a suppressed one. The race IT only shows the 500 now wins over the old 422, because the cancel no longer throws. Add a unit test that makes `charges.abandon` throw.
4. **minor** `src/main/java/com/agilityhub/core/clubs/common/application/CleanupJob.java:86` and `CleanupRepository.claimPlatformCycle` — The platform cycle is claimed in `plan()`, before any platform item is applied. If the claiming run then fails, loses its lease, or dies after the plan, no other club's run can take the platform pass that UTC day: they all get `DuplicateKey` and return false. That day's purge is silently skipped. Retention is 90 days, so this is harmless, but the report says "once per P9 cycle" without mentioning the case. Either document it, or release the claim when the run ends `FAILED`.
5. **minor** `CleanupJob.platformItems` / `JobRun.items` — The platform pass is recorded in the job run of whichever club claimed it: the counters `platformDomainEventsDeleted` and `platformJobRunsDeleted`, and the items `PlatformDomainEvents` and `PlatformJobRuns`. The club's ADMIN therefore sees counts of platform and identity rows in their own P9 history (`GET /jobs/.../runs`).
   - These are only counts, but they are data outside the tenant (AGENTS rule 4). The organizer ruling does not say where the platform pass should report.
   - Either confirm that this is acceptable, or hide the `platform*` counters and items from club-scoped run views.
6. **minor** `src/main/java/com/agilityhub/core/clubs/scheduling/application/SessionProjection.java:39-43` — The D1 placeholder for a missing ring changed from "—" to the translated `scheduling.noRing` ("Sense" / "Sin pista" / "No ring"). This changes the value in `GET /dashboard` `riskReview.ringName`, visible to the web. The report mentions it in its Assumption 9 and in `MESSAGES.md`, but not under "Web: nothing to regenerate". Tell the web explicitly, or check it against the S14 D1 mockup in `docs/pantalles/`.
7. **nit** `BookingConfirmationService.openCheckout` / E30 — In the tested race (the `UpfrontPaymentFailed` consumer cancels first), the member gets both the synchronous 500 and an N-40. The executor reads this as a genuine provider expiry. With Stripe, an expiry webhook cannot arrive while the create call is still running, so the case is theoretical. Leave it as the organizer's call.
8. **nit** `src/test/java/com/agilityhub/core/arch/ArchitectureRules.java:85-90` — `OffsetTime.now`, `Year.now`, `YearMonth.now` and `MonthDay.now` (with or without a `ZoneId`) also read the system clock and are still allowed. They are outside step 1's list, but they are cheap to add.
