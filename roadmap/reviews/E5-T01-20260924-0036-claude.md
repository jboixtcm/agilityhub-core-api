2. **major** `platform/application/jobs/JobRunner.java:208-216` + `TenantRepository.replace` — The reaper can overwrite a run that just finished.
   - **How:** `reap()` reads the `RUNNING` rows, then checks `locks.held(...)`, then calls `runs.replace(...)`. `replace` is an unconditional `findAndReplace` by `_id`.
   - **Scenario:** another instance's run finishes between the read and the `held` check. It has already replaced its row as `SUCCEEDED` and released the lock. The reaper then sees no lease and overwrites the row as `FAILED` with `leaseExpired=true`. It also publishes a second `SchedulerRun` plus a spurious `JobFailed` → N-42. The next tick retakes the occurrence as `CATCH_UP`, so the job runs twice.
   - **Same problem in reverse:** `complete()` of a slow holder whose lease was reaped overwrites the reaper's `FAILED` row. Leases are only renewed between items, never during `plan()` or a single long `apply`.
   - **Rules:** R-15-04 (one execution per occurrence), R-15-06.
   - **Fix:** make both final writes conditional, e.g. `updateFirst({_id, status: RUNNING, holder}, …)`. Publish the events only when exactly one document was modified.

3. **major** `JobRunner.java:213` / `JobRun.finished(...)` — A reaped run keeps `exclusive=true`, so it keeps its slot in the partial unique index `{clubId, job, scheduledFor, trigger}`.
   - **Scenario:** a run that was itself a `CATCH_UP` dies, e.g. the first run after a deploy restart, or the retake from T-15-31 dying again. Its retake is also `CATCH_UP` → `DuplicateKey` → `Optional.empty()`. This repeats on every tick with no `JobRun` and no alert until the next occurrence.
   - **Why it matters:** it contradicts T-15-31/§5 («el següent tick el reprèn amb `CATCH_UP`»). `T_15_03` asserts this silent empty result as intended ("a retake that loses the race").
   - **Fix:** set `exclusive=false` when reaping, so the slot is freed only for lease-expired rows. Add a test where a `CATCH_UP` run dies and is retaken.

4. **minor** `platform/application/jobs/SchedulerTick.java:43` — `jobs.tick.overrun` does not measure overruns.
   - The 55 s tick lease is never renewed, so a tick lasting more than 60 s does not block the next minute's tick on another instance. In-process, Spring's single scheduler thread silently skips the next fire.
   - The counter only increments when two instances contend within the same minute. With several instances that happens every minute, whether or not any tick overran.
   - **Rule:** R-15-01 says the metric rises when a tick lasts more than a minute and the next is skipped.
   - **Fix:** renew the tick lease per club, and/or count in-process overlap (an `AtomicBoolean`). Do not count same-minute contention as overrun.

5. **minor** `JobRunner.scheduled` / `JobOccurrences.lastDue` — There is no baseline for a club or job with no run history.
   - On the first tick after a club is created, or after E5-T05 deploys a process, `lastDue` returns the latest past occurrence.
   - For `week-opening` (`HOURS_24`) that gives `SKIPPED{MISSED_WINDOW}` + `JobFailed` → N-42 for every club, unless the deploy lands within 24 h of Sunday 20:00. The same happens for `risk-review` on a later day. The `UNLIMITED` jobs run an immediate `CATCH_UP` at deploy time.
   - The spec is silent on this. It is worth an organizer decision before E5-T05, e.g. no prior `JobRun` → treat as the first occurrence and don't alert.

6. **minor** `clubs/bookings/application/BookingContractAccess.java:26-38` — The ownership guard compares `booking.memberId()` with the caller's `memberId` only.
   - S08 §6 and the operation descriptions say «MEMBER own **or family group**», so a family-group member currently gets 404.
   - Acceptable for a stub, but the published description and the guard disagree. Note it as a hand-off to E5-T02 or implement the group check now.

7. **minor** `JobRunner.execute` for dry runs — A dry run acquires the `{clubId}:{job}` lease, which is a write to `job_locks`.
   - `T_15_06` explicitly removes `job_locks` from the before/after comparison. A running dry run also makes a concurrent scheduled run record `SKIPPED{LOCKED}`.
   - R-15-08 says «no s'escriu res» except the `JobRun`.
   - Either state this as an accepted exception in the report, or skip the lease for dry runs.
