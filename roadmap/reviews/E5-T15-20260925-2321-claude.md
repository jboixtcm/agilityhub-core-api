# Review E5-T15 — minor issues

## Findings
1. **minor** `src/main/java/com/agilityhub/core/clubs/scheduling/application/RiskReviewQuery.java:97`: E37 can still promise a cancellation that P2 will not make.
   - **What is wrong:** `reviewWillRun = reviewOn && reviewAt.isAfter(now)` ignores classes that start before their own day's review time. P2 skips any class that has already started (`RiskReviewJob.java:55` and `:74`, `skippedStarted`).
   - **Example:** a 07:00 class with `classes.riskReviewTime=07:30` and 0 registrants shows `WILL_CANCEL` («s'anul·larà … a les 7:30») until 07:00, but P2 never cancels it. With `autoCancelSameDay=false` the same happens with `WILL_REVIEW`.
   - **Why it matters:** this is the case E37 exists to prevent (S15 §6: «només quan P2 de debò revisarà la classe»). It only needs a parameter value that D11 allows editing.
   - **Fix:** use `reviewOn && reviewAt.isAfter(now) && c.startsAt().isAfter(reviewAt)`, and add that row to `RiskReviewQueryTest.T_15_15_…`.
2. **minor** `RiskReviewQuery.java:57`, together with S14 R-14-01 / §7: switching off the `risk-review` job does not invalidate the D1 cache.
   - **What is wrong:** S14 invalidates the dashboard only on `ParameterChanged{classes.risk*, dashboard.*}`. After `PUT /jobs/risk-review/switch {enabled:false}`, D1 keeps saying `WILL_CANCEL` for up to 60 s.
   - **Evidence:** the IT hides this by calling `dashboards.invalidate(CLUB)` by hand. The executor mentions it in Assumption 5 but raised no proposal.
   - **Fix:** add a proposal to `MESSAGES.md` to add `jobs.riskReview.enabled` to the S14 §7 invalidation list, or leave it as an accepted limitation.
3. **nit** `src/main/java/com/agilityhub/core/clubs/catalogs/application/CatalogService.java:182-183`: the `stopsBeingReservable` Javadoc is out of date.
   - It still says «this side answers `409 STALE_VERSION`, or the retried booking sees the ring».
   - Since step 1, the ring change is retried and answers `422 RING_HAS_BOOKINGS`. It is `409` only once the retry budget runs out.
   - **Fix:** update the sentence to match `update()`'s Javadoc.
4. **nit** `CatalogService.java:116`: the ring-change backoff is hard-coded.
   - It uses `Thread.sleep(ThreadLocalRandom…)`, while step 5 made the `SchedulingTransactions` backoff injectable. As a result, `CatalogServiceRetryTest` really sleeps 100–300 ms in two of its tests.
   - The 112 / 11000 / `TransientTransactionError` `conflict()` check now exists three times: `CatalogService:277`, `SchedulingTransactions:56` and `TrainingTransactions.retryable`.
   - **Fix (optional):** inject the backoff the same way, and move `conflict()` into `shared.application.TransactionRetries`.
5. **nit** `src/test/java/com/agilityhub/core/clubs/activities/application/ActivityIT.java` `T_07_16_T_07_18_theAppRowsCarryStartAndEndTimesNullWhenAbsent`: the name cites a spec test that it does not assert.

   - The rule the test does assert is R-07-13 (row hours), so AGENTS rule 5 asks for a name after the rule it asserts.
   - **Fix:** rename it to `T_07_16_R_07_13_…`.
6. **nit** `src/test/java/com/agilityhub/core/clubs/bookings/api/CleanupJobIT.java` `T_15_27_aFailedRunWhoseReleaseNeverHappenedDoesNotKeepThePlatformCycle`: the test fakes the failure by hand.
   - It writes `status=FAILED` into `job_runs` directly, instead of letting `JobRunner` commit FAILED with a `Job.failed` hook that throws (the path swallowed at `JobRunner:235-237` that step 13 names).
   - The takeover logic does not depend on how the claim was left behind, so the proof holds. It just does not cover the runner path.
