# Review E5-T12 — needs changes

## Findings

1. **major** `src/main/java/com/agilityhub/core/migration/application/PlayoffPlanner.java:160` — Removing `persones.csv` after an import silently overwrites the principal’s person. With fixture records 62/82, their different NIFs produce separate entries in `people`, but both resolve through `memberBySource` to the same stored member ID. Apply writes both changes sequentially, replacing the principal’s fields with record 82’s fields. This violates R-18-04(f) and R-18-14. Reject removal/change of an existing merge before planning writes, and enforce one member change per destination ID. The test at `PlayoffMigrationIT.java:171` currently accepts 188 changes without checking distinct IDs or applying this plan; replace that assertion with a preservation regression test.

2. **major** `src/main/java/com/agilityhub/core/migration/application/PlayoffPlanner.java:83` — Unsupported transitions can still block the entire import through dependent records. After importing the fixture:
   - Marking principal 62 `LEFT` skips it, but joined record 82 then fails at line 155 because its principal is absent from `people`.
   - Marking family holder 61 `LEFT` skips it, but `groups()` fails at line 340 because only one group member has a planned change.

   These generate blocking `INPUT_SCHEMA_MISMATCH` or `FAMILY_GROUP_MEMBER_ALREADY_IN_GROUP` errors, so unrelated records are never applied. This contradicts the round-2 requirement to leave rejected records untouched and apply the rest. Make dependent joins/groups aware of preserved records and add dry-run/apply tests for both cases.

3. **major** `src/main/java/com/agilityhub/core/migration/application/PlayoffPlanner.java:133` — Rejection protects a source row, not its destination member. Import two same-NIF records with a valid email on the older record, then change that older record to `LEFT`. The older row gets `REEXECUTION_UNSUPPORTED`, but the other alias bypasses `importedWithAccess()` because it is not `sourceIds.playoffMemberId`. It subsequently resolves to the rejected member’s ID and plans member and identity updates. The supposedly untouched member/membership can therefore change, violating R-18-14 and the round-2 preservation requirement. Track protected destination IDs and prevent aliases from scheduling writes to them; test byte-for-byte preservation with an existing same-NIF pair.

4. **minor** `src/main/java/com/agilityhub/core/migration/domain/MigrationReport.java:21` — The summary always says “the rest is applied” whenever an unsupported row exists, including dry runs and reports containing blocking errors. A mixed-error report consequently claims both “no changes applied” and “the rest is applied.” Under R-18-15, distinguish proposed changes, blocked application, and completed partial application; assert the wording for each case.
