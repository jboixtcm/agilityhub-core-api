# Review E5-T07 — needs changes

## Findings

1. **major** `src/test/java/com/agilityhub/core/clubs/census/application/DemoPlanningSeedIT.java:40`, `DemoScenarioSeedIT.java:47`: the report says the `BookingFixtures.impersonating:126 NoSuchElement` flake is "Not explained" and that "Nothing in the test sources deletes `signing_keys`". That is wrong.
   - Both seed ITs empty every non-`system.` collection in `@BeforeEach` (`mongo.remove(new Query(), collection)`), and that includes `signing_keys`.
   - `AbstractIntegrationTest` sets `core.oidc.master-key`, so `SigningKeys` is not ephemeral. It creates the ring only in its constructor (`SigningKeys.java:37`) and later reads it on every call with `repository.findById("active").orElseThrow()` (`:43`).
   - So any cached context built before a Demo*SeedIT run fails on its next token signing (`impersonations.create`, `BookingFixtures:126`) with `NoSuchElementException`. This depends on class order, which matches the CI pattern (Linux filesystem order).
   - The Objective explicitly lists this flake. Fix at the root: exclude `signing_keys` (and other bootstrap-owned collections) from the wipe, or have `SigningKeys.ring()` re-initialize a missing ring in local/test. Then add a counterfactual run (Demo*SeedIT before BookingsIT, same context) to prove it.
2. **minor** `src/test/java/com/agilityhub/core/clubs/training/api/TrainingLanesOffIT.java:169,181,193`: tests named `T_09_28_*` test S06 ring blocks. Spec T-09-28 is the **S05** case (`allowsFreeTraining=false` with a live booking); the block case is T-09-20/T-09-21. AGENTS rule 5 requires tests named after the spec id they really assert. Rename them to `T_09_21_…` or `R_09_13_…`.
3. **minor**, scope: R-09-13 names **S05** as well (deactivate a ring, or remove `allowsFreeTraining`). `CatalogService.update` (`CatalogService.java:97-103`) reads `futureTrainingBookings` and writes only the ring. A concurrent training booking reads `ring.active()/allowsFreeTraining()` and writes only its own documents, so the same write skew step 4 fixed for blocks and classes remains here. Task step 4 only named blocks and classes, so this is not a blocker. It should be recorded as a follow-up, or closed now by having the booking read the ring in a way that conflicts, or by having S05 touch the ring-day docs of the booking window.
4. **minor** `TrainingBookingService.java:92-94` (`day:` lane) + `RingDayLockRepository.touch`: the ring-day document makes **every** training booking on one ring and day conflict with every other booking on that ring-day, even for different slots. The new `day:` lane then serializes all training bookings of one club-day inside the process.
   - That is coarser than "keyed per aggregate", and `slot:` becomes redundant.
   - The lanes-off measurements only cover single-slot bursts. The report's claim that "S09 bursts end without exhaustion" does not cover a Sunday-opening burst on different slots of one ring-day, which is where the new hot spot would show up as `409 STALE_VERSION` with the lanes off.
   - Suggest either (a) adding a lanes-off burst of 20 bookings on 20 different slots of one ring-day and reporting its STALE_VERSION count, or (b) using a per-ring-slot document (a block touches each grid slot in its range; blocks are short and single-day) and dropping the `day:` lane.
5. **minor** `src/test/java/com/agilityhub/core/support/AbstractIntegrationTest.java:64-72`: the outbox fix is reasonable and well evidenced (counterfactual `05` fails the CI way, control `06` passes). It is still a test-side cleanup, not a change to the dispatcher.
   - The report should say in one line that production is unaffected: one real clock, and a background dispatcher always drains oldest-first.
   - It should also say that the discard deletes PENDING rows of **all** tenants before each test, so no IT may rely on events published in an earlier test or in `@BeforeAll`. Today only `LearnImportIT` uses `@BeforeAll`, and only to generate a file.
6. **nit** `RingBlockService.java:105-108`: `lockDay` uses `from`'s local date only. That is correct because blocks and activities are single-day within opening hours (`validate`), but it deserves a one-line comment next to `lockDay`, or a guard that `to` falls on the same local date.
7. **nit** `ActivityRegistrationService.java:95-96`: `cancelMatching` lanes include activities of already-CANCELLED registrations. This is harmless but broader than needed. Filtering on `state()!=CANCELLED` as the loop does would narrow it.
8. **nit** Report Question 1 (the `ring_day_locks` collection) was correctly proposed rather than silently added. It should also appear in `roadmap/MESSAGES.md` for `@organizer` so it is not lost. That file has a 15-line addition I did not cross-check.
