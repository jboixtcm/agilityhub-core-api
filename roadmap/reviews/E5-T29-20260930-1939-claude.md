## Findings
1. **nit** `src/main/java/com/agilityhub/core/platform/application/jobs/JobAdminService.java:124-128` — **A retried trigger can leave a manual run with no `JOB_TRIGGERED` entry.**
   - **What happens:** the retry path returns the earlier run without checking that it was audited. On this path (`NOT_SUPPORTED`), `AuditedAspect` writes the entry after `proceed()`, outside any transaction. If that audit write is what failed on the first attempt, the answer is a 500 and the key is released. The retry then answers the unaudited run, and the run stays without its `JOB_TRIGGERED` entry for good.
   - **Why it matters:** T-15-08 / R-15-09 require that entry. The failure is unlikely: it needs a transient error in the one write right after the run committed.
   - **Suggested fix:** in the retry branch, write the entry when none exists for that `runId`. Or log it in `docs/INCIDENCIES_OBERTES.md`.
2. **nit** `src/main/java/com/agilityhub/core/shared/application/IdempotentOperation.java:11` — **The key's 24 h lifetime is defined twice.**
   - `KEY_LIFETIME` is a new constant, but `IdempotencyRepository` still hard-codes `Duration.ofHours(24)` in its TTL index (`:25`) and in `claim` (`:32`).
   - Also, the run lookup compares the run's `startedAt` with the window, while the key's expiry is measured from the record's `createdAt`. That leaves a window of a few milliseconds in which an expired key would get the old run back instead of starting a new one. It has no practical effect.
   - **Suggested fix:** make `IdempotencyRepository` use the shared constant, so the two rules cannot drift apart.
3. **nit** `src/test/java/com/agilityhub/core/clubs/training/api/TrainingRegisterContractIT.java` (the round-2 `…T_09_30_theRegisterSearchesTheMemberTheDogAndTheRing` and `…T_09_27_theBlocksSearchTheRingAndTheNote`) — **The T-09-30 tag has no tenant assertion behind it.**
   - T-09-30 is the S09 tenant and role test («recurs d'un altre club → 404»). The search tests carry its id but never check the tenant boundary.
   - The blocks now join `rings` in a new `$lookup`. Isolation is correct when reading the code (the tenant `$match` goes first, and the join matches `clubId`).
   - **Suggested fix:** add one assertion that another club's booking or block, whose member, dog or ring name matches `q`, is never returned. That makes the tag earn its name (AGENTS rule 4).
