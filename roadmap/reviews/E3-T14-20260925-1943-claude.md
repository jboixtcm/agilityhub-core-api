## Findings
1. **nit** `src/main/java/com/agilityhub/core/platform/application/definition/ClubDefinitionWriter.java:173-182`: the "order" line also prints when a provider is added or removed.
   - **The problem:** `reordered` compares the whole name lists, so it is `true` when the set of providers changes, not only when their order does. Enabling `STRIPE` (as in `R_04_27_T_17_01_clubApplyRefreshes…`) prints `paymentProviders.STRIPE: null -> {"enabled":true}` and also `paymentProviders order: [SEPA_XML, MANUAL] -> [SEPA_XML, MANUAL, STRIPE]`.
   - **Impact:** the change count is right (1). Only the dry-run text is misleading.
   - **Why it matters:** R-17-01 dry-run readability.
   - **Suggested fix:** compute `reordered` only on the names both sides share: `names(before).retainAll(after names)` compared with `names(after).retainAll(before names)`. Or print the order line only when the two key sets are equal.
2. **nit** `src/main/java/com/agilityhub/core/clubs/census/application/SignupService.java:523-529`: an untested branch.
   - **The problem:** the report's round-2 assumption says an `ACTIVE` member without a `paymentMethod` gets `paymentMethods: []` in an add-dog view. No IT covers that case; the add-dog IT always has `MANUAL`.
   - **Why it matters:** imported members (migration) can plausibly be `ACTIVE` without a method, and the web (E3-W11) is told to render this list read-only.
   - **Suggested fix:** one extra assertion in `R_04_19_T_04_20_anAddDogView…`: `$unset` `paymentMethod` on the member, then expect `[]`.
3. **nit** Test id: R-04-27 in S04 §4 covers tenant, idempotency and transactions, not cache freshness. `R_04_27_T_17_01_clubApplyRefreshesTheSignupFormsPaymentMethods` therefore cites a rule that does not state what the test asserts.
   - **Not the executor's fault:** the organizer's round-2 point 3 prescribed "R-04-27".
   - **Organizer action:** if the organizer wants the rule id to match, R-04-10 (the offer) is the closer rule.
