# Review E7-T02 — needs changes

## Findings

1. **major** `src/main/java/com/agilityhub/core/clubs/messaging/persistence/NotificationRepository.java:115` — An early email webhook can be overwritten by the send response. `emailOutcome()` changes a claimed delivery to `DELIVERED` or `FAILED` without clearing its lease; subsequent dispatcher settlement matches only the claim token and writes `SENT`, clearing the bounce error. This violates R-11-08 and S11 §5. Preserve webhook terminal states while recording acceptance metadata, as the existing SYSTEM `finish()` path does. Add engine tests where the webhook arrives before `EmailSender.send()` returns.

2. **major** `src/main/java/com/agilityhub/core/clubs/messaging/application/engine/NotificationDispatcher.java:121` — The exception handler covers both provider submission and database settlement. If the provider accepts a message but the settlement transaction fails—for example, an outbox write fails—the handler treats it as a retryable **send** failure. The delivery remains queued and the provider receives it again. This breaks R-11-09 and the task’s no-duplicate requirement. Separate provider failures from persistence failures; retry settlement using the accepted result. Add a test that fails persistence after provider acceptance and asserts one provider call.

3. **major** `src/main/java/com/agilityhub/core/clubs/messaging/application/engine/NotificationDispatcher.java:154` — SMS-cap handling commits its effects separately. `SKIPPED_CAP` releases the claim before the forced email is added; a subsequent failure permanently loses that fallback. Likewise, `firstCapNotice()` persists the monthly marker before the transaction publishing `SmsCapReached`, so publication failure suppresses N-49 for the rest of the month. This violates R-11-06 and AGENTS rule 8. Commit the skipped delivery, fallback deliveries, monthly marker and outbox event atomically, with failure-injection tests.

4. **major** `src/main/java/com/agilityhub/core/clubs/messaging/application/engine/NotificationDispatcher.java:179` — Concurrent cap fallbacks can enqueue duplicate emails. Two dispatchers can claim different SMS phone deliveries of the same notification, both read no existing email, and both append it through the unconditional `$push` in `NotificationRepository.addDeliveries()`. Both emails can then be sent. This violates R-11-06/R-11-09. Make fallback insertion atomic and unique per normalized destination. T-11-30’s separate-notification concurrency case does not exercise this; add a same-notification, multiple-phone test at the cap.

5. **major** `src/main/java/com/agilityhub/core/clubs/messaging/persistence/NotificationRepository.java:103` — Existing E4–E6 SMS intents never become eligible for dispatch. Their E7-T01 shape has `target: null`, retains phones in `recipientPhones`, and lacks a due timestamp; `claimDue()` excludes them. No conversion expands those phones into due deliveries, and `LegacyNotificationRows.upgrade()` still produces the same null-target shape. This leaves the Objective, step 10 and Definition of Done partially unmet. Add an idempotent handoff for existing queued intents and test that each stored phone receives exactly one delivery.

6. **major** `src/main/java/com/agilityhub/core/clubs/messaging/application/engine/NotificationDispatcher.java:183` — Forced cap emails ignore `Account.emailStatus`. A SYSTEM-email bounce marks the account without marking `Member.contactEmails`; initial engine resolution correctly suppresses that address, but `forceEmail()` checks only the member mark and queues it again. This contradicts R-11-08 and the report’s stated reconciliation of both suppression marks. Reuse the combined suppression check for fallback delivery creation and test an account-only bounce followed by an SMS-cap fallback.

7. **minor** `src/main/java/com/agilityhub/core/clubs/messaging/application/engine/NotificationEmailRenderer.java:38` — Every email action links to bare `/notificacions`, discarding its action type and subject parameters. N-15 therefore loses its seat-claim destination, and N-08a loses the preselected dog. R-11-11 explicitly requires email actions to become deep links to the corresponding route. Generate links from the native action and parameters, and assert those destinations in renderer tests.

8. **minor** `src/main/java/com/agilityhub/core/clubs/messaging/application/engine/NotificationEngine.java:280` — A family member booking another member’s dog receives an N-04 with an empty dog name. `BookingNotificationFacts` adds the booker with the owner’s `dogId` but no dog values; rendering searches only the recipient’s own dogs, as returned by `MessagingCensusDirectory`. The removed booking implementation resolved the booking’s dog independently. This regresses R-11-05 and step 10’s preserved observable outcome. Resolve subject-dog details independently of the recipient and test the rendered confirmation for both owner and family booker.
