## Findings

1. **minor** `src/main/java/com/agilityhub/core/clubs/messaging/application/engine/TemplateValidator.java:79-86` together with `TemplateUpgrade.java:236-241` — D9 still accepts upper-case `gender` select keys, so the start-up correction keeps rewriting club texts on every deploy.
   - **What happens:** D9's save and preview never check the keys of a `{gender, select, …}`. An admin can save `{gender, select, FEMALE {Benvinguda} other {Benvingut}}` today and get 200. The preview and real deliveries then render `other` for every woman, because the engine lower-cases `gender`. At the next restart, the upgrade silently rewrites the club's text, with an event and an audit entry by `system:template-upgrade`.
   - **Why it matters:** the link sentence and `{class_description}` can no longer be saved, because D9 refuses them, so for those two the upgrade really is a one-off migration. For `gender` keys it is not: the bug can be re-created through the API. The admin's preview disagrees with what is delivered after the restart. This is S11 §10 (lower-case `gender`) plus R-11-12's "editing, preview and delivery read one list".
   - **Suggested fix:**
     - either lower-case the `gender` keys in `MessageTemplateService.clean`, using the same `TemplateUpgrade.lowerGenderKeys`, so a save stores what the upgrade would;
     - or refuse them with `TEMPLATE_SYNTAX_ERROR`.
     - Add a test: PUT with `FEMALE` → stored as `female`, or 400.

2. **nit** `TemplateUpgrade.java:193` — the event's `actorAccountId` is `"system:template-upgrade"`, which is not an account id.
   - **Why:** CATALEG_ESDEVENIMENTS (header) defines the envelope's `actorAccountId` as an account. The codebase's other system paths put `null` there with `origin = SYSTEM`: `MessageTemplateService.changed` (`:338`) and `JobRunner`'s `SchedulerEvent`. The executor's assumption R2-3 says so too.
   - **Risk:** today nothing consumes `MessageTemplateChanged`. But consumers that store `event.actorAccountId()` as an account reference (for example `AttendanceConsumers.java:51`) show where a future template-cache or audit consumer could resolve a non-existent account.
   - **Fix:** either have the organizer confirm that E81's "actor `system:template-upgrade`" is meant to go in the envelope, or publish `null` + `SYSTEM` and keep the process name in the audit entry. D9's «last change» reads the audit entry, not the event.

3. **nit** `src/main/java/com/agilityhub/core/platform/application/audit/AuditWriter.java:48-52` — the D9 «last change» now shows a technical string to club admins.
   - Until now, system audit entries had `actorName = null` and `actorRole = SYSTEM` (from `AuditConfiguration`'s provider). The new entries carry `actorName = "system:template-upgrade"`.
   - Unless the web maps `actorRole = SYSTEM` to a localized label (CONVENCIONS_I18N), a club admin will see that raw id under «Darrer canvi».
   - **Fix:** worth one line in `MESSAGES.md` for the web, or document the value in the D9 contract.

4. **nit** `src/test/java/com/agilityhub/core/platform/application/audit/AuditWriterTest.java:39-51` — the new test uses inline fully-qualified names (`java.util.Map.of` ×4, `org.assertj.core.api.Assertions.assertThatThrownBy`). This is the same style point as round 1's nit #8, which this round fixed in the two files it named. Use imports.

5. **nit** `TemplateUpgrade.java:137` / `TemplateUpgradeIT.java:371` — one bad document holds back its whole club.
   - A single template document the converter cannot read makes `findAll()` throw. The whole club is then skipped on every start-up until someone fixes that document, and the WARN names only the club.
   - This meets the organizer's "per club" requirement. Logging the failing document's id is not possible from `findAll`, but a `find` that skips unmappable documents would let the club's other templates be upgraded.
   - Optional; at most, mention it in the report's assumptions.
