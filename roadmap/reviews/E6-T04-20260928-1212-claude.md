## Findings

1. **minor** `src/main/java/com/agilityhub/core/clubs/census/application/DemoSeedCommand.java:61` — Changing the default seed anchor to `nextOrSame(MONDAY)` quietly rewrites the contracts of already-verified tasks.
   - **What breaks:**
     - E4-T05 step 1 fixes the plain `seed:demo` default as "the Monday of the club-local current week".
     - E5-T06 (a) wants the current week validated, so that screens 03/04 have bookable classes.
     - After this change, a plain run on a Tuesday–Sunday leaves the current week with only the two E6 history classes. That breaks both contracts.
   - **Why it goes unnoticed:** `DemoPlanningSeedIT` now forces `--week-start=MONDAY` into every E4 test (see the diff's `args.add("--week-start=" + MONDAY)`), so no test covers the plain command's E4 behaviour any more.
   - **A new, untested path: a backward `--reanchor`.**
     - A plain first run on a Wednesday records the anchor as next Monday. A `--reanchor` later that week (the README's routine for long-lived stacks) computes `previousOrSame`, one week *earlier*.
     - `DemoPlanningService.apply:49` has no guard against an anchor earlier than the recorded one.
     - `DemoPlanningSeeder:79` then validates the first run's draft W+1 (as the new W+2). The D4b draft state is lost and nothing is gained.
   - **Not re-run:** `bin/e3-smoke` and `bin/e4-smoke` call the plain `seed:demo` (e4-smoke parses its `week start`) and were not run against the new default.
   - **Fix:**
     - The organizer should rule explicitly on the anchor change (it goes with the executor's question 4).
     - At minimum, never let `--reanchor` go before the recorded `weekStart` (e.g. `max(previousOrSame(today), recorded)`), and add a test for it.
     - Alternative: keep W = the current week for the E4 planning and anchor only `scenario` on the next Monday.

3. **nit** `src/main/java/com/agilityhub/core/clubs/bookings/application/jobs/NoShowNoticesJob.java:37` — The one-item-per-club-and-day shape has two side effects:
   - **Misleading dry-run count:** the runner counts items, so a dry run always reports `WOULD_NOTIFY: 1`, while the real run reports `{notices: 4, late: 1}`. `[Simula]` therefore shows "1" for four notices, which weakens R-15-08 ("plan = effects").
   - **Unbounded trace:** the framework's 500-item cap on `effects.items` no longer limits the trace, because one item's `detail.attendances` grows with no bound (for example, an unlimited catch-up after downtime).
   - Fix: when `context.dryRun()`, record `notices`/`late` from the plan through the context's recorder, and cap or summarise `detail.attendances`.
