# Review E5-T22: minor issues

## Findings
1. **minor** `src/main/java/com/agilityhub/core/platform/persistence/audit/AuditListProjection.java:37`: the fix for the `INSTRUCTOR` audit origin only changes how entries are read, not where the value comes from.
   - **Where it comes from:** `DomainEvent.Origin` has an `INSTRUCTOR` value (`shared/domain/DomainEvent.java:17`), and `identity/api/CurrentUserFilter.java:27` sets it for every instructor request. CATALEG_ESDEVENIMENTS only allows `APP · BACKOFFICE · SYSTEM · WEBHOOK`, and S14 §3 says the audit uses that same enum.
   - **Effect:** outbox events still carry an origin outside the catalog, and new audit entries keep storing `INSTRUCTOR`. Every reader has to remember to map it.
   - **Rule:** AGENTS rule 2 (closed catalogs). The report states this as Assumption 4 but raises no question or catalog proposal in `MESSAGES.md`.
   - **Fix:** log it in `docs/INCIDENCIES_OBERTES.md` or MESSAGES for a writer-side fix (map instructors to `BACKOFFICE` in `CurrentUserFilter` and `DemoSeedActor`), or ask the organizer to add `INSTRUCTOR` to the catalog.

2. **minor** `src/main/java/com/agilityhub/core/configuration/OpenApiConfiguration.java:145`: exports and `filter-values` still publish a `fields` parameter without `x-fields`.
   - **Cause:** `addListParameters(operation, list.acceptsFields())` runs for every `paged = true` `@ListContract`, and `acceptsFields` defaults to `true`.
   - **Size:** the snapshot has 26 `fields` parameters but only 14 `x-fields`. The other 12 are exports and `filter-values` operations, for example `/activities/export`, `/activities/filter-values`, `/members/export`, `/training-bookings/export` and `/notifications/export`.
   - **Misleading text:** the parameter description (`:189`) says «published in the list operation's x-fields», which these operations don't have.
   - **Why it's hidden:** `ListFieldsContractIT.universalList()` skips `/export` and `/filter-values`.
   - **Rule:** step 4's rule «a list that cannot honour `fields` stops accepting the parameter and publishes no `x-fields`» (CONVENCIONS_API §4) is only applied to the three platform stubs.
   - **Fix:** set `acceptsFields = false` on these operations, or have the customizer publish `fields` only when `x-fields` is present. Also add an assertion that no operation has `fields` without `x-fields`. Can go to INCIDENCIES.

3. **minor** `src/main/java/com/agilityhub/core/clubs/census/application/SignupService.java:597`: the "member without a plan" rule doesn't cover a member whose own plan is no longer assignable (Assumption 2).
   - **What happens:** `GET /signup` shows that member no `current` plan. But `POST /me/dogs/signup` without `planIdRequested` answers `422 PLAN_NOT_AVAILABLE`, not `400 VALIDATION_ERROR/REQUIRED`.
   - **Why it matters:** the OpenAPI changelog and the web note say «Send `planIdRequested` when no plan is current». R-04-09 ties the obligation to having no usable plan.
   - **Fix:** treat `planId == member.planId` with a non-assignable plan like `planId == null`, so it answers 400 `REQUIRED`. Or document the 422 in the changelog and in the `planIdRequested` description.

4. **minor** `src/test/java/com/agilityhub/core/clubs/census/api/SignupPlansFollowUpIT.java:108`: the step-2 IT does not use the Cànic seed's family member, although the task asks for it.
   - **What the test does:** it registers a public `ABONAT` member, then rewrites `planId` to `ABONAT_FAMILIAR` directly in Mongo. `priceId` stays on ABONAT's price.
   - **What's missed:** the real way a member ends up on the family fare (R-04-13 validation) and the quote for a consistent `priceId` are never tested.
   - **e3-smoke:** it does run add-dog for a real family member, but does not check `plans`/`current`.
   - **Fix:** build the member through the family-group signup (or the demo seed), then assert `current` and `planQuotes`.

7. **nit** `src/main/java/com/agilityhub/core/shared/application/contract/ListContract.java:24`: nothing enforces `acceptsFields = false` beyond the contract.
