# Review E9-T03 — minor issues

## Findings
1. **minor** `src/main/java/com/agilityhub/core/courses/application/RingSetupService.java:184-203, 216-219` — `dismantle`, `renew` and `end()` call `setups.replaceActive(...)` (a `findAndReplace` on the setup document) without any write-conflict guard.
   - The same document is also written by P5 f `expire`, by `ringDeactivated`, and by `register`, which replaces the previous active setup. A dismantle or renewal that races one of them and loses gets a raw Mongo `WriteConflict`.
   - Unlike `register` and the new `WriteConflicts` sites, nothing maps it to `409`. `IdempotencyFilter` only retries or replays the routes it lists, so the client most likely gets a `500`.
   - This is the same class of bug that E115 point 6 closed for geometry and course writes ("never a `500`").
   - Fix: wrap the `replaceActive` and `releaseActiveSetup` writes in `WriteConflicts.guard`, answering `409 INVALID_STATE` or `STALE_VERSION`, and add a race test like `T_16_08_aSetupRacingTheDeletionOfItsCourseIsStale`.

2. **minor** `src/main/java/com/agilityhub/core/clubs/scheduling/application/ClassSessionService.java` (patch, `placements.check(edit.placementId, edit.ringId)` on a ring change) and `TemplateService.patchClass` — a class keeps its planned `placementId` when `COURSES` is switched off. Changing only its `ringId` then calls `ClassPlacements.check` with the kept id.
   - The result is `400 VALIDATION_ERROR {placementId, MODULE_DISABLED}`, about a field the client cannot see: R-16-15 says "S06/S07 ometen `placementId`", and `SessionProjection:75` hides it.
   - The client can only get past it by sending `placementId: null`, which nothing documents.
   - Fix: on a ring change with `COURSES` off, skip the check (or clear the stale placement). Extend the end of `PlanningIT.T_16_20_…` to cover it.

3. **minor** `src/main/java/com/agilityhub/core/clubs/training/application/RingSetupNotificationFacts.java:34` — the N-31 `level` variable joins only the club `levelIds` names (`RingSetupPort.Setup.levelNames`).
   - With `levels.enabled = false`, or a setup that only names an `agilityhubLevel`, `level` renders as `""`.
   - Yet R-16-09's `levelLabel` (`LevelLabels.label`) falls back to the AgilityHub level, and R-16-15 says that is the only level left when levels are off.
   - Fix: expose the AgilityHub-level fallback through the port, or pass `levelLabel`. Assert it in `TemplateVariableParityIT.T_16_13_…`.

4. **minor** `src/main/java/com/agilityhub/core/clubs/scheduling/application/SessionProjection.java:66-75` — R-16-13 says `ClassSession.placementId` «Recorregut previst» is shown, when `showSetupToMembers` is on, "com a línia informativa a 07". The member projection never carries the planned placement.
   - The report's assumption re-reads this as `GET /me/ring-setups`, which is the ring's *active* setup, a different thing from the class's *planned* placement. T-16-20's wording («A la pista hi ha muntat») supports the assumption, R-16-13's does not.
   - Fix: put this spec ambiguity to `@organizer` explicitly in MESSAGES rather than leaving it as a silent assumption.

5. **minor** `src/main/java/com/agilityhub/core/courses/api/CourseContracts.java:120-141` and `src/test/java/com/agilityhub/core/courses/api/PlacementsIT.java:200-202` — R-16-06 and T-16-17 say an active `RingSetup` on a stale placement shows «Geometria canviada: revisa la col·locació» to instructors.
   - The setup view has no stale indicator. The test only asserts that the setup's `placementId` equals the placement and then reads the placement list. That proves the client can join the two, not that the setup shows the warning.
   - Fix: either add a staff-only `placementStale` to `RingSetup` (an OpenAPI change), or record the "client joins" decision as an assumption for E9-W03.

6. **minor** Model vs spec, not reported:
   - `docs/MODEL_DADES_PLATAFORMA.md:242` says «Un ring **sense** geometria admet només `RingSetup` d'imatge». R-16-07 allows `courseId` without geometry, and the code follows R-16-07.
   - AGENTS.md says the model wins where the two disagree, and the report must say so. Neither the report nor MESSAGES mentions the conflict.
   - The same goes for the two new persisted fields, `courses.references` and `rings.geometryReferences`. They are proposed in MESSAGES, but they ship before the model accepts them. The organizer should accept or reject them explicitly.

7. **nit** `src/main/java/com/agilityhub/core/courses/application/RingSetupService.java:106` together with `RingSetupRules.hasViewer` — a setup registered from a placement whose course was soft-deleted meanwhile slips through.
   - `live()` returns `null`, so no course is referenced and no error is raised.
   - The setup is stored with `hasViewer = true`, because only `placementId != null` is checked, while it shows a deleted course.
   - Fix: when the placement's course is gone, answer `404` or `409`, or compute `hasViewer` from the live course.

8. **nit** `src/main/java/com/agilityhub/core/courses/application/PlacementService.java:90-91` — on a `PUT`, the placement's `version` check runs after `check(in)`. A stale `PUT` that carries a `critical` warning therefore answers `422 PLACEMENT_BLOCKED` instead of `409 STALE_VERSION`. The comment on line 109 claims the order "400, 409, then 422". Move the version check before the R-16-05 policy.

9. **nit** `src/main/java/com/agilityhub/core/courses/application/RingSetupService.java:111` — a replaced setup is stored as a plain `DISMANTLED`, with the new registrant as `dismantledByAccountId`. Nothing marks the R-16-07 `DISMANTLED{replaced}` reason. The history cannot tell a replacement from a manual dismantle; only the new setup's event carries `replacedSetupId`. The model has no field for it, so this is acceptable; mention it for D16's history view.
