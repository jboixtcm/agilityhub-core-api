## Findings

1. **minor** `src/test/java/com/agilityhub/core/arch/ArchitectureRules.java:79-84` — **The R-15-22 rule misses `now(ZoneId)`.**
   - **What is wrong:** ArchUnit's `callMethod(Owner.class, "now")` with no parameter types matches only the no-arg overload. So `LocalDate.now(ZoneId.of("Europe/Madrid"))` passes the rule, and so do `LocalDateTime.now(zone)`, `ZonedDateTime.now(zone)`, `OffsetDateTime.now(zone)` and `LocalTime.now(zone)`. Each of these reads the system clock.
   - **Why it matters:** this is the most likely way club-local code would bypass the clock. It breaks R-15-22 / T-15-07 ("time comes from the injected Clock"). No production code has this violation today (`grep '\.now(Zone'` finds nothing), but the gate does not guard against it.
   - **Suggested fix:** add `callMethod(X.class, "now", ZoneId.class)` for each of the five types. Alternatively, use a custom predicate that flags every `now` overload unless its single parameter is a `java.time.Clock`. Then extend `ClockRuleTest` with a `LocalDate.now(ZoneId)` case. `Calendar.getInstance()` could be added in the same change (nit).

2. **minor** `platform/application/jobs/JobRunner.java:178-181` — **A reaped holder keeps applying items.**
   - **What is wrong:** the return value of `locks.renew(...)` is ignored. Once the lease has been reaped and taken by a retake, `renew` returns false (it filters on `holder`), but the slow holder keeps calling `apply` on the rest of its stale plan, at the same time as the retake works through the same scope.
   - **Why it matters:** only the final overwrite is prevented now. Correctness then rests entirely on every future `apply` re-checking its idempotency mark inside the transaction (R-15-04 level 2). The current `plan()`-time scope filter does not cover that. `T_15_31_aSlowCatchUpHolder…` even asserts `applied = 2`, but its plan has one item, so this overlap is never exercised.
   - **Suggested fix:** when `renew` returns false, stop the loop and record a job-level error. `complete()` already handles the closed row, so the run would end without writing anything more. If the organizer prefers to keep the current behaviour, the hand-off to E5-T05 should say explicitly that every `apply` must re-read its mark inside its transaction.

3. **nit** `JobRunner.java:218-227` — **A reaped run is never counted in the metrics.**
   - **What is wrong:** `reap()` does not call `metrics.finished(...)`. Since Round 2, the slow holder also skips it (Round-2 assumption 2). So a lease-expired `FAILED` never appears in `jobs.run.duration{status=FAILED}`.
   - **Why it matters:** assumption 2 calls the reaper's `FAILED` "the outcome of record", but no metric records it. Dashboards and alerts built on that counter will miss dead runs (R-15-10 metrics).
   - **Suggested fix:** record the metric in `reap()` when `complete` returns true.

4. **nit** `JobRunner.java:206` — **A dead run gives a misleading manual result.**
   - **What is wrong:** when `complete` returns false, `run()` falls back to `runs.findById(...).orElse(finished)`. For a manual trigger, the audit entry `JOB_TRIGGERED.after.counters` then shows the reaper's copy of the counters, which is the empty or initial list. The items that were really applied are not reflected.
   - **Why it matters:** this is acceptable per Round-2 assumption 1, but the audited `after` will under-report the applied items.
   - **Suggested fix:** log the local counters in the WARN line, so the applied items are not lost.
