# Review E8-T02 — needs changes

The review covers the round-2 commit `ce145c7`, checked against the round-1 review and the organizer's «Round 2: fix these». All seven points are addressed, and each has a test the counterfactual log `20-before-the-fix-round2.log` shows failing on the old code. The new code introduces the problems below.

## Findings
1. **major** `src/main/java/com/agilityhub/core/payments/application/InvoiceActions.java:126` and `payments/persistence/BillingDocuments.java:108` (`forNextRun`): a manual receipt whose total is negative or zero still keeps `includeInNextRun`, and the next run direct-debits it.
   - **Failure case:** R-12-19's own example, «Ajust quota setembre −30,00 €», on a `SEPA_DD` member with `includeInNextRun: true`.
     - `createManual` stores the flag whatever the sign of the total. `forNextRun()` has no amount filter.
     - `BillingRunService.generate` (lines 115-124) then appends a `SEPA_XML` `Collection` of −3000, and the remittance total drops by 30 €.
     - The in-memory writer accepts this, so no test notices. pain.008 `InstdAmt` must be positive (≥ 0.01 under the EPC rules). Once E8-T03's writer validates the XSD before commit (step 7), that run fails with nothing written, and the same happens every month until an admin cancels the receipt. Incidents must never block a run (R-12-07).
   - **Fix:** set the flag (or pick the receipt up) only when `total.amountMinor > 0`. Otherwise answer `400 VALIDATION_ERROR {field: includeInNextRun}` at creation, or leave the receipt to R-12-16. Add a test with a negative adjustment.
2. **major (or an organizer ruling)** `src/main/java/com/agilityhub/core/payments/application/InvoiceNumbers.java:39` (floor = `highestNumber(series) + 1`): when an admin has cancelled one receipt of a run, rolling the run back loses the run's numbers below that receipt.
   - **Failure case:** run R1 numbers 0912…1026. The admin cancels cash receipt 0950 (`PENDING` → `CANCELLED`, which R-12-19 allows), then rolls R1 back. `blockers()` has no objection, and the counter goes back to 912.
     - On the next generation, `highestNumber` counts the admin-cancelled 0950 (it is not «rolled back»), so the floor is 951. R2 numbers 0951…1065.
     - Numbers 0912–0949 are never issued as live receipts. That is a gap of 38, not «a gap instead of reusing it» as round-2 assumption 1 puts it. If the admin cancelled 1026, the whole block is lost.
     - This contradicts T-12-13 («nova generació reprodueix els mateixos números») and R-12-14 («`nextNumber` torna al primer número del run»). In round 1 the same sequence reissued 0912…1026, with a duplicate `displayNumber` for 0950.
   - **Untested:** `BillingCycleIT.T_12_13_R_12_27_…` cancels `vila` only after the second run.
   - **Fix options (ruling needed):**
     - the floor ignores the numbers inside the run being reissued (`[firstNumber, firstNumber + n)`), and the rollback also marks the run's admin-cancelled receipts as rolled back;
     - or an admin cancellation inside a live run's block makes it non-rollbackable. That needs a reason the closed enum doesn't have, so it is a catalog proposal.
3. **minor** `src/main/java/com/agilityhub/core/payments/application/BillingRunService.java:85`: the `includeInNextRun` receipts skip the simulation entirely.
   - **What D6 shows:** they are not in `invoicesPreview` or the KPIs («Import de la remesa»), so the confirmation «Es generaran {n} rebuts per un total de {import}» does not match the remittance.
   - **Staleness:** a flagged receipt created after the simulation joins the remittance without `SIMULATION_STALE`. Manual numbering only bumps the club's version, and `stale()` ignores invoices. Charges created after the simulation behave the same way; with point 3, a member without a date who was not in the preview can now get a receipt.
   - **No incident checks:** a receipt whose member has since `LEFT`, has no IBAN left (`NO_BANK_ACCOUNT`) or changed method is still remitted with its old snapshot.
   - **Fix:** list the waiting receipts in the simulation (KPIs and incidents), and treat a newer flagged receipt as stale (R-12-07).
4. **nit** `src/main/java/com/agilityhub/core/payments/application/InvoiceActions.java:99` and `BillingDocuments.rolledBack()`: `cancelReason` holds the admin's free text for an admin cancellation, but the code `ROLLBACK` for a rollback. §5 models these as `CANCELLED{ADMIN}` / `CANCELLED{ROLLBACK}`.
   - The case-insensitive guard rejects a genuine admin reason such as «Rollback», with `400`.
   - Deriving «rolled back» from `runId` plus the run's `ROLLED_BACK` status, or from the `FAILED{ROLLBACK}` collection, would avoid overloading a free-text field.
5. **nit** `src/main/java/com/agilityhub/core/payments/persistence/BillingDocuments.java:94-101` (`highestNumber`, `numberedFrom`): neither query can use `invoice_club_series_number`.
   - The index is partial on `status ∈ NUMBERED_STATUSES`, and a `$nor` predicate does not imply that filter.
   - Each number reservation and each `GET /billing/periods/{period}` (through `blockers()`) therefore scans and sorts all of the club's invoices.
   - **Fix:** add a non-partial `{clubId, series, number}` index (not unique).
