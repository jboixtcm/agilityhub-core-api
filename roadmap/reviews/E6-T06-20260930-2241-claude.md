# Review E6-T06: minor issues

## Findings
1. **minor** `src/main/java/com/agilityhub/core/clubs/census/application/FollowupCensusAdapter.java:36-47`, `FollowupService.java` (`search`), `TaskRepository.java` (`idsContaining`): each non-blank `q` runs four unanchored, case-insensitive regex scans: dogs twice (by name, then by note), members, and tasks.
   - The scans load whole documents with no projection. Member documents include contact emails and signup data.
   - The matched ids go into D14's `$match` as `$in` lists with no limit. A one-letter `q` puts nearly every dog, member and task id of the club into the pipeline.
   - This repeats for every list page and every `filter-values` call. The web can call `filter-values` once per field (5) plus the list, so 6 times per search.
   - It is fine at club scale, but cheap to tighten: one dogs query with `$or` over `name` and `instructorNote.text`, `_id`-only projections for dogs and tasks, and names-only for members. If D14 grows, open an INC for an indexed or text-search strategy.
2. **minor** `src/test/java/com/agilityhub/core/clubs/followup/api/FollowupIT.java:810-918`: no test checks tenant isolation at the data level for the new search and facets.
   - FollowupIT already seeds club `s10f-b`: dog «Aliè», task «Aliena», and follow-up row `s10f-f-other` (lines 77, 324-326).
   - Neither new test asserts that `q=Ali`, or the `dogId`/`authorAccountId`/`kind` counts, leave them out.
   - The code is tenant-scoped on every read: the pipeline's first `$match`, `CensusRepository.matching`, and `tenantQuery()` in `TaskRepository.idsContaining` and `FollowupItemRepository.authorNames`. `E6ContractIT` covers role and tenant per route. So this is a coverage gap under AGENTS rule 4, not a bug. Suggest one assertion in each new test.
3. **nit** `src/main/java/com/agilityhub/core/clubs/followup/application/FollowupContractAccess.java:42`: `FOLLOWUP.searchable = [memberName, dogName, authorName, text]`, but only `authorName` is a real field of `followup_items`.
   - The list works only because `FollowupService.dataset` adds `withSearch`.
   - If a future caller builds a dataset from `FOLLOWUP` without `withSearch`, `MongoListRepository.search` falls back to regexes on fields that don't exist, and `q` silently matches only author names.
   - Suggest failing fast, or at least a Javadoc warning on the definition that these entries are labels that allow `q`, not Mongo paths.
4. **nit** `FollowupService.filterValues` (the label fallback, assumption 5): an erased member's `memberId` value gets the raw internal member id as its label.
   - D14 shows those rows with no name, so the filter button would list an opaque id.
   - This matches `/training-bookings/filter-values`, but it is worth confirming with the web or organizer; a neutral label may be better.
5. **nit** Evidence, Verifications 1 and 2: the `echo "exit $?"` runs outside the output redirect, so logs `07` and `10` don't contain the exit code. Only the report and the header of log `08` say "exit 0".
   - The script that produced log `08` (`target/e6t06-summary.py`) is not committed, and neither is the Python comparison behind log `11`. The numbers can't be re-derived from the repo.
   - The totals are plausible (surefire 878, failsafe 1268, 0 failures or errors). Log `07` has no `[ERROR]` or `FAILURE` line. Log `02` shows the 9 claimed failures with the messages quoted in the report.
