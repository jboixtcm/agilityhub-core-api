# Review E8-T11 — needs changes

## Findings

1. **major** `src/main/java/com/agilityhub/core/payments/application/PaymentRefunds.java:169` — **Credit absorption ignores outstanding refund reservations, allowing avoidable overpayment.** Example: capture €12, submit an admin refund of €2 that remains pending, then cancel with CREDIT, creating a €10 credit. A €1 dashboard refund succeeds; `overshoot` is `100 + 1000 − 1200`, so the credit stays €10. If billing consumes that credit before the pending €2 refund succeeds, the member receives €13. Reconciliation then requires an intervention although the credit could have been reduced while unbilled. This violates step 3 and the retained conservation requirement from E8-T09. Include live refund reservations when calculating the credit adjustment and test this billing interleaving. `CapturedPaymentInvariantsIT.java:523` currently disables full conservation checking whenever any dashboard refund exists, masking this case.

2. **major** `src/main/java/com/agilityhub/core/payments/application/PaymentRefunds.java:142` — **The required admin notification or D6 incident is missing.** `intervene()` writes an audit entry and WARN only. Step 1 explicitly requires “audit entry plus the existing notification or D6 incident”; an admin must still discover the problem by inspecting an individual member’s audit trail. The test named `aNeededInterventionTellsTheAdminOnce` checks database audit rows, not notification delivery or incident visibility. The catalog proposal correctly identifies the gap, but does not complete the requirement. Resolve the catalog decision with the organizer, implement the approved signal, and test admin visibility and deduplication.

3. **major** `src/main/java/com/agilityhub/core/payments/application/PaymentRefunds.java:143` — **The recorded intervention amount becomes incomplete when another pending refund subsequently fails.** With €12 captured, a €2 admin refund pending and a €10 compensation pending, failure of the compensation records `owed=1000`. If the €2 refund then fails, the club owes €12, but `compensateRemaining()` returns immediately because `interventionAt` exists, and this guard prevents another intervention audit. Repaying the advertised €10 leaves €2 silently outstanding. This undermines step 1’s requirement to surface necessary manual work. Preserve duplicate suppression while maintaining an accurate outstanding balance and reporting newly owed amounts; add this two-failure sequence to the tests.

4. **minor** `src/main/java/com/agilityhub/core/payments/application/PaymentRefunds.java:175` — **The billed-credit path does not preserve the “WARN once” requirement.** It ignores the return value of `upfront.intervention()` and always calls `warnIntervention()`. The existing point-3 test’s successive €5 and €3 dashboard refunds therefore emit two intervention WARNs for the same payment. Step 5 is tested only through the guarded compensation path. Keep the incremental audit entries, but guard the intervention WARN on the first persisted transition and extend the log-capture test to billed credits.
