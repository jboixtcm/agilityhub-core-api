## Findings

1. **minor** `src/main/java/com/agilityhub/core/clubs/common/application/ExpirationsJob.java:22` and `:34`: P5 sends each item back to its step by `JobItem.entityType`, and the constructor refuses two steps with the same `entityType`.
   - **Why:** `entityType` is also what R-15-21's run sheet links to, so it is not a good routing key. The real steps a–g will collide on it:
     - step d (`SignupPendingAging`, one per club and day) and step g (`Club.usage.smsMonthKey`) are both club-level items. The unit test itself gives step g `"Club"`;
     - step c (leaves) and step d are both about `Member`.
   - **Result:** the E8/E9 steps would need made-up entity types, or a rework of this dispatch.
   - **Fix:** route by action instead. Each step owns distinct actions in R-15-15's dry-run list (`EXPIRE_CHECKOUT`, `WARN_PACK`, `LEAVE`, …). Alternatively, the step could declare the actions it owns and the constructor could refuse overlaps. Pin the rule in `ExpirationStep`'s Javadoc before the next step arrives.

2. **nit** `src/main/java/com/agilityhub/core/shared/api/IdempotencyFilter.java:235-236`: when the original failure is an `ApiException`, a failing `records.abandon` is only added as suppressed.
   - **Why:** `ApiExceptionHandler` logs an `ApiException` at DEBUG, with its code only. The suppressed failure is therefore never logged.
   - **What goes wrong:** the key's claim then stays for up to 10 minutes (`CLAIM_LEASE`), every retry gets `409 IN_PROGRESS`, and nothing in the logs explains why. Before this change the abandon failure surfaced as a logged 500.
   - **Fix:** log a WARN (record id and club only) when `abandon` or `held` fails, in addition to the suppression.

3. **nit** `src/main/java/com/agilityhub/core/payments/application/CheckoutService.java:63-69`: `catch (RuntimeException fenced)` catches any failure of `abandon`, not only the key fence (`IDEMPOTENCY_KEY_REUSED`).
   - **What goes wrong:** a Mongo error or exhausted write-conflict retries inside `abandon` is logged as «…after the checkout's key was taken over», which misleads operations.
   - **Fix:** use that wording only for `ApiException` with code `IDEMPOTENCY_KEY_REUSED`, and a neutral wording otherwise.

4. **nit** `src/main/java/com/agilityhub/core/payments/application/PaymentProvider.java:40` and `FakeCheckoutGateway.java:32`: the timeout contract relies on the provider declaring its own timeout.
   - **The gap:** `callTimeout()` is only declared. The startup check (`PaymentProviderTimeouts`) cannot tell whether E8's HTTP client really uses that value.
   - **Fix:** add one sentence to the contract Javadoc: the adapter must build its client's connect, read and retry budget from `callTimeout()`. A contract test in E8 can then assert it.

5. **nit** `src/test/java/com/agilityhub/core/payments/application/PaymentProviderContractTest.java:25,34`: both tests are named `T_04_22_…`, but T-04-22 covers R-04-26's checkout flow, not the §7 timeout.
   - **Why:** CONVENCIONS_API §7 has no test id. The report handles the same situation for #8 by saying so; here the name implies coverage T-04-22 does not have.
   - **Fix:** use a task-based name, as `IdempotencyIT` does, or add a one-line Javadoc note explaining the choice.

6. **nit** Evidence: the final `./mvnw -q clean verify` (log `12`) ran before the last change.
   - **What changed after it:** the `PaymentProvider` class Javadoc and one assertion in `PaymentProviderContractTest`.
   - **What was re-run:** only three unit classes (log `14`).
   - **Risk:** low, and the report states this openly. Still, AGENTS says to run the full `clean verify` on the final tree, and CI on `main` is the only proof for the committed state.
