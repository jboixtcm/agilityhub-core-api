# Review E8-T12 — needs changes

## Findings

1. **major** `src/main/java/com/agilityhub/core/payments/application/PaymentRefunds.java:232` — **Shared checkouts can still accept refunds beyond the remaining capture.** External reservations are allocated using captured minus settled amounts, ignoring each row’s local reservations. Example: one €24 capture covers rows A and B (€12 each); A has a local €12 refund pending; another €12 dashboard refund becomes pending. `externalReserved()` assigns the dashboard reservation entirely to A, leaving B apparently refundable for €12. `upfront(B)` therefore accepts another refund, reserving €36 against €24. This leaves step 1 and the conservation invariant incomplete. Enforce a transactionally serialized allowance across the whole payment intent, with consistent allocation between reservations and settlement. Add a shared-checkout regression with overlapping local and external pending refunds; the new tests cover one row only.

2. **major** `src/main/java/com/agilityhub/core/payments/application/PaymentRefunds.java:214` — **Late-refund interventions can demand money already repaid through Stripe.** `reconsiderLate()` always reports the original operation amount. For an expired €12 checkout whose automatic refund is deferred, a €12 dashboard repayment leaves nothing owed. However, its unlinked success webhook still reaches `settled()`’s empty `upfront.forIntent(intent)` lookup and fails at line 403. When the automatic refund subsequently exhausts refusals because the capture is already refunded, the new path emits N-55 demanding another €12. This violates S12’s E101 requirement that intervention amounts represent the current outstanding balance. Reconcile external refunds against the late capture through its operation/provider reference, subtract settled and pending amounts, and close the balance at zero. Test partial and full dashboard repayment before late-refund exhaustion.
