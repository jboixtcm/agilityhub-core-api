   - When a club's part of an `ACCOUNT` request runs without completing the request (`completes == false`), the executor pushes that club's files into `filesPending`, pseudonymises the DB rows (`photoFileKey` removed, `files[].removedAt` set) and sets the status back to `SCHEDULED`.    - `ErasureFilesCleanup.clean` only acts on `ERASING` requests, and so does the daily retry (`ErasureRequestRepository`: "stuck in `ERASING`").
   - So the new route takes a `BLOCKED` request with `erasedClubIds = [A]` and non-empty `filesPending` to `CANCELLED`, and nothing ever deletes club A's dog photo, documents or task attachments. The DB says they were removed. Round 2 point 5 says "the clubs already erased stay erased", and R-14-15 says "esborrat d'S3 per un consumidor amb reintents".
   - `R_14_14_thePlatformCancelsAnAccountRequestBlockedHalfway` puts no file in club A, so it cannot catch this.
   - Fix: on cancel, if `filesPending` is non-empty, hand the files to the cleanup. For example, let `clean()` (and the daily retry) also process a `CANCELLED` request with `filesPending` without moving it to `ERASED`, or publish a cleanup event per club on `PARTIAL`. Then extend the IT: give club A a dog photo and assert it has left the store after the cancel.
   - Related, from round 1 but now permanent: while an `ACCOUNT` request waits or is `BLOCKED` between clubs, the erased clubs' files stay in S3 indefinitely.
