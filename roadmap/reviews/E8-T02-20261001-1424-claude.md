# Review E8-T02 — needs changes

## Findings
1. **major** `src/main/java/com/agilityhub/core/platform/persistence/ClubRepository.java:57`: a new counter key always starts at 1 once the club has any counter. The imported `billing.nextNumber` is only used while there are no counters at all.
   - **Failure case:** the series stays the same but the counter key changes. This happens when someone toggles `billing.invoiceResetYearly` from D11 (key `"2026"` becomes `"{YYYY}"`, or the reverse). The run then numbers `2026-0001…` again, which collides with live invoices of that series.
   - **What the user sees:** the duplicate key hits the partial unique index. `TransactionRetries.conflict` treats `DuplicateKey` as a retryable conflict, so after 6 attempts the run or the manual invoice answers `409 STALE_VERSION`, on every attempt from then on. If the series started at the imported 912, the reused range 1–911 even succeeds silently. Either way it breaks R-12-08 («Mai es reutilitza un número»).
   - **Fix:** seed a new key from the highest number already issued in the resolved series (excluding rollback-cancelled invoices), or from the other key's counter when the series is identical.
2. **major** `src/test/java/com/agilityhub/core/payments/domain/InvoiceArithmeticTest.java:30`: T-12-04 is only half-tested. Its yearly-reset half asserts `counterKey` strings, not numbers.
   - Nothing proves «canvi d'any amb `resetYearly` → 2027-0001; sense → continua» through the real counter (`InvoiceCounters`/`ClubRepository.reserveInvoiceNumbers`).
   - A grep of `src/test` for `2027-0001`, `reserveInvoiceNumbers` or `billing.counters` finds nothing. Finding 1 lives in exactly this untested seeding path.
   - **Fix:** add an IT (or a repository test) covering the new year with and without the reset, plus the toggle case.
3. **major (or an organizer ruling)** `src/main/java/com/agilityhub/core/payments/domain/InvoicingRules.java:238`: a member with `nextInvoiceDate == null` is `NOT_DUE` forever.
   - S04 validation only requires `nextInvoiceDate` for `MONTHLY` plans (`SignupService.java:981/994`), and `PlayoffPlanner.java:365` sets it only for monthly members.
   - So a `SINGLE_CLASS` member validated or migrated normally has no date. Their `PendingCharge`s are created by R-12-25 but never become `SINGLE_CLASS` lines (R-12-02, R-12-25 «Al run del mes es converteixen en línies»).
   - The tests hide this: `BillingItSupport` gives Mia a date, and the curl fixture sets dates by hand (assumption 18).
   - **Fix:** treat a member with unbilled charges and no date as due (and write the date the run advances to), or ask the organizer to have S04 set it for `SINGLE_CLASS`. Add a test with a single-class member who has no date.
4. **minor** `src/main/java/com/agilityhub/core/payments/application/InvoiceActions.java:124`: `includeInNextRun` is stored but no run ever picks it up (assumption 13 / Q2 hands it to E8-T03).
   - R-12-19 says such an invoice is «inclòs a la propera remesa». Yet `roadmap/tasks/E8-T03.md` never mentions `includeInNextRun`; only E8-T01 and E8-T02 do.
   - The run is what builds the collections it passes to `RemittanceWriterPort` (`BillingRunService.java:96-123`), so attaching a `SEPA_XML` collection to `PENDING` `SEPA_DD` manual invoices belongs to this run.
   - **Fix:** implement it here, or get the organizer to assign it explicitly to E8-T03. As it stands no task owns it.
5. **minor** `src/main/java/com/agilityhub/core/payments/application/BillingQueries.java:63` and `src/main/java/com/agilityhub/core/payments/api/BillingViews.java:111`: after a rollback and a new generation, each member has a `CANCELLED{ROLLBACK}` invoice and a live invoice with the **same** `displayNumber`.
   - This shows up in `/me/invoices`: the member sees two «Rebut 2026-0005», one «anul·lat».
   - It also shows up in the D6 list and `q` search, and `counts.all` (D6 «Tots (n)») becomes 230 for the curl's 115-invoice month.
   - This follows from R-12-14 plus the partial index (assumption 2), but it reaches members.
   - **Suggestion:** hide rollback-cancelled invoices from `/me/invoices` and from `counts.all` (or flag them in the view), or get a ruling. The relaxed `{clubId, series, number}` index is itself a model deviation (MODEL Annex B) that the organizer must accept.
6. **minor** `src/main/java/com/agilityhub/core/payments/application/InvoiceActions.java:143-147`: S12 §5 draws `COLLECTING → PAID «marca cobrat (SEPA)»`, and its transition table lists `COLLECTING → PAID | webhook · ADMIN | R-12-16/21`.
   - Under BR-08 (no bank integration in R1), a remitted SEPA receipt can therefore never become `PAID`. D6 «Cobrats» would never count SEPA receipts.
   - This is the executor's Q1; it needs a ruling before verification, not after.
7. **minor** `src/main/java/com/agilityhub/core/payments/application/BillingRunService.java:220-230`: `stale()` looks at members, groups, plans, prices and `billing.*` overrides. It ignores the club document: `paymentProviders` and modules.
   - **Failure case:** disable `SEPA_XML` or `FAMILY_GROUP` after simulating. The run then recomputes a different month (new `PROVIDER_DISABLED` skips, different payers) than the D6 confirmation showed, with no `409 SIMULATION_STALE`.
   - **Fix:** include the club config's `updatedAt`/version in the staleness check.
8. **nit** `src/main/java/com/agilityhub/core/clubs/bookings/application/PendingChargeConsumers.java:61`: voiding a charge (`PENDING` after `PRESENT`) leaves `Booking.charge.chargeInvoiceLineRef` pointing at the voided charge. Clear it on `VOID`.
9. **nit** `src/main/java/com/agilityhub/core/payments/application/ReceiptPdf.java:71-74`: the tax row uses the generic label `billing.receipt.tax` «Impost». S12 §10 asks for the country profile's label (`ES` → «IVA»). It doesn't show at the Cànic (0 % tax), but it does for other clubs.
10. **nit** `src/main/java/com/agilityhub/core/payments/application/BillingRunService.java:201-216`: `blockers()` ignores a `COMPLETED` run (it reports rollbackable). `runs.rollBack` only accepts `GENERATED`/`CHARGING`, so such a run would get `409 STALE_VERSION` rather than `RUN_NOT_ROLLBACKABLE`. Only reachable once E8-T04 writes `COMPLETED`.
