# Review E5-T06: minor issues

## Findings
1. **major** `src/main/java/com/agilityhub/core/shared/application/CacheLoads.java:15`: this change is outside the task's scope and can make cache invalidation ineffective. The new helper reads with `getIfPresent`, runs the loader and then calls `put`, with no link between the load and later invalidations. Before, `Cache.get(key, loader)` was atomic, so an `invalidate` issued during a load removed the loaded value. Now this sequence is possible:
   - a request starts loading the old `ClubConfig`;
   - an admin's `PUT /parameters/…` or module toggle commits, and `invalidateAfterCommit` runs;
   - the request then `put`s the old config.

   The result is a stale config for up to 5 min (`ClubConfigService` TTL). The same race hits `HostTenantResolver` (`invalidate()` after a domain change, also 5 min, negative lookups included). It matters most under the concurrent traffic this helper was written for. No test covers invalidation during a load. **Fix:** keep a generation counter per cache and read it before loading; skip the `put` if an invalidation bumped it. Alternatively, use `Caffeine.buildAsync()` with a platform-thread executor, which removes the pinning and keeps atomicity. Add an IT that toggles a module while a load is in flight.

2. **major** `perf/e5-seat-holds.js:98` / `roadmap/evidence/E5-T06/04-e5-perf-k6.log`: the peak run is weaker evidence for T-08-41 and the gate than the report's headline suggests.
   - **Only 46 distinct members.** The pool has 46 tokens ("46 members with an eligible dog"), so the "300 VUs" are 46 members each reused about 6.5 times (`POOL[index % POOL.length]`).
   - **The classes were not empty.** They had 37 free seats, not 10 × 5 = 50.
   - **Seats were not filled.** 260 of 300 holds were rejected, most of them early by the new lock-free pre-check (the same member hitting `BOOKING_LIMIT_REACHED`). Only 25 bookings were created, so the peak never filled the classes, and its "zero overbooking" proves little (the `last_seat` run does prove it).
   - **The gated p95 values rely on two relaxations.** Arrivals are spread over 5 s (Question 1). The simultaneous `burst` gives seat-holds p95 1232 ms and flow p95 1775 ms, which fail both the 500 ms and the 800 ms targets.

   The organizer must decide Question 1 before accepting «k6 dins d'objectius». **Suggested fix:** use a pool of at least 200–300 distinct fictional members, 10 empty classes of 5 seats, and report distinct users in the RESULT line.

3. **minor** `perf/e5-seat-holds.js:43`: the peak and burst runs count every 409/422 as expected (`expectedStatuses(200, 201, 409, 422)`) and never check the error `code`. Step 5 says `http_req_failed` should cover «only the expected 409s». An unexpected `422 VALIDATION_ERROR` or `BOOKING_BLOCKED` would pass unseen. Assert the allowed codes, as `lastSeat` already does.

4. **minor** `perf/e5-seat-holds.js:86`: `confirm` sends a random `uuid()` as `Idempotency-Key`. R-08-08 says the key is the `seatHoldId`, so the load test does not exercise the contract's key. Use `holdId`.

5. **minor** `DemoSeedStep.java` (`Input.scenario()`) and Verification: when `--week-start` is in the past, the scenario is skipped (counts 0). The Verification command as written (`bin/core seed:demo --club=canic --seed=42`, default week start) therefore creates **none** of the E5 states; only the smoke's `--week-start=2026-10-05` does. Step 3(a) ("bookings on the validated current week reproducing the D4 occupancy") was also kept on W+2 (Assumption 2). Both deviations are documented. The organizer should confirm that the web T-08-40 (DoD) will seed with a future `--week-start` and move the test clock to `demoNow`. `seeds/README.md` should state that exact command.

6. **minor** `bin/e5-smoke` (Step 4): the `jobs:run week-opening`, `waitlist-fifo`, `risk-review` and `payment-timeouts` steps are not proven through the CLI.
   - The CLI `jobs:run waitlist-fifo` and `payment-timeouts` runs report `counters={}`: they did nothing, because the CLI process uses the real clock (Assumption 6).
   - P1, P6 and P7 are proven only by the scheduler's own `SCHEDULE` runs, and P2 by `POST /jobs/risk-review/trigger` plus a scheduler run.

   This is acceptable, but it is not the CLI path Step 4 names. «Idempotent on a second run» holds only because each run uses a fresh disposable Compose project; the run-suffix and cleanup path against a reused stack is not exercised.

7. **minor** `BookableClassesQuery.java:148`: with `ACTIVITIES` off, `activities` comes back as `[]`. §9 says «04 sense bloc Activitats» (block absent). `null` would match `pack` and `singleClass`, and the OpenAPI schema should say so. Also, `MemberHomeQuery` always sends `dogName`, while T-08-12 cites «amb {gos} només amb Tots» (the front must hide it when a dog is selected). This works, but it slightly contradicts "the front computes nothing". Either null `dogName` when `dogId` is set, or record the choice as an assumption.

8. **nit** `BookingContext.java:26`: `asOf` became `public`, and `TrainingContext.now()` now delegates to it. This opens a thread-local business-time override to any caller. Add an ArchUnit rule that restricts callers to `Demo*Seeder` classes, or expose it through a seed-only facade.

9. **nit** `SeatHoldService.java:41`: the lock-free pre-check runs `admit` twice on every successful hold (two sets of reads per hold). It is correct because the locked path decides again. However, a `CLASS_FULL{heldOnly}` from the pre-check can now be based on a hold that expires milliseconds later without retry semantics. Say this in the Javadoc, or skip the pre-check when `heldOnly` would be true.

10. **nit** `MemberHomeQuery.java:341`: each waitlist row calls `classes.find(...)` (N+1 queries). This is cheap at today's volumes, but it could batch the lookups as `labelsOf` does for bookings.
