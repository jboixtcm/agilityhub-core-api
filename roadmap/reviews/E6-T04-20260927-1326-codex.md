# Review E6-T04 — needs changes

## Findings

1. **major** `src/main/java/com/agilityhub/core/clubs/bookings/application/WaitlistService.java:197` — P8 can silently cancel a future class’s waitlist after rescheduling. The check uses `WaitlistEntry.classStartsAt`, which is refreshed asynchronously by `BookingConsumers`. If a class moves from 18:50 to 19:50 and P8 runs before that consumer, entries are cancelled at 18:50; the later refresh ignores cancelled entries. This violates R-15-18/R-08-16, which require the **class** to have started. Recheck the authoritative class start inside the cancellation transaction and add a rescheduling test with dispatch delayed.

2. **major** `src/main/java/com/agilityhub/core/clubs/bookings/application/jobs/ClassFinishingJob.java:35` — The waitlist step runs with `WAITLIST` disabled. Neither planning nor the `SWEEP` application branch checks the module, and the called service provides no guard. Existing entries therefore become `CANCELLED` despite S15 R-15-03 and §9 requiring that step to be omitted. Guard both planning and application; test a disabled module with existing live entries while class finishing remains enabled.

3. **major** `src/main/java/com/agilityhub/core/clubs/bookings/application/NoShowNotifications.java:64` — N-19 email is unconditional whenever an address exists. Stored PERSONAL preferences are never read, so an explicit opt-out cannot suppress delivery. Step 1, T-15-16 and the N-19 catalog row require preference-aware delivery. The report’s deferral to E7 describes an unfinished requirement. Honor the member’s preference, retaining the documented default when absent, and test both opted-in and opted-out recipients.

4. **minor** `src/main/java/com/agilityhub/core/clubs/bookings/application/jobs/NoShowNoticesJob.java:51` — There is no explicit “batch already claimed” state for the run. If planned attendance B becomes `PRESENT` before A claims the batch, then returns to `NO_SHOW` before B’s application, B performs another claim and emits a second `NoShowNoticeDue`. The job lease does not exclude attendance edits. R-15-13 and step 1 require one batch transaction per run. Establish one claim result per run and derive subsequent traces from it; test this interleaving.

5. **minor** `src/main/java/com/agilityhub/core/clubs/bookings/application/DemoAttendanceSeeder.java:72` — The required unqualified `seed:demo --club=canic --seed=42` invocation omits E6 data Tuesday–Sunday: its default anchor is the current Monday, while `Input.scenario()` returns empty when that Monday precedes today. The smoke evidence instead supplies a future `--week-start`; it does not verify the command specified in step 5. Make the default invocation populate the required fixture and test a first run midweek followed by an unchanged second run.
