# Review E3-T17: needs changes

## Findings
1. **major** `src/main/java/com/agilityhub/core/clubs/census/application/SignupService.java:466-469` (`saveDocuments`): a D2 document edit of the reused dog throws away submitted documents that the edit does not mention.
   - **What happens.** For a readmission, the method replaces the whole `readmissionRequest.submitted.documents` list with the types in the PATCH, plus the `VACCINATION_CARD` row that `claimDocuments` always adds. For any other pending dog, `writeDocuments` replaces only the sent types, and the other types stay.
   - **Example.** The readmission sends a new card and a new insurance. The admin then replaces only the card on D2 (`PATCH /dogs/{id}` with `documents:[{VACCINATION_CARD,…}]`).
     - The submitted insurance disappears from the request.
     - D2 shows the dog's old insurance again, and validation keeps the old one.
     - The applicant's new insurance file is now unreferenced, so P9 deletes it after 48 h.
   - **Why it matters.** R-04-19 lets D2 add and remove files per dog. Step 1 says the submitted documents wait in the request and validation applies them "as a submission does". The D2 view has no `fileKey`, so the web cannot send the kept files back. Nothing tests this path: the new tests only edit `name` and `chip`.
   - **Fix.** Merge by type: start from the existing submitted documents keyed by `type`, overwrite the types just claimed, then call `putSubmitted`. Add an IT: the readmission sends card and insurance, D2 replaces only the card, then check that the submitted insurance is still in D2's view, is written at validation, and is not a P9 orphan while pending.
2. **minor** `DogService.java:67-68`, `DocumentService.upload/remove`, `DogsController` photo route: other routes can still change the reused dog's record while the readmission is pending, and a rejection does not undo it.
   - **What is exposed.** `handlerName` and `licenses` in `PATCH /dogs/{id}` (assumption 2), plus the S03 routes `POST /dogs/{id}/documents`, `DELETE …/files/{fileId}` and `PUT /dogs/{id}/photo`. `access.mutableDog` does not check the dog's status.
   - **Why it matters.** `restoreInactive` restores only status, reason, date and `signup`. R-04-23 says the dog returns "amb les seves dades i els seus documents originals", so after such an edit the rejection does not leave the dog "exactly as it was".
   - **Fix.** Either return `409 INVALID_STATE` (`READMISSION_PENDING`) on these routes for a readmission-pending dog, or have the organizer accept the gap explicitly. At least list it in the report beside assumption 2.
3. **minor** `SignupService.java:409`: the dog part of a readmission submission is never audited.
   - The `SIGNUP_SUBMITTED` audit entry diffs only the Member.
   - The reused dog's submitted values and documents live only in `Dog.readmissionRequest`. A rejection sets that to `null`, and `SignupSubmitted` carries only `dogNames`.
   - So after a rejection nothing records what was submitted for the dog. R-04-06 says "L'enviament d'una readmissió s'audita".
   - **Fix.** Include the dog's `readmissionRequest.submitted` in the submission audit (for example as a second `AuditCommand` on `Dog`), or ask the organizer whether the member entry is enough.
4. **nit** `DogsController.java:81`: on the reused dog, `PATCH /dogs/{id}` returns `queries.dog(id)`, which is the dog record.
   - After a successful edit the response still shows the old name and values; only `version` changes.
   - A client that updates its state from the response will show stale data.
   - **Fix.** State this in the description or in the report's web note (question 4), so the web re-reads `GET /members/{id}/signup`.
5. **nit** `SignupService.java:204-211` (`holder`, R-04-12): the family lookup matches the reused dog on its record name while the readmission is pending, no longer on the submitted name.
   - The legacy N-01 path for events without `locale` (`SignupNotifications.java:136`) also now reads the record name.
   - Worth one line in question 2, next to the D1 and list question.
6. **nit** Rules: validating a readmission that sent no card empties the dog's RECEIVED card, emits `DogDocumentPending{trigger: FILE_REMOVED}`, and leaves the old card file for P9 to delete.

   - With E38's wording ("els documents que ja tenia conserven els fitxers"), the organizer may want to confirm that "apply" includes emptying a document the applicant did not send.
