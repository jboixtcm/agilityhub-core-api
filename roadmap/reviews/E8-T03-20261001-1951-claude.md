# Review E8-T03: minor issues

## Findings
1. **minor** `src/main/java/com/agilityhub/core/payments/application/sepa/SepaRemittanceWriter.java:129` + `BillingRunService.java:332`: one stale manual receipt blocks the whole monthly run, and nothing routes this anywhere.
   - **What happens:** `remittedAttempt` takes the mandate frozen on an `includeInNextRun` receipt. If that member changed account in the meantime, `MemberService.java:157` has already issued a new `-2` mandate. The writer sees `mandate ≠ account.mandateRef()` and fails the entire run with `422 SEPA_NOT_CONFIGURED {memberIds}`.
   - **Why it bites:** the D6 simulation is clean, because manual receipts are not simulated until E8-T07. The error code wrongly says SEPA is not configured. The admin's only fix is to cancel and recreate the receipt.
   - **Not routed:** the report lists this as Q4, but the MESSAGES entry (`roadmap/MESSAGES.md:3056`) only carries Q1–Q3. E8-T07 step 3 covers `LEFT`, `NO_BANK_ACCOUNT` and "no longer SEPA_DD", not a changed mandate, even though Q4 assumes E8-T07 will handle it.
   - **Fix:** either add "the mandate changed since the receipt" as a skip/incident in E8-T07 step 3, or remit the receipt under the member's current mandate (re-freeze it in `remittedAttempt`). Either way, put the question in MESSAGES.
2. **minor** Deleting `InMemoryRemittanceWriter` (`payments/application/ports`) breaks the local demo billing cycle, and nobody is told.
   - E8-T02 kept that stub precisely so the Cànic demo could run a billing cycle. `seeds/club-canic.yaml:56` has no creditor, while `DemoSeedService.java:83` gives the demo members mandates "so remittance runs on the fictional census".
   - Now, on a `seed:demo` stack, every SEPA payer shows up as `PROVIDER_DISABLED` and `POST /billing/runs` answers `422`. The executor's own curl script had to inject a fictional creditor by hand (`11-remittances-curl.log`, "fixture").
   - This affects `bin/e8-smoke` (gate E8) and the web thread: `e2e:docker E8-W01` was running in the same hour (log header). The "For the web thread" note doesn't mention it.
   - **Fix:** have `seed:demo` (local only) give the demo club a fictional `SEPA_XML` creditor, or tell the web thread and the e8-smoke owner explicitly.
3. **minor** `src/test/java/com/agilityhub/core/payments/api/BillingItSupport.java:48,144`: the golden file cannot catch a debtor mix-up.
   - Every SEPA member in the fictional census has the same IBAN `ES00…4321` and holder «Titular Example».
   - So T-12-11's byte-for-byte comparison cannot detect a debit carrying another member's IBAN or name, which is the most damaging pain.008 bug. Only `S12_7_…` checks one distinct IBAN.
   - **Fix:** give each member its own fictional IBAN and holder. The `iban()` helper in `RemittancesIT` already produces valid check digits. Then regenerate the golden file with a note.
4. **minor** `Pain008Document.java:146,152`: `EndToEndId` and `MndtId` are written raw.
   - `EndToEndId` = `displayNumber`, and `billing.invoiceSeriesPattern` has `constraints: {}` (`catalog.yaml:1310`).
   - A series with `_`, `·`, accents, or longer than 35 characters makes every SEPA run fail with an opaque `422 SEPA_NOT_CONFIGURED {reason: SCHEMA}`. The log only gives a line and column.
   - **Fix:** propose a catalog constraint (SEPA character set, length) for the series pattern in MESSAGES. Or check the identifiers before marshalling and say which one failed in `details`, without its value.
5. **minor** `SepaRemittanceWriter.java:161`: the cleanup hook only deletes the file on `STATUS_ROLLED_BACK`.
   - When a commit fails, Spring reports `STATUS_UNKNOWN` (for example after `UnknownTransactionCommitResult` or a transient commit error).
   - In that case the stored file, which contains full IBANs, stays orphaned. `BillingTransactions` then retries with a new `remittanceId`, so a second file is written.
   - **Fix:** on `STATUS_UNKNOWN`, check whether the remittance id was persisted and delete the file if it wasn't. At minimum, log the key at WARN so someone can clean it up.
6. **nit** `src/main/java/com/agilityhub/core/payments/domain/SepaDirectDebits.java:69`: the creditor `suffix` length is never checked.
   - The code splices the suffix in at characters 5–7 assuming exactly 3 characters. A suffix like `"1"` produces `ES121B12345678`, which still matches the schema's creditor-identifier pattern, so the bank receives a wrong identifier.
   - **Fix:** treat a suffix that isn't 3 SEPA-charset characters as an incomplete creditor (`SepaCreditor.configured()`), giving `SEPA_NOT_CONFIGURED`.
7. **nit** `SepaText.java`: the typographic apostrophe `’` (U+2019), common in Catalan («Quota d’agost»), becomes a space and yields «Quota d agost».
   - The spec's set allows `'`, so mapping `’` → `'` (and `–`/`—` → `-`) would keep the bank statement readable.
   - This goes beyond the literal R-12-12 rule (which says "anything else → space"), so it is optional.
8. **nit** The schema used is not the plain ISO file that route (b) names. It is the Deutsche Kreditwirtschaft (DK) restriction of pain.008.001.02, from 2016 (EPC rules, ISO namespace), taken from an LGPL jar.
   - It is documented and defensible.
   - `Pain008Document` is tied to the DK's xjc type names (`GroupHeaderSDD`, `PartyIdentificationSEPA*`). Switching to the ISO or the bank's XSD therefore means rewriting the mapping, not just swapping the file. ADR-006's consequences should say so.
   - The organizer should confirm route (b) as taken and the licensing question (report Q6).
