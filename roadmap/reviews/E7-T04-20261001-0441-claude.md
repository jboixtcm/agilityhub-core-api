# Review E7-T04: minor issues

## Findings
1. **minor** `src/main/java/com/agilityhub/core/clubs/messaging/application/engine/NotificationEngine.java:132-135`: an announcement batch can be dropped after the client has already been told it was sent.
   - **What goes wrong:** the engine renders an announcement with the template's state at the moment the outbox is dispatched, not its state at send time. If the admin archives or disables the template between the `202 {batchId, recipientCount}` and the dispatch, the `continue` skips the whole batch. This is easy to do with a CUSTOM template in D9. The `Announcement` row then says `recipientCount = N` and the log has 0 notices. An edit made in that window also changes the text that goes out.
   - **Why it matters:** R-11-13 promises "una notificació `MEMBER` per abonat". `Announcement` stores no template version, so nothing can detect or replay this.
   - **Fix:** freeze the `templateId` and `version` (or the texts) in `Announcement`. Render a stored batch whatever the template's later status, or refuse to archive a template that has an undispatched batch. Add a test for the race.
2. **minor** `NotificationEngine.java:202` with `ChannelResolver.java:78`: a CUSTOM template that is not `CLUB_NEWS` ignores the `pushClubNews` opt-out on a mass send.
   - **What goes wrong:** the N-24 row is converted to the template's category, and `pushClubNews` is only checked when the category is `CLUB_NEWS`. A CUSTOM `PERSONAL` or `CLUB_CHANGES` announcement therefore pushes to members who turned club-news push off.
   - **Evidence:** `AnnouncementsIT.java:209` locks this in. Joan has `pushClubNews=false` and gets `PUSH:SKIPPED_NO_CONTACT`, not `SKIPPED_BY_PREFERENCE`.
   - **Also:** a `CLUB_CHANGES` CUSTOM template can send SMS to every member it selects (the caps allow it). The real-SMS branch of the smoke relies on this.
   - **Why it matters:** §8 N-24 says "PUSH (`pushClubNews`)". Report assumption 5 says "its push follows N-24's row" but does not mention that the opt-out is lost.
   - **Fix:** either apply `pushClubNews` to every `AnnouncementSent`, or record this as an explicit assumption or question for the organizer.
3. **minor** `src/test/java/com/agilityhub/core/clubs/bookings/api/RemindersJobIT.java`: no test proves P4 stays inside its own club (AGENTS rule 4).
   - **Gap:** `BookingFixtures` has an `OTHER` club, but no test seeds an `OTHER` booking that is due at the same tick. Isolation currently rests only on `TenantRepository`.
   - **Fix:** add an `OTHER` booking (and lead) that is due at 16:50 to `T_15_17_lauraChooses…`. Assert that the `CLUB` run neither plans nor marks it, and publishes no `ReminderDue` for it.
4. **minor** `src/main/java/com/agilityhub/core/shared/domain/events/SchedulerEvent.java:25` (`ReminderDue("Booking")`), used by `RemindersJob.java:74`: training reminders are stored with the wrong `aggregateType`.
   - **What goes wrong:** the event goes out as `aggregateType = Booking` with a training booking id as `aggregateId`. The event log or any consumer that routes by aggregate will mislabel it.
   - **Fix:** set the aggregate type per kind (`TrainingBooking` for training).
5. **minor** `CHANGELOG.md` / `seeds/README.md`: the CHANGELOG does not warn that existing seeded databases now fail `seed:demo`.
   - **Cause:** `DemoPlanningService.SECTIONS:23` now includes `messaging`. The planning signature therefore changes for every database seeded before this task, and `seed:demo` (including `--reanchor`) answers `CLUB_NOT_EMPTY` there. Those stacks also never get the profiles.
   - **Precedent:** earlier entries documented the same effect (CHANGELOG ~l.248).
   - **Fix:** add one line so the web and e2e lanes know to start from a fresh database.
6. **nit** `bin/e7-smoke:437`: the N-51 check falls back to "any N-51" (`… or self.settled({"code": "N-51"})`). It therefore does not prove that the N-51 is about the bounced member. Drop the fallback, or assert on the member in the subject or variables.
7. **nit** `src/main/java/com/agilityhub/core/clubs/messaging/application/DemoMessagingSeeder.java:25-26`: the Javadoc names the census half `clubs.census.application.DemoMessagingSeeder`. The class is `DemoContactsSeeder`.
8. **nit** `DemoScenarioSeedIT.java:166`: the seed test is named `T_11_20_E7_T04_…`, but T-11-20 is the preference-endpoints test. The seed has no T id of its own, so name it after the WP or task only (for example `E7_T04_…`).
9. **nit** `src/test/java/com/agilityhub/core/clubs/messaging/application/engine/NotificationMatrixTest.java`: the matrix moves e-mail preference and `pushClubNews` together (the same `c.preference()` for both). Mixed cases are never exercised, such as e-mail ON with push OFF on N-24, N-32a or N-15. It meets the letter of "preferences ON/OFF"; one extra axis would close the gap cheaply.
