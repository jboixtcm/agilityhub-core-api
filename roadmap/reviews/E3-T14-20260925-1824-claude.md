# Review E3-T14: minor issues

## Findings
1. **minor** `src/main/java/com/agilityhub/core/clubs/census/application/SignupService.java:522-529` (`paymentOptions`): the D2 view marks every offered method as `assignable: true` whatever the member's status.
   - **The problem:** for an add-dog signup (`POST /me/dogs/signup`), the member is `ACTIVE` and `GET /members/{id}/signup` still lists the methods as assignable. But `PATCH /members/{id}` accepts `paymentMethod` only when the member is `PENDING` (`MemberService.java:37-39`). Otherwise `CensusValues.allow` answers `400 READ_ONLY`.
   - **Why it matters:** R-04-19 says that with the member `ACTIVE`, D2 edits only the pending dogs; the person and the payment method go through D10. The new field documents "the methods D2 may assign", so the web will show a selector that the API refuses.
   - **Fix:** set `assignable = PENDING && enabled`, or return only the current method when the member is not `PENDING`. Add an IT on the add-dog path.
2. **minor** `SignupService.java:524` (`effectivePayment` in `paymentOptions`): the readmission case is not tested.
   - **The problem:** the report says that for a pending readmission, `current` marks the *submitted* method, "as the D2 PATCH edits it". No test in `SignupPaymentMethodsIT` covers a readmission.
   - **Why it matters:** this is a behaviour claim with no proof. A regression would go unnoticed, for example reading `member.paymentMethod` of the LEFT record.
   - **Fix:** add one case where the LEFT record has `SEPA_DD` and the submission has `MANUAL`. Assert `current` on `MANUAL`.
3. **minor** `src/main/java/com/agilityhub/core/clubs/census/application/SignupConfigurationEvents.java:14-18` and `ClubDefinitionWriter.apply`: the `GET /signup` cache is not cleared when `club:apply` changes the providers.
   - **The problem:** `club:apply` publishes `ClubConfigChanged`. The signup configuration cache (Caffeine, 60 s TTL) is cleared only on `ClubUpdated` / `ClubModulesChanged` / `PlanChanged` / `PriceChanged` / `ParameterChanged`.
   - **Why it matters:** after the deployment re-apply the report asks for (or any provider toggle), a running API keeps offering the old methods for up to 60 s. In that window, `POST /signup` answers 422 for a method the form still shows. D2's list is read live, so the report's "D2 list equals `GET /signup`" holds only after the cache is cleared; the IT clears it by hand (`signupService.invalidateConfiguration`).
   - **Fix:** add a `ClubConfigChanged` handler, or record this as a known limitation.
4. **minor** `ClubDefinitionWriter.java:106` (`diff` → `Objects.equals` on `ObjectNode`) together with `ClubDefinitionMapper.providers`: the club can't reliably change the order of its providers.
   - **The problem:** R-04-10 says the offer follows «l'ordre configurat», and the seed is the only way to configure that order. The diff ignores order, so reordering providers in the seed gives 0 changes and nothing is written. The new order is saved only when some other section changes in the same apply, and then silently. The report lists this as an assumption.
   - **Fix:** make the `paymentProviders` diff sensitive to order (also compare the field-name sequence), or ask the organizer to accept the limitation.
5. **minor** Behaviour change outside the three steps, and a divergence from the model. The strict rule in `PaymentProviderFlags.enabled` also changes `CheckoutService`, `SingleClassCharges`, `MemberService.payment` (D10) and `checkoutRequired`. The report and MESSAGES document this, and it is defensible.
   - **Existing stored clubs:** a club whose providers were stored without `enabled` loses every method. With BILLING on, `POST /signup` then cannot succeed at all until `club:apply` runs again (no data backfill).
   - **Model and specs:** `MODEL_DADES_PLATAFORMA.md` §2 has no `enabled` field, and the model wins over the specs. S17 §3 puts provider configuration in the definition, which the new schema refuses (`additionalProperties: false`).
   - **Organizer action:** accept or reject the three doc proposals explicitly before verifying. Otherwise the code diverges from the model.
6. **nit** `src/test/java/com/agilityhub/core/clubs/census/api/SignupPaymentMethodsIT.java`: two tests carry no `T-xx-nn` id: `R_04_19_theD2ViewPublishesTheAssignableMethodsAndAlwaysTheApplicantsCurrentOne` and `R_04_10_withoutBillingTheD2ViewHasNoPaymentMethods`. AGENTS rule 5 asks for spec ids; T-04-20 and T-04-26 would fit.
7. **nit** The mapping between provider and method (`SEPA_XML↔SEPA_DD`, `STRIPE↔CARD`, `MANUAL`) is still written out in three places: `SignupService.payment`, `SignupService.offeredMethods` and `MemberService.payment`. Moving it next to `PaymentProviderFlags` would make "one rule" true for the mapping as well.
8. **nit** Step 3 asked for "the same shape as `planOptions`". `planOptions` uses `name`, while the new option uses `label` (as `GET /signup` does). That choice is reasonable, but the report doesn't mention or justify the difference.
9. **nit** Evidence totals:
   - `01a-unit-before-fix-summary.log` shows surefire at 119 classes / 543 tests. The final clean run shows 118 / 533, and the report counts "+1 unit" against 532. The before-fix summary seems to have read stale `target/surefire-reports`.
   - The targeted summaries (`02a`, `10a`, `11a`) also print whole-suite totals from earlier reports. Only their per-class lines are meaningful. Say so, or clean the report directories before targeted runs.
   - `bin/openapi-snapshot` (Testcontainers) was not run through `heavy.sh`, although the task says heavy runs go through the host lock.
