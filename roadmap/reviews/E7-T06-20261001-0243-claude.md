## Findings

1. **minor** `src/main/java/com/agilityhub/core/clubs/messaging/application/TemplateUpgrade.java:161` — The upgrade is not a one-off migration. It runs at every start-up, and for every edited or `CUSTOM` template it **writes** D9's `normalized` view, which drops every language the club doesn't currently have.
   - Before this change, `normalized` was read-only on purpose (`MessageTemplateService.java:272`: "Nothing is written here").
   - **Failure case:** a `ca/es/en` club edits N-09 in all three languages. Its admin removes `en` from `club.locales` (for example with `club:apply`), and the API restarts. The club's English words are deleted for good, with no audit entry and no event. Adding `en` back does not restore them.
   - In the same way, never-edited templates silently pick up every future change to the seed JSON on the next deploy. That may be what we want, but it should be decided explicitly. Right now it only shows up in `seeds/README.md`.
   - **Fix:** for edited templates, apply only the two corrections the task asks for (lower-case `gender` keys, N-02's link sentence) to the stored values. Write only when one of them changes something, and leave language pruning to D9's next save. Or have the organizer confirm assumption 4 as a permanent behaviour.

2. **minor** `TemplateUpgrade.java:100` / `:85` — A failure in one club stops the whole API from starting.
   - If `configs.get(clubId)` throws anything other than `CLUB_NOT_FOUND`, or `templates.findAll()` fails, the exception escapes `afterSingletonsInstantiated` and the context does not start.
   - `MessagingE7T06UnitTest.E7_T06_aConcurrentSave…` (`assertThatThrownBy(upgrade::afterSingletonsInstantiated)`) asserts this behaviour.
   - This contradicts the report ("never stops the others or the start-up"). One club's broken configuration should not take the API down for every tenant.
   - **Fix:** catch `RuntimeException` per club, log a WARN with the clubId only, add it to `failed`, and continue.

3. **minor** `src/main/resources/seed/message-templates.*.json` (N-08b, N-32c) together with `MessageTemplateService.java:202` — Step 5 creates new cases of the very defect step 1 repairs, and the upgrade leaves them broken.
   - **Failure case:** an N-08b edited in round 1 or round 2 that kept the seed's `{class_description}`, or an N-32c SMS that kept `({date})`, is stored with `customized = true`. Since `seedArguments` now returns selectors only, D9's GET followed by an unchanged PUT now answers `400 TEMPLATE_UNKNOWN_VARIABLE`.
   - This is the same situation as round 1's `[[link]]`, but Q1 in the report covers only member variables outside the row.
   - **Fix:** in the upgrade, remove those two arguments from edited N-08b/N-32c texts, with a test doing GET → unchanged PUT → 200. Or at least add these two cases to Q1 so the organizer can rule on them.

4. **minor** `TemplateUpgrade.java` (assumption 3) — The upgrade changes templates without an audit entry and without `MessageTemplateChanged`.
   - S11 §4 (`S11-comunicacions.md:153`) lists `MessageTemplateChanged` for every template change from `ACTIVE` to `ACTIVE`.
   - `CATALEG_ESDEVENIMENTS.md:30` names its consumers as "auditoria, cache".
   - D9's "last change" (`audits.lastChange`) will keep showing the admin's older edit, while `version` and `updatedBy` have moved on (AGENTS rule 8).
   - The `messaging:migrate-notifications` precedent is reasonable, but it needs an explicit organizer ruling. Otherwise, emit `MessageTemplateChanged` (actor `system:template-upgrade`) through the outbox.

5. **nit** `src/main/java/com/agilityhub/core/clubs/census/application/CensusNotificationFacts.java:94-100` — Two small gaps around the applicant's name.
   - `member_name` strips each name part, but `member_first_name` is passed through as stored. A first name with stray whitespace would make `startsWith` fail, so `member_last_names` comes out as `""`.
   - The readmission variant (payload `applicant`, `lastName1` only, see P2) is not exercised for `member_last_names`. Both step-2 cases read the member document.
   - **Fix:** strip `firstName` the same way, and add one readmission case.

6. **nit** `src/main/java/com/agilityhub/core/clubs/messaging/application/engine/TemplateValidator.java:85` — Selector names are still accepted as *simple* arguments.
   - The check compares all of `icu()` against `icuNames()`. So `{mode}` or `{has_upfront}` printed on its own passes the save and renders the raw value (`FIFO`, `true`). That is a small leftover of the "hidden list" that review #3 described.
   - **Fix:** accept a seed selector name only in a `select`/`plural` position.

7. **nit** Evidence, "Before the fix" — The report says "the failures are the ones in the table". But log `01` (line 275) also shows `TemplateValidatorTest.T_11_12_aMandatoryTemplateCannotBeDisabledButAnotherOneCan` failing (`TEMPLATE_UNKNOWN_VARIABLE` instead of `TEMPLATE_MANDATORY`, a side effect of putting N-32c's `{date}` back). The unit count of 6 failures only adds up with it included. List it in the table.

8. **nit** `src/main/java/com/agilityhub/core/clubs/messaging/persistence/MessageTemplateRepository.java:30` — Two style points.
   - `clubIds()` is an untenanted, cross-tenant query added to a `TenantRepository`. It is acceptable for a system job, but it differs from how other system jobs iterate clubs.
   - Here and in `CensusNotificationFacts`, inline fully-qualified names (`java.util.List`, `org.springframework…Query`, `java.util.stream.Stream`) should be imports.
