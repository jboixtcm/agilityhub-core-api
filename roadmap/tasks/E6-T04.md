# E6-T04 · P3 and P8 jobs + E6 integration (back)

## Objective
Two of the ten scheduled processes become real `Job` beans on E5-T01's framework — `no-show-notices` (P3), which every morning turns yesterday's «no presentat» marks into a single batch of N-19, and `class-finishing` (P8), which every minute closes the classes whose grace period has run out and silently sweeps the waiting entries of classes that have already started. Then the stage closes: a demo seed that holds every state the E6 screens need (the Monday 8:30 class with Laura, Marc, Anna and Eva booked and Pau waiting, tasks with an attachment, a member note), a one-command smoke that reproduces the gate scenario on the local stack with the clock advanced, and the evidence the gate asks for.

## Steps
1. **`NoShowNoticesJob`** (`clubs/bookings/application/jobs`, registered as a `Job` bean, `JobName.NO_SHOW_NOTICES`, route id `no-show-notices`) — R-15-13 + R-10-06. `plan(ctx)`: `AttendanceRepository.claimForNoShowNotice`'s **read-only twin** — `state = NO_SHOW ∧ noShowNotice.queuedAt = null ∧ classDate < ctx.localDate` — returning one `JobItem` per attendance with `{attendanceId, bookingId, memberId, dogName, classDate}`; in dry run they surface as `WOULD_NOTIFY`. `apply`: **one transaction** that claims the whole set with `claimForNoShowNotice` (writing `noShowNotice.queuedAt = now` and the shared `eventId`) and puts a **single** `NoShowNoticeDue {attendanceIds[], bookingIds[]}` on the outbox; the dispatcher then renders **one N-19 per booking** to the dog's owner (APP+EMAIL subject to the member's `PERSONAL` preferences) with `dog_name` and `class_date` — the class's own date, never «ahir». Counters `{notices, late}` where `late` counts classes older than one day (a mark added two days after the class). Running the job twice, or manually right after the scheduled run, claims nothing and emits nothing (R-15-04). A mark changed to `PRESENT`/`NOTIFIED` **before** the batch is never notified; changed **after**, the notice is already out and the sheet shows «avís ja enviat» — which is the `NotificationSent{N-19}` consumer of S10 §7 writing `noShowNotice.sentAt` (implement it here if E6-T02 left it out; say which). Catch-up **unlimited** (the scope is by state, so a server that was down for three days notifies everything in one late run). No module guard. **T-15-16, T-10-26**.
2. **`ClassFinishingJob`** (`clubs/bookings/application/jobs`, `JobName.CLASS_FINISHING`, route id `class-finishing`, cadence CONTINUOUS) — R-15-18, two steps in this order: **(a)** `WaitlistService.sweepStarted(now)` → every `WaitlistEntry` `ACTIVE` or `NOTIFIED` whose class has `startsAt ≤ now` becomes `CANCELLED {cancelReason: CLASS_STARTED}` **silently** (no notification, S08 R-08-16); **(b)** `ClassSessionService.finishEnded(now)` → every `ClassSession` `ACTIVE` with `endsAt + classes.finishGraceMinutes (15) ≤ now` becomes `FINISHED` with `finishedAt`, over the index `{clubId, state, endsAt}`. **No business event** — only the framework's `SchedulerRun`. Idempotent by state. Dry run: `WOULD_SWEEP {entryId}` and `WOULD_FINISH {classId}` with no write anywhere. No rollback (`FINISHED` is terminal in S06). After finishing, only `notes` stays editable on the class and the attendance sheet keeps working until `T1` (R-10-03) — assert both. Example to encode: a class 18:50–19:50 is `FINISHED` on the 20:05 tick. **T-15-26**.
3. **Job wiring.** Both beans make their `JobCatalog` rows live: they now appear in `GET /jobs` with their cadence («cada dia a les 8:00» / «continu»), their switch `jobs.no-show-notices.enabled` / `jobs.class-finishing.enabled`, their last run and their `[Simula]` / `[Executa ara]`; `POST /jobs/{name}/trigger` no longer answers `404 JOB_UNKNOWN` for them (E6-T01 documented that as the interim behaviour — flip it and update the `JobCatalogContractTest` expectations). Manual triggers run even with the switch off (R-15-09) and write `AuditEntry{JOB_TRIGGERED}`. A continuous job records at most one `SKIPPED{DISABLED}` per hour, not per minute (R-15-03). Update the report with the list of catalog rows that still have no bean (`reminders`, `expirations`, `payment-timeouts`… whichever E5-T05 left open).
4. **Activities finishing — assumption in force.** E4-T04 exposed `ActivityLifecycleService.finishEnded(now)` saying «E5 schedules it», and no S15 process claims it: `class-finishing` is the only per-minute finishing process, so add it as **step (c)** of P8, guarded by the `ACTIVITIES` module, with its own counter `activitiesFinished` and dry-run action `WOULD_FINISH_ACTIVITY {activityId}`. Write the spec proposal (extend R-15-18 with the activities step, or give activities their own row) in the report and in `roadmap/MESSAGES.md`; do not leave the method unscheduled and do not invent a new `JobName`.

## Fixed conventions
- Closed catalogs: no new `JobName`, parameter, event, notification, error code or audit action. Both processes already exist in `CATALEG_PARAMETRES.md` through the `jobs.*` family and in R-15-01; N-19 exists with exactly `dog_name` and `class_date` (the `class_description` variable is listed as a **new** variable in the catalog's closing note — use it only if the row already declares it, otherwise propose it in the report and ship without it).
- Framework rules are E5-T01's and are not re-implemented here: occurrence arithmetic and DST (R-15-02), unique `{clubId, job, scheduledFor, trigger}` (R-15-04), `job_locks` (R-15-06), one Mongo transaction **per item** with the outbox and `PARTIAL` on item failure (R-15-10) — P3's batch is the documented exception: it is **one** transaction for the whole claim, exactly as R-15-13 writes it; `parametersSnapshot`, `effects.items` capped at 500, `SchedulerRun`, metrics and `JobFailed` → N-42 come for free from `JobRunner`.
- Dry run writes **nothing** anywhere (no collection, no outbox, no S3, no provider) except its own `JobRun{dryRun: true}`; a test asserts for both processes that the plan equals the real effects over the same data (R-15-08).
- Time comes from the injected `Clock`/`ClubClock` only (ArchUnit rule of E5-T01); tests advance it, they never sleep.
- Seeds are fictional and idempotent; the seed goes **through the application services** so every rule, event and counter is exercised; personal data of real people never enters the repo (the Cànic's real instructor and member lists live only in the staging seed, outside git).
- Evidence rule: report = command + exit code + last 40 lines; long outputs → `roadmap/evidence/E6-T04/NN-<name>.log`; task file ≤ 120 KB. No secrets, env vars only. Never edit other tasks, `ROADMAP.md` or the Organizer verification section. English identifiers from the glossary; i18n keys never literals; ca/es/en together.
