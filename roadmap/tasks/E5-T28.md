## Steps
1. **SEPA→SEPA `PATCH /members/{id}/payment-method` keeps what the request does not send (INC-17, ruling E42).** When the stored method is `SEPA_DD` and the request is `SEPA_DD`, `iban` (or `ibanEncrypted` + `ibanLast4` of a migrated member), `holderName` and `holderTaxId` are kept unless the request sends them; an explicit `"iban": null` clears the account (the member becomes «Compte no informat»); `mandateRef`/`mandateSignedAt` are kept as today. Changing the type still replaces the method. Adjust `CensusIT.T_03_13` (it pins the data-losing behaviour) and add the migrated-shape case. D10's «Compte no informat» badge and the SEPA remittance (E8) depend on this.
2. **White-label sender name (A2-01, ruling E48).** `catalog.yaml` default of `messaging.email.fromName` becomes `""`; `ClubEmailSettings` resolves an empty value to `Club.name`; remove the override from `seeds/club-minim.yaml`. In the same commit, change that row of `docs/specs/00-transversal/CATALEG_PARAMETRES.md`, as the organizer's amended source has it:
   - the default becomes `""`;
   - the description ends «; buit = el nom del club (`Club.name`) (organitzador 26-09, decisió E48: el valor per defecte no pot ser el nom d'un club)».

   This is the one `docs/specs/` edit this task makes. The synced copy changes together with `catalog.yaml`, so `T-02-03` stays green. Test: a club without the parameter sends N-25 with `From: <club name>`.
3. **Mandate reference of new SEPA members (ruling E43).** `SignupService.validate` assigns `mandateRef = "{clubSlug}-{memberNumber}-1"` (the migrated format, ≤ 35 characters) with `memberNumber` assigned three lines above, and keeps `mandateSignedAt = submittedAt` (S04 R-04-10 wins over S12 §7 — say so in the report). The demo seed (`DemoSeedService`, `DemoSignupSeeder`) gives its SEPA members the same references so E8-T03's golden run works on the fictional census. Unit test: every `mandateRef` written by the api is ≤ 35 characters and unique per club; existing development data may be re-seeded.
4. **Rejection while a checkout is open (A3-01).** `SignupService.reject` with `CHECKOUT_PENDING` rows expires the session locally (`CheckoutService`: session `EXPIRED`, rows `CANCELLED`) and calls `gateway.expire(id)`; a later provider completion of an `EXPIRED` session, or of a session whose rows are no longer `CHECKOUT_PENDING`, takes the E34 path for signup sessions too (`lateCompletionAt` mark + WARN, no `PAID` row rewritten, no `members.card(...)` on a LEFT record). Also run `POST /checkout-sessions` through the same retried transaction as `POST /signup` (`SignupTransactions.write`; add the route to `IdempotencyFilter`'s in-transaction-retry list) so a concurrent census write never gives a 500 (A3-06); the provider call stays outside the retried unit as `prepareBooking` does. ITs for the three cases.
5. **A week cannot be validated around a loose DRAFT class (A4-01).** `ClassSessionService.create` touches the `Week` document (a no-op `update` with its version) when the week is not VALIDATED, so a concurrent validation conflicts and one side retries; `validate` accepts a VALIDATED week that still has DRAFT classes (idempotent re-validation keeping `validatedAt`). Extend `CalendarIT.T_06_23` with the create-vs-validate race. Declare `409 INVALID_STATE`/`STALE_VERSION` on `POST /weeks/{id}/validation` and the class routes in `@ContractErrors` (A4-05).
6. **Chip normalisation on the ACTIVE-dog PATCH (A2-08).** `DogService.edit` normalises and validates the chip like the PENDING path and the signup (`DogChips.normalize`, country format); IT: an admin edit with spaces is stored normalised and the unique index catches a later signup with the same chip.
7. **D1 and the members list read a pending readmission's submitted values (A3-02).** `DashboardRepository` and `CensusListProjection` project `readmissionRequest.submitted.{firstName, lastName1, paymentMethod, consents}` and the submitted dog name when a readmission is pending (as D2 and N-01 already do): the «Compte no informat» badge, the image-consent warning and the method follow the submission. IT on D1 for a readmission that changes the method and renames the reused dog. One accessor on `Member` for «is a readmission pending» (A3 I-07).
8. **Docs.** `docs/openapi/CHANGELOG.md` (steps 5 and, if any shape changes, 7), `seeds/README.md` (mandates), `docs/DEPLOY.md` («fromName empty = club name»). The organizer has already amended S03 R-03-07 and the S12 §7 note (synced to `docs/specs/`), and the source of `CATALEG_PARAMETRES.md`. Do not edit `docs/specs/`, except the one `fromName` row of step 2.
