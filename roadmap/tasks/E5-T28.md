### Assumptions

1. **S04 R-04-10 wins over S12 §7** (ruling E43): `mandateSignedAt` stays the submission's instant; the validation only adds
   `mandateRef`. The IT checks it after moving the clock between submission and validation.
2. **A readmission's new mandate is `…-2`**: E43 names the format for a new member (`-1`). A readmitted member keeps its
   number; reusing `-1` would give a new mandate (new IBAN, new signature date) the reference of the old one, which a
   creditor must not do. The rule takes the next sequence only when the previous reference is the member's own
   `{slug}-{number}-{n}`; anything else (`AH-…`, migrated from another format) gives `-1`.
3. **A long slug is cut**: a slug may have 40 characters (`Club.java` `[a-z0-9-]{3,40}`); the slug part is cut to
   `35 − len("-{number}-") − 4` and trailing hyphens are removed. The last two segments are the number and the sequence,
   so two members of a club never share a reference (the unit test checks 2003 numbers).
4. **The demo's PENDING signups get no mandate** (`DemoSignupSeeder` unchanged): R-04-10 says the validation assigns it,
   and they have no member number yet. `DemoSeedService` gives the non-PENDING SEPA members `{slug}-{number}-1` signed at
   `joinedAt`. Development data seeded before this task keeps `AH-…` references: re-seed it (task step 3 allows it).
5. **The week touch changes `Week.version`**: an identical replacement ("a no-op update with its version") is not
   written by MongoDB and so conflicts with nothing (and `updatedAt` is not reliable either: the test clock is fixed).
   No request carries a week's `version` back, so nothing breaks; the snapshot description of `POST /class-sessions` says it.
6. **The catalogs' write locks already serialise the two writes**: every scheduling transaction first `$inc`s the
   catalog locks (`PlanningContext.lockReferences`), so on today's code a create and a validation of the same club
   already conflict. The week touch is the week's own guard, independent of those locks (which exist for catalog
   integrity and could be narrowed). `CalendarIT.T_06_23_aClassCreated…` stubs `lockReferences` (a `MockitoSpyBean`)
   to test that guard alone; that is why it fails on the old code.
7. **Re-validation of a VALIDATED week** writes no `WEEK_VALIDATED` audit entry (no audited field changes) but emits
   `WeekValidated` with the ids it activated, so the consumers (training, deferred N-33 with its occurrence key) see them.
8. **A4-05 (`@ContractErrors`) vs ruling E73 (30-09)**: E73 makes a `409 STALE_VERSION` after exhausted retries
   transversal and undeclared route by route, and after step 5 `POST /weeks/{id}/validation` no longer throws
   `INVALID_STATE`; the class routes already declare `INVALID_STATE` where they throw it (PATCH, cancellation,
   risk-exemption). So no scheduling declaration was added. `POST /checkout-sessions` does declare `STALE_VERSION`:
   T-04-25 (`S04ErrorContractTest`) requires every S04 route to document what its handler reaches, and `POST /signup` and
   `POST /me/dogs/signup` already declare it for the same retried transaction.
9. **The provider is asked to expire after the rejection's commit**, from a `TransactionSynchronization.afterCommit` that
   runs it with `PROPAGATION_NOT_SUPPORTED` (the fake provider calls back into `CheckoutService.expire`, which then opens
   its own transaction). A provider error is logged (session id, club id, error) and never fails the committed rejection.
10. **An empty chip still clears an ACTIVE dog's chip** (existing behaviour, `CensusIT` line 678; migrated dogs may have
    none); a non-empty one is normalised and must match the country format. S03 §3 marks the chip «obligatori»; making it
    required on the ACTIVE PATCH is left out because the task asks for normalisation only.
11. **D1 and the list also take the submitted `lastName2`** (the list's `fullName`) **and D1 the reused dog's breed**
    (the D1 row shows it); the task names `firstName`, `lastName1`, `paymentMethod`, `consents` and the dog name.
12. `club-fifo.yaml` and `club-perf.yaml` keep a `fromName` equal to their club name, and `club-template-default.yaml` keeps
    `"AgilityHub"`: the task names only `club-minim.yaml`.
