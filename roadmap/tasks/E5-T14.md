### Assumptions
1. **Step 1 hand-off.** `generatedWeeks` is a mutable set that the run shares between steps, created by the 8-argument `Input` constructor that `DemoPlanningService` uses. A record component is mutable only here. The alternative was a DB heuristic, which could not tell kept weeks from generated ones.
2. **Step 2, mid-week run.** Validating the kept current week also activates the DRAFT classes of its past days. Validation has no past-day guard, and those classes then finish through the usual P-finish job. On the real stack (run on a Thursday), the 38 classes of the kept week are in the future, so this did not occur. The IT runs on the Wednesday of that week and passes.
3. **Step 7, unreachable branch.** If the conditional mark misses after the rows were written, the transaction throws (`IllegalStateException`) so the rows roll back and the outbox retries. It cannot happen under Mongo transactions (a concurrent demotion is a write conflict) and has no test; it is a guard, like the E5-T11 census guard.
4. **Step 8.** Clearing the mark on expiry is the option the task offered. The model row keeps its meaning (the last offer whose N-15 rows were written) for live entries. An EXPIRED entry no longer carries it.
5. **Step 9.** The suspended fixture club (`e2-suspended`) stays in the class-scoped database of `E2ContractIT` (PER_CLASS). No other test in that class counts clubs.
