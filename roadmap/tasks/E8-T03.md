# E8-T03 · SEPA remittances (S12 WP-12-C)

## Objective
Work package S12 WP-12-C. The direct-debit half of the monthly cycle becomes real: `SepaRemittanceWriter` turns a `BillingRun`'s SEPA collections into a `pain.008` `CstmrDrctDbtInitn` document, validates it against the XSD **before** the run commits, stores it, and exposes the remittance list, the file download, the «mark as sent to the bank» action and the rollback interaction. Every mandate at the Cànic is new and every transaction is `RCUR` (Josep 08-09, B5/B6). This task closes **ADR-006**: write the decision summary in the report and in `roadmap/MESSAGES.md` so the organizer can file `04-arquitectura/decisions/ADR-006-*.md` — **never edit `docs/decisions/`, which `bin/sync-docs` overwrites from the organizer's folder**.

## Steps
1. **The XSD (Blocked · @jordi, with a written fallback).** The bank's own `pain.008` XSD is a @jordi input and is **not** in the repo. Order of preference: (a) if `src/main/resources/sepa/*.xsd` already contains the bank's schema, generate the JAXB classes from it with `xjc` at build time (`jaxb2-maven-plugin`, sources under `target/generated-sources/jaxb`, package `com.agilityhub.core.payments.sepa.generated`) — this is ADR-006's preferred route; (b) otherwise use the **public ISO 20022 `pain.008.001.02` XSD committed as a repository resource** at `src/main/resources/sepa/pain.008.001.02.xsd` and generate from it; (c) if neither is available in the sandbox (no network, no file), do **not** block the task: hand-write the JAXB-annotated classes for the subset R-12-12 names, in ISO element order, keep every other step identical, mark `Remittance.xsdValidatedAt = null` with `xsdValidationSkipped = true`, and finish the task with an explicit **«Blocked: bank pain.008 XSD — @jordi»** line in the report saying which route you took and what a real XSD would change. Record `billing.sepa.schema` (`pain.008.001.02` default, `.08` parametrisable) and fail fast with `422 SEPA_NOT_CONFIGURED` when the club has no `SEPA_XML` provider configured.
2. **`SepaRemittanceWriter`** (`payments/application/sepa`, implementing E8-T02's `RemittanceWriterPort`) builds `CstmrDrctDbtInitn`: `GrpHdr.MsgId = remittance.messageId` = `{clubSlug}-{period}-{seq}` truncated to **≤ 35 characters**, `CreDtTm` from the injected `Clock`, `NbOfTxs`, `CtrlSum`, `InitgPty`; **one `PmtInf` per `SeqTp`** — `FRST` for mandates with no previous `SUCCEEDED`/`SUBMITTED` collection **only when `billing.sepa.useFrst = true`**, otherwise everything `RCUR` (the Cànic value is `false`) —, `PmtMtd = DD`, `SvcLvl.Cd = SEPA`, `LclInstrm.Cd = CORE`, `ReqdColltnDt = collectionDate` (computed by E8-T02 from `billing.sepa.collectionDayOfMonth` as a day of the **billed** month; `≥ generation date + 2 business days` for RCUR/CORE, otherwise `422 COLLECTION_DATE_TOO_SOON`), `Cdtr`, `CdtrAcct` (the club IBAN), `CdtrAgt` when a BIC is configured, `CdtrSchmeId` (creditor identifier + `suffix`). Per transaction: `EndToEndId = invoice.displayNumber`, `InstdAmt` with the club currency and two decimals, `MndtRltdInf {MndtId = paymentMethod.mandateRef, DtOfSgntr = mandateSignedAt}`, `Dbtr.Nm` = account holder, `DbtrAcct.IBAN` = the **full** IBAN (this is the only place it leaves the database), `DbtrAgt` when known, `RmtInf.Ustrd` = the frozen invoice description truncated to **140 characters** and transliterated to the SEPA character set (`ç→c`, `·→-`, accents stripped, anything else outside `[A-Za-z0-9/-?:().,'+ ]` → space). Amounts come from the `Collection`, never recomputed.
3. **Validation and storage**: validate the marshalled document against the XSD with a `javax.xml.validation.Validator` **before** the run transaction commits (R-12-11); on success set `xsdValidatedAt`. Persist the `Remittance` (`runId`, `period`, `messageId`, `creationAt`, `requestedCollectionDate`, `creditor` snapshot, `collectionIds[]`, `count`, `total`, `sequenceBreakdown {FRST, RCUR}`, `fileKey`, `xsdValidatedAt`, `status = GENERATED`) and write the file through the existing `ExportStorage` under a key like `remittances/{clubId}/{period}/{messageId}.xml`. The **file is written outside the Mongo transaction but only after a successful marshal + validation**; a storage failure aborts the run (no invoice is created) — say in the report how you ordered it.
4. **Golden file (T-12-11)**: with a fixed `Clock` and the fictional census, the generated XML must be **byte-for-byte identical** to `src/test/resources/sepa/remesa-2026-09.golden.xml` (commit it; regenerate it only with an explicit note in the report). Assert in the same test that the XSD validation passes, that the full debtor IBAN appears in the XML, and that **no** API response of any route ever contains a full IBAN (scan `GET /invoices`, `GET /invoices/{id}`, `GET /remittances`, `GET /remittances/{id}` and `GET /me/invoices` responses with an IBAN regex).
5. **Writer unit tests (T-12-06)**, no Spring, no Mongo: `useFrst` on → two `PmtInf` blocks with the right counts; `useFrst` off (Cànic) → one `RCUR` block; «Cànic · Núria» → «Canic - Nuria»; a description longer than 140 characters is truncated on a character boundary; a `MsgId` built from a long club slug is ≤ 35; `collectionDate` too close → `422 COLLECTION_DATE_TOO_SOON`; a member with `iban = null` never reaches the writer (E8-T02 skipped them as `NO_BANK_ACCOUNT`).
6. **Mandates**: `mandateRef` and `mandateSignedAt` live on `Member.paymentMethod` and are frozen onto the invoice at generation. Consume `MemberValidated` (a new `SEPA_DD` member gets `{clubSlug}-{memberNumber}-1` with `mandateSignedAt = validatedAt`) and `MemberPaymentMethodChanged{SEPA_DD}` (new sequence number `-2`, `-3`… and a new signature date; with `useFrst = true` the next collection is `FRST`). For migrated members the mandate is created by the importer with `mandateSignedAt` = cut-over date (S18 R-18-08, implemented in E8-T06) — this task only reads it and **must fail loudly** (`422 SEPA_NOT_CONFIGURED` with `details.memberIds[]`) if a SEPA collection reaches the writer without a `mandateRef`.
7. **Endpoints** (ADMIN only; MEMBER and INSTRUCTOR → `403`; another club's id → `404`): `GET /remittances` as a universal list (`x-filterable: period, status`; `x-sortable: creationAt, period`) with the columns the screen needs (period, creation date, invoice count, total, status, whether a file is available) · `GET /remittances/{id}` with `sequenceBreakdown`, `submittedAt`, `submittedByAccountId` and the **masked** creditor IBAN · `GET /remittances/{id}/file` → a signed, short-lived URL with `Content-Disposition: attachment; filename="remesa-{period}.xml"` and `Content-Type: application/xml`, audited as a file access · `POST /remittances/{id}/submission {submittedAt}` (`Idempotency-Key`) on a `GENERATED` remittance → `SUBMITTED`, `submittedAt`, `submittedByAccountId`, audited **`REMITTANCE_SUBMITTED`**; on any other status `409 INVALID_STATE`. After submission the run's `rollbackable` is false and `POST /billing/runs/{id}/rollback` returns `409 RUN_NOT_ROLLBACKABLE {reasons: [REMITTANCE_SUBMITTED]}` (T-12-30). The screen at `/facturacio/remeses` has **no mockup**: the web task builds it with the design system and Josep validates it in staging — note that in the report so the organizer can tell the web thread.
8. **Rollback interaction (R-12-14)**: when E8-T02's rollback runs, set `Remittance.status = ROLLED_BACK` inside the same transaction and **keep the file and the `fileKey`** (auditability); the download stays available and the list shows the rolled-back remittance. A rolled-back remittance never counts for P10's «no remittance this month» check (E8-T06). T-12-13 SEPA half.
9. **No SEPA at all**: a club whose `CLUB.paymentProviders` has no `SEPA_XML` entry generates a run with no `Remittance` at all (every invoice stays `PENDING`), and `GET /remittances` returns an empty list rather than an error (R-12-28, T-12-32). A club **with** `SEPA_XML` but incomplete creditor data (`creditorId` or `iban` missing) → `422 SEPA_NOT_CONFIGURED` at run time, listed in the simulation as the incident `PROVIDER_DISABLED`.
10. **ADR-006 closure**: in the report and in `roadmap/MESSAGES.md`, write the decision in the ADR shape — *context* (a `pain.008` file must be produced and accepted by the club's bank), *options* (xjc-generated JAXB from the official XSD · an external SEPA library · hand-built XML), *decision* (JAXB generated from the XSD, with golden files as the regression net; an external library only if it matches the same validation), *consequences* (the XSD is a build input, the golden file must be regenerated deliberately, `billing.sepa.schema` allows `.08` later), and the **open point**: whether the club's bank requires `FRST` for new mandates (§13-4; assumption in force `useFrst = false`, everything `RCUR`, agreed with the bank — Josep 08-09).

## Fixed conventions
- Statuses (catalog first): `COLLECTION_DATE_TOO_SOON`, `SEPA_NOT_CONFIGURED`, `CURRENCY_MISMATCH` **422** · `INVALID_STATE`, `RUN_NOT_ROLLBACKABLE`, `IDEMPOTENCY_KEY_REUSED` **409** · `MODULE_DISABLED`, `NOT_FOUND` **404** · `VALIDATION_ERROR` **400** · MEMBER/INSTRUCTOR on any `/remittances*` route **403**.
- Assumptions in force (do not ask): every mandate is new, `{clubSlug}-{memberNumber}-1`, `mandateSignedAt` = cut-over date, and **every transaction is `RCUR`** (`billing.sepa.useFrst = false`, Josep 08-09, B5/B6) — the `FRST` branch stays in the code and is unit-tested for other clubs; the collection date is day 1 of the **billed** month at the Cànic, so the run happens the month before (A28), and both semantics are product; the remittance screen has no mockup (§13-12); the bank sends no return file at R1 (BR-08) — unpaid items are recorded by hand through `POST /invoices/{id}/failure`.
- The full IBAN is **decrypted/read only inside the writer** and must never appear in an API response, a log line, an audit `changes[]` entry (`@Sensitive(MASK_IBAN)`), an exception message or a test fixture that is not the golden file; the golden file uses fictional `ES` test IBANs only. No secrets in the repo: creditor identifiers live in the club document, bank credentials nowhere.
- The XML is produced with the injected `Clock` (`CreDtTm`) and club-local dates (`ReqdColltnDt`) — the E5-T01 ArchUnit rule applies; marshalling is deterministic (fixed encoding `UTF-8`, no standalone declaration drift, stable attribute order) so the golden comparison is meaningful.
- Closed catalogs: no new parameter, event, notification, error code or audit action beyond `REMITTANCE_SUBMITTED`, which E8-T01 already added; proposals go to the report and `MESSAGES.md`.
- Evidence rule: report = command + exit code + last 40 lines; long outputs → `roadmap/evidence/E8-T03/NN-<name>.log`; task file ≤ 120 KB; fictional data only; never edit other tasks, `ROADMAP.md`, `docs/` (synced) or the Organizer verification section; English identifiers from the glossary; i18n keys never literals; ca/es/en together.

## Definition of Done
A run on the fictional census produces a `pain.008` file that validates against the schema in use, is byte-identical to the golden file, carries one `RCUR` block with the right `NbOfTxs`/`CtrlSum`, transliterated remittance information and `ReqdColltnDt` = day 1 of the billed month; the admin can list remittances, download the XML through a signed URL and mark it sent to the bank, after which the run can no longer be rolled back; a rolled-back remittance keeps its file; a club without SEPA generates no remittance and no error; and ADR-006's decision text is in the report ready for the organizer to file.
