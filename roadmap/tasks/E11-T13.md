## Steps
1. **Bounded rate-limit caches** (`RateLimits`). E11-T08 round 2 gave each route its own Caffeine cache, each with `maximumSize(100 000)`: with 21 routes the total is no longer bounded by `MAXIMUM_BUCKETS`. Cap each route's cache so the total stays bounded: `MAXIMUM_BUCKETS / Route.values().length` per route, or a fixed 10 000 per route (say which, and why). Expose the per-route `estimatedSize` package-privately for the test. Test (`RateLimitsTest`): a default `RateLimits`, fill two routes with more distinct subjects than the cap (after `cleanUp()`, eviction runs on the caller's thread), assert each route's cache has `estimatedSize() ≤ cap` and that the sum over every route is ≤ `MAXIMUM_BUCKETS`.
2. **The webhook subject during a Mongo outage** (`RateLimitFilter`, `ClubConfigService.known`). `knownClubs.test(pathClub)` calls `clubs.ids()` through a one-minute cache; when Mongo is down the lookup throws and the Stripe webhook answers 500 from the filter. Catch the lookup's failure (in the filter or in `known`): the `STRIPE_WEBHOOK` subject falls back to `unknown:<ip>` and the request goes on to the controller (which answers what it answers). Test (`AnonymousRateLimitsTest`): a throwing predicate; the request is not a 500 from the filter and the bucket used is `unknown:<ip>`.
3. **A plan with a price twin is not offered** (ruling E138). Two `CURRENT` prices for one concept (a legacy start twin, INC-68 round 2) make billing refuse with `409 PRICE_OVERLAP`; the public offer still shows the first one. Now: `SignupPlanData.from` and `OfferViews.current` skip a plan whose concept has two current prices (the plan is not offered publicly: not in the signup's plan list nor in the public offer; the admin's list keeps showing it with its prices), and D2's validation of a submission whose plan has a twin refuses with `409 PRICE_OVERLAP {planId, concept, priceId, conflictingPriceId}` (the same details as billing's). Tests: the public offer and the signup plan list without the twinned plan; D2 refused; the admin's list unchanged. The `409` joins the validation operation's `@ContractErrors`.
4. **The cross-tenant price helpers** (`PriceRepository`). `normaliseValidityDates()` and `legacyStartTwins()` read every club (startup conversion, no tenant): make them package-private or name them `…AllClubs`, with a Javadoc line that says they are startup helpers; the twin removal logs at `WARN` (today `INFO`), with the same `Price start twins removed count=N ids=[…]` text. `named()` stops checking `collections.priceId` and `pack_balances.priceId`, which do not exist (`Collection` and `PackBalance` carry no `priceId`): the references are `members.priceId`, `invoices.lines.priceId` and `pending_charges.priceId`. The same three in `docs/DEPLOY.md`'s twin procedure (steps 2 and 3 of «Resolving a reported twin by hand»). Test: `ArchitectureTest` or a unit test that the two helpers are not public; `PriceDatesIT`: a twin named only by a `pending_charges` document is kept, and the WARN line is asserted.
5. **`StoredDays`'s rule is offset-based.** Its Javadoc and `PriceDateConverterTest` say «writer zone»; the rule depends on the writer's UTC offset at that midnight (valid from −11:59 to +12:00). Say «writer offset» in the Javadoc of `StoredDays` and in the test's Javadoc, and add the documented out-of-range example to `PriceDateConverterTest`: a date written by a JVM at +13 (`Pacific/Tongatapu` or a fixed `+13:00`) reads a day early, asserted as such (the test documents the limit; DEPLOY.md already states it).
6. **`CATALEG_ERRORS.md` row S12** lists `PRICE_OVERLAP` (the api's copy in `docs/specs/00-transversal/`; the organizer syncs it to the source, E109). `ErrorCatalogContractTest` stays green.
7. **The cancel path deletes the files at once** (E11-T11 review #1). An IT in `ErasureIT`: an `ACCOUNT` request `BLOCKED` halfway with a pending file (a dog photo or a task attachment of an erased club) in the store; `DELETE /platform/erasure-requests/{id}` → `204`; right after the response, before any daily run, the file has left the store and `filesPending` is empty. If the IT is green on the current code the step is the IT alone (say so); if it is red, fix `ErasureService.cancelAccountRequest` → `cleanAfterCommit`.
8. **A run with no active profile is `local`** (ruling E139). `application.yml` sets `spring.profiles.default: local`, so a run without an active profile is the local stack, by design. Fix the wording of `docs/DEPLOY.md`'s vault section (the sentence «staging, `prod` and a run with no profile included») and the Javadoc of `BankAccountVault.seal` («any other profile (staging, prod, none)»): with no profile the application runs `local` and keeps the IBAN in clear with the WARN. Relabel `BankAccountVaultTest.INC_31_E43_withoutTheKeyOnlyTheLocalProfileStoresAClearIbanAndItWarns`: its `new String[]{}` case models a `MockEnvironment` without the default profile, which the real configuration never has; make that case model the real one (`setDefaultProfiles("local")` and assert the clear path), or drop it and say why in the test.
9. **`ErasuresJob.filesCleaned`**. The counter counts only the daily run's `DELETE_FILES` items; the files the after-commit hook deletes (`cleanAfterCommit`, E11-T11) are not counted anywhere. Either count them in `filesCleaned` of the run that executed the request (the hook runs after the job's transaction: say how the count reaches the recorder), or document the gap in the Javadoc of `ErasuresJob` and in the report with the number the hook logs. A `PrivacyJobsTest` case for the behaviour you choose.
