# E3-T05 · E3 integration (back): signup end to end on the local stack with the mailbox (bin/e3-smoke), seed values for D1, gate E3 checklist

## Objective
Work packages WP-04-6 and WP-14-H (E3 part): the gate scenario runs unattended against the local stack (`compose.yaml` + published image) and the web integration task (E3-W03) reuses the same seed and mailbox.

## Spec references
S04 T-04-34 (the E2E path, here as an HTTP smoke), S14 T-14-11 · `backlog` gate E3: «a fictional signup enters through the public web (with and without family group, and a dog added to an active member), is validated in D2, the member receives N-02 and enters with the welcome link; D1 shows pending signups, KPIs and counters; `signup.enabled=false` closes the form» · E1-T10 (`bin/e1-smoke` pattern, local mailbox) · E1-T14 (`docker-compose.consumer.yml`, image).

## Context to load
`bin/e1-smoke`, `docker-compose.consumer.yml`, `seeds/club-canic.yaml`, E3-T03/E3-T04 reports · this file.

## Steps
1. `bin/e3-smoke [--image]`: starts the stack (or reuses `--image`), applies the Cànic seed, then runs with `curl`: `GET /signup` (enabled, 4 steps, plans, methods), identity check `NEW`, upload URL + PUT of a tiny fictional PDF, family lookup `FOUND` against a seeded holder, `POST /signup` (SEPA without IBAN → warning), `GET /dashboard` shows the pending signup (`count`, `olderThanWarn`), `GET /members/{id}/signup` warnings, `POST …/validation?dryRun=true` then real validation (level, next invoice date, amount) → `number` incremented, N-02 captured from the local mailbox and the welcome magic link exchanged for a session (`/me` = the new member), add-dog path (`POST /me/dogs/signup` → N-01 → validation → N-37 in the app inbox), a rejection path on a second applicant (N-03 captured), `signup.enabled=false` → `409 SIGNUP_CLOSED`; asserts exact statuses; prints a summary; tokens truncated; exit code.
2. Seed: `seeds/club-canic.yaml` (or `demo-seed`) holds the fictional pending signups of the D1 mockup (3 pending: two public, one older than the warn days with `ACCOUNT_NOT_PROVIDED`) so D1/D2 front work and screenshots have data; class/booking numbers stay `null`/0 until E4/E5 (documented).
3. `docs/DEPLOY.md`: the E3 variables (`SIGNUP_TOKEN_KEY` or whatever E3-T03 named the HMAC key, checkout fake vs Stripe placeholders, upload storage prefix) and the gate E3 checklist section (organizer-run steps).
4. `ROADMAP.md`: gate E3 checklist (back) with the smoke output as evidence.
