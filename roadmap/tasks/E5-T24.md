# E5-T24 · Real-core gaps from E4-W13, and the E5-T22 review

## Objective
The web's E4-W13 ran D2's edit of a readmission's reused dog against the real core (web repo, `roadmap/tasks/E4-W13.md`, report questions 1–3). It found two gaps that block ordinary use:

## Steps
1. **D2 adds a file (E4-W13 question 1, R-04-19).**
   - **What the web found on `d2952d5`:**
     - the drawer sends `PATCH /dogs/{id}` with `{documents: [{type: VACCINATION_CARD, files: [<kept signup key>, <new key>]}]}`. The new key comes from the admin's `POST /attachments/upload-url` (`purpose = DOG_DOCUMENT`). The PATCH answers `400 FILE_NOT_FOUND`;
     - the same PATCH with the kept key only answers 200;
     - the admin gets `403` on `POST /signup/upload-urls`.

     So no ADMIN route yields a key that the PATCH takes as a new file.
   - **The fix:**
     - on a `PENDING` dog, `PATCH /dogs/{id}` takes a new file key from the admin's `POST /attachments/upload-url` with `purpose = DOG_DOCUMENT`, when that key was uploaded in the same club and never claimed;
     - the reused dog of a readmission takes it too. Its other document routes stay frozen;
     - a key of another club, of another purpose, already claimed or never uploaded answers `400 FILE_NOT_FOUND`, as now. A removed key stays refused (E5-T21);
     - the limit of 10 new files per request counts these keys too (R-04-08);
     - update `DogPatch.documents`'s description. The `PATCH /dogs/{id}` description also says that the card requirement applies only when the card's keys change (E5-T23 question 1).
   - **ITs:**
     - an ordinary pending public-signup dog, and a reused dog, each get a new file through the admin's upload;
     - D2's view (`GET /members/{id}/signup`) then lists that file with its stored name;
     - the validation of the reused dog writes the file to the dog (E38).
2. **Signed local file URLs authorise themselves (E4-W13 question 2, CONVENCIONS_API §5, A31).**
   - **What the web found:** the local upload URL, `PUT /api/v1/attachments/uploads/{id}?expires=…&signature=…`, answers `401` to a `PUT` that carries only `Upload.headers`. It requires an ADMIN, INSTRUCTOR or MEMBER bearer on top of its signature. `GET /api/v1/attachments/files/{id}` and `GET /api/v1/signup/files` do the same. A signed URL must authorise itself, as S3's presigned URLs do: the web never sends a bearer to the storage, and an `<img>` cannot.
   - **The fix:**
     - on the local profile, these three endpoints are authorised by their `expires` and `signature` alone. They need no bearer, and a bearer does no harm;
     - the club comes from the signed file, never from a bearer;
     - a wrong signature or an expired URL answers `403`;
     - `PUT /api/v1/signup/uploads` already works without a bearer: keep it.
   - **ITs:**
     - a `PUT` with the URL and `Upload.headers` only answers 2xx, and the file can then be claimed;
     - a tampered signature answers 403, and so does an expired URL;
     - a download URL read without a bearer answers 200, and one of another file's signature answers 403.
3. **A LEFT member with an INACTIVE dog in the demo seed (E4-W13 question 3).**
   - `seed:demo` adds a fictional `LEFT` member with an `INACTIVE` chipped dog that has a vaccination card. Then the web's real-core e2e can reuse a seed dog in a readmission (R-04-06), as E4-W13 step 6 asks.
   - The seed stays idempotent: its second run reports 0 changes.
   - Update `bin/e3-smoke`'s counts if they change, and `seeds/README.md`.
4. **The instructor's audit origin (E5-T22 review #1, S14 §3, amended 26-09).**
   - An instructor's audited action is written with `origin = BACKOFFICE`. `actorRole = INSTRUCTOR` tells it apart.
   - The event envelope keeps `INSTRUCTOR` (`CATALEG_ESDEVENIMENTS.md`, amended 26-09): N-04 and N-05 route on it (S08 R-08-19).
   - Keep E5-T22's read-side mapping for the entries stored earlier.
   - IT: an instructor's audited action stores `BACKOFFICE`.
5. **`fields` on exports and `filter-values` (E5-T22 review #2 and nit #7, CONVENCIONS_API §4, amended 26-09).**
   - Exports honour `fields`: it picks the columns, through `selectColumns`. So each export publishes the same `x-fields` as its list, and a key outside it answers `400 INVALID_FILTER`.
   - `filter-values` does not publish `fields`.
   - The parameter's description no longer points to an `x-fields` that the operation lacks.
   - `@ListContract(acceptsFields = false)` together with `fields` fails at startup.
   - A contract test: no operation publishes `fields` without `x-fields`. Remove the `/export` and `/filter-values` skip from `ListFieldsContractIT` where it hid this.
6. **A member whose own plan is gone (E5-T22 review #3, R-04-09).**
   - A member whose plan is no longer assignable (inactive, or its module off) counts as a member without a plan.
   - `GET /signup` marks no plan `current` for that member.
   - Without `planIdRequested`, `POST /me/dogs/signup` answers `400 VALIDATION_ERROR` with `fieldErrors [{planIdRequested, REQUIRED}]`.
   - IT.
7. **The family member's IT (E5-T22 review #4 and nit #5).**
   - The add-dog IT builds its family member through the family-group signup and its validation (R-04-13), not by rewriting `planId`.
   - It asserts `current: true` on `ABONAT_FAMILIAR` and a quote with the family price.
   - Rename `R_05_19_T_04_09_…` to `R_05_19_T_05_07_…`, and `R_04_09_T_04_21_…` to `R_04_09_…` (AGENTS rule 5).
8. **Filters and nulls (E5-T22 questions 1 and 2).**
   - `/weeks`, `/class-sessions`, `/ring-blocks`, `/training-bookings` and `/bookings` already accept `id`: put it in their `x-filterable`. Contract test.
   - If `TemplateClass.placementId`'s projection sends `null` under COURSES, declare it `["string", "null"]`, as `ClassSession.placementId` is. Test with COURSES on.
