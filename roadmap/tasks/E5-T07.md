# E5-T07 · Concurrency guarantees proven on Mongo + deterministic outbox dispatch in ITs

## Objective
Three independent reviews (E4-T04 #1, E5-T02 #3, E5-T04 #1–#3) found the same pattern: `ActivityTransactions`, `BookingTransactions` and `TrainingTransactions` each keep 256 in-JVM fair `ReentrantLock` "lanes" held around the whole retried transaction. Inside one JVM they serialize the writers, so the concurrency tests (T-07-24/25, T-08-29/31/32, T-09-32/33) never reach the mechanism the specs name as the guarantee: the `$inc` sequences with `WriteConflict` retries (R-07-08, R-08-07) and the partial unique index `training_active_seat` (R-09-06). They would still pass if that mechanism were broken. R1 runs **one API instance** (ADR-003), so the lanes are acceptable as a contention bound, but the Mongo mechanism must be proven on its own, the lanes must be one shared component keyed per aggregate (the activity lanes are keyed by tenant, so unrelated clubs block each other), and the single-instance assumption must be written down.

The same reviews and the CI history found a second systemic problem: integration tests that call `dispatch()` on the outbox are flaky on the CI runner (T-07-23 in E4-T04, masked with Awaitility in round 2; `BookingsIT.T_08_24` failed and `T_08_26`/`T_08_27` errored at `BookingFixtures.impersonating:126 NoSuchElement` on the run of `8ce1b5c`, then passed on the next run with no test change). Find the root cause and fix it at the root.

## Steps
1. **One `LocalLanes` component** (in `shared.application`) replaces the three copies: fair locks taken in lane order, keyed **per aggregate** (activity id for S07, class id for S08, the S09 keys `dog:`, `member:`, `slot:`), never per tenant. It is switched by an application property `core.concurrency.local-lanes` (default `true`; infrastructure setting, not a club parameter), documented in `application.yml` and in `docs/DEPLOY.md`: «R1 runs a single API instance (ADR-003). The local lanes only bound contention inside one process; with more than one instance they protect nothing and the Mongo mechanisms below are the guarantee.»
2. **Mongo-path tests with the lanes off** (a test context with `core.concurrency.local-lanes=false`), one per mechanism, each asserting the invariant and proving the mechanism ran (for example a retry counter or metric incremented, or a `DuplicateKey` observed):
   - S07 (T-07-24/25): 20 concurrent registrations for 1 place → exactly one `ACTIVE`, never two; every other request ends `WAITLISTED` or `409 STALE_VERSION`; `registrationSeq` consistent.
   - S08 (T-08-29/31/32): last-seat burst → never overbooked; each request ends `201`, `409 CLASS_FULL` or `409 STALE_VERSION`; the `seat_locks` write conflict and its retry are exercised.
   - S09 (T-09-32/33): two direct inserts of an `ACTIVE` booking on the same `{clubId, ringId, startsAt, seatIndex}` → `DuplicateKeyException` → the service answers `SLOT_TAKEN`; a burst on one dog → the `trainingSeq` write conflict → retry → `TRAINING_LIMIT_REACHED` where due.
   Record in the report how many requests end in `STALE_VERSION` with the lanes off. Do not change the retry budgets of R-07-08/R-08-07/R-09-06 (spec values): if the numbers look too high, propose a value in the report.
3. **Same dog on two rings** (review E5-T04 #2): under `bookings.limitUnit = MEMBER`, two members of one family group can book the same shared dog at the same time on two rings, because their `$inc` hit different `Member` documents and the index is per ring and seat. Make every training booking also touch the dog (for example `$inc` a `Dog.trainingSeq`, whatever the unit), so the two transactions conflict in Mongo. Test with the lanes off.
4. **Write skew training ↔ ring block / class** (review E5-T04 #3, R-09-13): the booking reads «no class, no block» and inserts, while the S06 side reads «no live booking» through `TrainingConflictPort` and inserts; they share no document. Make both sides write one shared document per ring and day (for example a `$inc` on a ring-day sequence) so Mongo raises a write conflict and the retried side sees the other. Test with the lanes off: a concurrent block and booking on the same slot never leave a block over an `ACTIVE` booking without `RING_HAS_BOOKINGS`.
5. **Deterministic outbox dispatch in ITs**: find why `dispatch()` sometimes finds nothing to process on the CI runner (a likely cause: several cached Spring test contexts each run a background `OutboxDispatcher` against the same database and claim other test classes' events; or a lease/backoff in the dispatcher). Fix it at the root — for example no background polling in the test profile, or dispatch isolated per context — and remove the polling that only compensates for it (T-07-23's Awaitility loop). Then run `ActivityIT`, `BookingsIT`, `WaitlistIT` and `TrainingIT` **five times in a row** with `-XX:ActiveProcessorCount=2` (the CI runner has 2 cores) and paste the tails.
