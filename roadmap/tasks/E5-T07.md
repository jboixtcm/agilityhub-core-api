# E5-T07 · Concurrency guarantees proven on Mongo + deterministic outbox dispatch in ITs

## Objective
Three independent reviews (E4-T04 #1, E5-T02 #3, E5-T04 #1–#3) found the same pattern: `ActivityTransactions`, `BookingTransactions` and `TrainingTransactions` each keep 256 in-JVM fair `ReentrantLock` "lanes" held around the whole retried transaction. Inside one JVM they serialize the writers, so the concurrency tests (T-07-24/25, T-08-29/31/32, T-09-32/33) never reach the mechanism the specs name as the guarantee: the `$inc` sequences with `WriteConflict` retries (R-07-08, R-08-07) and the partial unique index `training_active_seat` (R-09-06). They would still pass if that mechanism were broken. R1 runs **one API instance** (ADR-003), so the lanes are acceptable as a contention bound, but the Mongo mechanism must be proven on its own, the lanes must be one shared component keyed per aggregate (the activity lanes are keyed by tenant, so unrelated clubs block each other), and the single-instance assumption must be written down.

The same reviews and the CI history found a second systemic problem: integration tests that call `dispatch()` on the outbox are flaky on the CI runner (T-07-23 in E4-T04, masked with Awaitility in round 2; `BookingsIT.T_08_24` failed and `T_08_26`/`T_08_27` errored at `BookingFixtures.impersonating:126 NoSuchElement` on the run of `8ce1b5c`, then passed on the next run with no test change). Find the root cause and fix it at the root.

## Steps
1. **One `LocalLanes` component** (in `shared.application`) replaces the three copies: fair locks taken in lane order, keyed **per aggregate** (activity id for S07, class id for S08, the S09 keys `dog:`, `member:`, `slot:`), never per tenant. It is switched by an application property `core.concurrency.local-lanes` (default `true`; infrastructure setting, not a club parameter), documented in `application.yml` and in `docs/DEPLOY.md`: «R1 runs a single API instance (ADR-003). The local lanes only bound contention inside one process; with more than one instance they protect nothing and the Mongo mechanisms below are the guarantee.»
2. **Mongo-path tests with the lanes off** (a test context with `core.concurrency.local-lanes=false`), one per mechanism, each asserting the invariant and proving the mechanism ran (for example a retry counter or metric incremented, or a `DuplicateKey` observed):
   - S07 (T-07-24/25): 20 concurrent registrations for 1 place → exactly one `ACTIVE`, never two; every other request ends `WAITLISTED` or `409 STALE_VERSION`; `registrationSeq` consistent.
   - S08 (T-08-29/31/32): last-seat burst → never overbooked; each request ends `201`, `409 CLASS_FULL` or `409 STALE_VERSION`; the `seat_locks` write conflict and its retry are exercised.
   - S09 (T-09-32/33): two direct inserts of an `ACTIVE` booking on the same `{clubId, ringId, startsAt, seatIndex}` → `DuplicateKeyException` → the service answers `SLOT_TAKEN`; a burst on one dog → the `trainingSeq` write conflict → retry → `TRAINING_LIMIT_REACHED` where due.
   Record in the report how many requests end in `STALE_VERSION` with the lanes off. Do not change the retry budgets of R-07-08/R-08-07/R-09-06 (spec values): if the numbers look too high, propose a value in the report.
3. **Same dog on two rings** (review E5-T04 #2): under `bookings.limitUnit = MEMBER`, two members of one family group can book the same shared dog at the same time on two rings, because their `$inc` hit different `Member` documents and the index is per ring and seat. Make every training booking also touch the dog (for example `$inc` a `Dog.trainingSeq`, whatever the unit), so the two transactions conflict in Mongo. Test with the lanes off.
4. **Write skew training ↔ ring block / class** (review E5-T04 #3, R-09-13): the booking reads «no class, no block» and inserts, while the S06 side reads «no live booking» through `TrainingConflictPort` and inserts; they share no document. Make both sides write one shared document per ring and day (for example a `$inc` on a ring-day sequence) so Mongo raises a write conflict and the retried side sees the other. Test with the lanes off: a concurrent block and booking on the same slot never leave a block over an `ACTIVE` booking without `RING_HAS_BOOKINGS`.
5. **Deterministic outbox dispatch in ITs**: find why `dispatch()` sometimes finds nothing to process on the CI runner (a likely cause: several cached Spring test contexts each run a background `OutboxDispatcher` against the same database and claim other test classes' events; or a lease/backoff in the dispatcher). Fix it at the root — for example no background polling in the test profile, or dispatch isolated per context — and remove the polling that only compensates for it (T-07-23's Awaitility loop). Then run `ActivityIT`, `BookingsIT`, `WaitlistIT` and `TrainingIT` **five times in a row** with `-XX:ActiveProcessorCount=2` (the CI runner has 2 cores) and paste the tails.

**4. Step 5: the root cause, and why the fix is at the root.** Every cached Spring test context uses the same database, `agilityhub_test`. `OutboxDispatcher.dispatch()` claims records across tenants (`OutboxRepository.claim`): PENDING records with `nextAttemptAt ≤ now`, oldest `nextAttemptAt` first, at most 100 per call. `nextAttemptAt` is stamped with each context's `MockClock`, and many tests run at `2026-01-01`, far earlier than the S07/S08 fixtures (`2026-09-14`, `2026-10-06`). Test classes that publish events without dispatching them leave them PENDING.

A test's few synchronous calls (`BookingFixtures.dispatch()` = 6 × 100, `ActivityIT` = 5 × 100) therefore first spend their claims on other tests' older events. If the claimable backlog exceeds 500–600, the test's own events are never reached. The assertion then sees nothing: `0 of 6` N-32b rows in T-07-23, or an entry still `ACTIVE` after `cancel(); dispatch();`.

How big the backlog is depends on which classes ran before, so on the class order. Failsafe's default `filesystem` order is directory order: stable on macOS, arbitrary on the Linux CI runner. That is why the CI failed and then passed without a test change. Awaitility "fixed" T-07-23 only because its 100 ms polling calls `dispatch()` up to about 100 times (about 10 000 claims), enough to drain the backlog.

Measured:

- The final clean verify prints the PENDING backlog each test starts with when it is above one batch: 446 before `DashboardIT`, 158 before `SignupIT`, 651/724 before `DemoScenarioSeedIT`, 651–663 before `DemoPlanningSeedIT`/`DemoSeedsIT`, and 163–167 before `PlayoffMigrationIT`. These are 15 lines `E5-T07 outbox backlog discarded…` in `07-final-clean-verify.log`.
- **Counterfactual** (`05-counterfactual-heavy-backlog-first.log`, exit 1): with the discard disabled (`-Dit.keepOutboxBacklog=true` in the forked JVM) and the backlog-heavy classes first (`PlayoffMigrationIT, DashboardIT, Demo*SeedIT, SignupIT` before `WaitlistIT, BookingsIT, ActivityIT`, `-Dfailsafe.runOrder=reversealphabetical`), `WaitlistIT.T_08_21` fails the CI way: `["state"="ACTIVE" (expected: "NOTIFIED")]` right after `cancel(...); dispatch();`. Result: `Tests run: 114, Failures: 1`.
- **Control** (`06-control-heavy-backlog-first-fixed.log`, exit 0): the same classes, order and 2 CPUs with the discard on give `Tests run: 114, Failures: 0`.
- `OutboxIT.E5_T07_anEarlierPendingBacklogIsClaimedFirstAndDelaysALaterEventByWholeBatches` reproduces the starvation deterministically: 150 older records, then 1 dispatch leaves our event PENDING and a second one delivers it.
- Honest note: two other counterfactual runs **passed** with the backlog kept. One ran `DemoScenarioSeedIT` first and then the three classes (`03-…`, exit 0). The other was the whole suite in the local filesystem order (`04-…`, 739 tests, exit 0). In those orders the claimable backlog stays under the 500–600 claims. Only an order like the one above reaches it.

The fix: `AbstractIntegrationTest.discardOutboxBacklog()` (`@BeforeEach`, runs before every subclass fixture) deletes the PENDING outbox records that earlier tests left behind. Each test starts with an empty backlog, so `dispatch()` only ever sees the test's own events and the 100-per-call batch holds for any class order. Tests never run in parallel (one failsafe JVM, no JUnit parallelism), and every fixture rebuilds its own data, so nothing else depends on another test's pending events. No background dispatcher runs in the ITs: all Spring test contexts set `shared.scheduling.enabled=false`. The T-07-23 Awaitility loop is replaced by the plain `dispatch()` + assertion.

### Assumptions
1. **Lane keys** carry the open tenant as a prefix, so the same id in two clubs never shares a lane. That is still "per aggregate", not per tenant. Training lanes add `day:<club-local date>` because the bookings of one day now share ring-day documents; the lane queues them locally instead of spending retries. `slot:` is kept as the task names it.
2. **The ring-day document** is keyed `clubId:ringId:date` (club-local date).
   - Blocks and classes are single-day (`RingBlockService.validate` and the class rules), so one document per write is enough.
   - S06 touches it only on the write paths that already check the training bookings: block create/patch, `syncForActivity`, and a class moved onto a ring. The read-only previews (`ring-conflicts`, the calendar) never write.
   - The touch is skipped when `FREE_TRAINING` is off, because then there are no bookings to conflict with.
3. **The `ActivitiesController` mutations** lane on the activity they write. `POST /activities` (create) has no existing activity, so it takes no lane. A registration cancellation lanes on its registration's activity, read before the transaction; the id never changes. `cancelMatching` (inactivity or member left) lanes on the member's registrations' activities.
4. **The outbox discard** deletes only PENDING records (PUBLISHED/FAILED stay for tests that count events). It runs in the base class `@BeforeEach`, before every subclass fixture. `-Dit.keepOutboxBacklog=true` disables it for the counterfactual evidence only. It is a JVM system property of the forked test JVM and never set by the build.
5. **Test support.** `AbstractIntegrationTest` prints `Integration JVM availableProcessors=N` once per JVM. It proves the `-XX:ActiveProcessorCount=2` runs.
6. **The retry meters** (`core.transactions.*`) are observability, not catalog items (parameters, events, notifications, error codes), so no catalog change applies.

That is because the burst's winners commit one by one while the losers have only 3 more attempts (S07) or 3 attempts in total (S08) at 50–150 ms.
