# E5-T12 · Josep's answers B29–B33 in the migration + level PENDENT + coverage over progression levels

## Objective
On 2026-09-24 Josep accepted the five proposals B29–B33 (`docs/DECISIONS_PENDENTS.md`, Part B). The organizer measured case 5 (B33) on the real export:
- 20 email addresses appear in two active records;
- **17** of them are the same person with two dogs: Playoff makes one record per dog, and the second record carries a different NIF;
- **3** are families.

This task does three things:
- it applies the answers to the migration (S18 `MappingConfig` v5, the new optional auxiliary file `persones.csv`, accounts only for `ACTIVE` members);
- it adds the level «Pendent» to the Cànic seed;
- it finishes ruling E29: levels outside the progression do not appear in the D3 coverage table.

## Steps
1. **Mapping (B29–B32).** Update `playoff-v1.yaml`, or move to a `playoff-v2.yaml` and say which in the report:
   - `"familiar abonat/curs"` → `ABONAT_FAMILIAR`, with the family-group behaviour of `"familiar abonat"` (B31).
   - `"quota reduïda"` stays unresolved, with the `PLAN_UNMAPPED` warning (B30, confirmed).
   - `pendent` → level `PENDENT`, with the `LEVEL_PENDING` warning; remove it from `unresolvedLevels` (B32).
   - `Foto` → `Dog.photoFileKey` (B29, confirmed).
   - Every target code of `plans` and `levels` must exist in the Cànic seed. `cadells: CADELLS` does not match the seed code `CAD`: fix it, and add a test that fails when a mapped code is missing from the seed.
2. **Seed.** Add the level `PENDENT` to `seeds/club-canic.yaml`, following the S05 §12 row:
   - name ca «Pendent», es «Pendiente», en «Pending»;
   - order 90, color `#9AA0A6`, capacity 5;
   - `grantsFreeTraining = false`, `progression = false`;
   - it is in no template class.

   Check which tests assert the derived capacity row of D11 or the list of levels, and update them. If the web real-core e2e must change, say so in `roadmap/MESSAGES.md`.
3. **Coverage (R-06-06, E29).** The coverage table lists only the active **progression** levels, so Teràpia and Pendent do not appear. Update the tests.
4. **The same person across several records (R-18-04 (f), E32).** Add the optional auxiliary file `persones.csv`, with the columns `ID associat principal`, `ID associat unida` and `NIF`.
   - The joined record adds only its dog to the principal record's person.
   - The person keeps the NIF given in the file.
   - The report gets the warning `PERSON_MERGED`.
   - Without the file, each NIF is one person, as today.
   - The anonymizer handles the file with the same HMAC ids as the members file.
5. **Accounts (R-18-12, E32).**
   - Only `ACTIVE` members get an `Account`. Migrated `LEFT` members keep their email as a contact email only.
   - Among `ACTIVE` persons who share an email, the account goes to the record with the oldest `Data alta` (tie: the lowest member number).
   - The other person gets `EMAIL_SHARED`, and the report proposes a family group with the account holder.
6. **Tests (T-18-06).** Extend the synthetic export with four cases:
   - a same-person pair, confirmed through `persones.csv`;
   - an unconfirmed same-person pair;
   - a family pair;
   - an ACTIVE/LEFT pair that share an email.

   Assert the persons, dogs, accounts, warnings and report lines. Never use the real export: fictional data only (`@example.test`).
