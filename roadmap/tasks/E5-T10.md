## Steps
1. **E5-T01 review #1 (R-15-22).** `ArchitectureRules.TIME_FROM_CLOCK` must also forbid, outside the clock configuration:
   - the `now(ZoneId)` overloads of `LocalDate`, `LocalDateTime`, `LocalTime`, `ZonedDateTime` and `OffsetDateTime`;
   - `Calendar.getInstance()`.

   Add a `ClockRuleTest` case that proves a `LocalDate.now(ZoneId)` violation is reported.
2. **E5-T01 #2: a reaped holder stops.** When `locks.renew(...)` returns `false`, the runner applies no further item of its plan. It ends as a reaped run: its row is already `FAILED`, and it writes nothing more. Test with a two-item plan that loses its lease after the first item. The slow holder must never apply the second item.
3. **E5-T01 #3 and #4.**
   - `reap()` records `jobs.run.duration{status=FAILED}` when it closes a row.
   - When a slow holder finds its row already reaped, its WARN logs its local counters.
4. **E5-T02 review #1: the provider-failure path.** In `BookingConfirmationService`, when the provider call fails:
   - cancel only if the booking is still `PAYMENT_PENDING`, re-read inside the locked transaction;
   - rethrow the original failure (any later exception is added with `addSuppressed`);
   - release the idempotency key; a 422 is never stored for it.

   Test the race: the `UpfrontPaymentFailed` consumer cancels the booking first.
5. **E5-T02 #2.** `SingleClassCharges.prepare` checks that the club has the provider enabled, as the signup checkout does (`422 PAYMENT_PROVIDER_NOT_ENABLED`). Test.
6. **E5-T02 #3: `checkoutUrl` on the booking.** Per S08 §6, the `Booking` resource carries `checkoutUrl`.
   - Persist it on the booking while it is `PAYMENT_PENDING`, so that `GET /bookings/{id}` returns it.
   - Clear it when the booking leaves `PAYMENT_PENDING`.

   With this, a failed store of the 201 no longer loses the link. Test.
7. **E5-T02 #4: P7 closes the provider side.** When P7 (`PaymentTimeoutsJob`) cancels a `PAYMENT_PENDING` booking, it also expires that booking's checkout session and line (`CheckoutService.expire` / `SingleClassChargePort.abandon`). A late provider success can then no longer capture money for a cancelled booking. Test.
8. **Ruling E30 (E5-T02 #5).** A booking cancelled because the provider call failed synchronously sends **no N-40**: the member already sees the error in the app.
   - Propose the mechanism in the report. It must be payload-only: no new reason value, event or notification.
   - Test that the P7 timeout path still sends N-40.
9. **E5-T05 review #2.** `fixtures/contracts/e5-notifications.json` also covers N-16 (both audiences), N-17, N-33 and N-54, with their catalog variables (`E5ResponseContractTest`).

### Assumptions
1. **E30 mechanism (step 8).** It is payload only. `BookingCancelled` of the synchronous provider-failure path carries
   `checkoutFailed: true`, and the N-40 handler skips such events. The reason stays `PAYMENT_TIMEOUT`; no new reason, event
   or notification. The flag is absent elsewhere, so P7 and a real `UpfrontPaymentFailed` still send N-40.
   - `openCheckout` cancels the booking **before** abandoning the checkout. The `UpfrontPaymentFailed` of that abandon then
     finds the booking CANCELLED, and the consumer path cannot send an N-40 either.
   - The only way the consumer cancels first is an expiry from the provider itself during the call (the tested race). That is
     a real payment expiry, so its N-40 stands.
2. **Order in step 4.** Cancel first, then abandon. If the abandon fails after the cancel, the line stays `CHECKOUT_PENDING`,
   but the provider never opened a session. The abandon failure is added as suppressed to the rethrown provider failure.
   `keepCheckoutUrl` is inside the same `try`: if persisting the URL fails, the booking is cancelled and the checkout
   abandoned as for a provider failure (the review's second option). The member then retries.
3. **Idempotency key (step 4).** "A 422 is never stored" is guaranteed by the key being released, whatever the status:
   `IdempotentOperation.release()`, called by the controller when `openCheckout` throws, makes the filter abandon the record
   even for a 409/422 (tested with a provider 409).
4. **Step 2 also covers a lease that expired without a retake.** For example, Mongo's TTL removed the lock. `renew` returns false,
   and the holder closes its own row `FAILED` with `leaseExpired=true`. The row is then not exclusive, so the next tick
   retakes the occurrence as `CATCH_UP`, and `JobFailed` → N-42 alerts. `renew` runs every 60 s against a 300 s lease, so a
   reaped holder always sees it before its next item (not during a single long `apply`).
5. **R-15-12b for P6 (step 10).** A `WaitlistExpired` expiry alerts whenever the class is below `classes.minDogs` with no
   standing alert (`risk.lowAlertSentAt == null`), even without a drop. This is the literal text of R-15-12b ("`WaitlistExpired`
   que deixi la classe igual … `countedDogs < minDogs` → emet"). It is the only path where N-54 fires without a cancellation.
6. **The model wins on names; one addition.** `Booking.charge.checkoutUrl` is a new persisted field. The model's `charge {…}` does
   not list it, but S08 §6 puts `checkoutUrl` on the `Booking` resource and step 6 asks to persist it. See proposal 2.
7. **Platform pass (step 14).**
   - The "P9 cycle" is the UTC day of the occurrence. The claim is a `job_locks` document `platform:CLEANUP` (`holder`,
     `acquiredAt`, `expiresAt` = end of that UTC day, removed by the existing TTL).
     - The first real P9 run of the day, of any club, claims it.
     - A dry run only peeks.
     - A late catch-up of an older day cannot reclaim while the lease is there.
   - Platform rows belong to no club, so their retention is the **catalog product value**
     (`ParameterCatalog.defaultInteger("jobs.retention.domainEventsDays" / "jobRunsDays")`, 90 · 90), never the claiming
     club's value. The queries match only `clubId: null`.
   - The existing `CleanupJobIT` tests insert a taken claim in `@BeforeEach`, so their exact club counters do not depend on
     platform rows other suites left in the shared database.
8. **N-17 variables (step 9).** The organizer's 24-09 ruling added `class_description` and `ring_name` to the N-17 catalog
   row. The code stored only `dogs_count`, so N-17 now stores them too (the fixture lists the catalog row).
   `RiskReviewJobIT.T_15_13` asserts them.
9. **D1 ring label (step 13 #9).** The placeholder is now `scheduling.noRing` in each product language ("Sense" / "Sin pista" /
   "No ring") instead of the literal "—". The default locale is the club's `defaultLocale` instead of `"ca"`. It only
   shows for a class whose ring is not in the catalog.
