# E8-T04 · Payment providers (S12 WP-12-D)

## Objective
Work package S12 WP-12-D. The `PaymentProvider` port E3-T03 opened for the signup checkout grows into the full contract of S12 §6 — `createCheckoutSession`, `createOffSessionPayment`, `refund`, `parseWebhook`, `forgetCustomer` — with three implementations: `StripePaymentProvider` (per-club keys, test or live mode), `FakePaymentProvider` (the deterministic double every test and the demo seed drive) and the `MANUAL` branch (no provider at all). On top of it: charging a run's card invoices off-session, retrying a failed one, refunding, the idempotent webhook endpoint backed by `StripeEvent`, the member's card-setup link and the «Targeta no vàlida» state. The Cànic uses `SEPA_XML` and `MANUAL` only (A14: no in-app payment screens at R1), so **everything here must be provable with the fake provider**; the real Stripe path is proved with test keys when they exist.

## Steps
1. **Port** (`payments/application/PaymentProvider`): widen the existing interface to `createCheckoutSession(Request)` (already there — keep the signature and add `mode = payment|setup`, `bookingId`, `upfrontPaymentIds`), `OffSessionResult createOffSessionPayment(OffSessionRequest {amount, currency, customerId, paymentMethodId, idempotencyKey, metadata {clubId, invoiceId}})`, `RefundResult refund(chargeId, Money amount, idempotencyKey, reason)`, `WebhookEvent parseWebhook(String payload, String signatureHeader, String webhookSecret)` and `void forgetCustomer(customerId)`. Add `boolean supports(Capability)` so `MANUAL`-only clubs answer `422 PAYMENT_PROVIDER_NOT_ENABLED` uniformly. A `PaymentProviderRegistry` resolves the implementation **per club** from `CLUB.paymentProviders`; a club with no `STRIPE` entry gets the null implementation that throws `422 PAYMENT_PROVIDER_NOT_ENABLED`. Keep `FakeCheckoutGateway` working for the signup flow (E3-T03) or fold it into `FakePaymentProvider` — say in the report which you did and prove `bin/e3-smoke` still passes.
2. **Per-club keys**: `secretKeyEnc` and `webhookSecretEnc` are stored **encrypted at rest** in the club document with a key that comes from an environment variable (`AGILITYHUB_SECRETS_KEY` or whatever E1 already established — reuse it, do not invent a second scheme); `publishableKey`, `mode` (`test|live`) and `accountId` are plain. **No secret value ever appears in the repo, in a response, in a log, in an audit `changes[]` entry (`@Sensitive(HIDE)`) or in a seed** — the fixtures use `sk_test_…example` placeholders. Decryption happens only inside `StripePaymentProvider`. A `mode = live` club must refuse to start a charge when the process is running with a `test` key and vice versa (`422 PROVIDER_CONFIG_INVALID`, 422 by §1).
3. **`StripePaymentProvider`** (`payments/application/stripe`, the official Java SDK added to `pom.xml`): Checkout sessions (`payment` and `setup`, `setup_future_usage` when the club wants the card saved, `success_url`/`cancel_url`, `client_reference_id`, `metadata`), off-session `PaymentIntent`s with `confirm = true, off_session = true` and an **idempotency key** (`invoiceId` for the first attempt, `invoiceId:attempt` for retries), `Refund`s, and `forgetCustomer` (delete the Stripe customer when S14 pseudonymises a member). Every call goes through a small `StripeCalls` wrapper that maps Stripe exceptions to `ApiException`s and retries `429` with exponential backoff. **Stripe test keys are a @jordi input**: if `STRIPE_TEST_SECRET_KEY` / `STRIPE_TEST_WEBHOOK_SECRET` are not in the environment, finish the task with the fake provider proving every rule, mark the live-SDK path as compiled-but-unexercised, and write **«Blocked: Stripe test account — @jordi»** in the report naming exactly which assertions are missing.
4. **`FakePaymentProvider`** (`test` and `local` profiles, deterministic): records every call with its idempotency key, returns scripted outcomes driven by the test (`succeed`, `fail(code)`, `require_action`), and exposes a `deliverWebhook(type, payload)` helper so the tests replay `checkout.session.completed`, `checkout.session.expired`, `payment_intent.succeeded`, `payment_intent.payment_failed`, `charge.refunded`, `setup_intent.succeeded`, `payment_method.detached` and `customer.deleted` — including **duplicates and out-of-order pairs**. The demo seed uses it.
5. **Charging a run (R-12-13)**: `POST /billing/runs/{id}/card-charges` (ADMIN, `Idempotency-Key`, `202`) implements E8-T02's `CardChargingPort` — for every `CARD` invoice of the run in **batches of 25**: `createOffSessionPayment` → `Collection SUBMITTED` and invoice `COLLECTING`; a member with `paymentMethod.CARD.invalid` or without a saved payment method is skipped as `FAILED{NO_PAYMENT_METHOD}` + **N-35** to the member and **N-10** to the admins; `run.status = CHARGING` and → `COMPLETED` when every STRIPE collection is resolved. `409 INVALID_STATE` when the run is not `GENERATED`/`CHARGING`; `422 PAYMENT_PROVIDER_NOT_ENABLED` for a club without Stripe. Audited **`CARD_CHARGES_STARTED`** with `details {runId, submitted, skipped}`.
6. **Retry (R-12-18)**: `POST /invoices/{id}/retry {version}` on a `FAILED` invoice whose member has a valid `CARD` → a new `Collection` with `attempt + 1` and `idempotencyKey = invoiceId:attempt`, invoice → `COLLECTING`. `409 MAX_ATTEMPTS` past `billing.stripeMaxAttempts` (3), `422 NO_PAYMENT_METHOD` without a card, `409 INVALID_STATE` on any other status. T-12-30 Stripe half.
7. **Refunds (R-12-20)**: `POST /invoices/{id}/refund {amount?, reason}` and `POST /upfront-payments/{id}/refund` on `SUCCEEDED` Stripe collections → `PaymentProvider.refund` with an idempotency key; the webhook `charge.refunded` appends to `Collection.refunds[]` and raises `Invoice.refundedTotal`; an invoice with `refundedTotal = total` stays `PAID` and the list renders «reemborsat» — **no new status**, the numbering series stays immutable (R-12-10). `409 REFUND_EXCEEDS_PAID` is written by S12 §6 but the catalog's rule 0 makes it **422**: ship 422. SEPA and manual collections have no automatic refund → `422 PAYMENT_PROVIDER_NOT_ENABLED` (the admin issues a negative adjustment invoice, E8-T02). `billing.singleClassCancelPolicy` on an in-time cancellation of a `PAY_TO_BOOK` booking: `REFUND` → automatic refund, `CREDIT` → a negative `PendingCharge`, `NONE` → nothing. Audited `PAYMENT_REFUNDED`. T-12-17.
8. **Webhook (R-12-21)**: `POST /webhooks/stripe/{clubId}` — no JWT, outside the tenant filter, resolves the club from the path and verifies the signature with that club's `webhookSecret`; a bad or missing signature → **`401 WEBHOOK_SIGNATURE_INVALID`** (§1; S12 §6 also writes 401 — the catalog moved it from 400 on 06-09) plus a `SecurityEvent` (S14 R-14-17). A valid event is **stored first** as `StripeEvent {eventId (unique), clubId, type, receivedAt, payloadHash}`; a duplicate `eventId` returns `200` with no effect. Processing runs **inside a transaction** per type: `checkout.session.completed` → `UpfrontPayment CHECKOUT_PENDING → PAID` with `amount_total`, saves `paymentMethod.CARD {customerId, paymentMethodId, last4, brand}` when `setup_future_usage` was set, emits `UpfrontPaymentSucceeded {paymentId, concept, bookingId?, packBalanceId?, memberId}` (which opens a pack through E8-T02's `PackBalanceOpeningPort`, implemented in E8-T05, and activates a `PAY_TO_BOOK` booking through S08) and **N-30**; `checkout.session.expired` → `UpfrontPayment DUE` + `UpfrontPaymentFailed`; `payment_intent.succeeded` → `Collection SUCCEEDED`, invoice `PAID`, `InvoicePaid{STRIPE}` and **N-30 only when `billing.stripeReceiptEmail = false`**; `payment_intent.payment_failed` → `Collection FAILED{code}`, invoice `FAILED`, `InvoiceFailed` → **N-35** to the member (with `retry_link = /me/card-setup`) and **N-10** to the admins; `charge.refunded` → step 7; `setup_intent.succeeded` → new card saved, `CARD.invalid = false`, `MemberPaymentMethodChanged` → **N-38**; `payment_method.detached` and `customer.deleted` → `CARD.invalid = true`, `MemberCardInvalidated` → N-35. **Out-of-order rule**: each handler checks the current state — a `succeeded` after a `failed` wins, a `failed` after a `succeeded` is ignored with `outcome = IGNORED`. Always answer `2xx` once the event is stored (processing may be deferred and retried internally); emit `StripeWebhookReceived {eventId, type, outcome}`. T-12-15, T-12-16.
9. **Member card (R-12-22)**: `POST /members/{id}/card-setup-link {successUrl, cancelUrl}` (ADMIN) and `POST /me/card-setup` (MEMBER, from the banner on screen 12) → a Checkout session with `mode = setup` returning `{checkoutUrl}`; the result arrives by `setup_intent.succeeded`. `Member.paymentMethod.CARD.invalid` drives the «Targeta no vàlida» badge on D10, the pending rows of D1 and the `CARD_INVALID` incident of the simulation. `forgetCustomer(customerId)` is called when S14 pseudonymises the member — expose it as a small `PaymentPrivacyPort` the privacy vertical can call, with a null object today. T-12-31.
10. **Checkout return (S04 R-04-26, S08 R-08-18)**: `GET /checkout-sessions/{id}` returns `{status PENDING | PAID | EXPIRED}` for the return screen's ≤ 10 s polling; the **truth is the webhook**, never the redirect. `POST /checkout-sessions {memberId?, signupToken?, bookingId?, upfrontPaymentIds?, successUrl, cancelUrl}` accepts the pack-purchase shape as well (§13-11: the endpoint is ready, **there is no app screen for it at R1** — A14). Keep the signup path byte-compatible.
11. **Modules and variants**: a club with only `MANUAL` never reaches any of this (`422 PAYMENT_PROVIDER_NOT_ENABLED` on the card routes, no `Collection STRIPE`, D6's button 2 labelled for its providers); a provider configured but disabled shows up in the simulation as `PROVIDER_DISABLED` and its members are skipped (R-12-28); `BILLING` off → every route `404 MODULE_DISABLED`. T-12-32 Stripe half.
12. **A payment completed after a local expiry (organizer 24-09, E34).** P7 expires a PAY_TO_BOOK session only on our side (E5-T10), so Stripe can still capture it. A `checkout.session.completed` for a session that is `EXPIRED` locally, or for a booking that is `CANCELLED`, is refunded at once through step 7 (reason `LATE_COMPLETION`) and audited. The reconciliation mark that E5-T13 adds is the input. Test it with the fake provider: a completion after P7 gives exactly one refund.
13. **The signup checkout (gate E3 audit, 24-09).** See `roadmap/reviews/gate-E3/consolidated.md`, «Routed elsewhere». Today `CheckoutService` (`:39-43`) generates a fresh UUID and calls the provider before the Mongo transaction commits.
    - Persist the checkout operation first. Then call the provider after the commit, with a stable idempotency id (the operation id), through a recoverable step: a retry after a failure reuses the provider session, or creates it once.
    - A `checkout.session.completed` that arrives after the local session expired or was cancelled is still recorded for the signup rows:
      - rows that are still payable (`DUE`/`CHECKOUT_PENDING`) → `PAID`;
      - rows already `CANCELLED` (a rejected signup) → the payment is refunded as in step 12, with reason `LATE_COMPLETION`.
    - A cancelled or expired Checkout session returns its rows to `DUE` (S04 §5).
    - N-01 carries `pay_link`: a bounded payment-retry action for the rows still `DUE` (a signed link, or the capability flow of S04 R-04-26). The notification never stores a raw secret.
    
    Tests with the fake provider:
    - a commit failure after the provider call → one provider session after the retry;
    - a completion after the local expiry → recorded, or refunded when the rows are cancelled;
    - a cancelled session → `DUE`;
    - the N-01 `pay_link` works, and expires.

## Fixed conventions
- Statuses (catalog first): `WEBHOOK_SIGNATURE_INVALID` **401** · `PAYMENT_PROVIDER_NOT_ENABLED`, `PROVIDER_CONFIG_INVALID`, `NO_PAYMENT_METHOD`, `REFUND_EXCEEDS_PAID` (S12 §6 writes 409; rule 0 gives **422**), `CURRENCY_MISMATCH` **422** · `MAX_ATTEMPTS`, `INVALID_STATE`, `STALE_VERSION`, `IDEMPOTENCY_KEY_REUSED` **409** · `MODULE_DISABLED`, `NOT_FOUND` **404** · `VALIDATION_ERROR` **400** · MEMBER/INSTRUCTOR on ADMIN routes **403**.
- Assumptions in force (do not ask): the Cànic does **not** use Stripe and has no in-app payment screen at R1 (A14) — build the vertical anyway, for the other clubs, and prove it with `FakePaymentProvider`; the pack-purchase endpoint exists without a screen (§13-11); each club uses **its own** Stripe account (ADR-009), never a platform account — Stripe Connect and SAAS billing are R4; an unpaid receipt triggers no automatic claim or booking block (BR-08) — N-10 tells the admin, who decides.
- Idempotency everywhere: provider calls carry an explicit idempotency key derived from the domain (`invoiceId`, `invoiceId:attempt`, `upfrontPaymentId`), and the HTTP routes honour `Idempotency-Key` through the existing filter (`CONVENCIONS_API` §7). The webhook's idempotency is the unique `{eventId}` index.
- Secrets only from the environment or the encrypted club field; fixtures and seeds use `sk_test_…example` / `whsec_…example` placeholders and `@example.test` addresses. `Clock` injected everywhere (E5-T01 ArchUnit rule).
- Closed catalogs: no new parameter, event, notification, error code or audit action beyond what E8-T01 added; proposals to the report and `roadmap/MESSAGES.md`.
- Evidence rule: report = command + exit code + last 40 lines; long outputs → `roadmap/evidence/E8-T04/NN-<name>.log`; task file ≤ 120 KB; never edit other tasks, `ROADMAP.md`, `docs/` or the Organizer verification section; English identifiers from the glossary; i18n keys never literals; ca/es/en together.

## Definition of Done
With the fake provider a run's card invoices are charged in batches with one idempotency key each, a `succeeded` webhook marks them paid, a `payment_failed` marks them failed with N-35 and N-10, a duplicate event changes nothing, an out-of-order `failed` after a `succeeded` is ignored, a fourth retry is refused with `409 MAX_ATTEMPTS`, a partial and a total refund land on `refundedTotal`, a bad signature is `401` with a `SecurityEvent`, a `setup_intent.succeeded` replaces the card and clears `CARD.invalid` with N-38, and a `MANUAL`-only club gets `422 PAYMENT_PROVIDER_NOT_ENABLED` from every card route. With real test keys the same sequence runs against Stripe; without them the task finishes with the fake provider and the blocked line.
