# E1-T14 · CI publishes the api Docker image to GHCR + consumer compose file

## Objective
The web executor (and later staging, E0-T13) must run the **real core** without building Java: the web sandbox cannot write into the api repo, and staging should deploy an image, not a checkout. Make CI build the existing `Dockerfile` on every green `main` push and publish it to GitHub Container Registry, and provide a compose file that starts core + Mongo replica set + the fictional seeds from that image.

## Spec references
E0-T03 (CI), E0-T13 (`DEPLOY.md`, staging), E1-T10 (`bin/e1-smoke`, seeds), `docs/DEPLOY.md` (Caddy recipe from E1-T13).

## Context to load
`.github/workflows/ci.yml`, `Dockerfile`, `docker-compose.yml`, `bin/e1-smoke`, `seeds/*.yaml`, `docs/DEPLOY.md`, this file.

## Fixed conventions
- Image: `ghcr.io/jboixtcm/agilityhub-core-api` with tags `main` (latest green main) and `sha-<short>`; built with the multi-stage `Dockerfile` (JRE 21 runtime, non-root user, `HEALTHCHECK` on `/api/v1/health`), for `linux/amd64` **and** `linux/arm64` (Jordi's Mac is Apple silicon; the droplet is amd64). Publish job runs only after the test job succeeds and only on `main` (not on `[skip ci]` commits — the existing behaviour). Auth: `GITHUB_TOKEN` with `packages: write`; the package visibility follows the repo (private) — document `docker login ghcr.io` with a `gh auth token` for local pulls.
- `docker-compose.consumer.yml` (new, committed): services `mongo` (replica set, same init as today), `core` (the GHCR image, `SPRING_PROFILES_ACTIVE=local`, `MAIL_LOCAL_DIRECTORY` mounted, `OIDC_MASTER_KEY` ephemeral in local, ports `8080`), and a one-shot `seed` service that runs `club:apply seeds/club-canic.yaml` + `seeds/club-minim.yaml` with `SEED_PASSWORD` from the environment (`.env.consumer.example`). No real secret in the repo. Hosts: `app.example.test`/`admin.example.test`/`id.example.test` resolved by the consumer through `/etc/hosts` or the Vite proxy `Host` header (document both).
- `bin/e1-smoke` gains `--image` mode (or an env var) so it can run against the compose stack instead of a locally built jar — the same assertions, proving the published image works.
- `docs/DEPLOY.md`: section «Run the published image» (compose commands, login, seeds, ports) and the staging note (E0-T13 will pull `sha-…` tags).
