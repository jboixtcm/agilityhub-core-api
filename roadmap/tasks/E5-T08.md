### Assumptions
1. **Step 1, `origin: SYSTEM`.** Only the event payload carries it. The stored `ActivityRegistration.origin` keeps the model enum `APP | BACKOFFICE`. S07 §7 lists `origin` in the payload without values, and the task file names `SYSTEM`.
2. **Step 3, unknown club.** With a missing or invalid key, an unknown slug now answers `403 INVALID_API_KEY` instead of `404 CLUB_NOT_FOUND`, so existence is not revealed. `E4ContractIT` was changed accordingly. The keyless `files/{fileId}` route still resolves the club first; it takes no key. `PublicPlansController` / `PublicClubAccess.resolve` are unchanged; they are outside S07.
3. **Step 6, fields kept on `Member`.** The model has `lastDogForClass`/`lastDogForTraining` on `Member`, so I did not move them to a new document. `@ForeignOwned` removes them from the optimistic lock instead. Root cause for the reviewers: the entity-class `MongoTemplate.updateFirst` increments `@Version` by itself. That means the earlier "no version bump" `increment()` of `Member.trainingSeq` (unit MEMBER) and `Dog.trainingSeq` also bumped versions. They no longer do. The write conflict that E5-T07 relies on is unchanged: it comes from the `$inc` on the same document.
4. **Step 8.** I prove the query count with a Mockito unit test over the 50-row page. A Mongo command listener would need a new Spring test context.
5. **Step 11, "N-15 delivered for this offer".** This means an N-15 APP row about the entry (`variables.entityId`) with `createdAt ≥ entry.notifiedAt`. Both instants come from the same injected clock, and offers are made by the outbox consumers, not inside «as of» seeds. The N-15 ids keep their E5-T03 shape (`eventId:entryId:channel`).
6. **Step 12, carrier event.** The carrier is `SeatHoldReleased`, which every confirmation emits in its transaction. The catalog row says «no notifica», and the event itself still does not notify. It only carries `classId`, so the consumer can see the demotion that the same transaction made. There is no catalog event for the demotion, and I created none.
7. **Step 13.** `null` applies to every `WaitlistEntry` view (member, staff lists, join response). Lists keep the stored order.
8. **Step 16.** The recount runs from S02's `ClubModulesChanged` (`diff.modules.before/after`). The IT publishes the event by hand, because its `modules()` helper writes the club directly.
9. **Seen, not changed (outside the findings).**
   - The census `censusLastClassDog` consumer re-writes `lastDogForClass` from each `BookingCreated`. Because it is a second writer, an out-of-order delivery can leave an older dog; this was already so before this task. `R_08_23` books the same dog twice for that reason.
   - A same-class swap still emits `SeatReleased` for its own class. The consumer finds no free seat, so nothing is offered.
