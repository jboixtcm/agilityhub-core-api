## Steps
1. **The cut-off comes only from a public signup (review #1, R-04-26).** The checkout leaves out superseded readmission rows by cutting at `Member.signup.submittedAt`. Before E3-T10, `addDog()` overwrote `Member.signup` with an `APP_ADD_DOG` block. On such a record, the cut treats the last add-dog as a boundary and drops the earlier add-dog's payable rows, although no readmission happened.
   - Use `Member.signup` as the cut only when its `source` is `PUBLIC` (a public signup or a readmission). An `APP_ADD_DOG` block is never a boundary.
   - Regression test: persist two add-dog submissions A and B the old way (`Member.signup` overwritten with B's `APP_ADD_DOG` block, distinct timestamps). The checkout includes A's and B's unpaid rows. A real readmission still leaves out the superseded rows.
2. **Payment descriptions use each submission's locale (review #2, R-04-26).** The checkout reads its locale from `Member.signup`, which is now the original public signup. Every payment line is described in the locale of the submission it belongs to:
   - the dog's own block, for an add-dog;
   - `Member.signup`, for the public signup;
   - the applicant's, for a readmission (E3-T09).
   
   Test: a public signup in `ca`, then an add-dog in `es`. The add-dog lines sent to the provider are in `es`.

### Assumptions
1. **Where the cut reads its public signup (step 1).** The task says to use `Member.signup` only when its `source` is `PUBLIC`. On its own, that rule turns a legacy record into «no cut at all». This case breaks it: a readmission, then an add-dog written by the old code that overwrote `Member.signup`. The rows the readmission superseded would become payable again, and log `04` shows it. The pre-E3-T10 `storeDog` copied the block it had just written into `Dog.signup` (commit `5fa199e`, `SignupService.java:313` and `:346`). So the public signup's own block survives on its dog. The cut is therefore the latest `PUBLIC` block among `Member.signup` and the blocks of the owed submissions. A block of a dog transferred in from another member does not count, because this member owes none of that dog's submissions. An `APP_ADD_DOG` block never counts.
2. **Rejected blocks need no filter.** A rejected readmission restores the LEFT record (R-04-23, E38), so the member cannot check out. The only way back is a new readmission, which is newer than the rejected block. So a rejected `PUBLIC` block can never be the latest one while a checkout is possible.
3. **The locale of a submission (step 2)** is read from the block that carries its `submissionId`: the dog's own block for an add-dog; the copied `Member.signup` for a public signup or a readmission. The applicant's language is `Member.signup.locale` of the pending readmission, the value `applicant()` also uses. Some rows have no such block left: rows written before submissions existed (`submissionId = null`), or a dog whose block a later submission replaced. Those rows keep the pre-task behaviour: `Member.signup.locale`, then the club's default.
4. **Test fixtures.** The legacy record is made exactly as the old code left it: `Member.signup` := the last add-dog's own block. The member «leaves» through a Mongo write, because S13 (no route in this stage) will write the LEFT record. The write follows MODEL §`Member`/`Dog`: `status LEFT`, `leftAt`, `leftReason LEAVE_REQUEST`; the dogs become `INACTIVE` with `MEMBER_LEFT`. The readmission itself goes through `POST /signup` and reuses the dog (R-04-07).
5. **No contract change.** `Line.submissionId` stays internal. `lineViews` and the provider port are unchanged. The OpenAPI document is byte-identical (Evidence 1).
