# E6-T03 · Tasks, attachments, observations and follow-up (S10 WP-10-C)

## Objective
Work package S10 WP-10-C. An instructor writes a task for a dog with a video attached and the member sees it and ticks it done; the instructor keeps a private observation on the dog that no member ever sees; the member's own note to the instructors is read-only here but lands in the same follow-up inbox; and D14 shows every one of those movements as a list where each instructor has their **own** unread marks. The task runs in parallel with E6-T02 — it depends only on the contract — and it also delivers the `DogFollowupPort` implementation that gives the attendance sheet its `pendingTasksCount` and the student card its three blocks.

4. **Observations** — R-10-12: `PUT /dogs/{id}/observations {text, version}` (INSTRUCTOR, ADMIN, `TASKS`, `Idempotency-Key`) writes `Dog.remarks` (single private field, ≤ 2000) and `Dog.remarksMeta {updatedAt, updatedByAccountId, updatedByName}` through `DogService` (census owns the `Dog` document — call the service, do not write the collection from `followup`), emits `DogUpdated {dogId, diff: {remarks}}` and writes `AuditEntry{action: DOG_UPDATED}` with `@Audited`; stale `version` → `409 STALE_VERSION`. **No notification and no D14 row.** `Dog.remarks` must never appear in any `/me/*` response — add the assertion to the S03 projection test as well. **T-10-17**.
5. **`FollowupItem` projection** — R-10-13: one row per task (`kind: TASK`) and **exactly one row per dog** for the member note (`kind: MEMBER_NOTE`, upserted on every change). Fields as S10 §3; `activityAt` = the task's creation or the note's last change (completing a task updates `completedAt` only); member name, dog name and `levelCode` are resolved **at read time** (pages ≤ 50 rows) so a rename never needs a backfill; `levels.enabled = false` → `levelCode: null`. Consumers, idempotent by `eventId`: **`MemberNoteChanged {dogId, memberId}`** (emitted by `DogService`) → upsert the `MEMBER_NOTE` row with `activityAt = occurredAt`, `textExcerpt` from `Dog.instructorNote.text`, `authorAccountId` = whoever wrote it, which makes it unread again for everyone except the author, and fire **N-22** to every active instructor; **`DogTransferred`** (S03 R-03-14) → move `Task.memberId` and the dog's D14 rows to the new owner (the task follows the dog); **`DogDeactivated`** → nothing (tasks and rows are kept); **`TaskDeleted`** → `hidden = true`. Consuming the same `MemberNoteChanged` twice leaves **one** row. **T-10-18**.
6. **Read marks and D14 queries** — R-10-13: `FollowupReadMark {clubId, accountId (unique), readAllAt, readItemIds[]}`; `unread(item, me) = item.activityAt > readAllAt(me) ∧ item.id ∉ readItemIds(me) ∧ item.authorAccountId ≠ me`. `GET /followup` = universal list with `x-filterable: kind, memberId, dogId, authorAccountId, unread` and ordering **unread first (`activityAt` desc), then the rest (`activityAt` desc)** — implement the ordering in the query, not in the front; an undeclared filter → `400 INVALID_FILTER`. `GET /followup/unread-count` → `{count}` (the admin menu badge, refetched every 60 s by the front; it is also what `GET /dashboard/counters.followUpUnread` of S14 R-14-08 reads — wire it to the existing dashboard counter and say so in the report). `POST /followup/{id}/read` → `readItemIds += id` (prune ids whose `activityAt < readAllAt`). `POST /followup/read-all` → `readAllAt = now`, `readItemIds = []` in **one transaction**, O(1) whatever the row count. **T-10-06, T-10-18**.

### Assumptions
1. **Dependency direction (deviation from step 4 and step 7's wording, forced by `E0_T01_contextsHaveNoCycles`).** Census depends on followup (attachments) and bookings on census, so followup can import neither. Followup reaches the census through the new shared port `FollowupCensusAccess`, which census implements; the observations write is `DogService.observations` (census owns the `Dog`). The `DogFollowupPort` adapter is `configuration/FollowupPortConfiguration`, which maps `FollowupCardQuery` (followup) to the port (bookings). A new ArchUnit rule pins «followup imports neither census nor bookings».
2. **Observations version** = `remarksMeta.version` (0 before the first change), not the dog's `version`: another write of the dog (the member's note, a level change) must not make the instructor's save stale. The response and the card's block carry it.
3. **Keyed follow-up writes** run in the idempotency filter's own transaction (like the keyed POSTs): `POST /tasks`, `PUT …/observations`, `DELETE /tasks/{id}`, `DELETE /attachments/{id}`, `POST /followup/{id}/read`, `read-all`. The non-keyed ones (`PATCH`, completion, reopening, `POST /attachments` without a key) run in `FollowupTransactions`, retried whole on a write conflict.
4. **The D14 row writes of the task lifecycle** (creation, excerpt, `completedAt`, `hidden` on delete) happen in the task's transaction, not in an outbox consumer: a read right after the write sees them. `MemberNoteChanged` and `DogTransferred` are outbox consumers (`followup.MemberNoteChanged`, `followup.DogTransferred`), idempotent through the derived row ids. `DogDeactivated` has no consumer (nothing to do).
5. **A MEMBER_NOTE row** is unread again after a change: its id leaves every account's `readItemIds` (R-10-12, T-10-06). An older replay of the event only refreshes the excerpt. An emptied note hides the row and sends no N-22.
6. **Unread first**: the list computes `unread` per account in a `$set` stage and sorts by it before `activityAt`; the universal `ListDataset` gained `leadingSort` for it (empty for every other list).
7. **N-20 email** goes to the member's contact email: through the account when it is the same address, through the applicant path otherwise, in the account's (else the signup's) language. PERSONAL preferences (12/D10) do not exist before E7-T03, so the email is always sent.
8. **N-21/N-22 recipients** are the active `Instructor`s' census members with an account in the club, deduplicated; the completer is not excluded («tots els instructors»).
9. **`member_name`** is the owner's full name (as D14's `memberName`); **`instructor_name`** the task's `createdBy.displayName`.
10. **The impersonated completion** is audited as `DOG_UPDATED` on entity type `Task` (`before/after {state, doneAt, doneBy}`), the closest existing action; the member's own completion is not audited.
11. **Attachment removal and registration** are audited `DOG_UPDATED` on `Attachment` for the three types (the E3-T03 registration already was).
12. **`GET /tasks`**: `state` wins over `includeDone`; `size` 1–200 (else 400); a member never sees staff account ids (`createdBy/doneBy.accountId: null`).
13. **Nullable fields** of `Task`, `Actor` and `FollowupItem` are sent as `null`, like E6-T02's rows (R-10-16 writes `levelCode: null`).
14. **`POST /attachments` checks the limit before the purpose**, as E3-T03 did for the note: at the limit, `ATTACHMENT_LIMIT_REACHED` answers first.
