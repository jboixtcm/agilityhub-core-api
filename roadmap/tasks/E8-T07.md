## Steps
1. **A receipt with a zero or negative total is never direct-debited (review #1, major; R-12-12, ruling E89).**
   - `includeInNextRun` applies only to a manual receipt whose total is positive. Creating one with a total of zero or less and the flag → `400 VALIDATION_ERROR {field: includeInNextRun}`.
   - The run never picks up a receipt whose total is not positive, whatever its flag says (a receipt stored before this fix).
   - The admin settles a negative adjustment by hand (R-12-16).
   - Test: R-12-19's own example, «Ajust quota setembre −30,00 €», on a `SEPA_DD` member.
2. **A rollback reissues its whole block (review #2, major; T-12-13, R-12-14, ruling E89).**
   - A rollback rolls back every receipt of the run, including any receipt the admin cancelled meanwhile. That receipt becomes rolled back as well, and its history keeps the admin's reason.
   - The counter returns to the run's first number, and the numbering floor ignores the run's own block. The next generation therefore reissues the same numbers.
   - Test the review's sequence: run R1 numbers 0912…1026; the admin cancels 0950; rollback; the second generation starts again at 0912, with no gap and no duplicate among the live receipts.
3. **The waiting manual receipts are part of the simulation (review #3; R-12-07).**
   - The `includeInNextRun` receipts the run would remit are in `invoicesPreview` and in the KPIs («Import de la remesa»), so D6's confirmation matches the remittance.
   - They get the run's incident checks: a member who has `LEFT`, has no bank account left (`NO_BANK_ACCOUNT`) or no longer pays by `SEPA_DD` is an incident, and the receipt is not remitted.
   - A flagged receipt, or a pending charge, created after the simulation makes it stale (`409 SIMULATION_STALE`).
   - Test each.
4. **Rolled back comes from the run (review #4; §5).**
   - A receipt is rolled back when it belongs to a run whose status is `ROLLED_BACK` (or carries the run's `FAILED{ROLLBACK}` collection), not when its `cancelReason` holds a reserved word.
   - The admin's cancellation reason is free text again: «Rollback» typed by an admin is accepted.
5. **An index the numbering can use (review #5).** Add a non-partial, non-unique `{clubId, series, number}` index, so that `highestNumber`, `numberedFrom` and `GET /billing/periods/{period}` use an index instead of scanning the club's invoices. Show the `explain()` before and after in the report.

### Assumptions
1. **The incident code of a waiting receipt that cannot be debited is `NO_BANK_ACCOUNT`**: the member has left, no longer pays
   by `SEPA_DD`, has no account, or has signed another mandate. No closed code names these cases. `NO_BANK_ACCOUNT` is the closest:
   the receipt has no account it can be collected from (billing's SEPA reader already leaves out a member who pays otherwise).
   It is a weak fit for a member who left and still has an IBAN. Proposal below.
2. **«Left» means not `ACTIVE`** (`LEFT`, also `PENDING` or `INACTIVE`), as R-12-01 never bills `PENDING` or `LEFT`.
3. **A changed mandate is an incident.** The receipt is not re-frozen under the new mandate. This is E8-T03 review #1's case,
   and E8-T03's Q4 expected E8-T07 to take it. Without it, the writer fails the whole run with `422 SEPA_NOT_CONFIGURED`.
   Skipping never debits under a mandate the receipt did not name.
4. **`SEPA_XML` off:** the waiting receipts are `PROVIDER_DISABLED` incidents in the simulation and in `skipped[]` (R-12-28).
   Before, they were silently not taken. When `SEPA_XML` is on without its creditor data, the simulation lists them as
   `PROVIDER_DISABLED`, and the run answers `422 SEPA_NOT_CONFIGURED`, as for the periodic debits (E8-T03's design).
5. **An admin-cancelled receipt in a rolled-back run** keeps its status, `cancelledAt`, `cancelReason` and version (its history).
   It gets the `FAILED{ROLLBACK}` collection and an `InvoiceCancelled{reason: ROLLBACK}` event like the others, so it is a
   second `InvoiceCancelled` for that invoice. No consumer exists in the code, and D6 learns that it is now rolled back. Its
   charges are unbilled, and its member's date is restored, so the reissued run bills that member again. The admin's
   cancellation does not carry over to the new receipt, which is what «the run never happened» means.
6. **The rollback still writes `cancelReason: ROLLBACK`** on the receipts it cancels (§5 `CANCELLED{ROLLBACK}`, and the
   event's `reason`). The authority is `rolledBack`, which comes from the run and is now on `Invoice` as well, so the drawer of
   an admin-cancelled, rolled-back receipt can tell.
7. **`kpis.count` includes the waiting receipts** (`count = invoicesPreview.length`). D6's «Es generaran {n} rebuts per un
   total de {import}» therefore matches the run plus the remittance. A client that wants only the receipts the run generates
   can leave out the rows that have an `invoiceId`.
8. **Staleness compares sets, not times.** The simulation keeps the unbilled charge ids and the waiting receipt ids it saw
   (stored, not published), and the run compares them with its plan. This covers a charge or receipt that was created,
   voided, reinstated, cancelled or returned by a rollback after the simulation (a reinstated charge has no timestamp). A
   simulation stored before this change has no sets: it counts as empty, so it is stale once if anything is waiting.
9. **Absent keys, not `null`**, on the run's own preview rows. S12 §6's JSON is the fixture, compared strictly, and it has no
   such keys. `ProviderTotals` is the precedent in the same file.
10. **The index is descending on `number`** (`{clubId: 1, series: 1, number: -1}`), so its key pattern is not the partial
    unique guard's, and both reads hint it (the planner trap above). `ensureIndexes` creates it at start-up before any request.
11. **E8-T03's `RemittancesIT.R_12_19_onlyAPositiveManualReceiptRidesTheNextRemittance`** created a negative receipt with the
    flag, which is now a `400`. It now creates the receipt without the flag and sets the flag in Mongo, as a receipt stored
    before this fix. Its assertions are unchanged. E8-T03 is `awaiting_verification`; if it comes back, this test and
    `forNextRun` are the shared points.
