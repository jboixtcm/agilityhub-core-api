## Steps
1. **D2 can add or remove one file (review #1, question 3, R-04-19).**
   - Each file row of `SignupDogView.documents[].files[]` carries its `fileKey` (additive).
   - A D2 `PATCH /dogs/{id}` with `documents` keeps the files whose `fileKey`s it sends back, and adds the new ones.
   - IT: the reused dog's submitted card has 2 files. D2 adds a third and removes one. The view shows the two kept and the new one, validation writes them, and P9 sees the removed file as an orphan.
2. **A plain id for signup files (question 2).** A file claimed at signup gets an `id` that is not its storage key, so `DELETE /dogs/{id}/documents/{docId}/files/{fileId}` can address it. Today the key's `/` splits the path, and D2's drawer gets 404 on the pending dogs of public signups (E3-T17 log `14`). IT: D2 removes one file of a pending public-signup dog. Development data may be re-seeded.
3. **The card requirement and a reused dog's own card (review #3).** With `signup.requireDogDocumentAtSignup=true`, a reused dog whose own card is RECEIVED meets the requirement, at submission and in D2's `PATCH`. A reused dog without a card still needs one. IT with the parameter on.
4. **`changedFields` without the automatic card row (review #4).** When the reused dog has no card and the applicant sent none, `changedFields` does not list `documents`. Pin it in `T_04_12_aReusedDogWithoutACardDocumentGetsTheEmptyCardAtValidation`.

- **Step 2.** A file claimed at signup gets a plain `id`: `AttachmentService.signupFileId(key)`, a name-based UUID of its key.
  - The same key always gives the same id. `DELETE /dogs/{id}/documents/{docId}/files/{fileId}` now reaches it, and `DocumentFile.id` (`format: uuid`) holds for these files too.
  - D2's view now hides a file removed through S03 (`removedAt`), as `GET /dogs/{id}/documents` already did. Before, D2 still listed the removed file.
- **Step 3 (R-04-06, R-04-08).** With `signup.requireDogDocumentAtSignup=true`, a reused dog whose own `VACCINATION_CARD` has a file meets the requirement:

  A new dog still needs a card. So does a reused dog whose card has no file, or that has no card document.

### Assumptions
1. **What «keep» means.** A key D2 sends back keeps its file only if D2's view shows it for **that type** of **that dog**: the dog's own active files, plus the reused dog's submitted files. The kept row is copied as stored and is never re-claimed. Any other key must be a signup upload bound to the same `dogId:type`, as before (`400 FILE_NOT_FOUND` otherwise). A key from another dog or type cannot be kept.
2. **A duplicate key in one type** is refused (`400 VALIDATION_ERROR`, field `documents.files.fileKey`, code `DUPLICATE`), at submission too. This uses the existing `DUPLICATE` reason. No real client sends the same key twice: each upload gets a new key.
3. **«Own card RECEIVED»** is read as «the reused dog's own `VACCINATION_CARD` has at least one file that is not removed». A PENDING own card (no file) does not meet the requirement. At submission, the check sees the dog as a pending readmission, because `prepareDog` marks it before the documents are claimed.
4. **No migration of old signup file ids.** Files claimed before this change keep their key as `id`, so `DELETE …/files/{fileId}` still cannot reach them. The task allows re-seeding development data, and there is no production data. A kept old row also keeps its old id.
5. **D2's view hides files removed through S03**, as `GET /dogs/{id}/documents` does. Step 2 needs this: otherwise D2 would still show the file it had just removed. The stored rows keep `removedAt`, and P9 still counts them as referenced, as before.
