# E7-T02 · Notification engine (S11 WP-11-B) — outbox consumer, RecipientResolver, ChannelResolver, TemplateRenderer (ICU + [[var]] + club formats), dispatcher with retries, TwilioSmsSender + monthly cap, WebPushSender (VAPID), email bounces and List-Unsubscribe; the E4–E6 SMS intents become real sends

## Objective
Work package S11 WP-11-B: one engine turns every domain event of the outbox into notifications — catalog lookup, template, recipients, channels, render in the recipient's language, dispatch behind `EmailSender` / `SmsSender` / `PushSender` with idempotency and retries — and replaces the ad-hoc notification code the earlier stages wrote per vertical. The SMS intents E4–E6 queued (`channel = SMS`, `status = QUEUED`, no sender) start being sent for real; CLUB_CHANGES messages and the released-seat notice (N-15) carry SMS; email bounces suppress the address.

## Steps
1. **Ports out of `messaging`** (`clubs/messaging/application/ports`, each with a null-object `@ConditionalOnMissingBean` default; the adapters live in the owning context's `application` package so ArchUnit stays green and `messaging` never imports another context's `persistence`): `MemberDirectoryPort` — `Optional<MemberContact> find(memberId)` and `List<MemberContact> findAll(Collection<String>)` where `MemberContact {memberId, accountId?, displayName, locale?, emails[{address, bounced}], phones[{e164}], preferences NotificationPreference, status, dogNames}`, `List<MemberContact> byIds/byFilters(...)` for E7-T04; `StaffDirectoryPort` — `List<MemberContact> admins()` (memberships `ACTIVE` with role ADMIN), `List<MemberContact> instructors()` (all active) and `instructorsOf(classSessionId)` (the `ClassSession.instructorIds`, new **and** old on `N-08b`); `BookingRelevancePort` — `boolean stillActive(bookingId?, trainingBookingId?, Instant startsAt)` (R-11-16) and `WaitlistRelevancePort` — `boolean stillNotified(waitlistEntryId, Instant now)` (R-11-11 `CLAIM_SEAT.enabled`, computed on read); `SignupContactPort` — `Optional<ApplicantContact {email, locale, displayName}> applicant(signupId|memberId)`. Every port has an in-memory double in tests reproducing the S11 examples.
2. **Outbox consumer** (`NotificationEventHandler`): one `DomainEventHandler` bean per distinct `eventTypes[]` value of the `NotificationCatalog`, registered programmatically in `MessagingConfiguration` with **durable bean names** `notifications.<EventType>` (the dispatcher uses bean names as consumer ids — never rename one). Pipeline exactly as S11 §6: `specsFor(evt.type, evt.payload)` → template (`MessageTemplate{clubId, code}`, else the product seed, created on first use per R-11-01; `status = DISABLED` → skip entirely) → `spec.stillRelevant(evt)` (else a single `Notification` with a `SKIPPED_STALE` delivery, R-11-16) → per audience and recipient: locale (`Account.locale` → `club.defaultLocale` → first available; `APPLICANT` → `signup.locale`), variables, render, `notifications.upsertByDedupKey(...)`, `channelResolver.resolve(...)` adding each delivery **if absent**, save, `dispatcher.trigger(id)`. Idempotent per `eventId` (the outbox already records `processedAt`): reprocessing reuses the document and creates no new delivery. Runs **outside** the business transaction (the outbox dispatcher already guarantees that) and never inside a Mongo transaction while doing network I/O (decision E13).
3. **`RecipientResolver`** (R-11-02): `MEMBER` = the members of the payload (`memberId`, `affected[]`, `entryIds[]`…; on a booking of a family-group dog, the owner **and** the booker); `INSTRUCTORS` = `instructorsOf(classId)` when the payload carries a class, otherwise all active instructors; `ADMINS` = `StaffDirectoryPort.admins()`; `APPLICANT` = the signup email. The same person in two audiences gets two notifications (different `dedupKey`s). `LEFT` members receive only what their own event mandates (N-28), never N-24. One notification **per dog** when the subject is a dog (`subjectKey = dogId`). T-11-14, T-11-08.
4. **`ChannelResolver`** — implement the R-11-03 truth table literally, one method returning the list of deliveries with their initial status: `APP` → always `DELIVERED` for `MEMBER`/`INSTRUCTORS`/`ADMINS` when the template's matrix cell is on; `EMAIL` → `QUEUED` to **every** non-`bounced` address, `SKIPPED_BY_PREFERENCE` when `emailByCategory[category]` is false (only for `MEMBER` and only when `category != SYSTEM`), `SKIPPED_NO_CONTACT` when every address bounced (plus the admin notice of R-11-08); `SMS` → `QUEUED` **per phone** when the matrix cell is on and the `SMS` module is on (preferences can never remove it — «+SMS» is fixed, Josep 18-08), `SKIPPED_MODULE_OFF` with the module off, `SKIPPED_CAP` + a forced `EMAIL` delivery at the cap (R-11-06); `PUSH` → from `catalog.push[audience]` (never from the template), `QUEUED` per `ACTIVE` subscription, `SKIPPED_NO_CONTACT` without any, gated by `pushClubNews` only for `CLUB_NEWS`, `SKIPPED_MODULE_OFF` with `PUSH` off; `INSTRUCTORS`/`ADMINS` ignore preferences entirely; `APPLICANT` is `EMAIL` only; a matrix cell off produces **no** delivery document and the notification is still stored (R-11-10). ### Assumptions
1. **N-19 `class_date`** keeps S10 §8 and ruling E65 («la classe de {class_date}», the class's own date in full, never «ahir»),
   not T-11-33's «`class_date = ahir`»: S10 owns N-19's variables (S11 §1 «Fora d'abast»), and E6-T04's verified evidence shows
   it. T-11-33 asserts yesterday's date written in full. The first session's design note said the opposite; the code never
   did it, and this report supersedes that note. See Question 1.
2. **APPLICANT + account** (S04 §8): an existing member who applies (add-dog) still gets N-01/N-03 in the app besides the
   e-mail (`SignupGateFixesIT` asserts it). R-11-03's «APPLICANT → EMAIL only» holds for new applicants. The truth-table test
   states this row.
3. **Retries:** 5 attempts at most, waits 1·5·15·60 min; the 240-min step of R-11-09 would be the 6th attempt and is never
   used («fins a 5 intents amb 1 · 5 · 15 · 60 · 240 min» cannot be both). `RetryPolicy.BACKOFF` keeps the 240.
4. **SMS truncation** in GSM-7 ends with «...» (three characters): GSM-7 has no «…»; without transliteration it is «…».
5. **English weekday** follows CLDR («9 Friday», «12 Wed»), as the front's `Intl` does; `ca` month phrases follow ICU
   («octubre del 2026»).
6. **Unsubscribe link** targets the club app's page `https://{clubs host}/comunicats/baixa?t=…`, which calls `POST
   /email-unsubscribes`; without a verified clubs domain no link (and no header) is written. The route of that page is
   the web's (to be confirmed in its S11 task).
7. **Account vs contact bounces** (decision E12 vs R-11-08): both marks coexist. A hard bounce of an engine mail marks
   `Member.contactEmails[address].bounced` for the notification's member (or, without one, every member with that address)
   and publishes `EmailBounced`; when the address is also the account's login address, the E1-T03 `Account.emailStatus` +
   `ACCOUNT_EMAIL_STATUS_CHANGED` audit are written too. The engine treats an address as bounced if either mark says so.
8. **Missing values:** a variable the owner does not give renders empty (never `{name}`), WARN at top level only.
9. **Consumers of `EmailBounced`/`SmsCapReached`** are engine consumers like the others (`notifications.EmailBounced`,
   `notifications.SmsCapReached`).
10. The dispatcher has **no per-attempt relevance hook**: `NotificationFactsPort` has `stored` (engine transaction) and `sent`
    (after acceptance). E6-T03 round 3 item 1 (N-20 owner check at each attempt) will add one; I did not start that round.
