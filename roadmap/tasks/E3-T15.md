# E3-T15 · A failure-safe recipient-cap admission

## Objective
The independent review of E3-T12 round 2 (`roadmap/reviews/E3-T12-20260925-1127-codex.md`) found two majors in the recipient cap of N-39 and the applicant's N-01 (R-04-20). The organizer confirmed them. E3-T12 was verified with these routed here, under the rule for rounds ≥ 2. They must be fixed before the gate re-run E3-T11, which depends on this task.
1. The allowance is charged before the admission decision is saved. If saving the decision fails, the retry finds no decision and charges the same bucket again; with a cap of 1 it records a refusal and completes without sending.
2. The admission's one-day TTL can delete the decision while its event is still pending (an outage, or a dispatch backlog). Another event can then take the allowance, and the admitted event is lost when it retries.

A simple shape that closes both: keep the admission **on the event's own record**, or keyed by the event id with retention that starts only after the event is processed. Write it idempotently **before** the allowance is charged, and let a retry read it and never re-charge. Other shapes are fine if they meet the tests.

**Each fix comes with a test that fails before the fix.**

### What changed
1. **The decision is written before the charge, and a retry never re-charges** (review #1).
   - `SignupNotifications.decide` works in three steps, under a per-instance lock (the buckets are per instance too):
     - probe the recipient's bucket without taking a token (`RateLimits.available`, Bucket4j `estimateAbilityToConsume`);
     - store the decision (`SignupNotificationAdmissionRepository.decide`, an idempotent insert keyed `eventId:code`);
     - only then, and only if this call stored an admission, take the token (`RateLimits.charge`).
   - A failed write throws before the charge, so the retry decides again on an untouched bucket.
   - A retry that finds a stored decision uses it and never touches the bucket.
   - A decision that a concurrent delivery of the same event stored first is used as it is. `decide` now returns `Decided(admission, stored)`, so only the delivery that stored it charges.
2. **The decision lives as long as its event** (review #2).
   - A decision is stored with no `expiresAt`, so the TTL index never removes it while its event can still retry, however long that takes.
   - The consumer calls `SignupNotifications.processed` after `deliver`, inside the outbox transaction that marks it processed.
   - That call registers an after-commit step: once the processed mark has committed, `expiresAt` = now + the club's `jobs.retention.domainEventsDays` (S15, 90), the retention of the event itself.
   - A rolled-back delivery never commits, so its decision keeps no expiry.
   - The fixed one-day `ADMISSION_RETENTION` is removed.
   - Why after commit and not inside the transaction:
     - the outbox transaction reads a snapshot taken at `records.lock`, before `deliver` stores a fresh decision, so an in-transaction update matched nothing;
     - my first attempt did exactly that (log `01`), and the fresh-decision check caught it.
   - If the after-commit update fails, the decision stays without expiry and a WARN logs the event id and code (no address). That is a leftover, never a lost admission.

No contract change: `bin/openapi-snapshot` was not needed, and `git status docs/openapi` is clean after the verify.

The step 2 scenario (cap 1):
1. A is admitted, and its delivery fails. The decision read while A is pending has no `expiresAt`.
2. The clock moves 1 d 1 h. The test emulates Mongo's TTL monitor: it removes the decisions whose `expiresAt` ≤ the test clock.
3. The test emulates the backlog: A's retry comes due 5 min later.
4. B, a competing N-01 to the same address, takes the new hour's only allowance and is sent.
5. C arrives while the cap is full and is refused.
6. A's retry still sends.
7. The decisions are `A=true, B=true, C=false`, and every event is `PUBLISHED`.
8. After processing, A's `expiresAt` = processed + 90 d.
9. With `jobs.retention.domainEventsDays = 7`, a fresh event D, decided and processed in the same attempt, gets `expiresAt` = processed + 7 d. This check is the one that failed in log `01`.

### Assumptions
1. **The shape: a separate collection, not the event's own record.** The organizer's first suggested shape (the decision on the `domain_events` record) does not fit this dispatcher:
   - the handler transaction write-locks the event record (`OutboxRepository.lock`) before `deliver` runs;
   - the decision must be written outside that transaction, so it survives a failed send;
   - a non-transactional write to the same record would wait for the transaction, which is waiting for it.

   So I kept `signup_notification_admissions` keyed `eventId:code`, and its retention now starts after processing. That is the second shape of the Objective.
2. **Step 2, the competing event.** R-04-20's cap is per hour, and E3-T12 round 2 (verified) made it count decisions, not sends. So after more than a day, the bucket has refilled:
   - the first competing event B takes the new hour's allowance and is sent;
   - the test then checks that a competing event arriving while the cap is full (C) is refused;
   - A's retry still sends, with its own decision.

   On the old code, A lost its decision to the TTL, re-charged behind B and was refused. That is exactly the review's loss scenario.
3. **Test emulations.** Two emulations, both on the test side only:
   - Mongo's TTL monitor runs on the server's clock, not on the test's `MutableClock`, so `ttlMonitor()` deletes what the monitor would have deleted at the test's instant;
   - the dispatcher claims by `nextAttemptAt`, so without the move A's retry would run before B. Moving A's `nextAttemptAt` 5 min ahead emulates "B is decided before A's retry" (a backlog, or a lease held by a dead instance).
4. **Events that end `FAILED`** (attempts exhausted, never re-driven): their decisions never expire, like the events themselves (S15: «els no processats no es toquen mai»).
5. **A write that commits but reports a failure** (a lost acknowledgement): the retry finds the stored admission and does not charge. So such a failure can leave at most one admission uncharged, which errs towards delivering.
6. **The lock is per instance, like the buckets.** It serialises probe → store → charge for the recipient-cap decisions. Only `SignupNotifications` uses `SIGNUP_RECIPIENT`, so no `retryAfter` call takes that token in between.
7. **Existing decisions** written by E3-T12 round 2 keep their `expiresAt` = decision + 1 d. Only development data has them.
