### Assumptions

Where R-16-11 is silent, the closest existing pattern (E9-T03's ring setups), recorded here:
- **Start.** `POST /build-sessions` stores `NOT_STARTED` with `startedAt = now` (§3 names `startedAt` without `?`, and the cleanup index `{clubId, status, startedAt}` needs it); the first tap makes it `IN_PROGRESS`. `selectedStrategy` defaults to `EQUIPMENT_TYPE`. The starter is `startedByAccountId`, not a participant (`participants[].joinedVia` is only `QR · CODE`). A `stale` placement is not refused. `live` is stored and exported; it gates neither the stream nor joining.
- **Taps.** «last-write-wins per obstacle»: the request's `version` is accepted and not compared; any status may follow any other (the client chooses the next state). A closed session is `422 BUILD_SESSION_FINISHED` (CATALEG_ERRORS rule 0, E9-T01 step 3); `409 STALE_VERSION` remains only E73's transversal write conflict.
- **Finish.** It registers a setup, so it follows `POST /ring-setups`: an INSTRUCTOR needs `courses.allowInstructorPublish` (`403`), and a new setup publishes `RingSetupChanged{ACTIVE}` (N-31) and audits `RING_SETUP_REGISTERED`. «crea/actualitza»: when the ring's active setup already shows this placement, it is refreshed like a renewal (built now by the finisher, a new `expiresAt`; no event, as E9-T03's renewal), otherwise the new setup replaces it. Kind: `AGILITY`/`JUMPING` from the discipline, `OTHER` → `FUN`. Levels: the course's `levelIds` while `levels.enabled`, and its `agilityhubLevel`. The placement's course must still be readable (a deleted club course → `404`).
- **12 hours.** An open session started `courses.buildSessionMaxHours` ago or more refuses taps and `finish` (`422 BUILD_SESSION_FINISHED`) and is no longer joinable (`404`); P9 (daily) records it `ABANDONED` with `finishedAt`. No outbox event for it (S16 §7 has none); its streams get `finished {status: ABANDONED}`. P9's item is `ABANDON_BUILD_SESSION` (dry run `WOULD_ABANDON_BUILD_SESSION`, counter `buildSessionsAbandoned`), the first P9 item that is not a `DELETE`: the session is a business document and is kept.
- **Stream.** Per API instance, in memory: each subscriber gets the difference against what it last received (`obstacle` per changed obstacle, `finished`, the event `id` = the session `version`), right after commit and from a one-second poll of the subscribed sessions (so another instance's write still arrives in < 2 s). No replay on reconnection: the client reads `GET /build-sessions/{id}` again (in the operation description). The heartbeat is an SSE comment (invisible to EventSource handlers). A stream lasts at most 30 minutes; EventSource reconnects.
- **Query token.** Only `GET /api/v1/build-sessions/{id}/events` reads `?access_token=` (Spring's resolver: GET only; header and query together → `401`). The app logs no query strings and Sentry drops the request (`SentryPrivacyConfiguration`); the reverse proxy is outside this repository (question below).
- **Join.** `code` is the six-character join code (case and blanks ignored, `CODE`) or the 43-character QR token (`QR`); the same account joins once. No rotation route (the planner's `rotate_build_session_invite` has no S16 row).
- **Export.** Derived values (E9-T01 Fixed conventions): `producer = agilityhub-core-api`, `judge_id` and `event_id` null (judges and events are R2; `Placement.activityId` is not the planner's event), `source_version` null, `theme = {id: null, palette_key: standard, theme_json: {}}`, `assetProfile = generic-fci`, `course.title` = `Course.name` in its default locale, `title_raw`/`units`/sizes/`origin` from `normalizedJson`, `course_type` from the discipline (`OTHER` → null). The schema requires exactly six markers while R-16-04 accepts three: a ring without six is `422 GEOMETRY_INVALID {violations: [{path: markers, rule: TOO_FEW_MARKERS}]}` before the build (question below); a club without a venue is a `500` (`RingGeometryService` creates it with the first geometry).
- **Concurrency.** Each build-session write is one transaction retried whole on a write conflict or duplicate key (5 attempts, the shared 50–150 ms jitter, as S09's writers); exhausted → `409 STALE_VERSION`. With an `Idempotency-Key` the request already runs in the idempotency filter's transaction, and the write joins it once. E117's guard covers the HTTP paths (`dismantle`, `renew`) only: P5 f's `expire` and the ring-deactivation consumer keep the raw conflict, which their own retries need.
- **Async dispatch.** `RequiresModuleInterceptor` skips the async dispatch that ends a stream: it runs without the tenant, so the module check could only fail after the response was committed. Counterfactual M3 shows the real stream still ends cleanly without the change (the failure comes after the last byte), so only its unit test proves it.
