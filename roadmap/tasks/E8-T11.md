### Assumptions

- **How the admin is told (point 1).** Under the closed catalogs: a `PAYMENT_REFUNDED` audit entry without money movement, `entityType UpfrontPayment`, with `memberId` so it shows in the member's audit trail. `reason` is `COMPENSATION_INTERVENTION` or `REFUND_OVER_CREDIT`; `details` is `{owed|overpaid: Money, intervention: true}`. It is written in the transaction that sets `compensationInterventionAt`, plus one WARN after commit.
  - No notification or D6 incident fits: N-10 needs an invoice, N-42 an S15 job, and R-12-07's incidents are the run simulation's.
  - A dedicated action and notification are proposed in MESSAGES.
- **Admin refunds keep their behaviour under an outage.** They keep their 3 attempts and are released when exhausted (rounds 1–3, `T_12_17_round2_point2`, `round3_point3`, `round4_point1` unchanged): the admin who asked can ask again. Only automatic ones wait.
- **A permanent outage waits indefinitely.** A key that is never repaired keeps automatic refunds waiting (5-minute deferral, no attempts), exactly like a disabled provider. No intervention is recorded, because nothing needs repaying by hand: the money is still reserved for the member.
- **A refused compensation stays terminal.** After 3 attempts, a content refusal (for example `charge_already_refunded`) is terminal. If a dashboard refund already settled the amount, `due` is 0 and no intervention is recorded.
- **Re-failure of an absorbing dashboard refund.** If a dashboard refund later fails after it voided a credit, the credit is not reinstated: re-growth needs an unvoided row, so this becomes an intervention.
