#### Assumptions
- Counters and active registrations contain only tenant IDs and numbers. No source data, credentials, emails, bank details or fingerprints are added. For an unscoped findAnd* claim, only the returned row's tenant is counted as changed. If the single-row query has a total sort including `_id`, only its first snapshot row needs registration: another tenant's maintenance cannot block that claim. A forced interleaving failed before that refinement (`45`) and passes afterwards (`47`).
- This adds two short coordination transactions per participating tenant and data transaction; no throughput benchmark is claimed. Short infrastructure transactions register and close ordinary writers; the data transaction need not hold the counter lock while a nested transaction runs. Only proven aborted conflicts are retried, with the existing bounded backoff and retry metrics. An unknown commit is never replayed as a fresh registration/release.
- An ordinary process crash or unavailable registration cleanup leaves a durable active count and **blocks destructive maintenance**. It is not expired automatically: an operator must establish the transaction's outcome before repairing it. Import transactions use the exclusive maintenance fence, so an interrupted import does not leave such registrations and retains the existing fenced restart behavior.
- Old counters may lack `activeWriters`; they remain readable.
