### Assumptions
- Paths follow CONVENCIONS_API §1 and S01 §6: OAuth/OIDC and `/auth/magic-link` at the identity root; other application paths at `/api/v1`, including `/api/v1/auth/handoff`. `/oauth2/authorize` is included because it appears in S01 §6 and the objective requires the complete identity contract, despite its omission from the step-1 enumeration. Existing `/oauth2/jwks` is retained as an alias.
- `Profile` represents MEMBER/INSTRUCTOR/ADMIN enum values, because S01 supplies role-based profiles without a separate profile object shape. Sessions are a bounded account-device array, not a desktop paginated resource; ids are public opaque revocation handles, never stored token hashes. Only the public session metadata from §3 is exposed.
- S01 §6 gives no success body for PATCH `/me` or account provisioning: assumed `Me` and public `AccountSummary` including `id`, respectively. Revocation, password changes and session deletion have empty success bodies with the specified 200 status. Authorization-code form includes `code`/`redirect_uri`; `code_verifier` and `client_secret` have client-dependent requirements described in the operation. The token schema describes the complete E1 response, including scope; existing E0 public-client restrictions remain until the implementation task.
- S01 §6 has no onboarding endpoint/body table. The requested GET/PUT contract follows §14: state `{onboardingPending, name?, locale?, phone?, requestedFields[], privacyPolicyVersion, privacyPolicyUrl}`; input `{name?, locale?, phone?, privacyAccepted, privacyPolicyVersion, imageConsent?}`. Missing data may be deferred; accepted current privacy policy is mandatory in the future service. No parameter, consent event or notification was invented or implemented.
- E0 Membership does not persist instructorId/rememberProfile. The existing club bootstrap reads instructorId/activeProfile from signed claims, derives profiles from membership roles, and reports rememberProfile=false until E1-T02 adds preference persistence. Optional null fields are omitted. Global and impersonated bootstrap return 501 until their services exist. Existing club membership/account validation remains active; pending handlers do not mutate data.
- The closed error catalog wins over S01 prose: REFRESH_EXPIRED is 400, not the 401 example in R-01-06. `invalid_grant`/`invalid_request` remain protocol descriptions, not new ErrorCode constants; the API uses the catalog codes and shared envelope.
- Git cleanliness after generation means no additional snapshot changes on regeneration, proved by byte comparison. The two API files necessarily remain modified until the external publish script commits them; no git write was attempted.
