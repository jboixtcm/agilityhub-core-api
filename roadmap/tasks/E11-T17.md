## Steps
1. **A partially paid row keeps its cash provenance through the checkout** (INC-39.2, ruling E149 = option a of the verification). Today `UpfrontPayments.pending` lets a `PARTIAL` row enter `CHECKOUT_PENDING` and `checkout` (completion) rewrites it `PAID / amountDue / STRIPE / Stripe's paidAt`: the cash part's provider and date are lost. Now: when a `PARTIAL` row goes to checkout, close it with the E39b pattern — the `PARTIAL` row becomes `CANCELLED` and a `PAID` correction row keeps the cash (`provider = MANUAL`, the cash `paidAt`, the cash amount) — and a **new `DUE` row for the remainder** is the one that goes to `CHECKOUT_PENDING` (`STRIPE` and Stripe's `paidAt` on completion); an expired or abandoned session returns that new row to `DUE` while the cash stays in its correction row. One provider per row, S04 §5's diagram unchanged, `UpfrontPaymentSucceeded.amountPaid` = the remainder. Update S04 §5 and R-04-22 in the api's copy (E109). Tests: `UpfrontPaymentsSurvivorsTest.T_04_22_INC_39…` with the two whitelisted transitions removed from `DOCUMENTED` (fails today); an IT: 100 due, 40 paid in cash (`PARTIAL`), checkout, completion → rows `[CANCELLED 100/40 MANUAL]`, `[PAID 40/40 MANUAL correction, the cash paidAt]`, `[PAID 60/60 STRIPE, Stripe's paidAt]`, totals paid 100, the event's `amountPaid = 60`; and the expiry variant (the 60 row back to `DUE`, the cash row untouched). E5-T30's «comes back with its history» tests are adapted to the two-row history (say which assertions changed and why).
2. **One notice per club-made training booking** (INC-40.10, ruling E150 = option b). A booking the club makes for a member sends N-06 and N-47 today. Now N-06 is skipped when `origin = BACKOFFICE` (the member gets the richer N-47: APP + EMAIL + SMS), mirroring the N-07 exclusion already in code. Edit the N-06 row's condition in the api's `CATALEG_NOTIFICACIONS.md` copy and S09 §8 (N-06 and the N-07 row, which must say «llevat MEMBER_LEFT i les anul·lacions del club», as the code does), `TrainingNotificationFacts.java` (`booked && !club`), and the tests `TrainingApplicationTest` / `NotificationActionsIT` (a club booking → one N-47, no N-06; a member's own → N-06).
3. **The audit entry links its own event** (R-14-10; E11-T10 verification N1). `TrainingBookingService` audits before it publishes in three places (`bookedByClub`, the impersonated cancel, `cancelByClub`), so the entry's `eventIds` lacks its own `TrainingBooked`/`TrainingCancelled` and, in a batch, carries the earlier cancellations' ids. Publish first, as `BookingCancellationService` does. Tests: `TrainingIT.T_09_21_INC_40…` with two bookings in the block asserts each `TRAINING_CANCELLED_BY_CLUB` entry's `eventIds` contains exactly its own `TrainingCancelled` id; `T_09_23` the same for `TRAINING_BOOKED_BY_CLUB` ↔ `TrainingBooked`.
4. **Legacy seat locks expire too** (R-15-19; N2). The TTL index on `seat_locks.lockedAt` only covers rows written after E11-T10; rows without `lockedAt` never expire and `CleanupJob`'s counter does not see them. `SeatLockRepository.ensureIndexes()` backfills `lockedAt = now` on every row without it (idempotent, all clubs, startup only; a racing `$inc` is a write conflict the booking writers already retry). Tests: `E5PersistenceIT` inserts a row without `lockedAt`, calls `ensureIndexes()`, asserts the field; `CleanupJobIT` counts it after 7 days.
5. **No audit for a pure reorder** (N3). `ClassSessionService` writes `CLASS_UPDATED_WITH_BOOKINGS` when `instructorIds` are only reordered (the event diff is empty, the audit diff is not). Skip the audit when the normalized diff is empty. Test: `CalendarIT.T_06_13_INC_40_reordering…` also asserts no new `CLASS_UPDATED_WITH_BOOKINGS` entry.
6. **N-50 names the job** (S14 §8; E11-W01 verification). The `OPEN_EXPORT` action of N-50 arrives with `params: {}`; the member app can only reopen a READY package from its own device storage. Send `params.jobId` (the export job id) with N-50; the web already honours it (`/perfil?jobId=`). Catalog: N-50's action params in the api's `CATALEG_NOTIFICACIONS.md`/S14 §8 copies. Test: `ExportEngineIT` (or the notification IT that covers N-50) asserts `params.jobId` on the delivered notice.
7. **Docs**: S04 WP-04-2 still names `UpfrontAllocator` (deleted by E11-T10): remove it in the api's copy.
8. **Evidence hygiene** (N7): `roadmap/evidence/E11-T10/66-inc40-jobs-all-its.log` is 15.9 MB. Trim it to its header, the per-class summary lines and any failure block (keep the first 40 and last 40 lines too); say the before/after size in the report. Do not touch the other logs.
9. **Evidence.** `./mvnw -q clean verify` under the host lock; `bin/e3-signup-smoke` (the checkout path) and `bin/e5-smoke` green; `bin/openapi-snapshot` (no diff expected; if N-50's params change a schema, explain it and add the `docs/openapi/CHANGELOG.md` entry).

Do not edit `docs/INCIDENCIES_OBERTES.md`: the organizer closes INC-39.2/INC-40.10's items when it verifies the task. If a step needs a product decision the rulings do not give, write the assumption in the report or ask in `MESSAGES.md`, and go on with the others.
