## Steps
1. **The registrant rows (`ClassBookingItem`, `GET /class-sessions/{id}/bookings`, INSTRUCTOR and ADMIN).**
   - `displayState`, computed as for `GET /bookings/{id}` (S08 §6): a past `ACTIVE` booking reads `DONE`, and one with a `NO_SHOW` mark reads `NO_SHOW`.
   - `levelCode`: the dog's level code; `null` with `levels.enabled = false` or without a level.
2. **The staff waitlist rows (`GET /class-sessions/{id}/waitlist-entries`, INSTRUCTOR and ADMIN).** Each entry carries `memberFirstName` and the dog's `handlerName` (`null` when the member handles the dog), as the attendance sheet does (S10 R-10-00), so D12 writes «En espera: {guia} + {gos}». The fields are optional in the schema; the member's own routes may leave them out.
3. **A training booking's end and member number (`TrainingBookingListItem`, `GET /training-bookings`).** `endsAt` and `endsAtLocal`, like `startsAt` and `startsAtLocal`, and `memberNumber` (`null` without one). Add them to the list's `x-fields`.
4. **A class booking's description and ring (`BookingListItem`, `GET /bookings`).** `classDescription` (the class's display description, in the reader's language), `ringId`, `ringName` and `ringColor`, for D10's «Classes» table. Add them to the list's `x-fields`.
5. **A ring block's ring (`RingBlockListItem`, `GET /ring-blocks`).** `ringName` and `ringColor`, a deactivated ring's included, since the register shows history.
6. **Filter values (`CONVENCIONS_API.md` §4).**
   - Publish `GET /training-bookings/filter-values`, `GET /ring-blocks/filter-values` and `GET /bookings/filter-values`, with `field` (one of the list's `x-filterable` fields), `q` and `filter`, like `/members/filter-values`.
   - Each value comes with its count over the whole filtered set, never over one page.
   - Tests: a value that only rows beyond the first 1000 have is listed; an undeclared field answers `400 INVALID_FILTER`.
7. **`nextBookableAt` is the start of the next booking week (S08 §6; §2 row 29 as amended 26-09).**
   - `BOOKING_LIMIT_REACHED.details.nextBookableAt` must be the end of the current booking week, `week(now).end()`, for a `CURRENT` class and for a `NEXT` class alike.
   - Today it is the end of the class's own week. For a `NEXT` class that instant comes after the class, so screen 29's «Podràs reservar aquesta classe a partir de…» is always false.
   - Fix `BookingWeeks.nextBookableAt`, its three callers and the schema's description.
   - Tests: a `NEXT` class refused at the limit carries the coming opening instant (Sunday 20:00 local at the Cànic); the same with `bookings.maxNextWeek = 0`.
8. **P9 run from the api (E5-W04, question 1).**
   - On the published images (`c12e8a0`, `c25e6b4`), `POST /jobs/cleanup/trigger` ends `FAILED` with `INTERNAL_ERROR` «ClientSessionException», and every `ttlPending*` counter is 0. The CLI (`bin/core jobs:run cleanup`) succeeds (api E5-T06's smoke, log `17`, line `:99`).
   - Fix the job's Mongo session handling on the trigger path, and on the scheduler's path if it shares it.
   - IT: trigger `cleanup` through the route → `SUCCEEDED` with its counters.
9. **The ring's colour on `Booking` (E5-W04, question 4).** Every `Booking` that a MEMBER reads carries the class's ring colour (for example `classSession.ringColor`), for mockup 07's dot before the title.

10. **RESET links carry their purpose (web E4-W16, question 1; S01 R-01-04 amended 28-09, ruling E70).** The N-25 link of a `purpose = RESET` magic link ends with `&purpose=reset`, for the club clients and for the ID. A LOGIN link carries no `purpose`. Screen 02 reads it to show «Ja hi ets». Test on the mailed link of both purposes.
11. **The demo seed retries a transient transaction error (web E5-W04, round-2 question R2-1).** A `TransientTransactionError` (the driver's `TransientClientSessionException`, for example) during `seed:demo` retries that transaction, as `TransactionRetries` does, instead of failing the command. Test: inject one transient failure → the seed completes, and its second run reports 0 changes.
12. **`--reanchor` never moves back (E6-T04 round-2 review #1, ruling E70).** The anchor of a `--reanchor` is the later of the Monday of the current week and the recorded `weekStart`. Test: a plain run on a Wednesday (anchor: the next Monday), then a `--reanchor` the same week → the anchor stays, with 0 changes.
13. **The owner's first name in the instructor's search (web E6-W01, question 2; ruling E71).** The instructor's projection of `GET /dogs` carries the owner's first name (for example `owner.firstName` in `OwnerSummary`), so the web writes «{guia} + {gos}» as S10 R-10-00 says, compound first names included («Joan Antoni»). Test on the projection.
14. **The impersonated member's name on `/me` (web E4-W16, question 5; ruling E73).** During an impersonation, `/me`'s `impersonation` object also carries `memberName`: the impersonated member's display name as D10 shows it (first name and last names). The banner «Estàs veient l'app com {nom}» names the member the admin opened, not the account (in a family group they differ). Test: an account whose name differs from its member record's → `/me` names the member.

### Assumptions

1. **Waiting-list fields everywhere.** `memberFirstName` / `handlerName` are sent on every route that answers a `WaitlistEntry`,
   not only the staff list. The schema keeps them optional, as step 2 says. One form everywhere keeps each answer's keys equal
   to the schema's (`SnapshotSchemas.assertConforms`). It is the member's own data (own or family group).
2. **Roles of the filter-values routes.** The three routes are ADMIN and INSTRUCTOR only, like `/members/filter-values`.
   `GET /ring-blocks` also serves MEMBER, but a member screen has no universal filter.
3. **Labels.** The names of dogs, members and rings, a class's `YYYY-MM-DDTHH:mm · {description}`, and the value for any
   other field. They are read per listed value (at most 50), as the census lists do for plans and levels.
4. **`q` on a list without search.** On a list with no searchable paths, a non-blank `q` is `400 INVALID_FILTER` in
   `ListQuery.parse`, for every such list. Before, the engine built `$or` from the empty searchable list, which Mongo refuses
   (a 500). I read that in `MongoListRepository.match` and did not run the old code with `q`. I gave none of these lists a
   search: the task did not ask for one.
5. **P9 in two places.** The suspension is in `JobAdminService` (the audited call), so the JOB_TRIGGERED entry's loader reads
   the committed run. The request's older snapshot would not see it, and the entry would lose its counters (the IT checks
   them). `JobRunner` also suspends a caller's transaction on the manual and scheduled paths. That part is defensive: the
   scheduler has no transaction today.
6. **`--reanchor` anchor.** The later-of rule applies without `--week-start`; an explicit `--week-start` still overrides it
   (tests). The recorded anchor is the latest `weekStart` among the club's `<clubId>:planning*` runs.
7. **Seed retry.** 3 attempts, as the retried writers. The retried failure is a `TransientTransactionError` label or a write
   conflict anywhere in the cause chain (`TransactionRetries.transientFailure`), or Spring's `TransientClientSessionException`.
   A duplicate key is not retried: the seed is deterministic, so it would fail again.
8. **`memberName` source.** It is the impersonated member's first name and last names, from the grant's `memberId`. A missing
   record falls back to the membership's member, then to the account name.
9. **`owner.firstName`** is required and whole («Joan Antoni»). A member record without a first name gives `""` (never seen:
   the census requires one).
10. **`ClassBookingItem` has no class description or ring.** Every row of `GET /class-sessions/{id}/bookings` is the same
    class, so step 4's fields stay on `BookingListItem` only.
