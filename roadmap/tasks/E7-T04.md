## Steps
1. **P4 `reminders`** (`clubs/messaging` owns the emission? No — the job lives where the data is: put the scanner in `clubs/bookings/application/ReminderJob` with a `TrainingReminderPort` into `clubs/training`, or in a small `clubs/common` job that talks to both through ports — choose one, justify it in the report, and keep ArchUnit green). Register it in the `JobCatalog` of E5-T01 with key `reminders`, trigger **every minute**, parameter `jobs.reminders.enabled`. Scope: `Booking` `ACTIVE` and `TrainingBooking` `ACTIVE` with `startsAt ∈ (now, now + maxLead]` and `reminderSentAt == null`, joined with the owner's (`memberId`, the dog's owner) `notificationPreferences.reminderMinutesBefore`; `maxLead = max(messaging.reminderOptionsMinutes)`. Due when `lead != null ∧ startsAt − lead ≤ now < startsAt ∧ bookedAt ≤ startsAt − lead` (a booking made after its own reminder moment gets none — N-04/N-06 already confirmed it). Instant arithmetic only (immune to DST). In **one transaction** per booking: set `reminderSentAt` and publish `ReminderDue{bookingId? | trainingBookingId?, memberId, dogId, startsAt}`. Counters `{classReminders, trainingReminders}`; dry run prints `WOULD_REMIND {bookingId, memberId, startsAt, lead}`; no rollback. Module guard: training reminders only with `FREE_TRAINING`. Add `reminderSentAt` and the indexes `{clubId, state, classStartsAt}` / `{clubId, state, startsAt}` if E5 did not create them. The engine (E7-T02) already turns `ReminderDue` into **N-13** with `stillRelevant` (R-11-16) and the channels APP + PUSH (+ EMAIL per `emailByCategory.OPERATIONAL`). Activity reminders: the catalog has **no** activity-reminder code and S15 P4 covers only bookings and trainings — do **not** invent one; if the backlog's «recordatori d'activitat» is wanted it needs a catalog row: write the proposal in your report and in `roadmap/MESSAGES.md` (`N-xx`, `OPERATIONAL`, `MEMBER → APP+PUSH`, action `OPEN_ACTIVITY`) and implement nothing meanwhile. T-15-17, T-15-18 (advance the injected `Clock`: a 2 h lead fires at the 16:50 tick for an 18:50 class; a booking made at 17:30 for 18:50 never fires; changing the preference to 24 h at 10:00 fires at the 10:00 tick).
2. **Mass announcements** (R-11-13): `POST /message-templates/{id}/send {recipients: {memberIds[]} | {filters[], q}, dryRun}` (ADMIN, `Idempotency-Key`) — allowed only for the N-24 template or a `CUSTOM` one (`TEMPLATE_NOT_SENDABLE`, **422** by rule 0 although S11 §6 writes 409); recipients are the members the same filters would return in `GET /members` (any status the list shows; the assumption in force from B18 is that the club sends to **active** members — apply the filters as given and do not add a hidden status filter, state it); empty result → `NO_RECIPIENTS` (**422**); `dryRun: true` → `200 {batchId: null, recipientCount}` and **nothing** is written. A real send: create an `Announcement` document (`announcements`: `batchId`, `templateId`, `filters`, `q`, `recipientCount`, `actorAccountId`, `createdAt`; it backs the idempotent replay and the log — S11 §3 lists only three own collections, so record this as an addition in the report), emit `AnnouncementSent{templateId, batchId, recipientCount, filters}`, write `@Audited(ANNOUNCEMENT_SENT)` (`entityType = MessageTemplate`, `details {batchId, recipientCount, filters}`) in the same transaction, and let the engine create one `MEMBER` notification per member with `dedupKey = {batchId}:{memberId}`, that member's preferences and the template's matrix (APP + EMAIL per `emailByCategory.CLUB_NEWS` + PUSH per `pushClubNews`). Sending is immediate — there is no scheduling (assumption in force). The same `Idempotency-Key` returns the same `batchId` and creates nothing new. T-11-18.
3. **The matrix test** (the deliverable the gate names, T-11-02 completed): a parametrised JUnit test whose data provider iterates **every** `NotificationCatalog` row of stage `R1` × every audience of that row × every channel of its `caps`/`push` × preference ON/OFF × module ON/OFF × contact present/absent, asserting the exact delivery list and `SKIPPED_*` reasons of the R-11-03 truth table. On top of it, a second parametrised test drives the **real E5/E6 actions** through the application services and asserts the resulting notifications end to end: member books (N-04) and cancels (N-05); the club books/cancels on their behalf (N-36, APP+EMAIL+SMS); training booked/cancelled (N-06, N-07) and by the club (N-47); a seat is released and the waitlist is notified (N-15, APP+SMS+PUSH, action `CLAIM_SEAT`); the club cancels a class with registrants (N-08a per dog, instructors and admins with the staff copy) and modifies one (N-08b); a class is at risk (N-16) and auto-cancelled (N-17); an on-time cancellation leaves the class below the minimum (**N-54** to the class instructors + admins, APP+EMAIL, no other effect); attendance marks a no-show the day before (N-19 with `class_date = ahir`); a task is created and completed (N-20, N-21); a member note changes (N-22); an activity is published, a registration changes and the club cancels or modifies the activity (N-32a, N-32b, N-32c, N-32d); a reminder falls due (N-13). Each case asserts code, audience, recipient set, channels with their status, and the rendered title/body **in the recipient's locale** (at least one recipient in `es` or `en` per group). Any code of the catalog that no E5/E6 action can produce yet (billing, inactivity, migration, courses, platform) is listed as «covered by stage Ex» in the report, never silently skipped.
4. **Seed additions** (through the application services, never raw inserts, deterministic with `--seed=42`, idempotent): the demo club gets members with **different preference profiles** so the matrix is visible in the UI and in the smoke — one with `emailByCategory.CLUB_CHANGES = false`, one with two phones, one with two contact emails (one of them marked `bounced`), one with `reminderMinutesBefore = 120`, one with `pushClubNews = false` and one `PUSH` subscription of a fake endpoint; at least ten active fictional members for the mass-announcement check; a `CUSTOM` template in `CLUB_NEWS` («Comunicat del club», fictional text) ready for the send dialog of D5/D15. Document them in `seeds/README.md`. Fictional data only, `@example.test`, fake phones (`+34600000001`…).
5. **`bin/e7-smoke [--image]`** (Python, pattern of `bin/e4-smoke`): start the stack (`compose.yaml` or `--image` with `docker-compose.consumer.yml`), `club:apply seeds/club-canic.yaml`, `seed:demo --club=canic --seed=42`, log in with the fictional seed accounts (`SEED_PASSWORD`, never printed), then assert with exact statuses and codes: `GET /message-templates` → one template per eligible catalog code with the four category counts → edit N-08a's body in `ca` **and** `es` (`PUT`, then `PUT` with the old `version` → `409 STALE_VERSION`) → cancel a seeded class with registrants → `GET /notifications?filter=code:eq:N-08a` shows one row per registrant with `deliveries[]` APP `DELIVERED` + EMAIL `SENT` (present in the local mailbox) + SMS `SENT`/`QUEUED` through the fake or log sender, **the edited text in each recipient's language** → `GET /me/notifications` as that member shows the card with `channels` containing SMS and `action.type = CHANGE_CLASS` → `read-all` → `unreadCount = 0` and it agrees with `GET /me/home` → `PUT /me/notification-preferences {emailByCategory:{CLUB_CHANGES:false}}` → repeat a club-made change → EMAIL `SKIPPED_BY_PREFERENCE` and SMS still sent → `POST /message-templates/{N-24}/send {filters, dryRun: true}` → `200` «recipientCount ≥ 10» with nothing written → the same call without `dryRun` → `202 {batchId, recipientCount}`, ten notifications in the log with `dedupKey {batchId}:{memberId}`, one `ANNOUNCEMENT_SENT` audit entry, the same `Idempotency-Key` replayed → same `batchId`, no new rows → `POST /message-templates/{N-08a}/send` → `422 TEMPLATE_NOT_SENDABLE`; empty filter → `422 NO_RECIPIENTS` → advance the clock (`bin/core` job trigger with `--at` or the framework's dry-run/apply commands of E5-T01) and run `jobs:run reminders --dry-run` then `--apply` → the member with `reminderMinutesBefore = 120` gets exactly one N-13 (APP + PUSH; EMAIL skipped by `OPERATIONAL` off), a second run creates nothing (`reminderSentAt`) → `POST /push-subscriptions` with a fake endpoint → 201; with `PUSH` off → `404 MODULE_DISABLED` → simulate a signed SendGrid bounce for one recipient → the delivery is `FAILED`, `contactEmails[].bounced = true`, an N-51 row for the admins, and the next message to that member skips that address → **if `TWILIO_ACCOUNT_SID`/`TWILIO_AUTH_TOKEN` are present in the environment**, send one real SMS to a number given in `SMOKE_SMS_TO` and assert `SENT` with its `providerRef` (truncated); when they are absent, print «real SMS skipped: no Twilio credentials» and keep exit 0. Print a summary table (step · status · key values), exit non-zero on the first failed assertion, and stay idempotent on a second run (the script creates its own template/announcement with a run suffix and archives them at the end). Never print a token, an API key, a phone number or a message body.
6. **Docs**: `README.md` (E7 commands: `bin/e7-smoke`, the reminders job, `messaging:migrate-notifications`), `seeds/README.md` (the preference profiles and the `CUSTOM` template), `docs/DEPLOY.md` (the new environment variables `TWILIO_ACCOUNT_SID`, `TWILIO_AUTH_TOKEN`, `TWILIO_MESSAGING_SERVICE_SID`, `VAPID_PUBLIC_KEY`, `VAPID_PRIVATE_KEY`, `VAPID_SUBJECT`, with the behaviour when they are missing, and the gate E7 checklist with this smoke as its evidence).

## Fixed conventions
- Catalogs are closed: N-13, N-24, N-49, N-51, N-54 and every other code used here exists in `CATALEG_NOTIFICACIONS.md`; `ReminderDue`, `AnnouncementSent`, `JobFailed`, `SchedulerRun` exist in `CATALEG_ESDEVENIMENTS.md`; `ANNOUNCEMENT_SENT` exists in S14 R-14-09. An activity reminder does **not** exist — propose, do not invent (step 1).
- Jobs never call `Instant.now()`: the `Clock` is injected and tests advance it; the job framework of E5-T01 owns locking (`job_locks`), catch-up, `job_runs` and the `JobFailed` → N-42 path — reuse it, never a bare `@Scheduled`.
- Assumptions in force: announcements are immediate, to members only, with each member's own preferences (B18, S11 §13-6); the log is never deleted (pseudonymised on erasure, R-14-15); `SENT` is the terminal SMS state at R1.
- Seeds and smoke use fictional people only (`@example.test`, fake phones, no real staff and no mockup first name as a real person); no secret is ever printed or committed; provider references truncated in evidence.
- Evidence rule: report = command + exit code + last 40 lines; long outputs → `roadmap/evidence/E7-T04/NN-<name>.log`; task file ≤ 120 KB. Never edit other tasks, `roadmap/ROADMAP.md` or the *Organizer verification* section.
