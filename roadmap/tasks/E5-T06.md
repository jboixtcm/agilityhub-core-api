## Steps
1. **`GET /me/home?dogId=`** (`MemberHomeQuery`, MEMBER incl. impersonation): the dog chips = own dogs plus, with `FAMILY_GROUP`, the group's, each with `levelName`, `own` and `ownerFirstName`; no `dogId` means «Tots». `limits` = the counters of R-08-02 for `W0` and `W1` summed over the filtered dogs, with `max` and `weekKey` (the screen shows no maximum, the API still returns it). `reservations` = one chronological list of future rows (`endsAt > now`) merged from four sources: class bookings (`CLASS`, states `CONFIRMED` / `PAYMENT_PENDING`), waitlist entries (`CLASS_WAITLIST`, `WAITLISTED`), training bookings (`TRAINING`, via the `MemberTrainingRowsPort` of `clubs.bookings.application.ports` whose adapter lives in `clubs.training.application` — the direction E5-T01 fixed) and activity registrations (`ACTIVITY`, `REGISTERED`/`WAITLISTED`, via `MemberActivityRowsPort` with its adapter in `clubs.activities.application` over E4-T04's `ActivityQueryService`). `instructorName` follows R-08-20 (`InstructorVisibility` of E5-T02): null plus `instructorVisibleAt` while it is too early. Plus `history.monthsVisible` (`history.monthsVisible`), `notifications.unreadCount` and `impersonation`. Module off: `FREE_TRAINING` removes the `TRAINING` rows, `ACTIVITIES` the `ACTIVITY` rows, `WAITLIST` the `CLASS_WAITLIST` rows, `FAMILY_GROUP` the other members' dogs. `404 DOG_NOT_ACCESSIBLE` for a dog that is not accessible. T-08-12, T-07-27.
2. **`GET /me/bookable-classes?dogId=`** (`BookableClassesQuery`, MEMBER): exactly **one** dog — the requested one, else `Member.lastDogForClass` while it is still accessible, else the first own dog. Returns the dog, the chips (no «Tots»), the `pack` card with `state ACTIVE|EXPIRING|EXPIRED|EMPTY` (module `PACKS`), `singleClass {chargeMode, pricePerClass}` (module `SINGLE_CLASS`), `bookingBlock` (banner), the `activities` block (module `ACTIVITIES`, filtered by the selected dog's level per part C S07) and `classes` = the `ACTIVE` sessions with `startsAt > now` up to the end of `W2` that the dog has neither booked nor is waiting for, each with the **server-computed** `state` in the priority order of R-08-03: `NOT_BOOKABLE{reason: BLOCKED|INACTIVITY|LEAVING}` → `NOT_YET_OPEN{opensAt}` → `PACK_EMPTY` → `WEEKLY_LIMIT_DONE` (limit reached **and** no swappable booking) → `WAITLIST_FULL` / `WAITLIST_OPEN` / `FULL` (without `WAITLIST`) → `BOOKABLE`, plus `week CURRENT|NEXT|LATER`, `freeSeats`, `waiting`, `waitlistMax`, `price` and the ring colour. Reuse `BookingLimits`, `BookingEligibility` and the waitlist counters — never a second implementation of the rules. Back the query with the base cache P1 warms (E5-T05 step 2, TTL 30 s, per-dog state always live) and state in the report which class owns the cache key. T-08-13, T-08-26.
3. **Seed** (`seed:demo`, deterministic `--seed=42`, idempotent, **always through the application services** so every invariant, index, counter and outbox event is real; extend `seeds/demo-canic.yaml` and `DemoSeedService`, keeping E4-T05's `--week-start` semantics): (a) class bookings on the validated current week reproducing the D4 occupancy E4-T05 faked (`4/5`, `3/5`, `5/5 +1`, `2/5`, `1/1`, plus the Wednesday 18:50 «B+C» class with 4 registrants — 2 paid with a pack — and 2 waiting, which D4c's modal counts), now created with `SeatHoldService` + `BookingConfirmationService` and `WaitlistService.join`; (b) one booking cancelled in time and one `CANCELLED_LATE` on the same dog and week so the limit rules and screen 07's two notices have data; (c) a member with the weekly limit reached and one swappable booking (screen 06's swap) and another with the limit reached and none (screen 29's informative variant); (d) a full class with 3 waiting entries (`WAITLIST_FULL` row) and another full with 1 (`WAITLIST_OPEN`); (e) free training: levels with `grantsFreeTraining` from level D up, three demo dogs covering the three eligibility cases of S09 R-09-01 (right by level, right by `freeTrainingOverride = true`, no right) — **use the seed generator's dog names, never the spec's or the mockups' first names, and let the front select rows by state** (E4-T05's rule) — two `ACTIVE` training bookings in the current training week so the counter shows 2/3, one slot booked by another dog on a capacity-1 ring, and a `RingBlock` `RESERVATION`/`PRIVATE_CLASS` created by an instructor on Petita with a note (screen 24 and the grids); (f) a class at risk for tomorrow with 1 registrant and one with 0 for the day after (S15 P2's fixture), plus one `riskExempt` class; (g) with a fictional second club (not the Cànic) `waitlist.mode = FIFO` and `SINGLE_CLASS` on, one `PAYMENT_PENDING` booking older than `bookings.paymentPendingMinutes` and one `NOTIFIED` FIFO entry with `confirmBy` in the past, so P6 and P7 have work. ## Fixed conventions
- The aggregates decide everything: the front never recomputes a row state, a limit, a threshold or an instructor's visibility. Any rule needed here already exists in `clubs.bookings.domain`/`application` — reuse it, and if something is missing add it there, not in the query.
- Context direction (ArchUnit): `clubs.bookings` declares `MemberTrainingRowsPort` and `MemberActivityRowsPort` in its `application.ports` package; the adapters live in `clubs.training.application` and `clubs.activities.application`. `clubs.bookings` imports neither of those two contexts.
- Fictional data only: names from the E2-T11 generator, `@example.test` accounts, tiny generated fixtures; never the club's real staff, never the mockups' first names as people; no secrets in any output (`SEED_PASSWORD`, API keys, tokens truncated). The seed uses the E5 application services and the shared `Clock`; it never writes `bookings`, `seat_holds`, `waitlist_entries` or `training_bookings` directly, and no counter is patched by hand.
- If Docker or k6 is unavailable in the session, block per the protocol (the organizer verifies the smoke and the load run from the executor evidence + CI) with the scripts committed.
- Closed catalogs: nothing new; any doubt about a seed value (dates, counts, which club carries FIFO) is an assumption in the report. Evidence rule: report = command + exit code + last 40 lines; long outputs → `roadmap/evidence/E5-T06/NN-<name>.log`; task file ≤ 120 KB; never edit other tasks, `ROADMAP.md` or the Organizer verification section.
