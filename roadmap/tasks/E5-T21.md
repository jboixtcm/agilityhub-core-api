1. **Removed files stay removed (E5-T19 review #1).**

   - Extend `R_04_19_R_04_08_d2RemovesOneFileOfAPendingPublicSignupDog`. After the `DELETE`: (a) a `PATCH` that sends back the view keeps the `removedAt` row, and P9 still counts the file as referenced; (b) a `PATCH` that sends the removed key answers 400, and the file does not come back. ### Assumptions
1. **What «changes no file key» compares.** It compares each sent type's set of file keys with the set D2's view shows for that type. Order and names do not count, because a kept file keeps its stored name (step 7's descriptions). For a reused dog, the view is the one after the merge, so withdrawing a submitted type is a change when the dog's own files differ.
2. **Unchanged types are not rewritten, even in a mixed edit.** For a public signup's dog, a type sent with the keys it already shows is not written. So a type sent without files while it shows none (a `PENDING` document, or no document) writes nothing, and emits no second `DogDocumentPending` (`REGISTRATION`). Before, each such edit rewrote the row and emitted the event again.
3. **The removed-key refusal also applies at submission.** `claimDocuments` is shared. At `POST /signup` for a readmission, a key removed from the reused dog's own card answers `400 FILE_NOT_FOUND`. A new dog has no stored rows, so nothing changes for it.
4. **Error order.** `TOO_MANY_FILES` is now checked after each type's own checks (type text, a type sent twice, `DOCUMENT_TYPE_UNKNOWN`), because counting uploads needs each type's stored files. A request with an unknown type and more than 10 uploads now gets `DOCUMENT_TYPE_UNKNOWN`. It is still checked before any file is claimed.
5. **Step 5's second test is a pin.** The definition schema already refused `null`. The failing-before test for step 5 is the contract test.
