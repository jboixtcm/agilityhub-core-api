# E11-T04 · Deploy assets provable locally (E0-T13, part 1)

## Objective
The release (E12-T01) deploys to one DigitalOcean droplet as ADR-003 describes. Until then everything runs on the local Docker stack (A31), so the deployment assets are written and proven locally now: the production compose, backups with a verified restore, and the runbook. E0-T13 (staging on the droplet) stays for the release; this task is everything of it that can be proven without SSH or DNS.

This is the first task of the third loop (thread D, ruling E78). It touches `deploy/`, `bin/` and `docs/DEPLOY.md`; it should not need a Java change. If it does, say why in the report.

**Each script comes with a local run that proves it, and a run that shows it fails when it must.**

## Steps
1. **`deploy/compose.prod.yaml` and `deploy/Caddyfile`.**
   - Services: `core` (the published image, by `IMAGE_TAG`), `mongo` (7 or later, a one-node replica set **with authentication**: a key file and the users from the environment, a persistent volume) and `caddy`.
   - Caddy serves `id.`, `clubs.`, `clubsadmin.` and `core.agilitydoghub.com` with automatic HTTPS; the three SPAs from mounted `dist/` folders; the same-site proxy of A1 on each front host (`/api/*`, `/oauth2/*`, `/.well-known/*`, `/connect/logout`), as DEPLOY.md's template does; and on-demand TLS for the clubs' own domains with `ask` → `http://core:8080/internal/domains/allowed` (A11). That route is E10-T02's: write the block, and say in DEPLOY.md that club domains wait for it.
   - No secret in the repository: `deploy/.env.prod.example` lists every variable with a placeholder.
2. **A local proof of the production compose.** An override (`deploy/compose.prod.local.yaml`) that runs the same services on the Mac: `*.localhost` hosts with Caddy's internal certificates, a MinIO for S3, the demo seed. `docker compose … up -d --wait` → through Caddy: `/api/v1/health` is `UP`, `/api/v1/branding` answers by host, one SPA's `index.html` is served, and a refresh through the proxy sets `ah_refresh` on the front host (A1).
3. **`bin/backup-mongo`** (daily, A13): `mongodump --oplog` of the authenticated replica set, packed and **encrypted** with a key from the environment (production backups hold personal data), uploaded to S3 (bucket and prefix from the environment), retention in days (default 30), exit codes a cron can alert on. The daily cron line goes in DEPLOY.md. Local proof against MinIO. A run without the encryption key or the bucket fails before it writes anything.
4. **`bin/restore-mongo --verify`**: fetch the latest backup (or a named one), decrypt it, restore it into a temporary Mongo container, and compare the document count of every collection with the source → exit 0 only when they match. Local proof: seed, back up, restore with `--verify` → equal counts; a tampered archive → a non-zero exit.
5. **`docs/DEPLOY.md` as the release runbook** (a new section; keep the existing ones):
   - a table of every variable of production (every `*_KEY`, secret, URI and provider credential: the OIDC master key, SendGrid, Twilio, VAPID, Stripe, S3, the bank key, the signing keys…), what each one is for, where it comes from, and whether and how it rotates;
   - deploy → smoke → rollback by the previous image tag, and the restore;
   - key rotation (which keys, what breaks, in what order), logs (where, how long), and a D+7 support checklist;
   - the pending items of the release (E12-T01): SSH, DNS, real providers, and «alta d'un domini de club» (E10-T03).

## Fixed conventions
- No secret in the repository; fictional data only; never point a script at a real database.
- Heavy runs go through the host lock. The task file stays ≤ 120 KB.
- Catalogs are closed: no new parameter, event, notification or error code.

## Verification (run all; evidence = command + exit code + last 40 lines; long outputs → `roadmap/evidence/E11-T04/*.log`)
- `docker compose -f deploy/compose.prod.yaml config` and the same with the local override (both valid).
- Step 2's local stack, with the four checks through Caddy.
- `bin/backup-mongo` and `bin/restore-mongo --verify` on the local stack (equal counts), and the two failing runs (no key; a tampered archive).
- `shellcheck` on the new scripts, when it is installed.
- `./mvnw -q clean verify`, only if a Java or resource file changed.

## Definition of Done
- Steps 1–5 are done and proven locally, the failing runs fail, and DEPLOY.md is a runbook that the release (E12-T01) can follow.
