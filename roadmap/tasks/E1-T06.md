# E1-T06 · Onboarding «Completa el teu perfil»: Account.onboardingPending and /me/onboarding

## Objective
The backend of the first-access screen for imported (Learn) and migrated (Playoff) accounts, decided by Jordi on 2026-09-05.

## Spec references
S01 §14 (onboarding block), R-01-14 · `docs/specs/S18-migracio-playoff.md` (migrated members) · `docs/DECISIONS_PENDENTS.md` A4, A12 · `docs/specs/00-transversal/CATALEG_PARAMETRES.md` (`signup.onboardingFields`, `club.privacyPolicyUrl`, legal version) · `docs/legal/POLITICA_PRIVACITAT_AGILITYHUB_ID.md` (link only).

## Context to load
S01 §14 · S18 §3 (migrated member fields) · DECISIONS A4/A12 · CATALEG_PARAMETRES · this file.

## Steps
1. `Account.onboardingPending` (set by the Learn import and the Playoff migration; `false` for accounts created by signup), `Account.consents[] {policy: PLATFORM|CLUB, version, acceptedAt}`.
2. Contract exactly as the E1-T01 snapshot (S01 §6 v0.3): `GET /me/onboarding` → `200 OnboardingState {pending, postponeRemaining, requiredConsent: {policy: PLATFORM|CLUB, version, url} | null, fields[]: {key, value, required}}` (fields from `signup.onboardingFields`, values prefilled from Account/Member; `requiredConsent` = the policy whose current version the account has not accepted — platform first, then club); `PUT /me/onboarding {consentAccepted, consentVersion, fields?: {name?, locale?, phone?}, imageConsent?}` → validates the consent (`consentAccepted=false` → `400 VALIDATION_ERROR`; `consentVersion` ≠ current → `422 CONSENT_VERSION_OUTDATED`), stores the optional fields (name/locale → `Account`; phone and `imageConsent` → `Member` when there is one), appends `consents[]`, sets `onboardingPending = false`, audit `ONBOARDING_COMPLETED`, returns the new state.
3. Policy-version change (A12): when the platform or club policy version increases (`Club.legal.legalTextsVersion`; platform version from configuration `agilityhub.legal.privacyPolicyVersion` + url), `GET /me/onboarding` reports `pending` again with `postponeRemaining` (parameter `legal.maxPostpones = 3`, already in the catalog); `POST /me/onboarding/postpone` → `200 OnboardingState` decrements it; at 0 it returns the state unchanged (no error) and the front blocks until acceptance (the API only reports the state).
4. `GET /me` returns the real `account.onboardingPending` (the field already exists in the contract with a constant `false`).

## Verification (run all; paste full output in the report)
- `./mvnw -q verify` → green with `OnboardingIT` (imported account → pending; accept → not pending; policy version bump → pending again; postpone 3 times then required).

## Definition of Done
Endpoints + consent storage + version bump logic tested.
