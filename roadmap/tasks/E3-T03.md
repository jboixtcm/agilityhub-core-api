## Steps
1. **`GET /signup`** (config in one call, cached 60 s per club + locale, invalidated by `PlanChanged`/`PriceChanged`/`ParameterChanged`/`ClubUpdated`): `enabled` (`signup.enabled` ∧ club `ACTIVE`, else only `closedText`), `steps` (4 with `FAMILY_GROUP`, 3 without), plans from `SignupPlanCatalog`, payment methods from the club's active providers (`SEPA_XML → SEPA_DD`, `STRIPE → CARD`, `MANUAL → MANUAL`, with `mandateText` = `signup:payment.mandate.{profile}` resolved with `[[club_legal_name]]`, `instructions` for MANUAL), texts from the `signup.text.*` parameters, `legal` from `CLUB.legal`; authenticated MEMBER → `member` block for the add-dog mode.
2. **`POST /signup/identity-checks`** (R-04-05): match on `idDocument.value` or primary email among `PENDING`/`ACTIVE` members → `NEW` · `SIGNUP_ALREADY_PENDING` · `VERIFICATION_SENT` (emit `SignupRecognitionRequested{memberId, accountId, redirect: /gossos/nou}` → N-39 through the SYSTEM magic-link path) · `CONTACT_CLUB` (ACTIVE without account); only `maskedEmail` leaves the server.
3. **`GET /signup/towns`**, **`POST /signup/upload-urls`** (signed PUT 15 min, key `signup/{clubId}/{yyyyMM}/{uuid}/{sanitisedName}`, `files.maxSizeMb`, `files.allowedTypes` image/pdf, ≤ 10 files, name ≤ 80 — reuse the S10 attachment storage of E2-T06 with a `SIGNUP_DOCUMENT` purpose), **`POST /signup/family-group-lookups`** (`FAMILY_GROUP`; `FamilyHolderMatcher`).
4. **`POST /signup`** (R-04-06…08, 10, 11, 17, 20, 27): honeypot `website` → `202` and nothing stored; body ≤ 64 KB; `Idempotency-Key` 24 h; identity re-check; readmission of a `LEFT` member keeps `number`; chip uniqueness (`DOG_CHIP_ALREADY_REGISTERED`, readmission re-activates the own `LEFT` dog); `DogDocument` `PENDING` + `DogDocumentPending` when no file (`DOG_DOCUMENT_REQUIRED` if `signup.requireDogDocumentAtSignup`); every `fileKey` must exist under the club prefix (`FILE_NOT_FOUND`); payment method validation (IBAN mod-97 optional, `holderName` default = applicant or holder, `CARD` only with Stripe configured); consents entries `{version, at, locale, ipHash}` immutable; family claim → `NONE·FOUND·NOT_FOUND_PENDING` (`leavePending` only with `signup.allowFamilyGroupPending`); `UpfrontPayment` lines `DUE` (E3-T02); one Mongo transaction (`Member` + `Dog` `PENDING`, documents, payments, consents, outbox `SignupSubmitted{source: PUBLIC, readmission, checkoutRequired}`); response `201 {memberId, signupToken (HMAC, 24 h, bound to memberId), upfront, checkout{required}}`; `SIGNUP_CLOSED` when disabled.
5. **`POST /checkout-sessions`** (R-04-26): `PaymentProvider` port (`createCheckoutSession`, `complete`, `expire`) with `FakeCheckoutGateway` in `local`/`test` (real Stripe = E8); ANON requires a valid `signupToken`; `mode = payment` (or `setup` when `totalDue = 0` ∧ `CARD`), one line per `UpfrontPayment`, metadata `{clubId, memberId, upfrontPaymentIds}`, `expires_at +24 h`; lines → `CHECKOUT_PENDING`; `fake.complete()` → `PAID` (+ `paymentMethod.CARD.last4`), `fake.expire()` → `DUE`; `INVALID_STATE` when nothing to pay; `PAYMENT_PROVIDER_NOT_ENABLED` without Stripe.
6. **`POST /me/dogs/signup`** (R-04-25): MEMBER `ACTIVE` (impersonated → audited with both ids, `origin = BACKOFFICE`), `Dog` `PENDING`, document, `ENTRY_FEE` (+ `ADDITIONAL_DOG_FEE` per R-04-14 add-dog mode), `SignupSubmitted{source: APP_ADD_DOG}` → N-01 to the member (APP+EMAIL) and admins; `MEMBER_NOT_ACTIVE` otherwise.
7. **D2**: `GET /members/{id}/signup` (aggregate with `warnings[]` of R-04-18, `pendingDays`, `proposals` from `dryRun` logic), `PATCH /members/{id}` · `/dogs/{id}` allowed in `PENDING` emitting `SignupEdited` (not `MemberUpdated`) and auditing before/after (R-04-19; consents not editable → 400), **`POST /members/{id}/validation?dryRun=`** (R-04-13…16, 21, 22, 25: `LEVEL_REQUIRED` with `levels.enabled`, `NEXT_INVOICE_DATE_REQUIRED` for `MONTHLY` with `BILLING`, family group creation/joining, fare proposal, upfront allocation, atomic `number` (`findAndModify` counter per club, never reused), `Account` reuse-or-create (`AccountCreated{source: SIGNUP}`, locale = signup locale, no password) + `Membership {roles: [MEMBER]}` (`MEMBERSHIP_EXISTS`), dogs `ACTIVE` with `levelAssignedAt`, `mandateRef` when SEPA, all in one transaction with the outbox `MemberValidated` (+ `DogRegistered` and **no** `MemberValidated` for the add-dog case) → N-02 with the welcome magic link; `dryRun=true` writes nothing), **`POST /members/{id}/rejection`** (R-04-23: `reason` 3–500, `LEFT{SIGNUP_REJECTED}`, dogs `INACTIVE`, payments `CANCELLED` except `PAID` (warning), `SignupRejected` → N-03; second rejection `INVALID_STATE`; add-dog case only the pending dogs).
8. **Rate limits and anti-abuse** (R-04-20): per IP (`X-Forwarded-For`) and club through the existing `RateLimitFilter` policies — `identity-checks` 10/h, `family-group-lookups` 20/h, `upload-urls` 30/h, `POST /signup` 5/h and 20/day, anonymous `checkout-sessions` 10/h, `towns` 60/h → `429` + `Retry-After`; structured logs with `traceId`, `clubId`, `ipHash`.
9. **Notifications** N-01, N-02 (gender ICU, welcome link), N-03, N-37, N-39 delivered through the E1 SYSTEM path with the S11 template codes (the club templates arrive in E7; here: default templates in ca/es/en from the notification catalog, rendered in the applicant's `signup.locale` / each admin's locale).
10. **Catalog constraints (from E3-T02)**: `src/main/resources/parameters/catalog.yaml` — `signup.firstMonthSplitDay` and `billing.nextInvoiceDayOfMonth` get `constraints.min = 1` (a calendar day is 1–28/31, never 0); `documentType`/`documentDefault` unchanged (the doc/yaml contract test only compares those); `ParameterValidator` rejects 0.
11. **Seeds**: `seeds/club-canic.yaml` gets the signup configuration (`signup.*` parameters already in the catalog; `legal.legalTextsVersion`, `privacyPolicyUrl`); `seeds/club-minim.yaml` variants for T-04-26 (modules off).

## Fixed conventions
- **From E3-T01**: the `501` stubs of `POST /signup` and `POST /checkout-sessions` bypass the authenticated idempotency filter through a narrow exception — replace it here with anonymous idempotency scoped by host + `Idempotency-Key` (+ `signupToken` for checkout) **before** enabling the mutations; the exception must not survive this task.
- Statuses and codes from the catalog (rule 0 literal: `SIGNUP_ALREADY_PENDING`, `SIGNUP_CLOSED`, `DOG_CHIP_ALREADY_REGISTERED`, `ID_DOCUMENT_AMBIGUOUS` are 422; `MEMBER_ALREADY_EXISTS`/`MEMBERSHIP_EXISTS` 409); no new parameter/event/notification without a proposal in the report (S04 §13 proposals `auth.welcomeLinkDays`, `signup.text.*` already in the catalog: check before proposing).
- Never log or return IBANs, id documents or emails in clear beyond the masked forms of S04; `signupToken` is an HMAC with the server key, never persisted in clear.
- Fixtures fictional (`@example.test`, `ES00…`), no real Cànic data.
