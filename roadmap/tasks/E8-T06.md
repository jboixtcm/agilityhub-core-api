## Steps
1. **P5 `expirations`** (`JobName.EXPIRATIONS`, route id `expirations`, daily at `jobs.dailyTime` = 06:00 club-local, unlimited catch-up, no module at the job level — **each step carries its own module and its own counter**, and a step whose module is off is simply skipped with a zero counter). One transaction **per item** with the outbox inside it; a failed item goes to `errors[]` and the run is `PARTIAL`. Steps: **(a) packs** (`PACKS`) — `PackBalance ACTIVE` with `expiresOn ≤ today + billing.packExpiryWarningDays` (14) and `expiryWarnedAt == null` → `expiryWarnedAt = now` + `PackExpiring` → **N-11b**; `expiresOn < today` → `PackBalanceService.expire(...)` → `state = EXPIRED`, `expiredAt`, **the remaining sessions are lost** + `PackExpired` → N-11b. S13's consumer (E8-T05) turns `PackExpired` into the planned leave — **P5 only marks and emits**. **(b) inactivity** (`INACTIVITY`) — `InactivityScheduler.startDue` (`APPROVED` with `fromMonth ≤ month(today)` → `ACTIVE`, `InactivityStarted`, no notice) and `finishDue` (`ACTIVE` with `toMonth ≠ null ∧ toMonth < month(today)` → `FINISHED`, `InactivityEnded` → **N-18c**); an open period never ends by itself; plus `expireStale` for a `REQUESTED` period whose month has passed → `CANCELLED{SYSTEM, EXPIRED}`, silent + audited. **(c) leaves** — `LeaveScheduler.executeDue(clubId, today)`: `ACTIVE` members with `leaveDate < today` → `LEFT` in the same transaction as the booking sweep, `MemberStatusChanged{ACTIVE→LEFT, effectiveDate = leaveDate}`; **no new notification** (N-28 went out when the date was confirmed). **(d) pending signups** — `PENDING` members whose `signup.submittedAt` is older than `signup.pendingExpiryDays` (30) local days → **one** `SignupPendingAging {count, oldestDays, memberIds[]}` per club and day → N-34; a repeated manual run the same day reports `alreadyDone`. **(e) documents** — only when `messaging.documentReminderDays > 0` (the Cànic has 0 = never): `DogDocument PENDING` of an active dog and member with `(lastReminderAt ?? createdAt) + days ≤ today` → `lastReminderAt = now` + `DocumentReminderDue` → N-23. **(f) ring setups** (`COURSES`) — `RingSetup ACTIVE` with `expiresAt ≤ now` → `EXPIRED` and `Ring.activeSetupId = null` when it pointed there + `RingSetupChanged{status: EXPIRED}`; if the courses vertical does not exist yet, register the step with a zero counter and say so in the report. **(g) SMS counter** — `Club.usage.smsMonthKey ≠ month` → `smsSentMonth = 0`, `smsMonthKey = month`. Dry-run actions exactly as R-15-15 names them: `WOULD_EXPIRE_PACK`, `WOULD_WARN_PACK`, `WOULD_START_INACTIVITY`, `WOULD_END_INACTIVITY`, `WOULD_LEAVE {memberId, futureBookings}`, `WOULD_REMIND_SIGNUPS {count}`, `WOULD_REMIND_DOCUMENT`, `WOULD_EXPIRE_SETUP`. Idempotent by the marks the spec names (`expiryWarnedAt`, `state`, `lastReminderAt`, `smsMonthKey`), so two runs or a lost day give the same result. T-15-19…T-15-23, T-12-24, T-13-27, T-13-28.
2. **P10 `billing-reminder`** (`JobName.BILLING_REMINDER`, route id `billing-reminder`, module `BILLING`, daily check that only fires on `billing.remittanceReminderDay` = 22, `0` = never): when the club has a `SEPA_XML` provider, at least one `ACTIVE` member with `paymentMethod.type = SEPA_DD` and `nextInvoiceDate ≤` the end of the month, **and** no `Remittance` created inside the month with a status other than `ROLLED_BACK` → `RemittanceReminderDue {period, pendingMembers}` → **N-41** to the admins. Once per month, no business effect, nothing to undo. **Say it explicitly in the code comment and in the report: no receipt and no remittance is ever generated automatically at R1** — D6 is manual. `BILLING` off → `SKIPPED{MODULE_OFF}`. T-15-28.
3. **Job registration**: add the two `Job` beans in the catalog order of R-15-01 (the rows already exist from E5-T01 and have been bean-less until now), each declaring its module and catch-up window; verify through the framework that the switch (`jobs.expirations.enabled`, `jobs.billing-reminder.enabled`), the module and the club status produce the right `SKIPPED{…}` rows, that a catch-up run behaves as R-15-05 says, and that `plan ≡ effects.items` for both (T-15-06 extended). `GET /jobs` must now list seven rows at the Cànic; expose both through the existing `jobs:run <route-id> [--club=] [--dry-run]` CLI command E5-T05 added.
4. **Billing importer (S18 WP-18-C)** — extend `PlayoffImportService`/`MigrationApplyService` with load **step 7 (historical receipts)** and **step 8 (live packs)**, in batches of 100 inside a transaction, idempotent by `sourceIds` so a re-run changes nothing: **step 7** maps each of the last `history.receiptsMonths` (24) months of receipts to an `Invoice {kind: MIGRATED, series: "PLAYOFF", number = the original number, displayNumber = the original, period from the concept («Febrer 2026 …») or from the date, total, status Pagado → PAID · Pendiente/Vencido → PENDING · Impagado → FAILED, paymentMethod from the receipt, lines: [{origin: MIGRATED, description: the original concept, total}]}` — no tax breakdown unless the export carries one, **no `Collection`, never part of any remittance**, and **no collision** with the new `{YYYY}` series (B8: 24 months, no outstanding unpaid items at the Cànic, but the branch stays); **step 8** maps «Control packs» to `PackBalance` per dog through `PackBalanceService` (initial `OPEN` movement with `reason: MIGRATED`, `expiresOn = openedOn + Plan.pack.validityMonths − 1 day`, `state = EXPIRED` when `expiresOn <` the cut-over, warning `PACK_DOG_AMBIGUOUS` when the record has several dogs and it is assigned to the first). **Mandates** (R-18-08): every migrated `SEPA_DD` member gets `mandateRef = {clubSlug}-{memberNumber}-1` and `mandateSignedAt` = the cut-over date passed on the command line, everything `RCUR`; an invalid IBAN (mod-97) → `iban = null` + warning `IBAN_INVALID`/`NO_BANK_ACCOUNT`; a card payment method → `MANUAL` + `CARD_NOT_MIGRATED`. Keep the «exported mandate» branch alive for other clubs. `nextInvoiceDate` = day 1 of `M+1` for every `ACTIVE` member on a monthly plan, none for packs (R-18-13). The importer **never rejects** a record for these reasons: it warns and continues (R-18-11b). T-18-05, and T-18-15 for the pack half.
   - **Dog photos (B29, added 24-09 from the E5-T12 verification).** The census import keeps the Playoff photo reference in `Dog.sourceIds.playoffPhoto` and leaves `photoFileKey` untouched. Add `migration:photos --club=<slug> [--dry-run]`: it downloads each reference with a read-only HTTP GET into the attachment storage as a `DOG_PHOTO` (same type and size rules as `files.dogPhotoMaxMb`) and sets `photoFileKey` **only when it is empty**, so an uploaded photo is never clobbered. It is idempotent, one report line per dog without personal data, and skips `[redacted]` (anonymised data). Tests against a local HTTP stub and the local storage: success, 404, too large, wrong type, second run = 0 changes.

## Fixed conventions
- Statuses (catalog first): `JOB_ALREADY_RUNNING` **409**, `MODULE_DISABLED` **404**, `JOB_UNKNOWN` and `NOT_DUE` **422** by rule 0 (E5-T01 already filed the proposal to move `JOB_UNKNOWN` to §1 — do not change it again), `MIGRATION_ALREADY_APPLIED` **409**, `MAPPING_INVALID` and `INPUT_SCHEMA_MISMATCH` **400**, `PRODUCTION_REQUIRES_CONFIRMATION` and `CLUB_NOT_EMPTY` **422**, impersonation on any `/jobs*` route **403**.
- Assumptions in force (do not ask): **no receipt or remittance is ever generated automatically at R1** — the only billing automation is P10's reminder (S15 §1); pack sessions left at expiry are lost (B11); the planned leave after a pack expiry is S13's consumer, not P5's job (R-15-15a); `leaveDate` is an active day, so the transition happens the **next** day and a late run catches up with `<`, never `=` (R-13-13); Playoff exports no mandates, so every mandate is new with `mandateSignedAt` = the cut-over date and every remittance is `RCUR` (B6); 24 months of receipts with no outstanding unpaid items at the Cànic, and the migrated series is `PLAYOFF`, separate from `{YYYY}` (B8, §13-7); processes run for clubs `ACTIVE` **and** `ONBOARDING`; retention values come from the catalog.
- Migration safety (R-18-01, T-18-12, T-18-16): the importer refuses an `--in` path inside a git repository or inside the Dropbox folder; **no real personal data ever enters the repo, a fixture, a log or an evidence file** — every test runs on the anonymised derivative E2-T10 produces; the staging report carries ids and codes only.
- Jobs: one Mongo transaction per item with the outbox inside it; dry run writes nothing anywhere except the `JobRun{dryRun: true}`; `parametersSnapshot` on every run; metrics as E5-T01 defined them; `JobFailed` → N-42 at most once per process and club-local day; `Clock` injected everywhere (the E5-T01 ArchUnit rule); occurrences computed in `club.timeZone`.
- Closed catalogs: no new parameter, event, notification, error code or audit action; proposals to the report and `roadmap/MESSAGES.md` while the closest existing item ships.
- Evidence rule: report = command + exit code + last 40 lines; long outputs → `roadmap/evidence/E8-T06/NN-<name>.log`; task file ≤ 120 KB; fictional data only (`@example.test`); no secrets, env vars only; never edit other tasks, `ROADMAP.md`, `docs/` or the Organizer verification section; English identifiers from the glossary; i18n keys never literals; ca/es/en together.
