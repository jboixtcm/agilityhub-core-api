# E5-T26 · Signed local file URLs, the rest

## Objective
Api E5-T24 made the local profile's signed file URLs authorise themselves (`CONVENCIONS_API.md` §5, A31). The independent review of E5-T24 (`roadmap/reviews/E5-T24-20260926-1636-claude.md`) and its report (question 2) found what is still missing:
- A MEMBER adding a dog while signup is closed cannot upload. The web sends no bearer to the signed URL, as §5 says, and `PUT /api/v1/signup/uploads` then answers `422 SIGNUP_CLOSED` (R-04-27).
- The review could not check that an `<img>` shows a local download, nor the CORS preflight of the signed routes.
- The signed routes run without a tenant, although a Javadoc says they have one.

The organizer confirmed and decided them all on 26-09. Until the release, the local stack is what runs (A31), so these are real flows.

The nits of this task's own review go to `docs/INCIDENCIES_OBERTES.md`. Its minors go there too, unless they block the web.

**Each fix comes with a test that fails before the fix.**

## Steps
1. **A member's add-dog upload while signup is closed (review #1, question 2, R-04-27).**
   - When an authenticated MEMBER calls `POST /signup/upload-urls`, the grant stores the member's account.
   - `PUT /api/v1/signup/uploads` with such a grant skips `requireSignupOpen()`: its signature already authorises it, with no bearer.
   - An anonymous grant still answers `422 SIGNUP_CLOSED` while signup is closed.
   - IT with `signup.enabled = false`:
     - a MEMBER's upload URL, then a `PUT` with `Upload.headers` only, answers 2xx;
     - the member's `POST /me/dogs/signup` then claims the file;
     - an anonymous grant's `PUT` answers 422.
2. **Local downloads answer like S3 (the review's «Not checked»).**
   - `GET /api/v1/attachments/files/{id}` and `GET /api/v1/signup/files` answer the file's stored MIME type, not `application/octet-stream`.
   - Images come with `Content-Disposition: inline`, and other files with `attachment`, with the stored name.
   - An `<img>` must show a dog's photo or an activity's image, even from another origin (the web's app runs on its own origin).
   - IT: the headers of an image and of a PDF.
3. **The CORS preflight of the signed routes (the review's «Not checked»).**
   - A cross-origin `PUT` from the club's web origin passes the preflight on `/api/v1/attachments/uploads/{id}` and `/api/v1/signup/uploads`, as it does on the api's other routes. These routes have no tenant, so check that the allowed origins do not depend on one.
   - IT: an `OPTIONS` with `Origin` and `Access-Control-Request-Method: PUT` from an allowed origin answers the CORS headers. An unknown origin gets none.
4. **The grant's club as the tenant (review #3).**
   - On the signed routes, the grant's `clubId` opens the `TenantContext` for the handler, as the `UploadGrantRepository` Javadoc already says.
   - Code that calls `TenantContext.require()` there then works.
   - Unit test or IT.
