## Steps
1. **A retried lost answer sends the provider exactly the first request (review #1; CONVENCIONS_API §7, R-04-26).**
   - Today a retry after a lost answer rebuilds the provider request from the member's current data. If an admin changes the contact e-mail or the payment method in between, the same `sessionId` reaches the provider with different parameters. Stripe refuses that as an idempotency error, and the catch then expires the local session but not the provider's.
   - Persist with the session what the first provider call sent (its parameters), or what the provider answered (its session id and URL), and replay exactly that on a retry. An edit between the two calls never changes what the provider receives.
   - Any failure after the provider created its session, an idempotency conflict included, expires the provider's session as well as the local one.
   - Test: fail the answer's persistence; change the member's e-mail and payment method; retry with the same key → the same checkout URL and one provider session. The provider double refuses changed parameters for a known `sessionId`, and it is never refused.
2. **A late completion needs every row still pending for that session (review #2; E5-T28 step 4, E34).**
   - `CheckoutService` accepts a completion when any one of the session's rows is still `CHECKOUT_PENDING` (`UpfrontPayments.checkoutPending`). A session whose rows were partly closed (a rejection cancelled one dog's rows and left another's pending, which the round-1 code could do) is marked `COMPLETE`, pays the surviving rows and records no `lateCompletionAt`. The money for the cancelled rows then escapes E34's reconciliation.
   - Accept a completion only when every `upfrontPaymentId` of the session is still `CHECKOUT_PENDING` for that session. Otherwise record the late completion as E34 says (`lateCompletionAt`, and the refund flag of the rows paid), release the surviving rows, and never mark the session `COMPLETE`.
   - Test: a session with one dog's rows cancelled and another dog's rows pending → the provider's completion records the late completion and pays no row.
3. **A released partial row keeps its payment history (review #3; S04 R-04-16, §3 and §5).**
   - A row that was `PARTIAL` (money received by hand) enters the checkout through `pending → state`, which replaces its provider with `STRIPE` and its `paidAt` with the checkout's time. `released` then sets the provider to `null` and keeps the overwritten `paidAt`.
   - Keep the received payment's metadata (provider, `paidAt`, the amount received) across the checkout's transitions, so a released row is exactly the row it was before the checkout.
   - Test: a partial payment at T1, the clock advanced, a checkout at T2 that includes the row, then a rejection of another dog → the row is `PARTIAL` again, with T1's `paidAt` and its original provider.
4. **The checkout's failure-path table.**
   - In the report, list every write of the signup checkout: `prepare`, the provider's session, the answer and the key, the rejection, the provider's completion and expiry callbacks, P7's expiry and the late completion.
   - For each, say what happens when it fails, or when the process stops right after it: the end state of the session and of its rows, whether money can be charged with no row to show it, whether a row can stay `CHECKOUT_PENDING` for good, and the test that proves it.
   - Fix any other path that can lose money or strand a row, with its test.

### Assumptions

1. **The request is stored, not the provider's answer.**
   - The URL exists only after the call. A stop between the call and storing the URL would leave a retry with nothing exact
     to send.
   - The request is stored in `prepare`'s transaction, before the call.
   - It holds the customer's e-mail. It lives only while the session is `PENDING` and unanswered: `answered` and `finish`
     drop it. It never reaches a log or a URL.
2. **Sessions opened before this change have no `providerRequest`,** and `openFor` ignores them: a retry gets `409` until
   they end, as before E5-T28. There is no production data (E0-T13 is blocked).
3. **`expiresAt` is truncated to milliseconds,** so the request read back from Mongo equals the first one (the double
   compares them with `equals`).
4. **Step 2's «the refund flag of the rows paid»** is read as E34's mark on the session (`lateCompletionAt`,
   `providerPaymentId`), which S12 refunds once. No row gets a new field.
5. **Step 3 at completion:** a `PARTIAL` row that the provider pays becomes `PAID` with `STRIPE` and the completion's
   `paidAt`, as before. The row has one provider.
   - The cash part stays in its `UpfrontPaymentRecorded` (`MANUAL`, 100, T1) and in the validation's audit entry.
   - `UpfrontPaymentSucceeded` now reports only the provider's part (4c). See question 2.
6. **4b:** a signup completion delivered after `expiresAt` is late, and refunded. The same holds for a booking, and for a
   session `lapsed` already expired. See question 1.
7. **`lapsed` never asks the provider:** the provider's session ends at the same `expires_at` we sent.
8. **A lost answer keeps the provider's session open on purpose,** because the retry needs it, until `expiresAt`. A completion
   meanwhile is a normal one: every row still waits.
9. **A side effect of step 3 in D2's validation.** `SignupService.validate` does not require `upfrontAmountPaid` when a row
   shows a Stripe payment (`provider = STRIPE` with money).
   - A cash `PARTIAL` row in an open checkout used to read as `STRIPE` with money.
   - It now reads `MANUAL`, like any cash row, so the field is required.
10. **Files edited by someone else during this session, left untouched:**
    - `docs/DECISIONS_PENDENTS.md`, `docs/INCIDENCIES_OBERTES.md`, `CONVENCIONS_API.md`, S11 and S16;

#### Assumptions (round 2)

1. **`CLAIM_LEASE` is 10 minutes, a constant**, like the key's 24 h. It is not a club parameter, and the catalogs are closed.
   - A request's Mongo transaction lives 60 s at most, and E8's provider calls must time out well within 10 minutes.
   - A synchronous job trigger renews its own run lease (S15 R-15-06), so a retry that takes its claim over meets that lease,
     never a second run.
2. **The takeover needs the same key, scope and body.** The new record has a new `createdAt`, so the key's 24 h restart from the
   takeover, as after a released key.
3. **The fence.** A request that outlives the lease loses its answer and answers `409 IN_PROGRESS`. Its effects roll back when
   they commit with the answer. A job trigger's run commits apart (E5-T29 round 2), and a retry finds it by its reference.
4. **The read view writes nothing.** Past `expiresAt`, the session stays `PENDING` in the database until P7, D2's validation or
   the next checkout. A confirmation of an on-time payment that arrives meanwhile still pays the rows (item 3).
5. **Item 3 applies to booking checkouts too.** A PAY_TO_BOOK payment made before its deadline but confirmed after it, while P7
   has not yet cancelled the booking, confirms it. Without a time from the provider (the fake's default), the delivery time is
   used, so the existing booking behaviour and tests are unchanged.
6. **The paid rows' `paidAt` is the provider's payment time.** The events' `occurredAt` stays the delivery time.
7. **The smoke's fixture:** `fifo`'s status `ACTIVE` and its `MENSUAL` plan `showOnSignup: true` are set with `mongosh` before the
