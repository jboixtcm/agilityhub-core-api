# E6-T06 · D14 and D12 contract gaps (the web's E6-W03)

## Objective
Three gaps the web found while building D14 and D12 (web E6-W03, review #1 and #5 and questions 3 and 5; ruling E75):
- D14's universal filter has no source for its values: `GET /followup` has no `filter-values` route (CONVENCIONS_API §4), so the web read them from the first page, and the «Creador» filter (`authorAccountId`, `x-filterable`) has none at all.
- D14's search box sends `q`, which the list refuses: it has no searchable paths.
- D12's legend says how long a half-height training cell is («mitja alçada: 30 min»), but an instructor cannot read `training.slotMinutes` (`/parameters` is ADMIN only).

A fourth comes from E6-T05's question: a history row can link to an activity page that answers 404. Web E6-W04 steps 0b and 0c adopt the four.

**Each change comes with a test that fails before it.**

## Steps
1. **`GET /followup/filter-values`** (INSTRUCTOR, ADMIN; module `TASKS`), with `field` (one of the list's `x-filterable` fields: `kind`, `memberId`, `dogId`, `authorAccountId`, `unread`), `q` and `filter`, like `/members/filter-values` and E5-T29's three routes.
   - Each value comes with its count over the whole filtered set, never over one page. `unread` is the caller's own (R-10-13: marks are per account).
   - Labels: the member's full name, the dog's name and the author's display name; `kind` and `unread` as their values.
   - Tests: a value that only rows beyond the first page have is listed; two instructors get different `unread` counts; an undeclared field → `400 INVALID_FILTER`.
2. **The follow-up list searches (CONVENCIONS_API §4).** `q` on `GET /followup` (and on its `filter-values`) matches the member's and the dog's names, the author's name and the text. Test: one `q` per field.
3. **`InstructorWeek.trainingSlotMinutes`**: the club's `training.slotMinutes` (S09), so D12's legend says how long a half-height cell is; `null` with `FREE_TRAINING` off. Test on the week, with both module states.
4. **`HistoryItem.activityId` only when the activity's page answers (E6-T05's question; S07 §6).** Send the activity's id when the activity is `PUBLISHED` or `FINISHED`, and `null` otherwise, so the web links exactly the rows whose page exists. Today a registration cancelled in time keeps its `CANCELLED` row when the club later cancels the activity, and that row links to a 404. Test: that row, and a `CANCELLED_BY_CLUB` row, carry `null`; a done row carries the id.
