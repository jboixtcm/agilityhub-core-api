# E5-T03 · Class waitlist (S08 WP-08-C)

## Objective
Work package S08 WP-08-C: a member whose class is full joins the waitlist, is notified when a seat is released (everybody at once at the Cànic, or one at a time in FIFO clubs), takes the seat with the same hold + confirm flow as a normal booking, and leaves or is removed by the club. The two modes, the limits that decide who may join at all, the demotion of the notified entries when the seat is taken, and the `SeatReleased` / `WaitlistExpired` consumers are the deliverable. The FIFO expiry job that produces `WaitlistExpired` is E5-T05 (P6); the sweep of entries whose class has started is E6 (P8).

## Steps
1. **`WaitlistService.join(classSessionId, dogId)`** (R-08-12, `@RequiresModule(Module.WAITLIST)`), one transaction with the `seat_locks` lock of the class: the class must be full **by bookings alone** (`ACTIVE` + `PAYMENT_PENDING` ≥ capacity, holds excluded) → else `422 CLASS_NOT_FULL`; the dog must have no live booking (`409 ALREADY_BOOKED`) and no live entry (`409 ALREADY_ON_WAITLIST`) for that class; the full `BookingEligibility` chain of E5-T02 runs (block, inactivity, member status, level, pack, `LEAVING`, `NOT_YET_OPEN`); then the four waitlist limits — live entries of the class < `waitlist.maxPerClass` (3) → `409 WAITLIST_LIMIT {scope: CLASS}`; live entries of the dog in the class's booking week < `waitlist.maxPerDogPerWeek` (2), or < `waitlist.maxPerDogPerWeekIfAttended` (1) when the dog already has a counted booking of that week with `classStartsAt ≤ now` or `CANCELLED_LATE` → `409 WAITLIST_LIMIT {scope: DOG_WEEK}`; and the entry must be *acceptable*: the week counter is below the limit **or** at least one `swappable` booking exists, else `409 BOOKING_LIMIT_REACHED` with the same `details.limit` shape as the hold. With `bookings.limitUnit = MEMBER` the «per dog» limits apply per owner. Persist `position = max + 1` (kept in both modes, used only by FIFO), `classStartsAt` and `bookingWeekKey` denormalized, write `Member.lastDogForClass` of the joiner, emit `WaitlistJoined`. T-08-08, T-08-19.
2. **Leaving** (R-08-16): `POST /waitlist-entries/{id}/cancellation` (member own or group; ADMIN too, from D4/D12) → `CANCELLED` with `cancelReason = MEMBER` or `ADMIN` + `WaitlistLeft`; only from `ACTIVE`/`NOTIFIED` (`422 WAITLIST_ENTRY_NOT_LIVE`). Service methods for the other reasons, called inside the callers' transactions and emitting nothing of their own: `cancelAll(classSessionId)` → `CANCELLED{CLASS_CANCELLED}` (completes `ClassBookingsPort.cancelAllByClub` of E5-T02, so S06's D4c flow and S15's risk review include the waiting members in `waitlistIds[]` and N-08a), `sweepStarted(now)` → `CANCELLED{CLASS_STARTED}`, silent (exposed as `WaitlistService.sweepStarted` for **E6**'s P8; do not schedule it here, state that in the report), `cancelByMember(memberId, reason)` → for S13/S15 leave handling (reason `MEMBER_LEFT`, a **catalog proposal** of S15 §13: use it and write the proposal in the report). Nothing is ever deleted (BR-12). T-08-19, T-08-25.
3. **`WaitlistService.offerSeats(classSessionId, freeSeats)`** — the `SeatReleased{notifyWaitlist = true}` consumer, idempotent per `eventId` (R-08-13, R-08-14): `waitlist.mode = ALL_AT_ONCE` → every `ACTIVE` entry of the class → `NOTIFIED` (`notifiedAt`, no `confirmBy`), one `WaitlistNotified {entryIds[], classId, mode}`; already `NOTIFIED` entries are **not** notified again. `FIFO` → the `freeSeats` lowest `position` `ACTIVE` entries → `NOTIFIED` with `confirmBy = min(now + waitlist.fifoConfirmMinutes, classStartsAt)`, one `WaitlistNotified` carrying `confirmBy` per entry. In both modes nothing happens when `minutesBefore ≤ waitlist.notifyThresholdMinutes` (the emitter already decides this, but re-check defensively) or when `WAITLIST` is off. `offerNext(classSessionId)` — the `WaitlistExpired` consumer (FIFO) — notifies the next entry while seats and time remain; two deliveries of the same `WaitlistExpired` must produce a single offer (T-08-34). T-08-20, T-08-21, T-08-45.
4. **Demotion** (R-08-13, `ALL_AT_ONCE` only): a consumer of `WaitlistConsolidated` and of `BookingCreated` that leaves `freeSeats = 0` turns the remaining `NOTIFIED` entries back into `ACTIVE`, keeping `notifiedAt` for the record, and produces **N-46** (MEMBER → APP only). A later release notifies them again. T-08-20, T-08-30.
5. **Claim** (R-08-15): `POST /seat-holds {classSessionId, dogId, waitlistEntryId}` is E5-T02's endpoint — add the checks it delegates here: the entry must be `NOTIFIED` (`422 WAITLIST_NOT_NOTIFIED`) and, in FIFO, `confirmBy > now` (`422 WAITLIST_OFFER_EXPIRED`); no seat available → `409 SEAT_TAKEN` (not `CLASS_FULL`); the waitlist limits do **not** apply to a claim, but BR-01 does: at the limit with a live swappable booking the hold answers `limit.swappable` and screen 06 proposes the swap, with none → `409 BOOKING_LIMIT_REACHED`. `POST /waitlist-entries/{id}/claim {seatHoldId, swapBookingId?}` with `Idempotency-Key`: one transaction that calls `BookingConfirmationService.confirm(seatHoldId, swapBookingId)` (same code path, same guarantees), asserts `hold.waitlistEntryId == entryId`, sets the entry to `CONSOLIDATED` with `bookingId`, emits `WaitlistConsolidated {entryId, bookingId}` and, in `ALL_AT_ONCE` with `freeSeats = 0`, demotes the rest (step 4). The 201 body is the same `Booking` schema as `POST /bookings`. T-08-22, T-08-30.
6. **Consolidation on a direct booking** (R-08-08): implement the `WaitlistConsolidationPort` E5-T02 declared — when a dog with a live entry books that class directly, the entry becomes `CONSOLIDATED` (`cancelReason = BOOKED_DIRECTLY` in the audit trail sense; the state is `CONSOLIDATED`, never `CANCELLED`) inside the confirmation transaction. T-08-19.
7. **Reads**: `GET /waitlist-entries/{id}` (member own, instructor, admin) with the class card, `position` (FIFO only), `confirmBy`, `state`; `GET /class-sessions/{id}/waitlist-entries` (instructor, admin) for 21/D4/D12 and for S06's cancellation preview; the `waiting` counter that `ClassSession.counters.waiting` carries is written in the same transactions as every state change (join, leave, consolidate, cancel-all) — never recomputed lazily.
8. **Notifications in the dispatcher** (`notifications.N-15`, `notifications.N-46`; idempotent per (`eventId`, recipient, channel), deterministic ids, same shape as E4-T03's `notifications.N-08a`): **N-15** «S'ha alliberat una plaça!» on `WaitlistNotified` → the notified members, APP + **SMS intent** (`Notification` row `channel = SMS`, `status = QUEUED`, body ≤ 160 GSM-7, or `SKIPPED_MODULE_OFF` when `SMS` is off; no sender until E7) + PUSH intent, variables `dog_name`, `class_date`, `class_time`, `confirm_by` (FIFO only), native action `CLAIM_SEAT`; exactly **one** N-15 per entry and offer even when several seats are released in the same event. **N-46** «La plaça ja s'ha ocupat» on demotion → APP only, variables `dog_name`, `class_date`, `class_time`. Back keys `notif.N-15.*` (+ `.sms`), `notif.N-46.*` in ca/es/en, rendered in the recipient's locale with the club time zone. T-08-20.
9. **Module and tenant behaviour** (§9): `WAITLIST` off → every `/waitlist-entries*` route `404 MODULE_DISABLED`, `waitlistEntryId` on a hold → 404, `SeatReleased.notifyWaitlist` always false, full rows are plain `FULL`, `counters.waiting` stays 0. Role matrix per endpoint (member own / group / foreign 404 / instructor / admin / anon), impersonation allowed on the member routes with `origin = BACKOFFICE` and the entry's `accountId` = the admin's account, cross-tenant 404 everywhere.

## Fixed conventions
- Statuses (catalog rule 0, literal; the catalog file wins over S08 §6, which writes 409 for several of these): `ALREADY_BOOKED`, `ALREADY_ON_WAITLIST`, `WAITLIST_LIMIT`, `BOOKING_LIMIT_REACHED`, `SEAT_TAKEN`, `SEAT_HOLD_EXPIRED`, `IDEMPOTENCY_KEY_REUSED` **409** · `CLASS_NOT_FULL`, `WAITLIST_NOT_NOTIFIED`, `WAITLIST_OFFER_EXPIRED`, `WAITLIST_ENTRY_NOT_LIVE`, `WAITLIST_FULL`, `SWAP_NOT_ALLOWED`, `MEMBER_NOT_ACTIVE`, `BOOKING_BLOCKED`, `INACTIVITY_PERIOD`, `LEVEL_NOT_ALLOWED`, `PACK_EMPTY` **422** · `MODULE_DISABLED`, `NOT_FOUND`, `DOG_NOT_ACCESSIBLE` **404**.
- Assumptions in force (do not ask): the seat goes to whoever holds **and confirms** first, not to whoever confirms first in absolute terms (A20a, R-08-15); «ja ha fet classe» for the `maxPerDogPerWeekIfAttended` limit = a counted booking of that week already started or `CANCELLED_LATE` (§13-3, part C S08); a dog's level change never touches its entries (R-08-16); the confirmation window is `bookings.seatHoldSeconds` (30 s) for the hold and `waitlist.fifoConfirmMinutes` (30 min) for the FIFO offer — two different clocks, both parameters.
- Every mutation is a Mongo transaction with the outbox inside it, serialized per class with `seat_locks` (lock order `seat_locks` → `class_sessions`, `BookingTransactions` retry); notifications only from outbox consumers; `Clock` injected; instants UTC, business dates club-local.
- Context direction (ArchUnit): this code lives in `clubs.bookings` and imports nothing from `clubs.training` or `clubs.activities`.
- Closed catalogs: no new parameter / event / notification / error code / audit action. `WaitlistEntry.cancelReason = MEMBER_LEFT` is an S15 §13 proposal — use it and record the proposal. ## Definition of Done
A full class accepts up to three waiting entries under the per-dog and per-week rules; an in-time cancellation more than 30 minutes before the start notifies every waiting member at the Cànic (or only the first in a FIFO club), the first to hold and claim gets the seat, the rest come back to `ACTIVE` with N-46; the FIFO offer expires into the next member when E5-T05's process delivers `WaitlistExpired`; cancelling the class cancels every entry inside S06's transaction; `WAITLIST` off removes the whole surface.
