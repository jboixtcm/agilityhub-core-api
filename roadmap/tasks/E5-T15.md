    - `GET /risk-review` (form A) returns `WILL_CANCEL`/`WILL_REVIEW` only when P2 will really run for that class: the `risk-review` job is enabled, and the class's `reviewAt` is still in the future.
    - Otherwise an at-risk class is `AT_RISK`, with `notified` when there was a notice. That covers the time after today's review, and a switched-off job.
    - D1 then never says «s'anul·larà … a les 7:30» about something that will not happen.

12. **The club's dry-run counter past 500 items (E5-T13 review #2).** `JobRunner` counts the whole plan but traces only its first 500 items. `JobViews` (`:75`) subtracts only the platform items that are in the trace, so 500 tenant items plus 1 platform item show `WOULD_DELETE=501` to the club. Record the tenant and platform totals **before** the truncation, and build the club counters from them. Add an ADMIN-view test with more than 500 items.
13. **Releasing the platform claim together with `FAILED` (E5-T13 review #3).** `JobRunner` (`:229`) commits the run as `FAILED` before the release hook runs. A crash in between, or an exception swallowed at `:235-237`, keeps the claim until midnight, and the reaper looks only at `RUNNING` rows. Release the claim in the same transaction as the completion, or let the claim acquisition take over a claim whose run is `FAILED`. Test a release that fails after the failed row is committed: the next run of the day still starts.

14. **Follow-ups of the E4-T06 review (S07).**

   - **`fields=` on the D7 list (review #3).** A property that was not selected is omitted or `null`, never a primitive default such as `allRings: false`.
   - **The app rows (E4-T06 question 2, R-07-13).** `RegisteredActivity` and `ActivityRow` carry `startTime` and `endTime`, `null` when absent, so a date-only activity never reads «0:00».
   - These changes are additive.

### Assumptions
1. **E26 budget (step 1).** A ring change gets **3 attempts**, the R1 budget of the S08/S09 writers it races with (E26: "the retry budgets stay").
   - The loop applies to every `PATCH /rings/{id}`. A conflict cannot be told apart before the attempt runs.
   - For a ring edit that does not touch the ring slots, the only conflict is another catalog write. The version check still answers `STALE_VERSION` to a concurrent edit of the same ring.
   - Inside an outer transaction (`club:apply`), the change joins it with no retry, as before.
   - Each attempt is `change()`, called through the proxy, so the transaction and the `CATALOG_CHANGED` audit entry stay one per attempt.
2. **Step 2.** The runner lives in `clubs/scheduling/persistence/SchedulingPersistence`, like `CensusPersistence`. The `@PostConstruct` index creation of the other scheduling repositories is unchanged, because the task names only the collection.
3. **Step 4, what I found:**
   - **Week generation** (`WeekGenerationUseCase`) places DRAFT classes without asking S09. That is by the spec (R-06-05: "classe generada sobre una TrainingBooking activa" is an inconsistency, not a refusal).
   - **Validation** (`WeekValidationUseCase`) reads the training bookings through `CalendarQuery.inconsistencies` and refuses with `RING_TRAINING_CONFLICT`. `TrainingIT` now proves this with the real adapters.
   - **P1 `week-opening`** (`WeekOpeningJob`, `WeekOpenings`) places no class: it only marks `openedAt`/`openingNotifiedAt`, invalidates caches and publishes events.
   - **The gap I closed:** a booking that started before the generation and was still uncommitted when the admin validated was invisible to the validation, which committed over it. The validation now touches the ring slots of its future DRAFT classes, only when `FREE_TRAINING` is on.
   - **Contention cost:** normal bookings cannot take a slot that has a DRAFT class (R-09-03), so this adds no contention in practice.
4. **Step 10.** The fields exist only in the detail. The schema marks them optional, and `@JsonInclude(NON_NULL)` keeps them out of the create/patch answers. Putting them on the calendar and list rows would cost three catalog reads per row.
   - A name is the instructor's `shortName`, the same as the member's `instructorName`. An id missing from the catalog gives `""`.
   - The detail always sends `ring`, `null` without a ring.
