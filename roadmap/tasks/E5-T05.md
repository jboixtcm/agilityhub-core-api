# E5-T05 · Scheduled processes of E5 (S15 WP-15-C + the api half of WP-15-B)

## Objective
Work package S15 WP-15-C plus the back half of WP-15-B: five of the ten processes become real `Job` beans on E5-T01's framework — `week-opening` (P1), `risk-review` (P2), `waitlist-fifo` (P6), `payment-timeouts` (P7) and `cleanup` (P9) — together with R-15-12b's immediate `ClassBelowMinimum` → **N-54** alert, and the admin API that drives them (`GET /jobs`, `/jobs/{name}/runs`, `/runs/{runId}`, `POST /jobs/{name}/trigger`, `PUT /jobs/{name}/switch`, `GET /risk-review`, `/platform/jobs/overview`, `/platform/clubs/{clubId}/jobs/{name}/trigger`). ## Steps
1. **`/jobs*` endpoints** (R-15-09, replacing E5-T01's 501 stubs; ADMIN only, impersonation tokens → 403): `GET /jobs` builds one row per catalog process **that has a registered `Job` bean and whose module is on**, with the localized name (`admin-settings:jobs.name.*` is front-side; the back returns `name`, `jobName`, `module`, `enabled`, `schedule{kind, localTime?, dayOfWeek?, dayOfMonth?}`, `nextScheduledForLocal`, `lastRun{runId, status, finishedAt, trigger, dryRun, counters}`); `GET /jobs/{name}/runs` = universal list over `job_runs` filtered by tenant; `GET /jobs/{name}/runs/{runId}` returns `effects.items`, `errors[]` and `parametersSnapshot`; `POST /jobs/{name}/trigger {dryRun}` runs the same code and the same lock with `scheduledFor = now` truncated to the minute and `trigger = MANUAL`, **even when the switch is off** (the switch stops the calendar, not the admin — principle 0.3.7), synchronous 200 with the `JobRun`, `409 JOB_ALREADY_RUNNING` when the lock is held, `404 MODULE_DISABLED` when the module is off, `JOB_UNKNOWN` for an unknown route id, `@Audited(JOB_TRIGGERED)`; `PUT /jobs/{name}/switch {enabled}` writes the parameter `jobs.<name>.enabled` through S02's parameter service (`ParameterChanged`, audited `PARAMETER_CHANGED`, config cache invalidated). Platform routes: `GET /platform/jobs/overview` (matrix club × process with `health OK|WARN|ALERT`: green = last success inside the period, amber = `PARTIAL`, red = `FAILED` or no success in more than two periods) and `POST /platform/clubs/{clubId}/jobs/{name}/trigger`, both AGILITYHUB_ADMIN. T-15-08, T-15-09.
2. **P1 `week-opening`** (R-15-11, `JobName.WEEK_OPENING`, weekly at `bookings.weekOpensAt`, catch-up 24 h, no module): **no business write** — `W0`/`W1` are functions of time (S08 R-08-01) and the training counter is per session week (S09 R-09-05). One transaction: invalidate the club's config and grid caches; warm the base cache of `GET /me/bookable-classes` (the `ACTIVE` classes of `W0…W2` with counters, no per-dog state, TTL 30 s — agree the cache key with E5-T06 and say in the report which class owns it); set `targetWeek.openedAt = opensAt` on the `Week` (get-or-create) that contains `openedWeekKey + 1 day`; emit `WeekOpened {openedWeekKey, isoWeekStart, currentWeekKey, opensAt, notified}` and, with `FREE_TRAINING`, `TrainingCounterReset {weekStart: opensAt}`. When `messaging.notifyWeekOpening` is true **and** the target week has at least one `ACTIVE` class → **N-33** to every `ACTIVE` member with at least one `ACTIVE` dog (APP + PUSH intent, variable `week_start` = `isoWeekStart` formatted «setmana del 12 d'octubre», action `OPEN_BOOKING`) and `openingNotifiedAt`; when the week is not validated yet the notice is **deferred**: a `WeekValidated` consumer sends it if `now ≥ Week.openedAt ∧ openingNotifiedAt == null`. Fan-out in batches (feed rows `insertMany` of 500, push in batches of 100 on a pool that does not share threads with the API). Dry run: `WOULD_OPEN {weekKey, activeClasses, recipients}`. T-15-11, T-15-12.
3. **P2 `risk-review`** (R-15-12, `JobName.RISK_REVIEW`, daily at `classes.riskReviewTime` 07:30, catch-up until the end of the local day, no module): scope = `ClassSession` `ACTIVE` with `date ∈ [today, today + classes.riskLookaheadDays]`, `risk.exempt = false`, `countedDogs < classes.minDogs`, where **`countedDogs` is recounted inside the transaction** (bookings `ACTIVE` + `PAYMENT_PENDING` through `ClassBookingsPort`), never trusted from `counters.booked`. Per class: (a) `date == today ∧ classes.riskAutoCancelSameDay` → `startsAt ≤ now` counts as `skippedStarted` (a late run never cancels a class that has begun), otherwise `ClassCancellationUseCase.cancel(classId, RISK_REVIEW, messages «scheduling.autoCancel.text»)` (E4-T03's transaction: bookings → `CANCELLED_BY_CLUB`, waitlist → `CANCELLED{CLASS_CANCELLED}`, packs refunded, holds deleted, counters zeroed) plus `ClassAutoCancelled {classId, dogsCount, affected[], waitlistIds[], adminText}`; (b) otherwise `ClassAtRisk {classId, dogsCount, reviewAt, newBookingIds[], notifyAdmins}` → **N-16** to every registrant not already in `risk.notifiedBookingIds` and to the ADMINS when `risk.adminNotifiedAt == null`, then update `risk`. Notifications: **N-17** «Classe anul·lada per manca d'alumnes» to the class's INSTRUCTORS + ADMINS (APP + EMAIL) on **every** auto-cancellation, including a class with 0 registrants (`dogs_count = 0`, decision §13-3); **N-08a** to the affected registrants (APP + EMAIL + SMS intent) — reuse E4-T03's `notifications.N-08a` handler, which already filters `reason ∈ {CLUB_MANUAL, DELETED, ACTIVITY}`: extend it to `RISK_REVIEW` **or** add the N-17/N-08a pair here and say exactly which handler owns which reason in the report; **N-16** «Possible anul·lació de classe» with `dog_name`, `class_date`, `class_time`, `review_time`, `review_day` (the class's day) and `auto_cancel`. Counters `{reviewed, cancelled, cancelledSilent, atRisk, notifiedMembers, exempt, skippedStarted}`; dry run `WOULD_CANCEL` / `WOULD_NOTIFY`. Each class's cancellation is its own transaction (R-15-10 exception). T-15-13, T-15-14.
4. **R-15-12b immediate low-class alert**: a consumer of `BookingCancelled{late: false}` and of `WaitlistExpired` (when the class ends up unchanged) that, inside its own transaction, checks the class is `ACTIVE`, future, `risk.exempt = false` and `countedDogs < classes.minDogs` and then emits `ClassBelowMinimum {classSessionId, countedDogs, minDogs}` → **N-54** «Classe amb pocs alumnes» to the class's INSTRUCTORS and the ADMINS (APP + EMAIL, variables `class_date`, `class_time`, `class_description`, `ring_name`, `dogs_count`, action `CHANGE_CLASS`) and **nothing else**: no student is warned and the class is untouched. Idempotency mark `ClassSession.risk.lowAlertSentAt`, **cleared** when `countedDogs` reaches `classes.minDogs` again so a second drop alerts again; nothing is sent when `date == today ∧ startsAt ≤ now`. E5-T02 already emits the event from the cancellation transaction: here implement the N-54 handler and the clearing path, and add the test that a second in-time cancellation on the same class sends nothing while the first alert stands. (Josep 08-09, decision B17.)
5. **P6 `waitlist-fifo`** (R-15-16, `JobName.WAITLIST_FIFO`, every minute, module `WAITLIST` **and** `waitlist.mode = FIFO`, continuous catch-up): `WaitlistEntry` `NOTIFIED` with `confirmBy ≤ now` → `EXPIRED` + `WaitlistExpired {entryId, classId}` (one transaction per entry); S08's `offerNext` consumer (E5-T03) notifies the next one while seats and time remain. In `ALL_AT_ONCE` the process records `SKIPPED{MODULE_OFF}` at most once per hour. Dry run `WOULD_EXPIRE {entryId, position}`. T-15-24, T-08-34.
6. **P7 `payment-timeouts`** (R-15-17, `JobName.PAYMENT_TIMEOUTS`, every minute, module `SINGLE_CLASS`, continuous): `Booking` `PAYMENT_PENDING` with `bookedAt + bookings.paymentPendingMinutes` (30) `≤ now` → `BookingCancellationService.cancel(bookingId, by = SYSTEM, reason = PAYMENT_TIMEOUT)` → `CANCELLED`, `SeatReleased`, N-40 (the handler is E5-T02's). Idempotent by state; two runs cancel once. Dry run `WOULD_CANCEL {bookingId, minutesPending}`. The module is off at the Cànic: test it on a fictional club that enables `SINGLE_CLASS` (and assert the `SKIPPED{MODULE_OFF}` row at the Cànic). T-15-25, T-08-35.
7. **P9 `cleanup`** (R-15-19, `JobName.CLEANUP`, daily at `jobs.dailyTime` 06:00, unlimited catch-up) — the **only** place where documents are physically deleted, and only technical ones: report (never delete) the `seat_holds`, `magic_link_tokens`, `idempotency_records` and `job_locks` whose TTL has not caught up yet (`ttlPending.*`); delete orphan `signup/{clubId}/…` S3 keys older than `jobs.retention.orphanUploadsHours` (48) not referenced by any `DogDocument.files[].fileKey` (`orphanUploadsDeleted`); purge finished `export_jobs` older than `jobs.retention.exportFilesDays` (7), deleting the file and marking the record `PURGED` (`exportsPurged`); delete `domain_events` with `processedAt < now − jobs.retention.domainEventsDays` (90) and **never** unprocessed ones (`domainEventsDeleted`); delete `stripe_events` older than `jobs.retention.stripeEventsDays` (400) if that collection exists yet — skip with a counter of 0 and say so if it does not (`stripeEventsDeleted`); delete `job_runs` with `finishedAt < now − jobs.retention.jobRunsDays` (90) **always keeping the last 5 runs of each process** (`jobRunsDeleted`). No business events; dry run = the same counters under `WOULD_DELETE`. T-15-27.
8. **`GET /risk-review`** (S15 §6 form A, ADMIN + INSTRUCTOR, MEMBER → 403): `reviewTime`, `lookaheadDays`, `minDogs`, `autoCancelSameDay` from the parameters and `items` = the `ACTIVE` at-risk classes plus the ones already `CANCELLED{RISK_REVIEW}` of `[date, date + lookaheadDays]`, ordered by `startsAt`, each with `dayLabel TODAY|TOMORROW|OTHER`, `bookedCount`, `status AUTO_CANCELLED|AT_RISK|WILL_CANCEL|WILL_REVIEW` (`WILL_REVIEW` when `classes.riskAutoCancelSameDay = false`), `reviewAt` and `notified[{memberName, dogName}]` resolved from `risk.notifiedBookingIds` (or from the cancellation's affected bookings). S14 embeds this in `GET /dashboard`: wire E3-T04's dashboard risk card to it and remove any remaining double. T-15-15.
9. **Registration and guards**: register the five `Job` beans in the catalog order of R-15-01, each declaring its module and catch-up window; verify through the framework that the switch, the module and the club status produce the right `SKIPPED{…}` rows (continuous jobs at most one per hour), that a `CATCH_UP` run behaves as R-15-05 describes (`risk-review` at 23:59 → `CATCH_UP`; at 00:01 the next day → `MISSED_WINDOW` + N-42; `week-opening` 26 h late → `MISSED_WINDOW` with no business effect lost), and that `plan` ≡ real `effects.items` for each of the five (T-15-06 extended). Every process reads its configuration through `ClubConfig`, never a constant, and writes `parametersSnapshot`.
10. **CLI**: expose each process as a `CoreCommand` (`jobs:run <route-id> [--club=] [--dry-run]`) so staging and `bin/e5-smoke` can drive them without the scheduler, documented in `README.md` next to the existing `scheduling:finish-ended`.

## Fixed conventions
- Statuses: `JOB_ALREADY_RUNNING` **409** (explicit in §1), `MODULE_DISABLED` **404**, `JOB_UNKNOWN` and `NOT_DUE` **422** by rule 0 (S15 §6 writes 404 for `JOB_UNKNOWN`; E5-T01 already filed the proposal to move it to §1 — do not change it again), `VALIDATION_ERROR`/`INVALID_FILTER` **400**, impersonation on any `/jobs*` route **403**.
- Assumptions in force (do not ask): there is **no** immediate risk review when a student cancels — only R-15-12b's alert; the action stays at 07:30 (§13-2, B17). N-17 is sent even with 0 registrants and N-16 reaches the admins only the first day (§13-3, §13-4). A class auto-cancelled by the review is never reactivated: the admin creates it again (§13-5). Manual execution is synchronous at R1 (§13-13). Processes run for clubs `ACTIVE` **and** `ONBOARDING` (§13-14, A18e). Retention values are the catalog's (§13-10). P3 and P8 are E6, P4 is E7, P5 and P10 are E8 — declare their catalog rows, do not implement them, and make sure `GET /jobs` simply omits the rows without a bean.
- Every item is applied in its own Mongo transaction with the outbox inside it, except P1 (one transaction) and each class cancellation of P2 (S06's transaction); a failed item goes to `errors[]` and the run is `PARTIAL`; a job-level exception is `FAILED` + `JobFailed` → N-42 (at most one per process and club-local day). Dry run writes nothing anywhere but the `JobRun`. `Clock` injected everywhere (the E5-T01 ArchUnit rule); occurrences computed in `club.timeZone`.
- Context direction (ArchUnit): the `Job` beans live in the vertical that owns the effect (`clubs.scheduling` for P2, `clubs.bookings` for P6/P7, `platform`/`clubs.common` for P1's cache warm-up and P9) and depend on `platform.application.jobs`; `platform` never imports `clubs`.
- Closed catalogs: no new parameter / event / notification / error code / audit action; proposals to the report and `MESSAGES.md`. Evidence rule: report = command + exit code + last 40 lines; long outputs → `roadmap/evidence/E5-T05/NN-<name>.log`; task file ≤ 120 KB; fictional data only (`@example.test`); no secrets, env vars only; never edit other tasks, `ROADMAP.md` or the Organizer verification section.

## Definition of Done
With the clock advanced to Sunday 20:00 the opening runs once, emits `WeekOpened` and queues N-33 for the right members; at 07:30 the review cancels today's under-strength classes in one transaction each with N-17 to the staff and N-08a to the students, warns tomorrow's once per registrant, and leaves exempt classes alone; an in-time cancellation that drops a class below the minimum alerts instructors and admins once with N-54 and does nothing else; a FIFO offer expires into the next member; a stale `PAYMENT_PENDING` booking is cancelled after 30 minutes and its seat released; cleanup purges only technical data and keeps the last five runs; the admin can list, simulate, run and switch every implemented process, and `GET /risk-review` feeds D1.
