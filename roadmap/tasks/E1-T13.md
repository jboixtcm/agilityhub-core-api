# E1-T13 · A1 — refresh token in an HttpOnly cookie for browser clients (`tokenDelivery = COOKIE`) + platform-roles API (A3)

## Objective
Jordi's decision A1 (06-09): the refresh token must never be readable from JavaScript. Browser clients get it in an **HttpOnly cookie** set by the token endpoint; every app host is served through a **same-site proxy** (Caddy: `/api/*` → core, `/oauth2/*` + `/.well-known/*` → id), so the cookie is first-party and there is no CORS for the SPAs. Server side this task; the web side is E1-W07; the Caddy/Vite proxy recipe is documented here for E0-T13/E10. Second, A3: platform admins must be manageable through the API (`GET/PUT /platform/accounts/{id}/platform-roles`, S17 R-17-09) — small, pulled forward from E10 so Jordi's first admin can be granted without a seed.

## Fixed conventions
- Client registration gains `tokenDelivery: BODY | COOKIE` (`COOKIE` for `clubs-app`, `clubs-admin`, `id-web`; `BODY` for `learn`, `ar-app`). Configuration only — no catalog parameter.
- Cookie: name `ah_refresh`, `HttpOnly; Secure; SameSite=Strict; Path=/oauth2/token; Max-Age=<auth.sessionDays in seconds>` (no `Domain`: host-only). On `COOKIE` clients the token response **omits** `refresh_token` from the body (contract: `TokenResponse.refresh_token` stays optional, documented); every rotation re-sets the cookie; `POST /oauth2/revoke`, `/connect/logout` and a revoked family clear it (`Max-Age=0`). `grant_type=refresh_token` without the `refresh_token` form field reads the cookie; the cookie is accepted only when `client_id` is a `COOKIE` client and the request `Origin`/`Referer` host equals the request host (same-site proxy) — otherwise `400 REFRESH_EXPIRED`-class rejection as today (`invalid_grant`). `Secure` is relaxed only under the `local` profile over plain http.
- Handoff (E1-T04) and magic-link grants on `COOKIE` clients also deliver the refresh token as a cookie on the target host.
- The OIDC bridge (E1-T05 `POST /oauth2/session`) and the encrypted key ring stay as they are (E18).
- Platform roles: `GET /platform/accounts/{id}/platform-roles` → `{platformRoles[]}`; `PUT` `{platformRoles[]}` (`AGILITYHUB_ADMIN` only; a non-admin caller → `403 FORBIDDEN`; removing the last `AGILITYHUB_ADMIN` → `409 LAST_PLATFORM_ADMIN` — add the code to `ErrorCode` + messages if absent, it is in the S17 catalog row); audit action `PLATFORM_ROLES_CHANGED` (added to S14 R-14-09 on 09-09: `entityType = Account`, `changes[].path = platformRoles`, `@AuditCovers` test) in the same transaction; no domain event (none catalogued). Also a CLI `identity:grant-platform-admin <email>` (idempotent) for the first admin at deployment.
- Deployment recipe in `docs/DEPLOY.md` (create the section if the file does not exist yet): Caddy snippet per app host (`handle /api/* { reverse_proxy core:8080 }`, `handle /oauth2/* /.well-known/* { reverse_proxy id }`), and the local `docker-compose` dev proxy or note for the Vite proxy the web uses (E1-W07).
