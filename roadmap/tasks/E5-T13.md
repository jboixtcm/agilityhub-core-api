#### Fix
`CheckoutService.finish` (`payments/application/CheckoutService.java`): a completion of a `PENDING` session past its
`expiresAt` no longer throws `INVALID_STATE` when the session belongs to a booking (`bookingId` set). In one
transaction it:
- sets the session `EXPIRED` and stores `providerPaymentId` (`SignupCheckoutRepository.finish`);
- runs `UpfrontPayments.checkout(…, false)`, which sets the line `CANCELLED` and emits `UpfrontPaymentFailed{bookingId}`.
  This is exactly what P7's `abandon` does to the session, so the booking is never confirmed and the line is never `PAID`;
- sets the E34 mark (`lateCompletionAt`, `providerPaymentId`) and logs the WARN line
  (`Late provider completion to refund: the checkout deadline passed checkoutSessionId=… bookingId=… providerPaymentId=… clubId=…`).

A provider retry then finds the session `EXPIRED` and takes the round-1 branch. `markLateCompletion` matches only
`lateCompletionAt = null`, so the retry changes nothing and logs nothing. A signup session (no `bookingId`) past
`expiresAt` still gets `INVALID_STATE`, as before.

Result for the two cases:
- **The club cancelled the booking** (`CANCELLED_BY_CLUB`, session still `PENDING`): the session is marked; the
  `UpfrontPaymentFailed` consumer finds the booking already cancelled and does nothing.
- **A `PAYMENT_PENDING` booking whose deadline passed before P7 ran**: the session is marked, and the booking stays
  `PAYMENT_PENDING` until P7 cancels it (`PAYMENT_TIMEOUT`, N-40). P7's `abandon` then finds the session `EXPIRED` and
  does nothing. If the outbox dispatches `UpfrontPaymentFailed` before P7 runs, the consumer cancels the booking the
  same way (`cancelPaymentPending`, the same reason, N-40), and P7 then skips it. Either path cancels it once.
