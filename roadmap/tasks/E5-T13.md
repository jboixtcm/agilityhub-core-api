### Assumptions
1. **E33, «sense cap JobRun previ»**: I read this literally. Any `JobRun` of the process in the club counts as history,
   including dry runs, manual runs and other skips. Other clubs' rows do not count (tested).
2. **E33, S17 matrix**: a baseline row is not a lost run, so the overview reads it as «never executed» (OK) instead of
   ALERT. Otherwise every club would show red on release day until the next occurrence: up to a week for `week-opening`
   and a month for `billing-reminder`. D11's `lastRun` still shows the row as it is, `SKIPPED{MISSED_WINDOW}`. The
   baseline is recognised as the first `JobRun` of the process in the club (no new stored field).
3. **E34, where the mark lives**: on the `checkout_sessions` row (`lateCompletionAt`, `providerPaymentId`). The session
   ties together `bookingId`, `memberId` and the line, which is what the S12 refund needs. The model's `checkout_sessions`
   has no such fields yet: see question 1. The fake gateway supplies `fake_payment_<sessionId>` as the provider payment
   id. E8's Stripe webhook will pass the PaymentIntent id.
4. **E34, the two cases**:
   - the session is already `EXPIRED` (P7 or a failed provider call abandoned it), handled in `CheckoutService`;
   - the booking is cancelled while its session is still `PENDING` (today only S06's `cancelByClub`). The completion is
     then applied as before (line `PAID`, `UpfrontPaymentSucceeded`, which S12 can refund), and the S08 consumer adds
     the mark.

   A success for a booking that was **paid and then cancelled** (`charge.paidAt` set) is a redelivery, so it gets no
   mark (tested).
5. **E34, a `PENDING` session past `expiresAt` before P7 runs**: unchanged, still `INVALID_STATE`. The task names only
   `EXPIRED` sessions and cancelled bookings. A provider retry after P7 then finds the session `EXPIRED` and marks it.
6. **Step 5**: the release happens when the claiming run ends FAILED, whether it fails itself, loses its lease, or is
   reaped after it died. The hook runs only from the call that closed the row, so a slow holder whose row was reaped
   never releases a claim that its retake took again. The claim stores the claiming `runId`, and the release removes
   only that claim.
7. **Step 6 scope**: besides the two named views, I applied the club filter to two more places:
   - the club's `POST /jobs/{name}/trigger` response;
   - the `JOB_TRIGGERED` audit snapshot.

   Both are club-readable. The stored `JobRun`, the platform trigger response and `GET /platform/jobs/overview` keep
   the counters. The dry-run plan counter (`WOULD_DELETE`) is lowered by the hidden items, so it matches the items
   shown. This is exact while the plan has ≤ 500 traced items, and platform items come last in the plan.
8. **Step 10**: «the five `/jobs/{name}*` operations». Only four routes have `{name}`, so I counted `GET /jobs` as the
