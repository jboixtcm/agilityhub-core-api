### Assumptions

- The model/current S03 take precedence over the task's historical wording: newly transitioned Member states are `PENDING`, `ACTIVE`, `LEFT`; inactivity uses `inactivity_periods`. Legacy `INACTIVE` stays readable/reactivatable and valid for the E1 impersonation compatibility requested in step 0a. B19 preserves bookings without warnings. B10 is derived from `Plan.billingMode`; Member never stores or accepts billingMode.
- Catalog HTTP statuses win where S03 examples say 409 but the catalog says 422 (for example MEMBER_NOT_ACTIVE and TARGET_MEMBER_NOT_ACTIVE). No error codes were invented.
- The task explicitly permits a Stripe setup-intent placeholder: CARD returns `PAYMENT_PROVIDER_NOT_ENABLED` when disabled, otherwise `NOT_IMPLEMENTED` until S12 can confirm the setup intent. Overview reads real recent invoices but omits optional nextInvoice when there is no authoritative calculated amount; it does not invent a price or run S12 billing.
- Read-only future-context contracts: tasks use `clubId/dogId/state/text/createdAt/doneAt`, instructor display data and attachment references; inactivity uses `memberId/from/to/status`; packs use `dogId/remaining/total/expiresOn/status`; booking guards inspect bookings, training_bookings and waitlist_entries using `dogId`, state/status and startsAt or joined classSessionId/classId. Unknown active-booking dates fail closed. S06/S08/S09/S10/S12/S13 own later writes. MemberStatusService activation requires the account, membership and number already prepared by S04.
- Only the minimal S10 attachment purposes required here are implemented: DOG_DOCUMENT, DOG_PHOTO and INSTRUCTOR_NOTE. TASK/observation lifecycle remains S10; physical retention/erasure remains S14. Local/test uploads require bearer authorization; staging/prod use private S3 URLs. Live S3 credentials were not used: signing, headers and metadata checks were tested with the real SDK and a mocked client. Configure the new ATTACHMENT_S3_* environment variables and bucket CORS for the returned PUT headers in deployment. Compose has a persistent `/app/attachments` volume owned by the existing unprivileged application user.
- N-27 is delivered through the existing SYSTEM mail path, using the AccessResent event id for notification replay. Other S03 events are published transactionally for future S11 notification consumers; scheduled document reminders belong to S15. This does not claim exactly-once external email delivery across a provider-success/process-crash gap.
- Full verification exposed three pre-existing stale text values in `parameters-canic.json`. Only that test fixture was synchronized to the already-approved CATALEG_PARAMETRES values for signup.text.paymentDay, signup.text.cashConditions and signup.text.monthlyPaymentIntro; production defaults and documentation were not changed. List/export fixtures were adjusted only to satisfy the new real indexes.
