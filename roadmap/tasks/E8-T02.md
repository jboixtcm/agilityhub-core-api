# E8-T02 · Invoicing and the monthly cycle (S12 WP-12-B)

## Objective
Work package S12 WP-12-B. The admin simulates a month on D6, generates it, and the club has numbered, immutable receipts with one collection attempt each; a wrong generation can be rolled back whole; cash receipts are marked paid; corrections are new receipts. This task owns `InvoicingService`, numbering, `BillingSimulation`, `BillingRun` (generation + rollback), the invoice state actions, manual invoices and `PendingCharge`. SEPA file writing is E8-T03, Stripe is E8-T04, packs / inactivity / leave are E8-T05: this task consumes them through **ports with null-object defaults** and names the task that replaces each one.

Nothing in `payments` may import `clubs.census.persistence` or `clubs.catalogs.persistence` directly: go through the `application` services (ArchUnit).
2. **`InvoicingService.linesFor(member, period)`** (R-12-01…05, pure where possible so T-12-01…03 run without Mongo): selection — `Member.status = ACTIVE` (including members inside an inactivity period), `nextInvoiceDate ≤` last day of `M`, `paymentMethod` present, and `M ≤ LeaveBillingPort.lastInvoicedMonth(member)` when that returns a value; `PENDING` and `LEFT` never; non-holders of a `FamilyGroup` produce no invoice (R-12-04, `billedViaMemberId` **derived, never persisted**). Lines by `Plan.type`: `MONTHLY` → one `MONTHLY_FEE` at `PriceResolver.current(planId, MONTHLY_FEE, issueDate)`, **replaced** by `INACTIVITY_FEE` when `InactivityFeePort.feeFor` returns an amount, or by `MAINTENANCE_FEE` when `Plan.billingMode = MAINTENANCE` (Teràpia: the plan carries the fee automatically until an admin changes the member's plan — Josep 08-09, B10); `PACK` → no periodic line; `SINGLE_CLASS` → one line per unbilled `PendingCharge`. No current price → incident `NO_PRICE` and the member is **skipped**, never invented (R-12-03). Total 0 or no lines → **no invoice**, and `nextInvoiceDate` advances anyway (R-12-02, T-12-28). Descriptions are frozen at generation in the club's `defaultLocale` from the keys `billing.line.monthlyFee`, `inactivityFee`, `maintenanceFee`, `singleClass`, `pack`, `adjustment` (R-12-30) — «Quota {pla} — {Mes any}», «Quota inactivitat — {Mes any}», «Classe {data} — {gos}». A non-holder's inactivity fee becomes a **separate line on the holder's invoice** (R-12-04). T-12-01, T-12-02, T-12-28.
3. **Cash (R-12-05) — both branches are product, both are tested.** `billing.cashInvoicing = SEMESTER` (Cànic): one `PENDING` invoice with `k` monthly lines, `k` = months left to the end of the **natural half-year** (`billing.cashPeriodMonths = 6`: January–June and July–December), and `nextInvoiceDate` → day 1 of the next half-year; a new member's **first fraction** starts at `month(nextInvoiceDate)` — the first month is paid up front at signup as `FIRST_MONTH` (S04 R-04-14/15; ruling E44, 26-09) — and runs to the end of the current half-year, full half-years afterwards: signup 17-08 option A → September–December, **4** lines, `nextInvoiceDate` 01-01; option B (start 1 September) → October–December, 3 lines; the January run → 6 lines and 01-07 (T-12-03 as amended). `MONTHLY` → one single-line invoice each month, identically supported. The signup copy `signup.text.cashConditions` describes the `SEMESTER` case: **do not change it**, but make the executor report say it must be reviewed whenever the key changes (Jordi 09-09, A29). T-12-03.
4. **Numbering (R-12-08)**: series = `billing.invoiceSeriesPattern` resolved (`{YYYY}` → year of `issueDate`); number = the counter **of the series** (`CLUB.billing.counters[series]`, so the yearly reset is «no counter for the new series yet» and December's run for January keeps the series of its `issueDate`), taken atomically through a `platform.application` counter service (it invalidates `ClubConfigService`'s cache; `payments` never writes `clubs` directly) **inside the run transaction**; a manual invoice (`POST /invoices`) uses the same counter and answers `409 BILLING_BUSY` while the run holds `billing_locks`, assigned in a deterministic order (last names, first name, member number) so a rollback can give them back; `billing.invoiceResetYearly` → 1 on the first invoice of a new year; `displayNumber = "{series}-{number:04d}"`. A number is never reused except through the rollback of R-12-14. T-12-04.
5. **Amounts (R-12-09)**: everything in `amountMinor`; per line `tax = round_half_even(base × taxPercent / 100)`, `total = base + tax`; the invoice total is the **sum of lines**, never recomputed from the total; a `Price` in another currency → `422 CURRENCY_MISMATCH`. The Cànic has `taxPercent = 0` and `billing.taxIncluded = true` (Jordi 05-09, B3): keep the mechanism working for other clubs. T-12-05.
6. **`POST /billing/simulations` (R-12-07)**: computes R-12-01…05 **writing nothing of business value**; incidents `NO_BANK_ACCOUNT` (`SEPA_DD` with `iban == null ∧ ibanEncrypted == null` — migrated members carry only the encrypted form, E8-T01), `NO_PLAN`, `NO_PRICE`, `CARD_INVALID`, `CURRENCY_MISMATCH`, `PROVIDER_DISABLED` (provider not active in `CLUB.paymentProviders`); `cashMembers[]` with `plannedLeaveDate` from `Member.leaveDate`; `invoicesPreview[]`; `kpis {count, total, byProvider, cashPending, inactivityFees{count, firstMonth, following}}`. Persisted as the **single** `BillingSimulation` of that period (unique `{clubId, period}`: replace). A period more than three months ahead → `400 VALIDATION_ERROR` (§13 assumption). `409 BILLING_BUSY` while the lock is held. Emits `RemittanceSimulated`.
7. **`POST /billing/runs` (R-12-11)** — `Idempotency-Key`; one **live** run per `{club, period}` (the partial-unique index of E8-T01 → `409 RUN_EXISTS`); club lock in `billing_locks` with a 10-minute TTL → `409 BILLING_BUSY`; the run requires a simulation of the same period taken **after** the last relevant change (`simulation.at ≥ max(updatedAt)` over the members, prices and `billing.*` parameters involved) → otherwise `409 SIMULATION_STALE`. One transaction (retry on `WriteConflict` through a new `BillingTransactions` helper modelled on `SchedulingTransactions`): create the `Invoice` documents, one `Collection` per invoice — `SEPA_XML` → `CREATED` and the invoice `COLLECTING` after `RemittanceWriterPort` returns (**the XML is generated and XSD-validated before the commit; if it fails nothing is written**), `MANUAL` → `CREATED` with the invoice `PENDING`, `STRIPE` → `CREATED` with the invoice `PENDING` until E8-T04's charging step —, advance `nextInvoiceDate` to `billing.nextInvoiceDayOfMonth` of `M+1` **only for the included members** and store the old values in `run.previousDates[]`, stamp `PendingCharge.invoiceId`, and emit `InvoiceIssued` per invoice plus `BillingRunCreated`, `RemittanceGenerated` (when there is one) and `InvoiceCollecting`. Members with an incident are **skipped**, listed in `run.skipped[]`, and never block. Audit: `REMITTANCE_GENERATED` as **one** entry with `details.invoiceIds[]` (R-14-10: one entry per aggregate, not per invoice). Errors: `422 NO_INVOICES`, `422 SEPA_NOT_CONFIGURED`, `422 COLLECTION_DATE_TOO_SOON`. T-12-09, T-12-10.
8. **Collection date (R-12-12 arithmetic only)**: default from `billing.sepa.collectionDayOfMonth` read as a day of the **billed** month — `1–28` = that day (clamped to the month length), `0` = last day. The Cànic value is **1**, so September's run happens in August (≈ day 25) with `ReqdColltnDt = 2026-09-01`; the two-business-day rule of R-12-12 is measured from the generation date and a shortfall is `422 COLLECTION_DATE_TOO_SOON`. An explicit `collectionDate` in the body wins. **Both semantics are product, the key is edited from D11 and both are tested** (Jordi 09-09, A28) — and changing the key never recomputes an already generated remittance (R-02-04). T-12-29b.
9. **Rollback (R-12-14)**: `POST /billing/runs/{id}/rollback {reason, confirmation}` with `confirmation` exactly `"RETROCEDIR"` (otherwise `400 VALIDATION_ERROR`). Allowed only when the `Remittance` is not `SUBMITTED`, no `Collection` of the run is `SUBMITTED`/`SUCCEEDED`, and no invoice of the run is `PAID` — otherwise `409 RUN_NOT_ROLLBACKABLE {reasons[]}` with `REMITTANCE_SUBMITTED · COLLECTION_SUBMITTED · INVOICE_PAID · MANUAL_INVOICE_AFTER`. One transaction: invoices → `CANCELLED{ROLLBACK}`, a **new appended** `Collection FAILED{ROLLBACK}` per invoice, `Remittance` → `ROLLED_BACK` (the file is kept), `billing.nextNumber` returned to the run's first number (possible only because the run is the last consecutive block — a manual invoice issued afterwards gives `MANUAL_INVOICE_AFTER`), each member's `nextInvoiceDate` restored from `run.previousDates[]`, `PendingCharge.invoiceId` → null; events `RemittanceRolledBack` + `InvoiceCancelled` per invoice; audit `REMITTANCE_ROLLED_BACK`. The same month can then be simulated and generated again and **must reproduce the same numbers**. T-12-13.
10. **Invoice state actions**: `POST /invoices/{id}/payment {paidAt, channel CASH|TRANSFER|BIZUM, reference?, version}` and the bulk `POST /invoices/payments {invoiceIds[], paidAt, channel}` on `PENDING`/`FAILED` invoices whose `paymentMethod.type ∈ {MANUAL, SEPA_DD}` → appended `Collection MANUAL SUCCEEDED` + invoice `PAID` + `InvoicePaid{MANUAL}`, audited `INVOICE_MARKED_PAID` (R-12-16) · `POST /invoices/{id}/failure {reason, at, version}` on a `COLLECTING` SEPA invoice **or on a `PAID` one with a SEPA collection** (later bank return) → appended `Collection FAILED{BANK_RETURN}` + invoice `FAILED` + `InvoiceFailed` → **N-10** to the admins, with no automatic claim or block (BR-08), audited `INVOICE_MARKED_FAILED` (R-12-17) · `POST /invoices/{id}/cancellation {reason, version}` only on `PENDING`/`FAILED`, never on `PAID`/`COLLECTING` (`409 INVALID_STATE`), audited `INVOICE_CANCELLED` (R-12-19) · `POST /invoices {memberId, lines[], includeInNextRun?, note}` creates a `kind = MANUAL` invoice with `ADJUSTMENT` lines (positive or negative), numbered in the same series, `PENDING`, audited `INVOICE_CREATED_MANUAL` (R-12-19). Every action takes `version` → `409 STALE_VERSION`, and `Idempotency-Key` where §6 says so → a repeat returns the stored response (`CONVENCIONS_API` §7). T-12-14, T-12-18, T-12-30 (its non-Stripe half).
11. **Immutability (R-12-10)**: no `PATCH /invoices/{id}` (the route must answer `405 METHOD_NOT_ALLOWED`); the repository exposes **no** method that updates lines, amounts, member or number; `Collection`, `Remittance` and `UpfrontPayment` are append-only. ### Assumptions
1. **Contexts.** `payments` cannot reach `clubs.census` (the census's signup already calls payments: a cycle) nor
   `clubs.bookings`/`clubs.messaging`. So the census is read through the new `shared.application.BillingCensusAccess`, the
   R-12-25 consumers live in `clubs.bookings` (they call `PendingChargeService`), and N-10/N-35's facts are adapted in
   `configuration` (as `FollowupPortConfiguration`). `FirstMonthCalculator` (`clubs.signup.domain`) cannot be imported by
   `payments`; T-12-03 uses it to derive the signup's `nextInvoiceDate`, and billing starts from that date.
2. **The number guard covers the invoices that are not cancelled.** R-12-14 reuses a rolled-back block, while nothing is
   deleted, so E8-T01's unconditional unique `{clubId, series, number}` became partial on `status ∈ PENDING, COLLECTING, PAID,
   FAILED` (replaced at start-up). Without it the second generation answers `409 STALE_VERSION` (log `04`).
3. **Counters.** `CLUB.billing.counters[key]` holds the next number; the key is the resolved series with
   `billing.invoiceResetYearly`, the unresolved pattern without it (a pattern without `{YYYY}` cannot reset). A missing key
   starts at the imported `billing.nextNumber` only while the club has no counter. The counter writes bump the club's version.
4. **`MANUAL_INVOICE_AFTER`** means «something was numbered after the run's block»: a manual invoice, or a later run.
   A run already rolled back answers `409 RUN_NOT_ROLLBACKABLE {reasons: []}`.
5. **Cash half-years:** from `month(nextInvoiceDate)`, never before the start of `M`'s natural period, to its end; a leaving
   member's lines stop at the last billed month. `cashPeriodMonths ≤ 1` is monthly.
6. **Family group:** the holder's invoice also carries a non-holder's inactivity fee and single classes; the non-holder's date
   advances with the holder's (to the holder's next date). A skipped holder skips the group.
7. **Incident order:** the member's own data first (`NO_BANK_ACCOUNT`, `CARD_INVALID`), then `PROVIDER_DISABLED`; only when the
   member has something to bill. A member without any payment method is out of the month (R-12-01), not an incident.
8. **R-12-16 vs §5:** marking paid takes `PENDING`/`FAILED` only, as the task and R-12-16 say (§5's diagram also draws
   `COLLECTING → PAID`). A bank return of a `PAID` invoice needs a SEPA collection of it.
9. **Collections:** the stored `providerRef` stays the provider's unique id (Stripe); a SEPA attempt stores `mandateRef` +
   `endToEndId` (= `displayNumber`, which a rollback reproduces) and a manual payment its `channel` + `reference`; the
   published `providerRef` is derived from them. A rollback's `FAILED{ROLLBACK}` and a bank return keep the attempt number they
   close; a manual payment after another provider's attempt is `attempt + 1`.
10. **Staleness (R-12-07):** members (the simulation's and every `ACTIVE` one), family groups, plans and prices, and
    `billing.*` overrides. The run recomputes the month inside its transaction; it never copies the preview.
11. **Collection date:** only with SEPA invoices; two business days are Monday–Friday (no bank holidays).
12. **Dates the admin picks:** today's is the current instant, an earlier day its start in the club's zone, a later day 400.
13. **A manual invoice** bills its issue month (`period`), takes the member's current method (MANUAL without one), and

#### Assumptions (round 2)
1. **The floor applies to every reservation, not only to a new key.** Otherwise toggling twice in one year meets a live number
   (the toggle test does exactly that). An admin's cancellation counts in the floor: it is a real document. If a run with an
   admin-cancelled receipt inside its block is rolled back, the second generation starts after that number, which leaves a gap
   instead of reusing it.
2. **A `"{YYYY}"` counter is the same series only when the series has receipts.** It runs across the years, so in a new year it
   says nothing about that year's series: the reset still gives `2027-0001`. Inside a year it covers the rolled-back block of
   an imported series (the `nextNumber` case).
3. **«A plan without a monthly fee gets no date from the run»:** a member due only for its charges keeps its own date, and none
   stays none. A `PACK`/`SINGLE_CLASS` member whose date is due still advances, as R-12-02/06 say (unchanged from round 1).
4. **Charges are due whatever the date.** This includes a cash member billed by half-years: a charges-only receipt in between,
   with the half-year's date kept. R-12-25 says charges become lines «at the month's run».
5. **`includeInNextRun`:**
   - receipts are taken only while `SEPA_XML` is enabled;
   - a rollback returns only the `COLLECTING` ones (a `FAILED` one stays as it is);
   - `422 NO_INVOICES` is unchanged: waiting receipts alone do not make a run.
6. **Rolled back = `CANCELLED` + `cancelReason ROLLBACK`.** This is the reason only the rollback writes. An admin may not type
   it (`400 VALIDATION_ERROR {field: reason}`, case-insensitive) because the cancellation would then read as rolled back. D10's
   recent receipts leave such receipts out too, for the same duplicate number.
7. **Staleness reads the club's `updatedAt`.** Any D11 settings change (also the name or the theme) makes the simulation stale,
   which is conservative. Numbering only bumps the version.
