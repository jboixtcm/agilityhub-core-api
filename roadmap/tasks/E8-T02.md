# E8-T02 · Invoicing and the monthly cycle (S12 WP-12-B)

## Objective
Work package S12 WP-12-B. The admin simulates a month on D6, generates it, and the club has numbered, immutable receipts with one collection attempt each; a wrong generation can be rolled back whole; cash receipts are marked paid; corrections are new receipts. This task owns `InvoicingService`, numbering, `BillingSimulation`, `BillingRun` (generation + rollback), the invoice state actions, manual invoices and `PendingCharge`. SEPA file writing is E8-T03, Stripe is E8-T04, packs / inactivity / leave are E8-T05: this task consumes them through **ports with null-object defaults** and names the task that replaces each one.

## Steps
1. **Ports this task declares** in `payments/application/ports`, each with a `@ConditionalOnMissingBean` null object and the task that replaces it named in the javadoc: `InactivityFeePort` (`Optional<Money> feeFor(memberId, YearMonth)`, `List<MemberFee> feesForMonth(YearMonth)` — null object: empty; **E8-T05**), `LeaveBillingPort` (`Optional<YearMonth> lastInvoicedMonth(memberId)` — null object: empty, i.e. nobody is leaving; **E8-T05**), `PackBalanceOpeningPort` (`open(...)` for `UpfrontPayment PAID{PACK}` — null object: no-op; **E8-T05**), `RemittanceWriterPort` (`Remittance write(BillingRun, List<Collection>, LocalDate collectionDate)` — null object: throws `422 SEPA_NOT_CONFIGURED`; **E8-T03**), `CardChargingPort` (`chargeRun(runId)` — null object: `422 PAYMENT_PROVIDER_NOT_ENABLED`; **E8-T04**). Nothing in `payments` may import `clubs.census.persistence` or `clubs.catalogs.persistence` directly: go through the `application` services (ArchUnit).
2. **`InvoicingService.linesFor(member, period)`** (R-12-01…05, pure where possible so T-12-01…03 run without Mongo): selection — `Member.status = ACTIVE` (including members inside an inactivity period), `nextInvoiceDate ≤` last day of `M`, `paymentMethod` present, and `M ≤ LeaveBillingPort.lastInvoicedMonth(member)` when that returns a value; `PENDING` and `LEFT` never; non-holders of a `FamilyGroup` produce no invoice (R-12-04, `billedViaMemberId` **derived, never persisted**). Lines by `Plan.type`: `MONTHLY` → one `MONTHLY_FEE` at `PriceResolver.current(planId, MONTHLY_FEE, issueDate)`, **replaced** by `INACTIVITY_FEE` when `InactivityFeePort.feeFor` returns an amount, or by `MAINTENANCE_FEE` when `Plan.billingMode = MAINTENANCE` (Teràpia: the plan carries the fee automatically until an admin changes the member's plan — Josep 08-09, B10); `PACK` → no periodic line; `SINGLE_CLASS` → one line per unbilled `PendingCharge`. No current price → incident `NO_PRICE` and the member is **skipped**, never invented (R-12-03). Total 0 or no lines → **no invoice**, and `nextInvoiceDate` advances anyway (R-12-02, T-12-28). Descriptions are frozen at generation in the club's `defaultLocale` from the keys `billing.line.monthlyFee`, `inactivityFee`, `maintenanceFee`, `singleClass`, `pack`, `adjustment` (R-12-30) — «Quota {pla} — {Mes any}», «Quota inactivitat — {Mes any}», «Classe {data} — {gos}». A non-holder's inactivity fee becomes a **separate line on the holder's invoice** (R-12-04). T-12-01, T-12-02, T-12-28.
3. **Cash (R-12-05) — both branches are product, both are tested.** `billing.cashInvoicing = SEMESTER` (Cànic): one `PENDING` invoice with `k` monthly lines, `k` = months left to the end of the **natural half-year** (`billing.cashPeriodMonths = 6`: January–June and July–December), and `nextInvoiceDate` → day 1 of the next half-year; a new member's **first fraction** runs from their `startDate` to the end of the current half-year, full half-years afterwards. `MONTHLY` → one single-line invoice each month, identically supported. The signup copy `signup.text.cashConditions` describes the `SEMESTER` case: **do not change it**, but make the executor report say it must be reviewed whenever the key changes (Jordi 09-09, A29). T-12-03.
4. **Numbering (R-12-08)**: series = `billing.invoiceSeriesPattern` resolved (`{YYYY}` → year of `issueDate`); number = `billing.nextNumber` taken atomically with `findOneAndUpdate` on `clubs` **inside the run transaction**, assigned in a deterministic order (last names, first name, member number) so a rollback can give them back; `billing.invoiceResetYearly` → 1 on the first invoice of a new year; `displayNumber = "{series}-{number:04d}"`. A number is never reused except through the rollback of R-12-14. T-12-04.
5. **Amounts (R-12-09)**: everything in `amountMinor`; per line `tax = round_half_even(base × taxPercent / 100)`, `total = base + tax`; the invoice total is the **sum of lines**, never recomputed from the total; a `Price` in another currency → `422 CURRENCY_MISMATCH`. The Cànic has `taxPercent = 0` and `billing.taxIncluded = true` (Jordi 05-09, B3): keep the mechanism working for other clubs. T-12-05.
6. **`POST /billing/simulations` (R-12-07)**: computes R-12-01…05 **writing nothing of business value**; incidents `NO_BANK_ACCOUNT` (`SEPA_DD` with `iban = null`), `NO_PLAN`, `NO_PRICE`, `CARD_INVALID`, `CURRENCY_MISMATCH`, `PROVIDER_DISABLED` (provider not active in `CLUB.paymentProviders`); `cashMembers[]` with `plannedLeaveDate` from `Member.leaveDate`; `invoicesPreview[]`; `kpis {count, total, byProvider, cashPending, inactivityFees{count, firstMonth, following}}`. Persisted as the **single** `BillingSimulation` of that period (unique `{clubId, period}`: replace). A period more than three months ahead → `400 VALIDATION_ERROR` (§13 assumption). `409 BILLING_BUSY` while the lock is held. Emits `RemittanceSimulated`.
7. **`POST /billing/runs` (R-12-11)** — `Idempotency-Key`; one **live** run per `{club, period}` (the partial-unique index of E8-T01 → `409 RUN_EXISTS`); club lock in `billing_locks` with a 10-minute TTL → `409 BILLING_BUSY`; the run requires a simulation of the same period taken **after** the last relevant change (`simulation.at ≥ max(updatedAt)` over the members, prices and `billing.*` parameters involved) → otherwise `409 SIMULATION_STALE`. One transaction (retry on `WriteConflict` through a new `BillingTransactions` helper modelled on `SchedulingTransactions`): create the `Invoice` documents, one `Collection` per invoice — `SEPA_XML` → `CREATED` and the invoice `COLLECTING` after `RemittanceWriterPort` returns (**the XML is generated and XSD-validated before the commit; if it fails nothing is written**), `MANUAL` → `CREATED` with the invoice `PENDING`, `STRIPE` → `CREATED` with the invoice `PENDING` until E8-T04's charging step —, advance `nextInvoiceDate` to `billing.nextInvoiceDayOfMonth` of `M+1` **only for the included members** and store the old values in `run.previousDates[]`, stamp `PendingCharge.invoiceId`, and emit `InvoiceIssued` per invoice plus `BillingRunCreated`, `RemittanceGenerated` (when there is one) and `InvoiceCollecting`. Members with an incident are **skipped**, listed in `run.skipped[]`, and never block. Audit: `REMITTANCE_GENERATED` as **one** entry with `details.invoiceIds[]` (R-14-10: one entry per aggregate, not per invoice). Errors: `422 NO_INVOICES`, `422 SEPA_NOT_CONFIGURED`, `422 COLLECTION_DATE_TOO_SOON`. T-12-09, T-12-10.
8. **Collection date (R-12-12 arithmetic only)**: default from `billing.sepa.collectionDayOfMonth` read as a day of the **billed** month — `1–28` = that day (clamped to the month length), `0` = last day. The Cànic value is **1**, so September's run happens in August (≈ day 25) with `ReqdColltnDt = 2026-09-01`; the two-business-day rule of R-12-12 is measured from the generation date and a shortfall is `422 COLLECTION_DATE_TOO_SOON`. An explicit `collectionDate` in the body wins. **Both semantics are product, the key is edited from D11 and both are tested** (Jordi 09-09, A28) — and changing the key never recomputes an already generated remittance (R-02-04). T-12-29b.
9. **Rollback (R-12-14)**: `POST /billing/runs/{id}/rollback {reason, confirmation}` with `confirmation` exactly `"RETROCEDIR"` (otherwise `400 VALIDATION_ERROR`). Allowed only when the `Remittance` is not `SUBMITTED`, no `Collection` of the run is `SUBMITTED`/`SUCCEEDED`, and no invoice of the run is `PAID` — otherwise `409 RUN_NOT_ROLLBACKABLE {reasons[]}` with `REMITTANCE_SUBMITTED · COLLECTION_SUBMITTED · INVOICE_PAID · MANUAL_INVOICE_AFTER`. One transaction: invoices → `CANCELLED{ROLLBACK}`, a **new appended** `Collection FAILED{ROLLBACK}` per invoice, `Remittance` → `ROLLED_BACK` (the file is kept), `billing.nextNumber` returned to the run's first number (possible only because the run is the last consecutive block — a manual invoice issued afterwards gives `MANUAL_INVOICE_AFTER`), each member's `nextInvoiceDate` restored from `run.previousDates[]`, `PendingCharge.invoiceId` → null; events `RemittanceRolledBack` + `InvoiceCancelled` per invoice; audit `REMITTANCE_ROLLED_BACK`. The same month can then be simulated and generated again and **must reproduce the same numbers**. T-12-13.
10. **Invoice state actions**: `POST /invoices/{id}/payment {paidAt, channel CASH|TRANSFER|BIZUM, reference?, version}` and the bulk `POST /invoices/payments {invoiceIds[], paidAt, channel}` on `PENDING`/`FAILED` invoices whose `paymentMethod.type ∈ {MANUAL, SEPA_DD}` → appended `Collection MANUAL SUCCEEDED` + invoice `PAID` + `InvoicePaid{MANUAL}`, audited `INVOICE_MARKED_PAID` (R-12-16) · `POST /invoices/{id}/failure {reason, at, version}` on a `COLLECTING` SEPA invoice **or on a `PAID` one with a SEPA collection** (later bank return) → appended `Collection FAILED{BANK_RETURN}` + invoice `FAILED` + `InvoiceFailed` → **N-10** to the admins, with no automatic claim or block (BR-08), audited `INVOICE_MARKED_FAILED` (R-12-17) · `POST /invoices/{id}/cancellation {reason, version}` only on `PENDING`/`FAILED`, never on `PAID`/`COLLECTING` (`409 INVALID_STATE`), audited `INVOICE_CANCELLED` (R-12-19) · `POST /invoices {memberId, lines[], includeInNextRun?, note}` creates a `kind = MANUAL` invoice with `ADJUSTMENT` lines (positive or negative), numbered in the same series, `PENDING`, audited `INVOICE_CREATED_MANUAL` (R-12-19). Every action takes `version` → `409 STALE_VERSION`, and `Idempotency-Key` where §6 says so → a repeat returns the stored response (`CONVENCIONS_API` §7). T-12-14, T-12-18, T-12-30 (its non-Stripe half).
11. **Immutability (R-12-10)**: no `PATCH /invoices/{id}` (the route must answer `405 METHOD_NOT_ALLOWED`); the repository exposes **no** method that updates lines, amounts, member or number; `Collection`, `Remittance` and `UpfrontPayment` are append-only. Add an `ArchitectureTest` rule that fails if any repository in `payments` declares a method matching `update*|save*` over `InvoiceLine`. T-12-12.
12. **`PendingCharge` (R-12-25)**: a `DomainEventHandler` for `AttendanceMarked {state ∈ PRESENT, NO_SHOW, previousState = PENDING}` and `BookingCancelled {late = true}` of a booking whose `charge.mode = CHARGE_ON_ATTENDANCE` creates a `PendingCharge` (unique by `bookingId`) at the `SINGLE_CLASS` price current on the class date, and stamps `Booking.charge.chargeInvoiceLineRef` provisionally; `AttendanceMarked {state PENDING, previousState PRESENT|NO_SHOW}` before billing sets `voidedAt`. Idempotent by `eventId`. With `SINGLE_CLASS` off, nothing happens. `PAY_TO_BOOK` and refunds are E8-T04. T-12-08 (the domain half lands here; the port contract with S08 stays as E5 left it).
13. **Reads**: `GET /billing/periods/{period}` (the D6 aggregate: `simulation?`, `run?` with `rollbackable` and `rollbackBlockers[]`, `remittance?`, `counts {all, pending, remitted, paid, failed}`) · `GET /invoices` as a universal list with the declared filters, sorts and `q` · `GET /invoices/{id}` with `collections[]` and refunds · `GET /me/invoices` and `/me/invoices/{id}` (R-12-27: own invoices **plus** the holder's invoice when the caller belongs to that family group, flagged `familyGroup: true`, and **never** an IBAN) · `GET /members/{id}/pending-charges`. Modules (R-12-28): `BILLING` off → every route `404 MODULE_DISABLED` and no `nextInvoiceDate` written anywhere; `INACTIVITY` off → never an `INACTIVITY_FEE`; `FAMILY_GROUP` off → everyone is billed on their own. T-12-22, T-12-32.
14. **Tenant, time and concurrency**: every query filtered by `clubId` (an admin of club B gets `404` on club A's invoices, runs and remittances — T-12-21); `issueDate`, `collectionDate` and `paidAt` are **club-local** dates through `ClubClock` (a run at 23:30 local in `America/Argentina/Buenos_Aires` must not slide a day — T-12-23); no `Instant.now()` anywhere (the E5-T01 ArchUnit rule); two simultaneous `POST /billing/runs` → one `201` and one `409 BILLING_BUSY`/`RUN_EXISTS`, and the same `Idempotency-Key` returns the same response (T-12-10).

## Fixed conventions
- Statuses (catalog first): `RUN_EXISTS`, `BILLING_BUSY`, `SIMULATION_STALE`, `RUN_NOT_ROLLBACKABLE`, `INVALID_STATE`, `STALE_VERSION`, `IDEMPOTENCY_KEY_REUSED` **409** · `COLLECTION_DATE_TOO_SOON`, `CURRENCY_MISMATCH`, `NO_INVOICES`, `SEPA_NOT_CONFIGURED`, `NO_PAYMENT_METHOD`, `PAYMENT_PROVIDER_NOT_ENABLED` **422** · `VALIDATION_ERROR`, `INVALID_FILTER` **400** · `MODULE_DISABLED`, `NOT_FOUND` **404** · `METHOD_NOT_ALLOWED` **405** · MEMBER or INSTRUCTOR on any `/billing/*` or `/invoices` route **403**.
- Assumptions in force (do not ask): cash = `SEMESTER` at the Cànic with `MONTHLY` equally implemented and tested (A29); collection day = 1 of the **billed** month with `0` = last day equally implemented and tested (A28); no VAT at the Cànic (B3); `Plan.billingMode = MAINTENANCE` drives the Teràpia fee and `Member.billingMode` does not exist (B10); incidents never block a run, the member is skipped; corrections are new invoices, never edits (R-12-10); no automatic claim, block or dunning for an unpaid receipt (BR-08).
- One Mongo transaction for the whole run and for the whole rollback, outbox inside it (`EventPublisher`); every state action is its own transaction. Money only as `Money {amountMinor, currency}` in the club's currency. Frozen line descriptions are rendered **once**, at generation, in the club's `defaultLocale` — never in the admin's locale (R-12-30).
- Closed catalogs: no new parameter, event, notification, error code or audit action beyond what E8-T01 already added; proposals go to the report and `roadmap/MESSAGES.md` while the closest existing item ships.

## Definition of Done
On the fictional census the admin can simulate a month and see incidents, cash members and KPIs; generate it into numbered immutable receipts with one collection each and the members' next-invoice dates advanced; roll the whole thing back so the numbers and the dates return and a second generation reproduces them exactly; mark cash receipts paid in bulk and a SEPA receipt unpaid with N-10; issue a manual adjustment receipt; and see all of it through `GET /billing/periods/{period}` and `GET /invoices`. A cash member at the Cànic gets one receipt per natural half-year, a cash member of a `MONTHLY` club gets one per month, and `billing.sepa.collectionDayOfMonth` produces `1`, `0` and `28` correctly.
