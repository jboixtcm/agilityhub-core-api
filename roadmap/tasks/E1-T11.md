# E1-T11 · OpenAPI required-by-default for response DTOs (springdoc customizer) + contract test — fixes the branding schemas

## Objective
The web generates TypeScript types from `docs/openapi/openapi.json`. Only the identity DTOs carry `@Schema(requiredMode = REQUIRED)` (E1-T01), so `BrandingResponse`, `ClubSummary`, `Theme`, `Colors`, `Manifest`, `HealthResponse`, `ApiError`, … have **no `required` arrays** and every generated property is optional — the web has to "runtime-refine" what the backend always sends (E1-W06 finding). Make **required the default** for every response/request schema property, with an explicit opt-out for optional ones, and lock it with a contract test.

## Spec references
`docs/specs/00-transversal/CONVENCIONS_API.md` (contract = snapshot; nullable/optional fields are the exception) · E0-T12 (snapshot + CI diff) · E1-T01 (identity DTO annotations).

## Context to load
`configuration/OpenApiConfiguration.java` · `configuration/OpenApiSnapshotTest.java` · `platform/api/BrandingResponse.java`, `shared/api/ApiError` (or equivalent), `identity/api/*Response*.java` · `docs/openapi/openapi.json` · this file.

## Fixed conventions
- Rule: a schema property is **required unless** its Java type is `Optional<…>`, it is annotated `@Nullable` (JSpecify or Spring's), or it carries `@Schema(requiredMode = NOT_REQUIRED)` / `nullable = true`. Collections are required (empty list, never null). Apply the rule with a springdoc `PropertyCustomizer` / `OpenApiCustomizer` in `OpenApiConfiguration` — **not** by annotating every record by hand.
- Existing explicit annotations stay valid; the customizer must not turn an explicit `NOT_REQUIRED`/nullable property into required.
- Fields that are optional by contract must be reviewed and marked explicitly in this task: `ClubSummary.city`, `MeAccount.emailVerifiedAt`, `MembershipSummary.{activeProfile, defaultProfile, memberId, instructorId, gender}`, `Me.{membership, impersonation}`, `Session.{lastUsedAt, clubId, activeProfile}`, `Theme.{logoUrl, logoDarkUrl, markUrl, logoDark…}` (a club may have no logo yet), `TokenResponse.{refresh_token, id_token}`, `OnboardingState.requiredConsent` (nullable), `OnboardingField.value` (nullable), `ApiError.{details, fieldErrors, traceId?}` (check the S00 envelope: `code` and `message` always present). Anything else that is nullable in practice must be justified in the report.
- The snapshot must be regenerated (`bin/openapi-snapshot`) and committed; `docs/openapi/CHANGELOG.md` line.

## Steps
1. Implement the customizer in `OpenApiConfiguration` (walk `components.schemas`, derive `required` from the Java model — springdoc gives access to the annotated type via `AnnotatedType`/`ModelConverter` — or, if simpler and equivalent, a `ModelConverter` that marks properties required when the accessor type is not `Optional`/nullable).
2. Annotate the optional fields listed above (`@Schema(requiredMode = NOT_REQUIRED)` or `@Nullable`), nothing else.
3. Contract test `OpenApiRequiredContractTest`: (a) every object schema in the snapshot has a `required` array (possibly empty only for schemas whose properties are all optional — list them explicitly in the test), (b) `BrandingResponse.required` ⊇ `{club, theme, locales, defaultLocale}`, `ClubSummary.required = {slug, name}`, `Colors.required` = all twelve colors, `Me.required = {account, features}`, `MeAccount.required` ⊇ `{id, email, name, locale, platformRoles, hasPassword, onboardingPending}`, `ApiError.required ⊇ {code, message}`.
4. `bin/openapi-snapshot`; make sure `OpenApiSnapshotTest` (byte-identical regeneration) is still green.

## Definition of Done
Customizer in place; optional fields explicit; snapshot regenerated; contract test green; the web can regenerate types with non-optional properties (the organizer copies the snapshot).
