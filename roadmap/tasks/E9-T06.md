## Steps
For each point, first write the test that fails without it, named after the rule.
1. **Keyed build-session writes never answer 500** (review #1, major; INC-47's pattern). Put `POST /build-sessions`, `/build-sessions/join` and `/build-sessions/{id}/finish` in `IdempotencyFilter`'s retrying route groups, as FOLLOWUP and BILLING are, so a write conflict or a join code already taken retries the whole request; exhausted → `409 STALE_VERSION`, never a 500. Tests: a keyed `finish` racing taps on the last obstacle; two keyed joins at once; a keyed create that draws a join code already taken.
2. **`finish` without the publish switch** (review #2; ruling E118). `POST /build-sessions/{id}/finish` is not gated by `courses.allowInstructorPublish`: whoever may write to the session closes it (`finishedAt`, `FINISHED`, `BuildSessionFinished`). The setup registration (R-16-07) still follows the switch: with it off, an INSTRUCTOR's finish registers no setup, the response shows that none was registered, and an ADMIN registers it with `POST /ring-setups`. The S16 line (R-16-11) and a `docs/openapi/CHANGELOG.md` entry in the same commit (E109).
3. **A refreshed setup keeps its `expectedUntil`** (review #3). When the ring's active setup already shows the placement, the refresh keeps `current.expectedUntil()`, recomputes `expiresAt` from it as `renew` does, and leaves the same audit trail as a renewal.
4. **Six active markers for the export** (review #4 and question 1; ruling E118). `BuildSessionExportV1` counts the ring's **active** markers and needs exactly six (the AR schema's A–F): fewer → `422 GEOMETRY_INVALID {violations: [{path: markers, rule: TOO_FEW_MARKERS}]}`, more → `rule: TOO_MANY_MARKERS`. R-16-04 keeps «≥ 3» for the geometry itself. The S16 line in the same commit.
5. **One slow client does not stall the streams** (review #5). Each subscriber gets its own bounded send queue (or a small pool) instead of the one shared thread, with a write timeout; a subscriber whose queue fills or whose write times out is closed (EventSource reconnects and reads `GET /build-sessions/{id}` again). Test: a subscriber that never reads does not delay another subscriber's events beyond R-16-11's 2 s.
6. **A stream lives no longer than its token** (review #6). The stream's timeout is the smaller of 30 minutes and the access token's remaining lifetime (`exp`), so a lost role, module or membership stops at the next reconnection. Test with a short-lived token.
7. **An outlived session ends its streams** (review #7). Once `courses.buildSessionMaxHours` has passed, the next poll sends `finished` and ends the stream, without waiting for P9.
8. **`finish`'s `@ContractErrors`** include `RING_WITHOUT_GEOMETRY` (review #8), so the contract lists what the code throws.
9. **The query token stays out of the logs** (E9-T04's question 3 and the review's «Not checked»). The production `deploy/Caddyfile` drops `access_token` from the access log's URI (Caddy's log filter on `request>uri`, query `delete access_token`); a test proves that `RequestTraceFilter` and the app's request logs never write the query string; and `?access_token=` is refused (`401`) on every other route and on a non-GET to the stream's path.

### Assumptions

- **Step 1.** Like FOLLOWUP, a keyed build-session write that fails (4xx) releases its key rather than replaying the error. A conflict inside `RingSetupService.activate` is still converted to `409 STALE_VERSION` at once (E9-T03's code, shared with `POST /ring-setups`). Because `finish` now registers the setup before its closing write, a tap that races it meets that last write, which is retried.
- **Step 2.** The answer «shows that none was registered» through `setupId`, a new nullable field of `BuildSession`. It is stored on the session, so `GET` shows it too.
- **Step 3.** «The same audit trail as a renewal»: a renewal writes `updatedAt`/`updatedByAccountId` and no audit entry or event, so the refresh does the same. It also moves `builtAt`/`builtByAccountId`, because the course was built again. If the kept `expectedUntil` is already past, the setup keeps it, and P5 f expires the setup at its next run.
- **Step 5.** A blocked servlet write cannot be cancelled from outside, because the emitter's lock is held. So the watchdog takes the subscriber out of its session and drops its queue, and the stream completes when the blocked write returns, at the latest at Tomcat's own socket write timeout. The pool holds at most one thread per stalled client. `WRITE_TIMEOUT` is 10 s and `QUEUE` is 64 frames; both are constants, not parameters, because the catalog has neither.
- **Step 7.** The early `finished` carries `status: ABANDONED` with `finishedAt: null`: P9 has not recorded the end yet, and `GET` still shows `IN_PROGRESS` until it does. The stream does not write the session itself, because that write is P9's.
- **Step 9, «every other route»**: the routes under the global bearer requirement (395 operations). Public routes (`security: []`) never read a token, and optional-auth or API-key routes do not take the query either. The app's own console output was captured at the test profile's levels; DEBUG on `DispatcherServlet` would print query strings, which DEPLOY.md already forbids on live traffic.
- The S16 edit is in the api's copy only (E109). The project documentation source needs the same lines.

### Questions / catalog proposals

1. **Caddy access log (step 9)**: the production Caddyfile has no access log on purpose. `docs/DEPLOY.md` §Logs says «Caddy access logging is off: query strings can contain signed capabilities». Turning the log on so the filter has something to filter would start logging the other capabilities (signed file URLs, `.ics` and unsubscribe tokens, OIDC codes) and client IPs (R-14-18).
