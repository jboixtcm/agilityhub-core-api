### Assumptions
- **Where P9 re-checks.** S17 R-17-03 says «Es reverifica setmanalment (S15 P9 opcional)», and S15's P9 is `cleanup`, so the re-check is a new R-15-19 row of that daily process. Each club's own run re-checks its own domains, which keeps the tenant rule and the `SchedulerRun` trace.
- **«Setmanalment».** A domain is due when its last re-check, or its verification, is `platform.domainRecheckDays` (catalog, 7) or more days before the occurrence. `0` turns it off for that club; the catalog's `min` is 0 and the catalog uses 0 = off elsewhere.
- **«3 cops».** Three failures in a row (a product constant, as S17 states it). A good re-check clears the count.
- **The proof.** A verified apex domain has no CNAME, and its TXT challenge was removed at verification (model §2). So the re-check also passes when the host shares an A/AAAA address with its app's product host (`ADDRESS`). Without this, every TXT-verified domain would become BROKEN after three weeks. The production adapter resolves addresses through the JVM resolver, which follows CNAMEs.
- **A console verify of a BROKEN domain accepts the same `ADDRESS` proof.** A PENDING domain still verifies by CNAME or TXT only.
- **What BROKEN does.** Tenant resolution and Caddy's `ask` already serve only `VERIFIED` hosts (E10-T04), so a BROKEN host stops resolving at once (`ClubUpdated` evicts the host cache after the commit). The primary flag is kept, so a restore puts the domain back as it was.
- **Audit and events.** Only the status changes (BROKEN, RESTORED) are audited `CLUB_DOMAIN_CHANGED`, by the system with `details.job = cleanup`, and only they bump the club's version. A plain check updates `checkedAt`/`failedChecks` without touching the version, so a console form open meanwhile does not go stale. A status change that races a console write gives the item `STALE_VERSION`: the run ends PARTIAL and the next day retries it, since the domain is still due.
- **N-43 recipients.** «Admins de plataforma» = every ACTIVE account with `AGILITYHUB_ADMIN`. The e-mail is platform-branded, sent without a tenant, in each account's language. The row id derives from the event and the account.
- **The demo platform account.** It lives in the demo seed's new `platform` section, as the E118 note asks, not in `club-canic.yaml`: it has no club, and the club file is also the production definition. `platform@example.test` signs in through AgilityHub ID (`id-web`, password grant on the ID host), whose token has no `clubId`. A `clubs-admin` code flow needs a club host (`OidcService`), so the console's entry is the ID token (S01 R-01-17, «S17 usa apps/id»).
- **The fake resolver on a local stack.** Unpublished hosts resolve to `127.0.0.1` under `local` only. Otherwise every seeded club's trusted host would become BROKEN after three weeks of a long-lived or clock-moved stack.
- **The template club.** `seeds/club-template-default.yaml` has empty catalogs today, so the smoke's clone copies 0 rows. It still exercises the route. The template's content is S17 §13 #5, which is open.
- **The OpenAPI addition.** One enum value, staged for the web like E10-T04's additions.
