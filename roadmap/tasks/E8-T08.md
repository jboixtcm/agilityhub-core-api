## Steps
1. **A waiting receipt is remitted under the member's current mandate, and its incident names the receipt (E8-T03 review #1, E8-T07 review #2; ruling E90).**
   - `remittedAttempt` builds the `Collection` of an `includeInNextRun` receipt with the member's **current** `mandateRef` and `mandateSignedAt` (the collection is what the remittance freezes; the receipt's own mandate field, if any, is informational). The writer no longer refuses a debit because «the member now holds another mandate»; it still refuses one whose current mandate lacks its reference or signature date.
   - `BillingIncidentCode` gains **`MEMBER_NOT_ACTIVE`** (the member of a waiting receipt is `LEFT` or `PENDING`) and **`PAYMENT_METHOD_CHANGED`** (they no longer pay by `SEPA_DD`); `InvoicingRules.waitingReceiptIncident` returns them instead of `NO_BANK_ACCOUNT`, which goes back to its R-12-07 meaning (`SEPA_DD` with no account). A changed mandate is **not** an incident any more.
   - `BillingIncident` gains optional **`invoiceId`** and **`displayNumber`** (absent on member-level incidents). A member who also gets a periodic receipt in the same run appears in `incidents[]` with the receipt's incident but **not** in `skipped[]`.
   - Tests: the member who changed account between the receipt and the run → the debit carries mandate `-2`, the run succeeds; a `LEFT` member's waiting receipt → `MEMBER_NOT_ACTIVE` with its `displayNumber`, still billed members absent from `skipped[]`; `S12 §6`'s simulation fixture updated (`E8ResponseContractTest`), `openapi.json` + `docs/openapi/CHANGELOG.md`.
2. **Distinct fictional debtors in the golden file (E8-T03 review #3; T-12-11).** Every SEPA member of `BillingItSupport` gets its own fictional IBAN (valid check digits, `ES00`/test range as the existing `iban()` helper does) and holder name. Regenerate the golden file with a note in the test, and add one assertion that fails when two debits swap their IBANs.
3. **SEPA identifiers checked before marshalling (E8-T03 review #4; R-12-12).**
   - `billing.invoiceSeriesPattern` now carries a catalog constraint (SEPA character set `a-zA-Z0-9/-?:().,'+ ` and the expanded `displayNumber` ≤ 35 characters): enforce it in the parameter validation (`422` on a bad value from D11, as the other constrained parameters do — no new error code).
   - The writer validates `EndToEndId`, `MndtId`, `MsgId` and `PmtInfId` against the schema's `Max35Text` **before** marshalling and answers `422 SEPA_NOT_CONFIGURED {reason: IDENTIFIER, field}` (the field's name, never its value) instead of `{reason: SCHEMA}` with a line and a column.
   - Tests: a series with `·` is refused at D11; a receipt stored with an over-long number makes the run answer the identifier reason and nothing is written.
4. **No orphan file after an unknown commit (E8-T03 review #5).** On `afterCompletion(STATUS_UNKNOWN)`, check whether the attempt's remittance id was persisted; if it was not, delete the stored file; in every case log the storage key at `WARN` with the `traceId`. Test with a transaction synchronisation driven to `STATUS_UNKNOWN`.
5. **The creditor suffix and the texts (E8-T03 reviews #6 and #7).** A `suffix` that is not exactly three SEPA-charset characters makes the creditor not `configured()` → `422 SEPA_NOT_CONFIGURED`. `SepaText` maps `’` → `'` and `–`/`—` → `-` before the rest of R-12-12's rule. Tests for both.
6. **The mandate sequence survives a method change (E8-T03 Q2, accepted).** When a member leaves `SEPA_DD`, the census keeps the last mandate sequence (for instance `paymentMethod.sepa.lastMandateSequence`, not shown in any response); a return to `SEPA_DD` issues the next reference (`-2`, never `-1` again). `CensusRules.mandateRef` takes the sequence from there. Test SEPA → MANUAL → SEPA.
7. **The misnamed test (E8-T07 review #1).** Rename `BillingCycleIT.T_12_19_R_12_14_rolledBackComesFromTheRunAndTheAdminsReasonIsFreeText` to `R_12_19_R_12_14_…`: T-12-19 is the CSV export (R-12-26), which E8-T06 owns.
8. **Exact staleness (E8-T07 review #5).** The simulation's stored sets hold the unbilled charge ids and waiting receipt ids **the drafts bill**, and the run compares its plan with those; a new charge of a member with an incident, or of a member not invoiced this month, no longer makes the simulation stale. Test both the still-stale case (a billed charge voided) and the no-longer-stale one.
9. **The nits.**
   - E8-T07 review #6: a paragraph in `docs/DEPLOY.md` (restore section): the numbering reads hint `invoice_club_series_number_all`; a restore must keep the indexes (`ensureIndexes` recreates them at start-up; a restore with `--noIndexRestore` needs a restart before the first run).
   - E8-T07 review #7: `InvoiceNumberingIT`'s evidence `System.out.println` only with `-Dagilityhub.evidence=true`.
10. **`SimulationKpis.collectionDate` (E8-W01 Q1, accepted).** The simulation's KPIs carry the collection date the run would request (`billing.sepa.collectionDayOfMonth` applied to the billed month, club-local, as `BillingRunService` computes it), so D6 can show «data de cobrament: 01/09» at simulation time. Additive; snapshot + CHANGELOG; fixture of S12 §6 updated.
