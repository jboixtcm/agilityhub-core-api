# E11-T07 · Spring Boot 4.1 and Spring Framework 7

## Objective
Move the api from Spring Boot 3.5.16 (Spring Framework 6.2.19) to the latest Spring Boot 4.1.x patch on Maven Central, so that `spring-webmvc` is 7.0.9 or later. Then remove the time-limited exception for CVE-2026-47890 that E8-T10 added to `bin/security-scan-suppressions.json` (ruling E97: it expires on 07-12, and the only open-source fix is on the 7.0 line). Only the platform changes: the HTTP contract, the data stored in MongoDB and every gate stay as they are (size L, ruling E129).

Spring Boot 4.0 reaches the end of its open-source support on 2026-12-31, so the release (E12) should run on 4.1.

## Spec references
`docs/specs/00-transversal/CONVENCIONS_API.md` (the contract and its snapshot), `docs/DEPLOY.md`, `bin/security-scan-suppressions.json`. Upstream guides: the Spring Boot 4.0 Migration Guide (`github.com/spring-projects/spring-boot/wiki/Spring-Boot-4.0-Migration-Guide`), the Spring Boot 4.1 release notes, and the Spring Security 7 and Spring Framework 7 migration notes.

## Context to load
`pom.xml`, `src/main/resources/application.yml`, `bin/openapi-snapshot`, `bin/security-scan*`, `bin/mutation-gate`, E11-T03's report (the same-line pins), E8-T10's note on the exception, `AGENTS.md`.

## Steps
1. **The baseline, on `main`, before any change:** `./mvnw -q clean verify` (exit code plus the surefire and failsafe totals), `bin/openapi-snapshot` (no diff), `bin/security-scan`, and the `mutation` profile on one small package of your choice (exit code and score). The upgrade must keep these numbers.
2. **The BOM.** Set the parent to the latest 4.1.x. If its BOM still selects `spring-webmvc` below 7.0.9, set `spring-framework.version` to the latest 7.0.x at or above 7.0.9 and say so. Remove E11-T03's same-line pins that Boot 4 supersedes (`tomcat.version` 10.1.x, `netty.version` 4.1.x), unless the image scan needs a newer patch of the new lines.
3. **Starters.** The old names still work but are deprecated: use `spring-boot-starter-webmvc`, `spring-boot-starter-security-oauth2-resource-server`, `spring-boot-starter-security-oauth2-authorization-server` (Spring Authorization Server is now part of Spring Security, with no version property of its own), `spring-boot-starter-aspectj` only if AOP is still needed, Micrometer's starter, and the per-technology test starters (`spring-boot-starter-webmvc-test`, `spring-boot-starter-security-test`, and so on). Do not use the `-classic` fallback starters.
4. **Jackson stays on 2 in this task.** Add the deprecated `spring-boot-jackson2` module and move `spring.jackson.*` to `spring.jackson2.*`. That way the 322 files that import `com.fasterxml.jackson.databind` do not change, and the JSON on the wire stays the same. Jackson 3 is a later task: it must land before Boot drops the module. If 4.1 no longer ships `spring-boot-jackson2`, set the task `blocked` with the evidence; do not start a Jackson 3 migration here.
5. **MongoDB.** Move the renamed properties (`spring.data.mongodb.{uri,host,port,database,username,password,ssl.*}` → `spring.mongodb.*`; `management.health.mongo` → `mongodb`). Boot 4 no longer sets a default UUID or BigDecimal/BigInteger representation: set them explicitly to exactly what Boot 3.5 used, and add an IT that reads documents written the old way (a `UUID` and a money `BigDecimal`) and writes them back unchanged. Money must not change type, scale or precision.
6. **Tests and PIT.**
   - `@SpringBootTest` no longer brings MockMvc (add `@AutoConfigureMockMvc`), and the test slices moved to their `spring-boot-<tech>-test` modules.
   - Testcontainers 2 renamed its artifacts and the Mongo container's package.
   - PIT must keep working: `pitest-maven` and `pitest-junit5-plugin` at versions that support the JUnit Platform that Boot 4 brings. The `mutation` run of step 1 runs again with the same score; api-c's E11-T06 depends on it.
7. **The rest of the platform:**
   - Spring Security 7 and Spring Framework 7 removals.
   - Jakarta EE 11 and Bean Validation 3.1 (messages).
   - The liveness and readiness probes, now on by default: the health endpoints and the deploy's checks stay as they are.
   - `org.springframework.lang.Nullable` → `org.jspecify.annotations.Nullable`.
   - springdoc-openapi on its Boot 4 line, Sentry's Boot 4 starter, Tomcat 11.
8. **The contract does not change.** `bin/openapi-snapshot` regenerates `docs/openapi/openapi.json` byte-identical to step 1. If springdoc's new line emits OpenAPI 3.1 or orders schemas differently, configure it back (for example `springdoc.api-docs.version=openapi_3_0`). If you cannot, list every remaining difference in the report and set the task `blocked`: the web generates its client from this file.
9. **The exception goes.** Remove CVE-2026-47890 from `bin/security-scan-suppressions.json` (the mechanism and its test stay), and show `bin/security-scan` and the image scan green without it.
10. **Docs:** `docs/DEPLOY.md` and anything else that names versions. Add an `## Upgrade notes` section to the report for the other lanes: what changed in the build, the properties and the tests.
11. **Rebase last.** Other lanes merge into `main` while you work: cloud E (E11-T01, E11-T02), cloud F (E9-T07) and api-c (E11-T06). Before `awaiting_verification`:
    - `git pull --rebase origin main`;
    - make the newly merged code compile and pass under Spring 7;
    - run the clean verify again on the rebased tree.

    Do not edit another lane's task file.

## Fixed conventions
One task, one publish. No functional change, no new endpoint, and no change to `docs/openapi/openapi.json`, to the stored data or to the coverage and mutation thresholds. Deprecated APIs that Boot 4 still offers stay only where this file says so (Jackson 2); list them in the report.
