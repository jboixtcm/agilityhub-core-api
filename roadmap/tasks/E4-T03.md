# E4-T03 · Calendar, classes, cancellation, ring blocks and grids (S06 P3): ClassSession + RingBlock lifecycle, WeekValidationUseCase, ClassCancellationUseCase over the S08/S09 ports, RingBlockService.syncForActivity, RiskEvaluator, DayGridQuery, CalendarQuery, N-08a/N-08b in the dispatcher

## Objective
Work package S06 P3: the admin validates a whole week, edits an active class ([Accepta]), cancels or deletes it — never physically: it becomes `CANCELLED` — with the D4c flow that notifies every registrant (N-08a app + mail + SMS intent), blocks rings from D4 (and the instructor from screen 24 through the same endpoint), and everybody sees the day: student grid (10, never counts), instructor «Visió global» (23) and the D4 calendar (forms B and D). Bookings, waitlist, packs and training bookings are E5: this task defines the **ports** S06 §7 names, proves the transaction with in-memory doubles, and exposes the contracts S07 (E4-T04) and S15 (E5) call.

## Steps

Tests use in-memory doubles that reproduce the S06 examples.
2. **`ClassSessionRules` + state machines** (pure, T-06-08): `ClassSession` `DRAFT → ACTIVE` (week validation) · `DRAFT → CANCELLED` (`DELETED`) · `ACTIVE → CANCELLED` (`CLUB_MANUAL`, `DELETED`, `RISK_REVIEW`, `ACTIVITY`) · `ACTIVE → FINISHED`; `Week` `PENDING → GENERATED → VALIDATED`, `PENDING → VALIDATED`; every forbidden transition → `INVALID_STATE`; `FINISHED`/`CANCELLED` accept only `notes`.
3. **`WeekValidationUseCase`** (R-06-08): every `DRAFT` class of the week → `ACTIVE` in one transaction (`Week.state = VALIDATED`, `validatedAt/By`, `WeekValidated{weekId, classIds[]}`, `@Audited(WEEK_VALIDATED)`); `NOTHING_TO_VALIDATE` without drafts; `WEEK_INCONSISTENT` when the week-scope `InconsistencyDetector` (drafts + actives + `RingBlock` `ACTIVE` + `TrainingConflictPort` bookings, only with `FREE_TRAINING`) finds anything (§13-4: blocks, like generation); drafts stay invisible to members until then. Bookability (`bookings.weekOpensAt`) is S08's concern: nothing here. T-06-12, T-06-23 (validation concurrent with a `PATCH`: never a `DRAFT` in a `VALIDATED` week).
4. **Class creation and edition** (R-06-09): `POST /class-sessions` → `ACTIVE` if the (get-or-create) week is `VALIDATED`, else `DRAFT`; holiday dates allowed; `ClassSessionCreated{classId}`; a ring with live training bookings → `RING_HAS_BOOKINGS {bookings[]}` unless ADMIN sends `cancelBookings: true` (→ `TrainingConflictPort.cancelByClub`, same transaction). `PATCH /class-sessions/{id}`: editable `ringId`, `levelIds`, `instructorIds`, `capacity` (`null` → back to `AUTO`), `startTime/endTime` (instants re-derived, R-06-14), `description`, `notes`, `riskExempt`; `date` → 400; `version` → `STALE_VERSION`; `capacity < counters.booked` → `CAPACITY_BELOW_BOOKINGS`; `ClassSessionUpdated{classId, diff, bookedCount}`; `@Audited(CLASS_UPDATED_WITH_BOOKINGS)` when `counters.booked > 0`. `POST …/risk-exemption {exempt}` on `ACTIVE` only (`INVALID_STATE`), `risk.exempt` persisted, `ClassRiskExemptionChanged{classId, exempt}`, `@Audited(CLASS_RISK_EXEMPTION_CHANGED)` (§13-6 chip). T-06-13.
5. **`ClassCancellationUseCase`** (R-06-10; public method `cancel(classId, reason: CLUB_MANUAL·DELETED·RISK_REVIEW·ACTIVITY, adminText?, actor)` used by the endpoint, by S15 (`RISK_REVIEW` with `scheduling.autoCancel.text`) and by `RingBlockService.syncForActivity` (`ACTIVITY`)): preconditions `state ∈ {DRAFT, ACTIVE}` (`INVALID_STATE`), `adminText` 1–500 mandatory when `counters.booked > 0 ∨ counters.waiting > 0` (`ADMIN_TEXT_REQUIRED`); **one transaction**: class → `CANCELLED` + `cancellation{reason, adminText, byAccountId, at, affectedBookings, affectedWaitlist}`, `ClassBookingsPort.cancelAllByClub`, `counters {0,0}`, `ClassCancelledByClub{classId, reason, adminText, affected[{bookingId, memberId, dogId}], waitlistIds[]}` to the outbox, `@Audited(CLASS_CANCELLED)`; any failure → full rollback; `Idempotency-Key` on the endpoint (same key → same response; two concurrent → one 200 + one `INVALID_STATE`). `GET …/cancellation-preview` = the port's bookings/waitlist resolved to `memberName`, `dogName`, `levelName` (reader's locale), `channels[]` (APP if the member has an account, EMAIL if it has a contact email, SMS if `SMS` module on and phones > 0 — preferences of S11 refine it in E7) and `phoneCount`, plus `waitlistCount`. ## Fixed conventions
- Statuses (catalog rule 0, literal; the catalog file wins): `INVALID_STATE`, `STALE_VERSION`, `RING_BLOCK_CONFLICT`, `IDEMPOTENCY_KEY_REUSED` 409 · `NOTHING_TO_VALIDATE`, `WEEK_INCONSISTENT`, `CAPACITY_BELOW_BOOKINGS`, `ADMIN_TEXT_REQUIRED`, `RING_HAS_BOOKINGS`, `RING_BLOCK_MANAGED_BY_ACTIVITY`, `OUTSIDE_OPENING_HOURS`, `LEVEL_REQUIRED`, `TOO_MANY_INSTRUCTORS`, `DESCRIPTION_REQUIRED` 422 · `INVALID_TIME_RANGE`, `INVALID_SLOT_GRANULARITY`, `VALIDATION_ERROR` 400 · `MODULE_DISABLED`, `NOT_FOUND` 404 — S06's narrative writes 409 for several 422 codes: ignore it.
- Every transaction of this task is a Mongo transaction (`TransactionTemplate`/`@Transactional` with the replica set); ports run inside it; events through `EventPublisher` in the same transaction; notifications only from the outbox consumers, never from services; `Clock` injected; instants UTC, business dates club-local.
- Assumptions in force: the student never sees counts (A22(e), §13-2); [ELIMINA] = `DELETED` and shows under «Anul·lades» with its reason (§13-3); validation is blocked by inconsistencies (§13-4); the risk-exemption toggle is a chip on the selected class (§13-6); a block over a class is refused interactively, `RING_BLOCKED` only for generated/moved classes (§13-11); R-15-18's grace minutes refine R-06-09's «`endsAt < ara`». S15's 7:30 review, N-16/N-17 and `ClassBelowMinimum` are E5: only the evaluator and the cancellation use case are exposed here.
- Closed catalogs: no new parameter/event/notification/error/audit action; proposals in the report + `MESSAGES.md`. Statuses per `CATALEG_ERRORS.md` (16-09): `BAND_OVERLAP`/`RING_BLOCK_CONFLICT` 409, `WEEK_ALREADY_GENERATED`/`BAND_NOT_EMPTY` 409, `TEMPLATE_INCONSISTENT`/`WEEK_INCONSISTENT`/`NOTHING_TO_VALIDATE`/`RING_HAS_BOOKINGS`/`RING_BLOCK_MANAGED_BY_ACTIVITY`/`RING_BLOCKED` 422. `RING_BLOCKED` is thrown by the manual class creation/edition (`POST /class-sessions`, `PATCH /class-sessions/{id}` moving a class) onto a ring blocked at that time; generation records it as an `Inconsistency` instead. Recipients are resolved through the census/identity application services (reuse), never by reading other contexts' collections.
- Evidence rule: report = command + exit code + last 40 lines; long outputs → `roadmap/evidence/E4-T03/NN-<name>.log`; task file ≤ 120 KB; fictional data only (`@example.test`); no secrets; never edit other tasks, `ROADMAP.md` or the Organizer verification section.
