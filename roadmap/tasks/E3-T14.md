# E3-T14 · The payment methods of a signup

## Objective
E3-W07 round 2 (web) found this on the real core (`roadmap/evidence/E3-W07/d2-payment-methods-core.json` in the web repo):
- the seed club's `GET /club` lists `SEPA_XML` and `MANUAL` with `{configured: false, enabled: false}`;
- the anonymous `GET /signup` still offers «Domiciliació» and «Efectiu»;
- `GET /signup` with an ADMIN bearer answers `403`, so D2 cannot read the public form's methods either.

R-04-10 says the form offers the club's **active** providers. Either the flags or the offer is wrong. D2 (web) also needs the methods it may assign without depending on `/club`. This must be done before the gate re-run E3-T11, which depends on this task.

**Each fix comes with a test that fails before the fix.**

## Spec references
- S04: R-04-10 (payment methods), R-04-19 (the D2 edit), §2 row D2, §6.
- S02 (the club's `paymentProviders`).
- S12 (providers: `configured` against `enabled`).

## Steps
1. **One rule for the offer (R-04-10).** `GET /signup`, and the validation of `POST /signup` and of the D2 `PATCH`, offer and accept only the methods of **enabled** providers:
   - `SEPA_XML` → `SEPA_DD`;
   - `STRIPE` → `CARD`;
   - `MANUAL` → `MANUAL`.
   
   Anything else answers 422 `PAYMENT_METHOD_NOT_AVAILABLE`. `configured` does not gate the offer: a SEPA provider without a creditor id can still collect mandates, and S12 needs `configured` only to generate remittances. Say so in the report if S12 reads otherwise. Test: a disabled provider disappears from `GET /signup` and is refused at submission and in the D2 `PATCH`.
2. **The Cànic seed enables what the club uses.** The Cànic seed has direct debit and cash: `SEPA_XML` and `MANUAL` become `enabled: true`. Leave `configured` as it is; the seed has no real creditor data. After this, the real-core e2e sees the same methods in `GET /club`, `GET /signup` and D2. Seed test, plus `club:apply` (the second apply gives no changes).
3. **The D2 view publishes the assignable methods (web proposal, E3-W07 round 2).** `GET /members/{id}/signup` returns `paymentMethods: [{type, ...}]`: the methods of step 1 that D2 may assign. The applicant's current method is always included, even when its provider has since been disabled; mark it so. Use the same shape as `planOptions`. Contract test and IT.

### What changed
1. **One rule for "enabled" (step 1, R-04-10).** New `platform/application/PaymentProviderFlags`: a provider is enabled only when its stored entry has `enabled: true`. `configured` means any other non-null key; it never gates the offer. `GET /club` (`SettingsMapper`) and the census check (`CensusClubSettings.providerEnabled/providers`) now use the same rule. Before, the census counted a provider listed without `enabled` as enabled, while `GET /club` showed `enabled: false`: that was the E3-W07 finding. `GET /signup` offers the enabled providers' methods in the configured order. `POST /signup` and the D2 `PATCH /members/{id}` (both go through `SignupService.payment`) answer `422 PAYMENT_METHOD_NOT_AVAILABLE` for anything else.
2. **Seeds (step 2).** `club-canic.yaml` and `club-canic-consumer.yaml` now have `paymentProviders: {SEPA_XML: {enabled: true}, MANUAL: {enabled: true}}`, with no creditor data, so `configured` stays `false`. `club-definition.schema.json` accepts either the old list of names or `{NAME: {enabled: bool}}`. Only `enabled` is allowed there (`additionalProperties: false`), so no credentials. `ClubDefinitionMapper`:
   - **merge:** the object form sets `enabled` and keeps the configuration stored outside the file (creditor, keys, instructions). The list form keeps the stored flags, and a new provider starts disabled. A definition without the section keeps the providers as stored.
   - **export:** writes `{NAME: {enabled}}` in the stored order.
   
   Reapplying the new seed on a club applied before gives one change (`~ paymentProviders changed`), then none. The seeds `minim`, `fifo` and `perf` now declare the providers they already listed, with `enabled: true`. This keeps their effective behaviour: the old rule enabled them implicitly.
3. **D2 view (step 3).** `GET /members/{id}/signup` returns `paymentMethods: [SignupPaymentMethodOption {type, label, current, assignable}]`:
   - the methods `GET /signup` offers, in the same order, each with `assignable: true`;
   - `current` marks the applicant's method (for a pending readmission, the submitted one, as the D2 PATCH edits it);
   - if the applicant's method belongs to a provider disabled since, it is added last with `assignable: false`;
   - the list is empty without BILLING.
   
   The response is additive and the field is required. The snapshot is regenerated, with an entry in `docs/openapi/CHANGELOG.md`.
4. **`bin/e3-smoke`** now also checks, on the real stack after `club:apply seeds/club-canic.yaml`, that `GET /club` shows `{SEPA_XML, MANUAL}` as `{configured: false, enabled: true}`, that `GET /signup` offers `[SEPA_DD, MANUAL]`, and that D2 lists the same methods (SEPA_DD current, all assignable).
